# host

The native-messaging hosts (the config host and the bridge host) and the script that installs them. Linux only. Design: `docs/design.md`, Native host.

- `desertfox-host`: Python 3.9+, stdlib only. Firefox starts it for one request and it exits after one reply: a 4-byte native-endian length, then UTF-8 JSON. Verbs: `read_config`, `write_autoconfig`, `self_update`, `editor_start`, `editor_collect` and `open_firefox_page`. Every reply, ok or error, carries `host_version` (the protocol, 1) and `release_version` (the release it came from, `dev` in the repo). Outside an update and the editor verbs its only write is `autoconfig.toml` in the config folder. `DESERTFOX_CONFIG_DIR` replaces the folder, for tests. The file set `read_config` returns mirrors `tools/build-config/source_files.ts`, minus `autoconfig.toml` and `editor.toml`.
- `self_update` (`{"cmd": "self_update", "version", "sha256": {"desertfox-host", "desertfox-bridge", "desertfox"}}`) replaces the installed files with GitHub release `v<version>`. The extension sends its own version and the hashes its signed build carries (`dist/host_sha256.json`). The request takes no other field, so no URL, channel or path gets in. The host:
  - accepts only `x.y.z` or the beta form `x.y.z.N` and builds every URL from one template on this repo's releases;
  - refuses a development host (`release_version` `dev`) and a version older than this host or the host file on disk, and does nothing when the installed scripts match the hashes and the manifests match what it would write;
  - takes a non-blocking `flock` on `update.lock` in the data folder beside the scripts (`install.sh` locks the same file), so a second caller gets `update running`;
  - downloads over HTTPS only, through at most 5 redirects that must all stay on HTTPS, with 1 MiB and 20 s per file;
  - checks each script against the release `.sha256` and against the extension's hash, then its shebang and stamped version, all in memory before it writes anything;
  - writes each of the five paths install.sh writes (found from where the host itself sits) as `<path>.new` and renames it over the old file: the bridge, the command line, both manifests, then the config host last. Until that last rename the host still reports the old version, so a crash midway gets a retry, and the retry finishes the rest because the "already current" check covers the manifests too. It runs no shell and no subprocess. A rename keeps the old inode, so a running bridge keeps its code until the extension reconnects. A rename that fails names the files already replaced.
- External editor (`{"cmd": "editor_start", "text", "ext"?, "insert"?}` then `{"cmd": "editor_collect", "job"}`). The request carries text, a file extension (1 to 10 letters or digits) and an insert flag, and nothing executable: the command comes from `editor.toml` in the config folder, which only the host reads (`read_config` and the tool reader skip it). Absent file means no editor, and the verb refuses with the path to create. The file takes two string lists, in TOML syntax (the host reads only this subset):
  - `argv`: the program first, then its arguments. One element holds `{file}`, which becomes the scratch file path. No shell runs: each element is one argument, so page text can never become a command. The host adds no flag of its own and does not assume vim.
  - `insert_argv` (optional): extra arguments placed just before the first element that holds `{file}`, only when the request has `insert: true`.
  - The terminal must stay in the foreground until the editor quits (for `foot`, `kitty` and `alacritty` that is the default). A launcher that forks and exits at once reads as an editor that ended with no save.
  - A Neovim recipe, which opens in a floating terminal, quits after one save and starts at the end of the text in insert mode:

    ```toml
    argv = ["foot", "--app-id", "desertfox-editor", "nvim", "+autocmd BufWritePost <buffer> quit", "{file}"]
    insert_argv = ["+normal! G", "+startinsert!"]
    ```

    A window rule on the app id floats it. The text comes back only when the editor exits, so an editor that stays open after a save keeps the answer pending.
  - `editor_start` refuses text over 128 KiB (a JSON reply may not pass 1 MiB), writes it to `$XDG_CACHE_HOME/desertfox/editor/doc-<time>-<id>[.ext]` (folder 0700, file 0600, mtime set a minute back so a save always changes it), starts the editor detached (own session, no stdio) and returns `job`, a random 32-digit hex id. A job file `job-<id>.json` beside it holds the scratch name, the mtime and the editor's pid with its start time. A job the host did not make, or one already collected, is refused. A job whose editor is gone and which nobody collected for a day is swept at the next start.
  - `editor_collect` waits up to 20 s. It answers `{"pending": true}` while the editor runs, or `{"done": true, "changed": false}` or `{"done": true, "changed": true, "text"}` (trailing newlines stripped). It reads the file only after the editor exited, never mid-write, and a missing or changing file while the editor runs (a rename-and-write save) is still pending. `changed` means the mtime moved. It removes the scratch file and the job file exactly once on every outcome, including an editor that exited without saving and an edit over the size cap, and of two collectors only one wins the job.
- Firefox pages (`{"cmd": "open_firefox_page", "page"}`). `page` is a key of the host's `FIREFOX_PAGES` table (`settings`, `addons`, `config` and ten more), never a URL, and an unknown key is refused. Extensions cannot open these `about:` pages, so the host asks Firefox to:
  - The program is the parent process's `/proc/<ppid>/exe`, with a ` (deleted)` suffix stripped, and its name must be `firefox`, `firefox-bin`, `firefox-esr` or `firefox-esr-bin`. A run by hand or by another program is refused, and so is a program that a package upgrade removed.
  - The profile is the folder of the `.parentlock` the parent holds open, else `MOZ_CRASHREPORTER_EVENTS_DIRECTORY` minus `/crashes/events`. It must be absolute and hold `.parentlock`. Two sources that disagree, or none, are refused. `--profile` is always passed, because without it the URL goes to the default profile.
  - It runs `[exe, "--profile", profile, url]` with no shell, stdin and stdout on `/dev/null`, stderr in a temporary file, in a session of its own, and without the `MOZ_CRASHREPORTER_*`, `XRE_*`, `MOZ_LAUNCHED_CHILD` and `MOZ_APP_SILENT_START` variables, and without `MOZ_NO_REMOTE` and `MOZ_NEW_INSTANCE`, which would stop the hand-off. The running Firefox takes the URL and the client exits within about a second. After 10 s the host kills the process group and refuses with "Firefox did not take the request": a failed hand-off starts a second Firefox that waits on a dialog. A nonzero exit refuses with the last stderr line.
  - Review note: any code with the nativeMessaging grant can open these pages. That is the trust `editor_start` already needs.
- `install.sh`: `install.sh <version|main> [--channel main]`. A version fetches the host from that GitHub release and refuses to install on a checksum mismatch. `main` fetches from the main branch with no checksum. The script is one function called on its last line, so a cut-off download runs nothing. It writes both hosts and the `desertfox` command line to `$XDG_DATA_HOME/desertfox/` (a relative value is ignored, default `~/.local/share`), the manifests to `~/.mozilla/native-messaging-hosts/desertfox_host.json` and `desertfox_bridge.json`, and a symlink `~/.local/bin/desertfox` (left alone when a file that is not a link is there), and stops with an error without python3 3.9 or newer. After the downloads and before the first write it takes the same non-blocking `flock` on `update.lock` in the data folder that `self_update` takes, and holds it until it exits. While an update runs, `install.sh` fails with `update running` and writes nothing. It checks for `flock` only at that point.
- `desertfox`: the command line for the bridge socket, see below.
- Release stamp: `just release_stamp <version>` copies the scripts into `release-assets/` (`RELEASE_ASSETS_DIR` replaces it), writes that version (the `src/manifest.json` one) into both hosts as `release_version`, then hashes the stamped files into a `.sha256` per script and `host_sha256.json`. The extension build copies that file into `dist/` when its version matches the manifest, so the signed build carries the hashes. `just release_publish <version> <xpi>` uploads the same stamped files and the signed xpi as `desertfox-<version>.xpi`, as a prerelease for a four-number `x.y.z.N` version, and refuses any file whose hash differs from `host_sha256.json`.
- `test_host.py`, `test_editor.py` (a stub editor script under a temporary cache and config folder: lifecycle, races, forged jobs, config errors), `test_firefox_page.py` (a stub Firefox under a fake `/proc`: the page table, the parent and profile checks, the environment, the inherited descriptors and the timeout kill), `test_install.py`, `test_cli.py`, `test_self_update.py`, `host_under_test.py`: run them with `just host-test`. The install tests use a temporary HOME and a stubbed `curl`, and never touch the real home folder or the network. `test_self_update.py` drives the updater through an injected fetch under a temporary HOME. `test_install.py` also runs `just release_stamp` and `just release_publish` against a stubbed `gh`, and `just release_commit_push` against a local bare remote. `just release` commits and pushes the bump first, so the release tag targets that commit.

## Bridge host

- `desertfox-bridge`: Python 3.9+, stdlib only, native name `desertfox_bridge`. Unlike the config host it stays alive on a `connectNative` port while the extension has `bridge = true` and the `nativeMessaging` permission. It takes the lock, then says `{"ready": true, "host_version": 1, "release_version": "<version>"}` once, and the extension trusts the port only after that. It takes three verbs from the extension, `mode`, `reply` (the answer to a request the host sent) and `event` (a tab event for subscribers), and skips a malformed or oversized message.
- Files, all in `$XDG_RUNTIME_DIR/desertfox/` (created with mode 0700). The bridge host writes nothing else.
  - `bridge.lock`: the first host to take its `flock` owns the socket and the state file. A second host waits 3 s for it, then exits with code 1 and says nothing on stdout. The kernel drops the lock when its holder dies.
  - `bridge.sock`: a Unix socket, mode 0600, made under a restrictive umask. A leftover file from a crashed host is replaced at start. A connection from another uid is closed. One JSON object per line in, one line out. Verbs: `ping` gives `{"ok": true}` and `state` gives `{"ok": true, "state": <snapshot or null>}`. `run` (`{"verb": "run", "command": "<command line>", "tab_id"?}`), `list` and the tab verbs go to the extension, which decides what runs. The host sends `{"verb": "run", "request_id", "command"}` or `{"verb": "list", "request_id"}` on stdout and routes the reply that carries the same `request_id` back to the connection that asked. A run reply is cut to `ok` and `message` (500 characters at most), so no page data can pass. A `list` reply is `{"ok": true, "commands": [...]}`. The tab verbs work only while `bridge_share_tabs` is on, and a tab of a private window is never listed or accepted: `tabs` (`{"current"?}`) gives `{"ok": true, "tabs": [{tab_id, window_id, title, url, active, audible, discarded, last_accessed, pinned, hidden, fav_icon_url, fav_icon_path, thumbnail, thumbnail_at}]}`, only the active tab of the last focused window with `current: true` (none when that window is private or a popup), `activate` (`{"tab_id", "preface"?}`) gives `window_id`, `focused` and `preface_set`, `clear_preface` (`{"window_id", "preface"?}`) gives `cleared`, `close` (`{"tab_id"}`) gives `ok`, and `capture` (`{"tab_ids"?}`, up to 64) gives `{"ok": true, "results": [{tab_id, ok, thumbnail, thumbnail_at, error?}]}`. The host checks field types before anything goes to the extension, cuts each reply to its known fields and drops any listed tab flagged private. A stale or private id is refused with `no such tab`. Anything else gets `{"ok": false, "message": ...}`. Requests are capped at 64 KiB, idle connections close after 5 s, and at most 16 are open. The whole host takes 10 `run` and `list` requests per second, because the CLI opens a connection per call. An excess request is answered with an error and goes no further. At most 16 requests wait on the extension, one waits 10 s at most, and every waiting request fails when the port closes. `subscribe` turns the connection into a one-way stream: `{"ok": true}`, the current mode, then one line per event with a rising `seq`: `mode` (from the mode messages, no tab sharing needed), `tab_activated`, `tab_updated`, `tab_audible`, `tab_removed` and `tabs_off` (fields in `EVENT_FIELDS`). At most 4 subscribers, each with a queue of 64 events and its own writer: one that falls behind or does not take a write within 2 s is dropped. A stream has no idle timeout and counts once against the rate limit. A `tab_removed` goes only to a subscriber that an earlier event told about that tab (the last 1024 per subscriber). A `tabs_off` event also deletes both caches. The extension sends one each time the port comes up with sharing off. A client that closes its write side (as `nc -U` does at the end of its input) reads as gone, and its stream ends.
  - `state.json`: `version` (2), `seq`, `host` (`pid`, `start`), `firefox`, `mode`. A normal window gives `firefox` as `window_id`, `private` and `mode` as `id`, `label`, `tab_id`. A private window gives `firefox` as `{"private": true}` and `mode` as `id` and `label` only. The extension sends no ids for a private window and the host drops them if it did. Writes go to a temp file in the same folder and are renamed. The host removes a leftover file at start and its own files on exit. The shell reader treats a dead or reused `pid` as no state.
  - `theme.json`: `{"palette": "<name>"}`, the last palette a client pushed with the `theme` verb (`{"verb": "theme", "palette"}`, a name that starts with a letter or digit, then letters, digits, `_` and `-`, 1 to 64 characters; the host checks only that, the extension checks the name, and the host deletes the kept file when the extension refuses the name, whether in a push or in the replay). It is written the same way as `state.json` but the host removes it neither at start nor at exit, so the next host still has it. A host sends the kept name to the extension right after `ready`, in the same step that opens the link, so a push comes either before and is the replayed one or after and is sent once. A temp file a dead host left is removed at start. The CLI: `desertfox theme <palette>`. With no host listening, the CLI writes `theme.json` itself, atomically and under a non-blocking flock on `bridge.lock`, and exits 0 quietly. A held lock means a host is starting, so the CLI asks the socket again for up to 5 s instead. Because the host takes that lock before it reads `theme.json`, a write never lands after the load. `-h` or `--help` after any verb prints the usage and sends nothing.
  - `$XDG_CACHE_HOME/desertfox/bridge-thumbs/` and `bridge-favicons/` (mode 0700, default `~/.cache`): the only writes outside the runtime folder. A JPEG per tab address, named by the hash of the address, written only for a tab the extension just listed as a normal one and only after `capture`. An icon per data URL, named by the SHA-256 the extension lists for a tab and the suffix of its type, asked for during a `tabs` answer when the file is missing (3 s for all of them). A file of no open tab is deleted after 7 days, at most 500 stay in each folder (the oldest go first), the host prunes at start (and the icons after each full `tabs` list), and an answer that says sharing is off or a `tabs_off` event deletes both folders. Writes and deletes share one lock, and an image asked for before a delete is dropped.
- The installer puts both hosts in place (see above). Check `$XDG_RUNTIME_DIR/desertfox/state.json` after a key press in Firefox, with `bridge = true` in `settings.toml` (or `:set bridge true`) and the permission granted on the `:native.install` page.
- `desertfox` (the command line): `desertfox run [--tab <id>] <command> [args...]` runs one command in the focused Firefox window or in a tab, `desertfox list [--json]` prints the allowed commands (command word, id, label and params, tab separated) `desertfox state [--json]` prints the latest snapshot, `desertfox events` prints the event stream one JSON line per event until the host ends it, and with `bridge_share_tabs` on `desertfox tabs [--current] [--json]` lists the tabs (or only the current one), `desertfox activate <id> [--preface <nonce>]` selects one and focuses its window (the nonce goes in front of the window title for 10 s, so a script can find the window), `desertfox clear-preface <window id> [--preface <nonce>]` clears it early, `desertfox close <id>` closes one and `desertfox capture [id...] [--json]` saves thumbnails and prints their paths. A single argument to `run` is the command line as it is, several are quoted into one. It prints plain text, errors on stderr. Exit codes: 0 done, 1 refused or failed, 2 bad usage, 3 the bridge is not running. What may run is the extension's decision: the command's `bridge` field, a never-list and the one validator (see `docs/design.md`, Bridge host).
- `test_bridge.py`: real processes with a temporary `XDG_RUNTIME_DIR`: two hosts at once, a stale socket after a kill, atomic writes, the socket verbs, caps and rate limit, `run` and `list` routing between clients, and a client or the extension leaving mid-request. `test_bridge_tabs.py` covers the tab verbs: field checks, reply cutting, the private guard, concurrent requests, a port that closes mid-request, the `current` filter and the thumbnail and icon caches. `test_bridge_events.py` covers `subscribe`: the event shapes, the private guard, the caps, a stuck subscriber, host exit, and the hub's queues and writers in process. `test_cli.py` runs the command line against a fake socket and the real host. Run with `just host-test`.
