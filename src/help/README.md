# help

The help page, opened by `help.open`. It reads `commands.json`, the compiled keymap, the stored warnings and the resolved engines.

- `route.ts`: the pages and the hash parser. The sidebar lists Home, Settings, Quick Start, Commands, Search Engines and Styling, at `#/`, `#/settings`, `#/quick-start`, `#/commands`, `#/search-engines` and `#/styling`, then Site Rules at `#/site-rules`. `#section=<page>/<slug>` shows that page at one of its sections (see `render.ts`). `#command=<id>` shows the Commands page at that command's card (`command-<id>`), and `main.ts` scrolls to it and highlights it like an engine row. `?advanced` at the end of any of those hashes also shows the cards of commands flagged `advanced` (hidden by default, see `visible_commands_model` in `model.ts`); the Commands page has a button that sets it, and a card the hash names stays visible. An unknown hash shows Home.
- Site Rules page (`#/site-rules?address=<address>`, opened by `:help site_rules` from the tab it names, with the address encoded as one value; `route.ts` reads it before it decodes the rest of the hash): the rows of the site table that fit the address, in table order, from `site_rules_view` in `background/site_rules_view.ts` through `model.site_rules_for`. Each row is a section with a column table and a key table. Columns draw as name and value, so a new per-site setting needs no code here. A column or key an earlier row decides, or a key the page does not run (off, freed by pass, dropped by only, hidden by a shorter bind), carries `desertfox-help-shadowed` and a reason. The two tables use `desertfox-help-site-rules` (with their own narrow-window labels), not the Commands params class. It has no sidebar sections. Without an address it says where to run the command. It lists the tab's own address only.
- `quick_start.ts`: the Quick Start text as blocks. A `{name}` in a sentence is looked up in the compiled keymap by command and args, shortest key first. A command with no key shows its command line instead, so a rebind or unbind never leaves the text wrong.
- `model.ts`: turns those three inputs into plain rows. Key args and the `flags` column are written by the registry printer, so the page matches the command line. Tests read the rows, so no DOM is needed.
- Home: the tip and the warnings. Its sidebar entry has no section list. `config_view.ts` builds the config source line and the apply steps that Settings shows.
- Settings page (`#/settings`, the target of `options_ui` in the manifest, so the add-on Preferences button opens it): one field per setting, grouped by name prefix, with its help text, a source tag for the top layer and a Reset that drops the saved and temp edit. A change saves at once through the `change_setting` background message, the same plan as `:set`. Settings that `:set` refuses show read-only with a note. The intro shows the config source in one line. An "Apply a config file edit" section sits above the groups, outside the section list: the steps (`:native.install` once, then `config.reload`) and an Install native host button that opens the `:native.install` panel by the same hash.
  - `settings_model.ts`: no DOM. Picks the control per setting kind (`control_of`), checks typed values with the setting's own check, and holds the session. The session keeps a draft per field and ignores a refresh for a field with a draft or an edit in flight, so a `storage.onChanged` refresh never clobbers typing or an answer. A refresh only reads, so the page's own write cannot loop. The page refreshes on a write of the config status in `storage.local` (`touches_settings` in `shared/storage_watch.ts`), which every edit ends with, and `main.ts` stops the listener before it renders another route.
  - `settings_page.ts`: draws the fields and wires events to the session. Text fields check as you type and save when left. `render.ts` draws the group headings, so section links work before the list loads. The page gets the settings through the `list_settings` message and the engine names from the config it already loads, and never imports the registry.
  - `transfer_model.ts`: no DOM. The state of the "Export and import" section: it reads a picked zip or folder (checking each `File.size` against the zip limits before it reads the file), asks the background for the preview, and holds which snippets the user ticked, none at first. `commit` sends only the ticked snippets with the code the preview showed. Every commit outcome ends the review and reloads the installed list. It also builds the two export zips, `desertfox-config.zip` and `desertfox-snippets.zip`, from the `export_config` answer. It also exports and imports `desertfox-sessions.json` (`export_sessions`, `import_sessions`), with no review step.
  - `transfer_page.ts`: draws the section: export buttons (config, snippets, sessions), a zip picker, a sessions file picker and a `webkitdirectory` folder picker, the consent screen (each snippet's full code, `matches` and `requires`, and the warning that a snippet can use every DesertFox permission) and the installed snippets with Remove.
  - `host_start_model.ts`, `host_start_page.ts`: the banner at the top of Settings while a host start waits on the user (`desertfox_host_start_pending`, which `main.ts` follows in storage). It lists the files the config folder would replace, add or drop, and offers Export config (the transfer section's export), Use the folder and Keep the browser copy. A choice sends the digests the banner showed, so the background refuses an answer to an older question.
  - `files_model.ts`, `files_page.ts`, `file_templates.ts`: the "Config files" section. It lists the stored files (`config_files` read), opens one in a text box and saves through `config_files` save, which the background applies like an import but as the user's own config. A new file starts from a short commented template. A refused save keeps the text and lists every build problem. A snippet save shows the same consent card as an import (`snippet_card` from `transfer_page.ts`) and sends the code back as `accepted`; an edit voids the tick.
- Search Engines page: the guide from `docs/search_engines.md`, then every resolved engine in tree order with label, URL, needed slots, fallback and the file and level that set each field. `engine.show <name>` opens the page at `#engine=<name>`, which `route.ts` maps to this page, and `main.ts` scrolls to the row.
- `blocks.ts`: the block list type, including `tip`, the callout on Home and Commands. `quick_start.ts` writes it (`tip_block`) so its command line key follows the keymap, and `render.ts` adds the "Tip" label. It has no dismiss control. `tools/render_docs.ts` turns the guide's markdown subset into blocks at build time (it fails on any other markdown) and `tools/build.mjs` writes `dist/search_engines_guide.json`. `main.ts` fetches it.
- `render.ts`: draws the rows with DOM calls. Command text never goes through `innerHTML`. A `code_block` gets its own themed box with the fence language as a label and a Copy button. The command usage line keeps the plain `desertfox-help-usage` look. Each page gets a sidebar group: a link, a chevron button and a list of section links. `page_sections` builds the list for every page, and the headings take their ids from the same list. Going to a page opens its group, the others start closed, and each chevron toggles its own group. A toggled group keeps its state across renders, in memory only. `main.ts` scrolls to the section heading and focuses it. Search Engines lists the guide's `###` headings and "Your engines", and `main.ts` fetches the guide before the first render. If that fetch fails, only "Your engines" is listed.
- `user_css_gate.ts`: `create_user_css_gate` keeps the user CSS sheet off the page while the import review or the grant panel is on screen.
- `grant_panel.ts`: the panel `:permissions.grant <permission>` and `:native.install` open (`#grant/<permission>?<nonce>`, a new nonce each time so a tab already on the page sees a hash change and shows it again after Close). It sits outside the body, because the router rebuilds the body on each route. Its button asks for the permission and must stay inside the click handler, since Firefox grants an optional permission only from a click. For `nativeMessaging` it also shows the `curl` command for this build's channel (`src/shared/native_host.ts`) and, on a release build, the "Install and keep the host updated" button, which saves `host_auto_update` through a `change_setting` message and installs nothing. `main.ts` calls `mount_grant_panel` with the user CSS gate, which hides user CSS while the panel shows.
- `main.ts`: loads the inputs (`commands.json` through `shared/load_commands.ts`) and renders the route in the hash, and renders again on `hashchange`. It draws through `follow_settings` (`shared/storage_watch.ts`), so a settings change reads the inputs again and redraws the route with scroll and focus kept. The Settings route is not redrawn, because that page follows storage itself and keeps what the user is typing.
- `home.html`: the page and its styles. The defaults use the `--desertfox-` variables. It loads `content.js` by script tag, because `moz-extension://` pages do not match `<all_urls>`. That gives the page `j`, `k`, `gg` and the mode badge. `hints.js`, `whichkey.js`, `cmdline.js` and `caret.js` load the same way, for the Quick Start keys (`caret.js` also holds page search). `executeScript` cannot reach extension pages, so each bundle registers itself on load.
- The sidebar ends with a support card linking GitHub Sponsors and Ko-fi (`support_card` in `render.ts`).
- At 40rem or less the sidebar is a drawer (the `@media (max-width: 40rem)` block in `home.html`). `render_help` adds a top bar with a menu button and a backdrop, both hidden above the breakpoint, and `wire_drawer` opens and closes it. The open flag is a class on `.desertfox-help`, so each render starts closed. `main.ts` registers `close_drawer_on_escape` in the capture phase before `content.js` loads, so Escape closes the drawer and never reaches the key flow.

`STYLE_VARIABLES` and `STYLE_CLASSES` in `model.ts` list the public styling surface. The variables come from the theme role list, so a new role shows on the Styling page with a meaning the compiler forces you to write. Add a surface's class names there when it ships.
