# Privacy policy

DesertFox collects no data. It has no account, no telemetry, no analytics and no ads. The developer receives nothing from your browser.

This file is the privacy policy of the DesertFox add-on. The same text is the privacy policy on its addons.mozilla.org page. It uses plain paragraphs and lists so it reads the same in both places.

## What stays on your device

DesertFox keeps its settings, keymap, quickmarks, macros, registers, command history and closed-tab list in Firefox storage on your device. It reads your tabs, history, bookmarks, cookies, downloads and clipboard only to run a command you typed or a key you pressed. The add-on sends none of that to a server. The one exception is the optional desktop link described below, which hands tab titles and addresses to programs on your own computer.

## Requests the add-on makes by itself

DesertFox makes two kinds of request on its own, both from the built-in new tab page. Each is a card you can switch off, and neither sends anything from a private window.

### Weather card (Open-Meteo)

The card is the setting `newtab_weather`. It sends nothing until you allow it. Its button, "Show the weather here", asks Firefox for the optional data collection permission "location information". When no city is set, the same prompt also asks for the optional `geolocation` permission. Until you accept, the card draws only the button, even with a city set. With a city set, the card uses the city and never reads your position.

After you accept, the card asks Open-Meteo (`api.open-meteo.com`) for the forecast. With a city it first sends the city text to Open-Meteo's geocoder (`geocoding-api.open-meteo.com`), then the rounded coordinates of the answer. With no city it sends your position, with the coordinates rounded to two decimals, about one kilometre. When you open the More panel, it asks Open-Meteo's air quality host (`air-quality-api.open-meteo.com`) with the same rounded coordinates.

The requests carry no cookies and no referrer. Open-Meteo sees your IP address as any server does, and Firefox adds an `Origin` header that holds a random address of your DesertFox install, the same for every request from that install. DesertFox checks the consent again before every request, so withdrawing it stops later requests at once. The answers stay in local storage until a newer one replaces them. DesertFox refetches after 30 minutes and shows a stored answer for up to 6 hours. The stored answers hold the rounded coordinates, the place name and the forecast. Turning the card off, or a new tab that finds the consent withdrawn, deletes them. You can withdraw the permissions in `about:addons`, on the Permissions tab of DesertFox. A user with a city set holds the consent only.

### IP info line (Cloudflare)

The line is the setting `newtab_ip_info`. It is off by default. When you turn it on, each new tab asks Cloudflare (`https://1.1.1.1/cdn-cgi/trace`) for your public IP address and country code, and shows those two values. Cloudflare sees your IP address, as any server does. The request carries no cookies and no referrer. The answer stays in local storage until a newer one replaces it, and DesertFox shows it for up to one hour. Turning the line off deletes the stored answer. DesertFox declares no data collection category for this line, because it sends no data of its own beyond the request.

## Requests you cause

- A search command sends the text you typed to the search engine you set. The default is DuckDuckGo.
- A command that copies or saves an image fetches that image from the page it came from.
- The command line shows the icon of each open tab. For a tab whose icon has an http or https address, the add-on page loads that icon from the address the page gave, which can be any site you have open.
- Opening a link or a page loads it, as in any browser.

## The optional native host (Linux)

The native host is a helper program you install yourself. It talks to DesertFox through Firefox. Its only network use is the update download described below. It reads your config folder and writes these files there: `settings.toml` when you change a setting, a theme file under `themes/` when you import or remove a theme, the Search engines section's own files `search_engines.d/zz-desertfox.toml` and `keymap.d/zz-desertfox.toml`, an empty lock file `.settings.lock`, and `autoconfig.toml`, which holds only a copy of the key edits you made in the browser. Outside that folder it writes only the files of its own update, the scratch files of the external editor and the cache files of the desktop link. The last two are described below.

Two paths download files from GitHub over HTTPS. The `:native.install` command shows an install command that you paste into a terminal yourself. The install script downloads a script from this project's GitHub releases and checks it against a hash that comes from the signed add-on. The setting `host_auto_update` is off by default. When you turn it on, DesertFox asks the host to replace itself, and the host itself downloads the scripts of the same release from GitHub over HTTPS and checks each script against the same hashes. GitHub sees these downloads as it sees any download.

The external editor sends the text of a page field to a program you chose in `editor.toml`. The host writes that text to a scratch file (a temporary file the editor opens) in `$XDG_RUNTIME_DIR/desertfox/editor`. The host uses that folder only when it is a real folder that only you can write. When that folder is memory-backed (the usual case), the text does not reach the disk. Memory can still be written to swap (disk space that holds memory pages), as it can for Firefox itself. If the folder is not memory-backed, the text goes to the disk there. If the folder is missing or not trusted, the host uses `~/.cache/desertfox/editor` (or `$XDG_CACHE_HOME/desertfox/editor`) instead, and that folder is on disk. The host deletes the scratch file when the editor closes and DesertFox has read the result. If the editor never finishes, for example when you close the browser, the next editor start deletes files that are a day old. A text from a private window goes to the editor only when the folder is memory-backed. Otherwise the host refuses the request and writes no scratch file. The host cannot control your editor, so the swap, backup and undo files of the editor go where the editor puts them, often on the disk. Turn them off in the editor. The host deletes any such file left in its own scratch folder after a day. DesertBird, the Thunderbird add-on, uses the same editor path through its own host manifest and sends the text of a message you are composing to the same program from `editor.toml`. Thunderbird has no private windows, so it sends `private: false`.

## The optional desktop link

The setting `bridge_share_tabs` is off by default and needs the desktop link (bridge) to be on. When it is on, programs on your own computer that connect to the link's local socket (readable by your user only) can list your open tabs with their titles and addresses, switch to them, close them and capture them. Tabs in private windows never show. The host keeps a screenshot of a captured tab and the icon of a listed tab as files in `~/.cache/desertfox/` (or `$XDG_CACHE_HOME/desertfox/`), outside Firefox storage. These files stay on your computer, and the host deletes the files of tabs that are no longer open after 7 days, and deletes both folders when sharing is turned off. DesertFox sends none of this over the network.

The same host also serves DesertBird, the Thunderbird add-on. Its share settings are off by default and need its bridge setting on. With them on, programs on your computer that connect to its own local socket (readable by your user only) can list your mail folders, list messages with sender, subject and date, read a message body and list attachment names. The host passes each answer to the program that asked and keeps none of it. Nothing goes over the network.

## The optional browser module

The browser module is a script you install yourself, with administrator rights, into the folder where Firefox loads its own startup scripts. It is not part of the add-on, and DesertFox never installs or loads it. It stays off until you turn on the setting `browser_module`, which is off by default.

Key events stay on your device. The module sees your key presses in the browser window, because that is how it takes the tab and scroll keys on pages an extension cannot reach. It sends DesertFox no raw key events, with two exceptions: the command line below, and the keys you type while hint labels over Firefox's own buttons or DevTools show (see the hints paragraph below). When you finish a DesertFox key sequence on such a page that DesertFox runs, it sends DesertFox only that finished match: the keys of the binding and the typed count, so DesertFox can run the command. A key the module runs itself, such as a tab switch or a scroll, sends nothing. The keys of a sequence you have not finished stay in the module. It sends them to nobody else. While the setting is on, DesertFox writes to its own session storage the on or off switch, at most 32 single-key bindings for tab, scroll and stop-loading commands, the key sequences of your keymap that work on such pages, the mode of each tab and whether the setting `blur_on_load` is on. While the module draws the status bar, DesertFox also writes, for each tab, the keys you have half typed (at most 8), a typed count, whether pass-next is armed, the name of a macro register that is recording and, outside private windows, the label of a site mode, and it writes the mode colors of your theme and the bar's item lists and corner style from your settings. This stays in session storage on your device and leaves the browser at no point. The status bar reads the open tab's address, container and tab position in the browser itself, and the scroll place of about: and add-on pages, the PDF viewer and Reader View from a script in that tab. These stay in the browser process and are written nowhere. The module sends DesertFox a hello that holds a protocol version number, its version text and optional flags: whether it drew the status bar (`bar`), whether it runs hints in DevTools (`devtools_hints`) and visual mode in DevTools (`devtools_visual`), and whether it opens Firefox's own pages (`firefox_pages`). It can also send a short list of typed requests, each naming one kind from a fixed list of requests that DesertFox handles. With only this setting on, DesertFox handles two groups of requests from the module and refuses all others. One is the finished match of a key sequence, which DesertFox checks against your own keymap before it runs the command. The other is the hint requests described in the hints paragraph below. The requests that carry page text from the PDF viewer and Reader View need the second setting, `browser_module_pages`, and the hint requests do not. DesertFox also sends the module a short list of typed requests of its own, each naming one kind from a fixed list: split the window with a new tab or the next tab, unsplit, close both tabs of a split, resize the split by whole 5 percent steps, and move the focus to the sidebar, the page, the other pane or DevTools. These change the browser window only when you run a pane command, by its key or from the DesertFox command line. When you press `:` or a key that asks for a value on a page with no DesertFox command line, DesertFox asks the module to open its own command line page in a panel over that tab, and names only the tab. The module holds the keys you type while the panel opens, so none of them runs a command on the page. Its answer carries a random key for the panel's page and the characters you typed meanwhile (at most 32), which go into the line. Once the panel is open, DesertFox writes to its session storage that tab, its window, whether the window is private, the page's address with its key and the command text with the typed characters, so the page knows which tab it serves. The page runs as a DesertFox page, as the command line does on web pages, and a line from a private window adds nothing to the history. When the module cannot open the panel, DesertFox asks it to open the address bar with the command text typed in instead. That text can hold the page address, the selection or clipboard text the command takes. The module only puts it in the field and starts no address bar search, so Firefox sends it to no search suggestion service unless you edit it there. Apart from the panel's answer, the module answers with a short refusal text or none. DesertFox also sends the module the keys it may take in DevTools: a short table of single keys, each with one of four fixed tree moves (down, up, collapse, expand) or the start of hints. The module turns each tree move into an arrow key on the focused DevTools element. When you press the hint key in DevTools, the module asks DesertFox for hints with a random one-time number and then sends the place and size of each DevTools tab, button, row and pane it can label, under a number, never its text. The keys you type while those labels show go to DesertFox as described in the hints paragraph below. DesertFox sends back short labels made of your hint letters and the label colors of your theme, and names the label you typed. The module then clicks, presses or focuses that element in DevTools, as a mouse click would. The table can also hold the key that starts visual mode in DevTools. Then DesertFox sends a second short table of single keys, each with one of nine fixed selection moves or copy. The module selects text in the DevTools text area you are in and copies it to the clipboard when you press the copy key. That text stays in the browser: neither side sends it, and DesertFox learns nothing of it. DesertFox can also ask the module to open one Firefox page from a fixed list (settings and its sections, add-ons, downloads, about:config and the others `:firefox` offers), by name. The module picks the address from its own list. DesertFox sends the module no code, address, selector or page text for it to run, and the module makes no network request.

With the browser module, the hint key `gB` (or the key you bound to the command `hint.browser`) labels the controls of Firefox itself: the toolbar buttons, tabs, menus, permission prompts, the downloads panel, dialogs, the Library and Page Info. It reads no page content. For the focus in a dialog, DesertFox writes to its session storage the key sequences of your `hint.browser` bindings (at most 4, each at most 4 keys), so the module can see you type one, and the module then asks DesertFox to start with one request, `chrome_hints.want`, that holds a random number and no key. While labels show, the module sends DesertFox, by kind: `chrome_hints.targets` (for each control a number and its box in pixels, at most 400, with no name and no text), `chrome_hints.key` (the session number, a counter and each key you type while the labels show, one per message: any single character, so also digits, punctuation and space, or Backspace, Enter or Tab) and `chrome_hints.end` (the session number, when the labels end). DesertFox sends the module: `chrome_hints.collect` and `chrome_hints.collect_here` (a session number, a window number or the random number, and the three label colors of your theme as hex values), `chrome_hints.draw` (control numbers with their label letters and the letters typed so far), `chrome_hints.pick` (a session number and a control number) and `chrome_hints.clear` (a session number). DesertFox keeps the session, which holds those boxes, labels and typed letters, in its session storage until the labels end. A control that grants something, such as Allow on a permission prompt, is marked and waits for an Enter that you type in that window. No message can confirm it. The module labels such a control only after it saw you type the whole hint key just before. For that it keeps the last key tokens you typed in each window in its own memory (at most 4, each with its time, even keys that go on to the page) and sends them to nobody. A start on a part of Firefox that grants nothing, such as the toolbar, needs no such key. The keys you type while its labels show then go to DesertFox until you press Escape, click or pick. The keys `j`, `k`, `h` and `l` that walk Firefox's menus and panels are fixed in the module, which types the arrow key itself and sends DesertFox nothing. None of this leaves your device.

A second setting, `browser_module_pages`, is on by default and works only with `browser_module` on, so turning the module on is the consent step. In the PDF viewer, DesertFox keys override the viewer's own keys. It lets the module run DesertFox's own page code, the same code that runs on web pages, inside the PDF viewer and Reader View. There it gets no more privilege than on a web page. While both settings are on, DesertFox writes to its session storage a copy of your keymap with the patterns of your site rules, your settings in force, your theme and the which-key list, so that the page code can read them there. The messages between that page code and DesertFox pass through the same storage, and the module only hands them on. They can hold text from those pages, such as the link text that hints show, the text you copy and page addresses. Code with browser privileges can read this storage. DesertFox removes the copies when you turn either setting off. None of it leaves your device.

## Permissions

DesertFox asks for `nativeMessaging`, `browsingData`, `geolocation` and the location information data collection permission only when you click the button that needs them.
