## Config

The user config is a directory of files, one file per kind of setting. `config.reload` reads them through the native host, and the extension merges and checks them with the same code `tools/build-config` runs. Each start rereads the files through the host once and applies them when they differ from the stored build, so an edit made while the browser was closed needs no `config.reload`. When the browser copy holds changes made in the browser (an import, an editor save, a snippet change), the start asks on the settings page first. Without the host or its permission the extension runs on the stored build, and on the built-in defaults before the first load. `just build-config` only lints the directory and writes nothing Firefox reads. The native host is optional: browser edits cover casual use, and only the config files (TOML, snippets and CSS) need it. A stale `~/.mozilla/managed-storage/desertfox@uhs-robert.json` from older versions is ignored and safe to delete.

### Source files

The tool reads `~/.config/desertfox/` by default. Every data file is TOML. The build reports any file or directory it does not know as unknown, a leftover `.jsonc` file included. Only `.toml` files belong in the `.d` directories and in `themes/`, only `.css` files in `style.d/` and only `.js` files in `snippets/`.

| File | Holds |
| --- | --- |
| `keymap.toml` | Every key: bindings per mode, plus the `search_keys`, `container_keys`, `site_keys` and `modifiers` shortcuts. `""` removes a default binding. |
| `search_engines.toml` | Search engines: a tree of named URL templates with slots (`{query}`, `{repo}`, and others). `%s` still reads as `{query}`. Data only, no keys: the letters of the `s/` group live in `[site_keys]` in `keymap.toml`. The built-in `duck` and `site` need no entry, and an entry with their name replaces them. See [Starting engines](#starting-engines). |
| `command_aliases.toml` | Extra command line names, for example `g = "open.search"`. |
| `quickmarks.toml` | Quickmarks: one letter or digit mapped to an address, for example `g = "https://github.com"`. `M<key>` adds entries in browser storage on top of these, and the stored entry wins for the same key. |
| `settings.toml` | Settings such as the which-key delay and the new tab page. |
| `snippets/*.js` | One custom command per file. See [Snippets](../design.md#snippets). |
| `themes/<name>.toml` | A local theme that `theme = "<name>"` picks. Every file counts, and the theme importer saves each scheme here. See [Themes](#themes). |
| `style.css` | Custom CSS for the DesertFox surfaces. See [Styles](#styles). |

Each data file can also have a matching directory, for example `keymap.d/`. The tool merges the main file first, then the files in the directory in name order. A later entry wins for the same key. This is how private config joins without editing public files: a private repo links `keymap.d/50-private.toml` and `snippets/` files into place.

Every key lives in `keymap.toml`. The other files hold only data. A binding is one line of command text, in the grammar of [Command line syntax](interfaces_cmdline.md#command-line-syntax), or a list of them that run in order, or a table `{ run = "...", label = "...", intent = "..." }` that names the key for which-key and can replace its hover text (`run` is a string or a list). TOML quotes any key that has symbols, so `"<C-[>"` and `"$"` are quoted and `gx` is not. Two shortcut sections remove most repetition:

```toml
# keymap.toml
[search_keys]                   # sa/Sa, sb/Sb
a = "arch"
b = "brave"

[site_keys]                     # s/i, S/i: the engine of the page's site
i = ["github.issues", "gitlab.issues"]
I = ["github.repo.issues"]

[container_keys]                # ca/Ca, cc/Cc, cp/Cp
a = "Family"
c = "Client"
p = "Personal"

[normal]
J = "tab.next"
b = "bookmark.open"
gO = ":open -t @current_url"    # types the command into the command line and waits
y = ""                          # removes a default binding
ww = { run = ":open -w @current_url", label = "New window, edit current URL" }
```

- `sa` searches with the `arch` engine in this tab, and `Sa` in a new tab.
- `ca` reopens the current page in the Family container, and `Ca` opens a prompt, set by an explicit `prompt` on the generated key, prefilled with the current URL in a new Family tab.
- `s/` is the group for the page you are on. Each `[site_keys]` letter lists engines of different sites. On a page the first listed engine whose `hosts` include the page host and whose page slots the page fills runs. Which-key shows a letter only when such an engine exists, so on a GitHub repo page `s/` offers GitHub-wide search and search in this repo, on a user page the GitHub-wide ones, and on an unrelated site nothing. `S/` does the same in a new tab. A member key behaves like `sa`: it searches the selection at once, or opens the command line with the engine typed in. A letter is one key, not `/`, and lists only engines whose `hosts` do not overlap (an engine with no `hosts` overlaps all). `tools/build-config` refuses the rest, and a `search_keys` letter `/` unless the user unbinds both `s//` and `S//`. A row reads the label of the engine the page selects, and which-key hides a letter it cannot resolve. A typed key on a site that fits none refuses with a toast, "No <letter> search for this site".
- `s//` and `S//` search the current site with the built-in `site` engine: the default engine's URL with `site:{host}` added to the query. They show on every page that has a host. The shipped keymap sets the letter `/`, which the build refuses in a user file. If the default engine needs a page slot, `site` uses DuckDuckGo and the load warns. `site` is built when the config loads, so a live `:set default_engine` does not change it.
- `[modifiers]` maps a key inside a group to the args it adds, for example `";r" = { rapid = true, label = "Rapid" }`. The key becomes a group that holds a variant of every other key of the group, with those args added. The `label` names the group. A variant exists only when the command's param schema accepts the args, so an invalid combination is never bound or shown. A key that sets its own `action` gets no variants, and modifiers do not stack. An explicit key at the modifier key wins and the load warns. An explicit key under it wins silently. Normal mode only.
- Containers themselves need no file. Firefox lists their names, colors and icons through `contextualIdentities.query()`, and completion and the `container` param use that list. A name in `container_keys` that does not exist gets a warning at load and is skipped.
- The prefixes for generated bindings (`s` and `S`, `c` and `C`) are settings. An explicit binding in the keymap wins over a generated one.
- A key cannot be both a binding and the start of a longer one, so a user key that extends a default binding (default `sg`, user `sgg`) takes its place: the build drops the default binding and warns once per mode, naming the user keys. A default that a user key replaces includes a binding made by a modifier. The default stays when no extending user key passes the registry check. The build does not check the mode of the extending key, so a user key whose command does not run in its mode still drops the default. This holds for keys from `search_keys` and `container_keys` too. The reverse needs no rule. A user binding shorter than a default group (user `g`, default `gg`) keeps the user key and skips the longer default keys. Two user keys that clash, or two default keys, still skip the longer one with a warning. A vim-style wait on the shorter key is not built, because it adds a pause to every such key.

#### Starting engines

DesertFox has one built-in engine, `duck` (DuckDuckGo), and the `default_engine` setting defaults to it. So clipboard search works with no config. It is added when the config loads and when `tools/build-config` checks names, so the merged file stays as written. An entry named `duck` in `search_engines.toml` replaces the built-in whole. Nothing hides or removes it.

[`examples/engines.toml`](../../examples/engines.toml) resolves to 69 engines, `duck` among them, and teaches the tree rules in two worked trees (GitHub and YouTube). Copy it to `~/.config/desertfox/search_engines.toml` and edit it. A TOML file cannot include another file. A `search_engines.d/` file also works, and a later file replaces the table at the same dotted path (a later `[github.repo]` replaces only that node and leaves `github` alone).

#### Engines

An engine is a named URL template. It replaces the former site commands. No provider is built in except `duck`.

- Slots. `{query}` is the typed or selected text, and `%s` means the same. Page slots read the current tab: `{url}`, `{host}`, `{title}`, `{repo}` (GitHub), `{subreddit}` and `{channel}` (YouTube). Each page slot is a small pure function in `src/shared/engines/slots.ts` with its own message for a page that cannot fill it. `{a|b}` takes the first slot that has a value, so `{query|url}` is the typed address, else this page. `{name:raw}` skips escaping, for a path such as `/web/{url:raw}`. Every other value takes `encodeURIComponent`.
- Tree. A table inside an engine is a child, named with a dot (`github.repo.issues`). A child inherits every field and overrides by name. `label`, `keyword` and `reverse` do not inherit: the label is the chain of labels on the path ("GitHub: this repo: issues"), and a `label` field sets one link. A `keyword` names one engine, so a child sets its own. A child cannot be named `url`, `label`, `params`, `fallback`, `hosts`, `keyword` or `reverse`, or like a field or param of its parent. `reverse` is an optional regex that reads the query back from a results page address (see `docs/search_engines.md`, "Reading the query back"); without it the reader comes from `url`. A later file replaces the table at one dotted path.
- Params. `[github.params.type]` declares `default`, `values` (name to URL text) and `children = true`, which generates one child per value. A field set to a value name picks it, and `type = { only = [...] }` narrows the values below that level. A hand-written child beats a generated one. A query pair whose whole value is one empty param (`&type=`) is left out.
- Hosts. `hosts = ["github.com"]` lists the host names of the sites an engine belongs to, and children inherit it. A host matches only itself, so `gist.github.com` needs its own entry. It gates only the generated `s/` and `S/` keys: explicit keys and completion ignore it. The build refuses a `hosts` that is not a list of lower-case host names, and one on a node with no url on it or above it.
- Availability. An engine is available on a page only when every page slot in its URL can be filled. Which-key hides the keys of an unavailable engine, and a group left empty. A key still works when typed, and shows the slot message. An engine with `fallback = "<engine>"` never hides and runs the fallback when its slots cannot fill. Snippets can require slots with a `// requires: repo` header. The background filters the key list, so the content script is unchanged.
- Resolution. The config build (`src/shared/config_build/merge.ts`) resolves the tree into a flat map keyed by the dotted name and the extension stores the result, so it only fills page slots and the query. `tools/build-config` runs the same resolution as a lint and writes no engine file. It rejects an unknown slot, a param no URL uses, a field that is neither a known field nor a var some URL reads, a value outside the declared list, a fallback to a missing engine, a fallback loop and a default engine that needs a page slot.
- Help. `help` lists the resolved tree with each engine's URL, slots and the file and level that set each field. `engine.show <name>` opens it at that engine.
- Which tool. A result that is a URL is an engine. Page DOM or several steps is a snippet. Browser APIs (tabs, windows, bookmarks, containers) is a built-in command. A fuller real example: [https://github.com/uhs-robert/oasis-dots/blob/main/home/desertfox/.config/desertfox/search_engines.toml](https://github.com/uhs-robert/oasis-dots/blob/main/home/desertfox/.config/desertfox/search_engines.toml).

### Merge and checks

The merged file has one section per kind: `keymap`, `search_engines`, `command_aliases`, `quickmarks`, `settings`, `snippets` and `css`, plus a format version. The stored keymap holds invocations, so the extension never parses command text. The tool:

- rejects unknown files and unknown sections with a message, so a misspelled file name does not vanish silently. A TOML syntax error names the file, line and column.
- parses every binding string with the registry grammar, then checks it, every alias and every snippet against `commands.json` and reports errors before the extension loads.
- reads snippet code and CSS as text and escapes it, so nobody edits code inside JSON.
- generates a JSON Schema for each data file from `commands.json`, so an editor with TOML schema support (Taplo) completes command names and setting names.

The TOML parser (`smol-toml`) is a dev dependency of the tool only. None of it reaches the extension bundles.

### The settings table

- Each setting is one row of data in `src/shared/settings_table.ts`: its kind (true or false, a word from a list, a number, text, a list, a table), the values the kind takes and its default. The check, the expectation text in a problem message, the values the command line offers, the editor JSON Schema, the `Settings` type and the defaults all follow from the row, so a new setting takes one row and one description.
- A row of kind `custom` (`hint_letters`, `theme`, `new_tab_page`) has its check and expectation written in `settings_schema.ts`. `settable: false` marks a setting that `:set` refuses. `per_site: true` lets a `site_rules` row set the setting for its sites (see [Site table](#site-table)). The one row of kind `site_table` (`site_rules`) takes each such setting as an extra column, checked by that setting's own check.
- A table field of kind `site_modes` (the `modes` column) holds named site modes, each `{ label, bind }`, where `bind` follows the rules of the `bindings` kind. A table field of kind `mode_bindings` (the `keymap` column) holds one `bindings` table per keymap mode in `SITE_KEYMAP_MODES`. A table field of kind `bindings` (the `bind` column) holds a table from a key sequence to a binding in the formats of a keymap entry (a command string, a list of steps, `{ run, label, intent }`, plus `when_focus` and `when_present`, or a list of such tables as choices; the stored form is an invocation table `{ id, args }`, and a list of step lists for choices).
- Every setting has a default except `home_page`, because `page.home` refuses without one, and `zoom`, because without one Firefox keeps the zoom it remembers for each site. The editor descriptions live in `settings_docs.ts`, which only the tool imports: the prose is large and no page needs it. The content script reads `src/shared/default_settings.ts`, which `just settings-defaults` writes from the table with one constant per setting, so the content script carries only the defaults it reads.
- The command line page reads `src/shared/setting_completion.ts` the same way, one row per setting with its name, flags, expectation text and listed values (theme names as of generation), so it bundles neither the table nor the setting rules. The page checks the shape of a line only (`check_args_shape`), and a bad `:set` value shows its error at Enter, from the background. `just test` fails when either generated file is stale, and `just themes` changes the theme names in the second.

### Styles

Every surface (which-key, the command line, hints and the mode indicator) draws from CSS custom properties, for example `--desertfox-bg-core`, `--desertfox-fg-core`, `--desertfox-primary` (titles and groups), `--desertfox-secondary` (keys), `--desertfox-font` and `--desertfox-radius`. The variables are the stable way to restyle DesertFox. Documented class names use the same `desertfox-` prefix.

- The defaults are declared on an inner element of each surface, not on the shadow host. The host sits in the page, so page CSS can match the host, but a variable set on the host or on `:root` does not reach the inner element, which sets every role token itself. The long prefix and the inner element together keep page CSS out.
- Exception: the help and new tab pages read their fallback tokens from `:where(:root)` in `page_base.css`, so a variable set on `:root` reaches them. The shadow-root surfaces keep the rule above.
- User CSS must name the inner class of a surface to change a variable there, for example `.desertfox-whichkey { --desertfox-primary: #ff6ec7; }`. Variables on `:root` or `:host` alone do not reach inside a surface. The help page lists the classes.
- `style.css` and `style.d/*.css` load after the built-in styles in the shadow roots (hints, which-key, toast, badge) and in the command line, help and new tab pages, after the theme sheet, and follow a reload. Those pages stay hidden until the theme and the user CSS have both been read. Variables set outside DesertFox, on `:root` or in a browser user stylesheet, stay unsupported.
- The help and new tab pages share one base sheet, `src/shared/page_base.css`, which they link before any other style. Its fallback palette and tokens sit in `:where(:root)`, so the theme and user CSS always override it. Its classes (`desertfox-keycap`, `desertfox-card`, `desertfox-pill`) are listed on the Styling page.
- The background resolves the theme at startup and at every `set`, and stores it as `desertfox_theme` (`{ dark, light }`, the light set already picked by `light_intensity`) in `storage.local`. Each surface turns it into one style block on its inner element, after the built-in styles and before user CSS, and follows `storage.onChanged`, so a `set theme` reaches open pages at once. A surface stays hidden until the first read of the theme and of user CSS returns, and a page stays hidden until the theme read returns, so the default colors never show. A failed read counts as returned. The first hint or which-key panel on a page appears a few ms later, once per page. Light or dark is a `prefers-color-scheme` block.
- The `font_family`, `font_family_mono` and `font_scale` settings ride in the same stored record, in an optional `font` field that holds `--desertfox-font-family`, `--desertfox-font-family-mono` and `--desertfox-font-scale` (the percent divided by 100), written once in the base block and only for the settings that are set. Each surface writes its font as `var(--desertfox-font, calc(<own size> * var(--desertfox-font-scale, 1)) / <line height> var(--desertfox-font-family, <own family>))`, so the order is the surface's own font, then the setting, then a `--desertfox-font` or family variable in `style.css`. `parse_font_family` checks the family text and stores it canonical. The help and new tab pages scale only their text, in the font variable and the small text token, and keep the root size, so the layout and the breakpoints stay as they are. Firefox zoom is the whole-page tool. The command line, the key caps and the hint labels read the mono variable.
- The font list that the Settings page and `set font_family` (and `font_family_mono`) offer comes from one of two sources: the names `list_fonts` returns where the native host is installed (they stand alone, because Firefox resolves fontconfig aliases and the probe would add names that are not installed), else a canvas probe of a built-in candidate list (`src/shared/font_candidates.ts`) in the background page. A name counts as installed when its width differs from the width of the generic family it falls back to, measured against both `monospace` and `serif`. The background stores the list in `storage.local` as `desertfox_font_names` and refreshes it at startup, when the Settings page opens, after a host update and when a permission is granted. A host that is missing (not installed, no permission, or too old to know the verb) gives the probe list. A host call that fails keeps the cached host list, and only a refresh with no cached host list falls back to the probe. It is a cache, so a missing or malformed value rebuilds. The command line page gets the stored names when it opens and does no probing. Typing any name always works: the list only suggests. Measured on Firefox 160 for Linux, neither `privacy.resistFingerprinting` nor Strict tracking protection changed what the probe finds: the background page is exempt from the first, and a web page probing the same names found the same set under both. Other systems are not measured.
- Setting variables covers colors, fonts and sizes. Full selectors can change layout. The documented class names on each surface are part of the public format, and the help page lists them.
- In Oasis Dots, the theme switcher writes `style.d/00-oasis-theme.css` with the variables for the current Oasis theme, then runs the reload. Without Oasis, the built-in defaults apply.
- CSS cannot run code. User CSS may not load remote addresses: `style.css` or `style.d/*.css` that holds `@import`, `@font-face`, `image-set(`, `src(` or a `url()` that is not `data:` is refused, with the file and line. The check runs on an import, a reload of the config folder and a save in the files editor, so the current config stays when it fails (`build_files_config`). The engines and aliases layer rebuild skips it, because it reuses CSS that already passed. CSS that an older version stored stays until the next reload, because there is no recheck at startup. `@namespace` with a quoted string passes, because it names an XML namespace and fetches nothing. Its `url()` form is refused like any other non-`data:` `url()`, so write the string form. A theme color value cannot carry CSS, because `parse_color` accepts only a hex, `rgb()`, `rgba()` or `hsl()` color and stores it as hex. The import review and the permission grant panel show no user CSS.
- The manifest CSP covers the extension pages (new tab, help, popup, command line frame, workers) and not the surfaces DesertFox draws inside web pages, which the check above covers. It sets `script-src 'self'`, `object-src 'none'`, `style-src 'self' 'unsafe-inline'`, `font-src 'self'`, `worker-src 'self'`, `img-src` limited to `'self'`, `data:`, `blob:`, `resource:` and `moz-icon:`, and `connect-src` (with `'self'`) open to `https:` and `http:`. Remote scripts, `@import`, remote fonts and remote images are blocked in those pages, so a remote `url()` image in user CSS does not load on an extension page. Tab favicons arrive as `data:` URLs and container icons as `resource:`. Only the image copy fetch and the weather fetch need the remote `connect-src`.

### Themes

A theme file maps colors onto a fixed public list of roles. The theme's own color names never reach DesertFox. A file is TOML with a `[dark]` table, a `[light]` table or both, and a file with one table serves both system settings. Each table maps a role to a color: `#rgb`, `#rrggbb`, `rgb()`, `rgba()` with alpha 1 or `hsl()`, stored as `#rrggbb`. Named colors are not accepted.

The 27 roles: `bg_core`, `bg_mantle`, `bg_crust`, `selection`, `fg_core`, `fg_comment`, `fg_dim`, `fg_muted`, `primary`, `secondary`, `accent`, `border`, `error`, `warn`, `ok`, `info`, `mode_normal`, `mode_insert`, `mode_ignore`, `mode_caret`, `mode_visual`, `mode_item`, `mode_media`, `search_bg`, `search_fg`, `search_current_bg` and `search_current_fg`. `fg_core` is the text, `fg_comment` is secondary text, `fg_dim` is hints such as the command line usage line, and `fg_muted` is disabled text, which has no contrast floor. `error`, `warn`, `ok` and `info` color the toast kinds. A mode badge is its `mode_*` role with `bg_core` as the text. `selection` also paints the selection in visual mode, and caret mode paints one cell in `mode_caret` with `bg_core` text. `mode_caret` is the Neovim cursor color, so the badge and the cell match, with exceptions in the Oasis build (`tools/build_themes.ts`), made because two badges sat too close in color. Every Oasis dark theme sets it to `#f7d46c`, because the shared yellow cursor `#f0e68c` sits too close to the yellow normal or insert badge in five of them. Oasis Desert light sets it per level (1, 2 and 4) for the same reason. The build also sets Oasis Scorpion light level 4 `mode_insert` by hand and gives Oasis Canyon light `mode_visual` the theme's own `secondary` at every level, because its brown visual badge sat on its brown normal badge. `mode_item` colors the ITEM badge and derives from `info` when a theme leaves it out. The Oasis build sets it from the terminal magenta. No base16 slot feeds it. `mode_media` colors the MEDIA badge and derives from `error`. The Oasis build sets it from the green `ok` diagnostic color. No base16 slot feeds it either. The `search_*` pair colors every match of a `/` search and the `f`, `t`, `F` and `T` targets, and the `search_current_*` pair colors the current match. They come from the Neovim `Search` and `CurSearch` groups without the bold, because a CSS `::highlight()` rule cannot set it. The page document has no tokens, so the caret bundle reads these colors from the stored theme. `bg_core`, `fg_core`, `primary` and `accent` are required. Every other role derives from them when missing, by the one table in `src/shared/theme/derive.ts`. A role's CSS variable is `--desertfox-` plus the role with hyphens, for example `--desertfox-bg-mantle`. The list is a contract: a later rename breaks contributed themes, an addition does not. An old name such as `bg`, `fg` or `muted` in a theme file is an unknown role, and the error lists the valid ones.

`theme = "<name>"` looks in `<config dir>/themes/<name>.toml` first, then in the built-in themes. The default is `oasis_moonlight`, and a bare name such as `moonlight` is a config error that lists the known names. A local file wins over a built-in theme of the same name. Every file of `themes/` is kept, not only the one `theme` names, so `:set theme <name>` takes any of them.

`theme = "desktop"` follows the theme the desktop pushed over the bridge (the `theme` verb, see [Bridge host](host.md#bridge-host)). The background resolves it at every publish to the last stored push, or to `oasis_moonlight` while none was stored, with the bridge off too. `:set theme <name>` stops the following until `:set theme desktop`. A push stores its name either way and changes the theme only while `theme` is `desktop`. The default stays `oasis_moonlight`, so following is off until chosen. A built-in theme name is what a push can carry, so a local theme is not reached through it. Light or dark and `light_intensity` stay as they are.

A base16 or base24 scheme can be imported on the settings page, under the Appearance settings. Schemes are in the tinted-theming collections at `github.com/tinted-theming/schemes`, browsable in the tinted gallery at `tinted-theming.github.io/tinted-gallery`. The box takes pasted text or a picked file and shows a live preview (hint labels, mode badges, toasts, which-key and search highlights) before Save. `src/shared/theme/base16.ts` reads the classic YAML, the tinted-theming YAML and base24 with no YAML library: one `baseNN: "hex"` line per color, `name` or `scheme`, `variant`, and a refusal of flow style, a second document and a duplicate slot. The slot-to-role table sits in that file: `base00` to `bg_core`, `base01` (base24 `base10`) to `bg_mantle`, base24 `base11` to `bg_crust`, `base02` to `selection`, `base05` to `fg_core`, `base03` to `fg_comment` and `border`, `base04` to `fg_dim`, `base0D` to `primary` and `mode_normal`, `base0E` to `secondary`, `accent` and `mode_visual`, `base08` to `error`, `base09` to `warn` and the current search match, `base0B` to `ok` and `mode_insert`, `base0C` to `info`, `base0A` to `mode_caret` and the search match. The rest derive, `mode_item` from `info` and `mode_media` from `error`. `fg_dim` is raised to 3:1 by the clamp in `src/shared/theme/contrast.ts`, which the Oasis build uses too. A scheme has one variant, so it fills both the dark and the light table. A built-in name, `desktop` and a name outside lowercase letters, digits, `_` and `-` are refused. A save writes the scheme as `themes/<name>.toml` (`set_theme_file`), in the browser copy and through the host's `write_config_files` (kind `theme`), the same way a `:set` writes `settings.toml` (see Settings in the file): one queue turn, the same record of a lagging folder, the same base check. The page lists every theme file with a Remove button. A file whose name the host does not write (for example `themes/Nord.toml`) is listed with no Remove, and a remove of it is refused. Saving over a name asks first. A file added to the folder by hand since the last read is never overwritten: the write is refused and the copies-differ question takes over. `:set theme` accepts the names and the picker lists them. Remove deletes the file through the host, only while it still holds the text of the last read. A file that shadows a built-in theme of the same name leaves every `theme` selection alone, as the built-in takes over. Otherwise, when `settings.toml` sets `theme` to that name, Remove takes the key out in the same change, and it drops a saved or temp `theme` edit that names it, so the theme falls back to the default. A `settings.d` file that sets `theme` to it refuses the remove and names that file. An editor save of a theme file starts no write, as for `settings.toml`. A `settings.toml` that names a theme file goes in one batch with that file, and a remove sends the `settings.toml` that no longer names the theme in one batch with the delete, so the folder builds after every batch, except for a file the rollback cannot put back and a host crash midway (see [host.md](host.md)). A host from before `write_config_files` holds both until it is updated. When that `settings.toml` write goes to the copies-differ question, the delete goes with it. Versions before theme files kept imports in `storage.local` (`desertfox_imported_themes`). The first start after the update moves each into `themes/<name>.toml`, or `<name>-browser.toml` when a file of that name holds other text, and moves a saved `theme` edit that names one into `settings.toml`, under the new name (a `settings.d` file that sets `theme` keeps it a saved edit). The stored list goes in the same queue turn, after the files and the record are stored, so a stop before that moves nothing twice: a file that holds an import's text already counts as moved. Without the host the record waits and a later start writes the files. The importer changes no Firefox chrome and needs no permission.

The 16 Oasis themes are not TOML. `themes/oasis/` holds byte copies of the oasis.nvim CSS files, one dark file and five light files per theme (`just oasis-themes <oasis.nvim dir>` copies them). `tools/build_themes.ts` reads each role from one named `--oasis-*` variable, with no mixing, and the table of which variable fills which role is at the top of that file. The `light_intensity` setting (1 to 5, default 3) picks the light set of an Oasis theme. Other themes have one light set. `tools/build-config` checks every local theme file and rejects an unknown role (the error lists the valid ones), a missing required role and a bad color, each with the file, table and key. `just themes` compiles `themes/oasis/*.css` and the contributed `themes/*.toml` into `src/shared/themes.ts`, and `just test` fails when that module is stale. The stored theme sets every role token on every surface.

`primary` is the brand color: links, titles, groups, the hint labels (a filled label with `bg_core` text and a 1px primary border). `secondary` colors the keys in which-key and the new tab clock second hand. `accent` marks highlights. A `style.css` that sets or reads `--desertfox-accent` for the brand color moves to `--desertfox-primary`.

### Site table

- `site_rules` adds up across files, unlike every other setting, which a later file replaces. The combined list is `settings.toml`'s rows, then each `settings.d` file's rows in name order, then the shipped rows. An earlier row wins (first match per column), so this order is the reverse of a scalar, where the later file wins. Each row keeps its file (`origins`, section `settings.site_rules`, by index in the combined list), so a problem names the file of the row. A list saved in the browser by an older version is folded into `settings.toml` once at start (rows no file has yet) and dropped, so nothing replaces the combined list. The popup and the keys form write `settings.toml` only.
- `site_rules` is one site table: a list of tables, each with `site` (a match pattern) and optional columns. `off` is true or false. `pass` or `only` holds key sequences in keymap notation split by spaces, and `check` refuses a row that sets both. Each column resolves on its own: the first matching row that sets a column decides it, and `pass` and `only` form one column, the key rule.
- So a broad row can turn a whole domain off while a narrower row above it sets `off = false` for one path, and a key row and an off row for the same page combine. So a narrow key row above a broad bare row now leaves that site off, unless the narrow row also sets `off = false`. A row that sets nothing but `site` loads as `off = true`, the shape older configs and the popup wrote.
- A page is all off when `off` resolves true or when its key rule frees every normal binding: it enters ignore mode, so the badge and `<S-Escape>` work as before. This is how to start a site in ignore mode: there is no start-mode setting. The top frame matches its own address. A subframe matches its own address or the tab address. `pass` removes the listed sequences from the normal tree, and a passed prefix removes its whole subtree, so `pass = "g"` frees every `g` key and `pass = "gg"` frees only that key.
- `only` keeps just the listed sequences, and a listed prefix keeps its subtree. It also keeps `<C-v>` and `<S-Escape>`, so the one-shot pass and the way into ignore mode work on every ruled page. Normal-mode `<Escape>` goes to the page under `only`, and insert mode still leaves on `<Escape>`. The key rule covers normal mode only. Insert, hint, command line, caret and visual behave as before, `browser` chords stay on, and `<C-v>` stays the one-shot escape.
- The `bind` column is a table from a key sequence to a binding in any format a keymap entry takes (a command string, a list of command strings that run in order, or `{ run, label, intent }`, which also takes `when_focus`) that binds normal-mode keys on the row's sites, for example `h` to `page send_key ArrowLeft`. The config build parses the text with the keymap's own parser and stores invocations, the form the shipped rows write directly.
- `when_focus` on a bind (`{ run, when_focus }`, or on the first step's invocation table) is a CSS selector, a focus guard. The bind runs while nothing has focus (body counts as none) or the focused element or one of its ancestors matches it, so a control inside a map counts as the map. Otherwise the key runs the binding the bind replaced, with its count, as if the row did not bind the key. A bind that replaced no leaf (a new key, or a key that was a prefix) passes the key to the page then, as if the key were unbound. A selector that does not parse matches nothing. The background keeps the replaced leaf on the bind's leaf (`otherwise`) when it grafts, and the content script picks one of the two before it runs the leaf (`leaf_for_page`). A keymap entry with `when_focus` is skipped with a warning, as it replaces nothing.
- `when_present` on a bind is a CSS selector, a page guard. The bind runs while the frame's document shows a match: a match counts only when `is_shown` accepts it (a box, and not hidden by `visibility` or opacity), the rule `page.item` uses for its items, so a guard never runs a move that finds nothing. A bind with both guards runs only while both hold. A selector that does not parse matches nothing. The guard is read when the key runs, so it follows a page that changes its view without a load. A keymap entry with `when_present` is skipped with a warning, as for `when_focus`. A bind with `otherwise = "page"` (a field on the bind table or its first step, with the guards) keeps the leaf it replaced off the chain, so a failed guard leaves no leaf and `run_leaf_` in the content script hands the real key to the page, as a key with no binding gets it. A keymap entry with `otherwise` is skipped too. The setting accepts only the value `page`.
- A bind can be a choice list, an ordered list of up to 8 `{ run, label, intent, when_present, when_focus }` tables, so one key does different things by what the page shows, for example `h = [{ run = "page.item --direction=left li.tile", when_present = "ul.grid" }, { run = "page.back", when_present = "table.list" }]`. The first choice whose guards hold runs. With none, the key runs the binding the bind replaced, as for a single guarded bind. Every choice but the last needs a guard, or the choices after it could never run, and the settings check refuses such a list. A list that mixes `run` tables and steps is refused too. The build stores each choice as its own list of invocations. The compiler turns the choices into a chain of leaves through `otherwise`, the graft adds the replaced leaf at the end of the chain, and `leaf_for_page` walks it. The merge across rows does not change: the first row that binds a key decides it, choices and all. Which-key shows the first choice's label, and the site rules view lists each choice with its guards. A keymap entry cannot be a choice list.
- A list is a chain: the steps run in order, a failed step stops it, the count goes to every step, and the first step's `label` (or the bind's `label`) is what which-key shows. A bind holds at most 20 steps, checked by the settings check and again by the compiler. A macro is a chain too: `macro play a` with a fixed register binds like any command. It merges key by key: for each key the first matching row that binds it decides, so a user row that binds only `j` keeps the other keys of a later row.
- The `keymap` column binds keys in other keymap modes: `[site_rules.keymap.<mode>]` is a table of binds in the same formats as `bind`, and `<mode>` is `normal`, `visual`, `visual_line`, `caret` or `item` (the validator refuses any other mode and names the allowed ones). `bind` is the short form of `keymap.normal`: a row may set both, the two merge key by key into one normal table, and the same key in both is a config error that names the key. Each mode merges across rows as `bind` does (the first matching row decides each key), the compiler checks each bind against the commands that run in its mode, and prefix clash warnings are per mode. The background grafts a mode's merged binds onto that mode's tree for the page, so the content script and the matcher do not change, and which-key reads the same grafted trees. A mode bind is skipped on a page that is all off, and `pass` and `only` leave it alone, because they prune the normal tree only. The Site Rules view tags each such change with its keymap mode. This is not a site mode: `modes.visual` (the shipped Sheets row) is an overlay on normal mode that `mode.site visual` starts, and `keymap.visual` binds keys in visual mode.
- The background grafts the merged binds onto the normal tree, then `pass` and `only` prune it, so `pass = "j"` frees a bound `j` and `off` wins over all of it. The compiler checks each bind with the one validator and skips a bad one with a warning. A bind that waits for a key press is refused. When rows bind a key and a longer key under it (`g` and `gx`), the compiler warns and the shorter bind wins, as a complete binding hides the keys under it in a keymap.
- This holds for rows of one pattern and for rows of different patterns, unless their hosts are provably different (a page can fit both patterns otherwise), and it holds in either row order. Named site modes are not compared across rows, as a mode comes whole from the first matching row. A cross-site iframe can still drop a bind silently, as a frame resolves rules by its own address and the tab's.
- `page.send_key` takes optional `ctrl`, `shift`, `alt` and `meta` flags (all off by default) that set the modifier flags of its events, a `keypress` flag that adds a keypress between the keydown and the keyup (skipped when the page cancelled the keydown, and carrying the character code of a one-character key), and a `focus` flag that focuses the target before the key, for a page that reads keys only while its element has focus.
- It takes the count as its `times` param and sends the pairs through a per-page queue with 10 ms between pairs, one entry per call, because Sheets applies only the first of several pairs sent in the same millisecond. DesertFox ships site rows after the user's rows (`src/background/default_site_rows.ts`).
- `page.click <selector>` clicks the first element that the selector finds and that shows (`is_shown`, the rule of `when_present`), with the pointer and mouse events of a hint click (`click_like_a_hint` in `lib/actions.ts`). It is for a control that a site script opens only on a click and ignores Enter on. It refuses when nothing shown matches. The handler lives in the hints bundle, which holds that click, because the `site_actions` bundle has no room for it.
- The first is `sheets`, two rows for the two address forms of Google Sheets, which bind `h`, `j`, `k` and `l` to the arrow keys through `page.send_key` (a `keydown` and a `keyup` with `keyCode`, which Sheets reads, sent to `#waffle-rich-text-editor`), `gg` to Ctrl+Home, `G` to a chain of Ctrl+End then Home (the bottom of column A, labeled so) and `<C-h>`, `<C-j>`, `<C-k>` and `<C-l>` to Ctrl+Left, Down, Up and Right (so they hide Firefox's Ctrl+H, J, K and L on Sheets tabs, and Sheets' own Ctrl+H (find and replace) and Ctrl+K (insert link)), bind `x`, `y` and `p` to `page.clipboard` (cut, copy and paste, which a synthetic Ctrl+X, Ctrl+C or Ctrl+V does not do, so `xx`, `xp`, `pp`, `pt`, `pw` and the whole `y` group are gone on Sheets only), and give the row a `visual` site mode (label VISUAL) that `v` and `V` start: in it `h`, `j`, `k`, `l`, `gg`, the `G` chain and `<C-h/j/k/l>` send the same keys with Shift held, and `x`, `y` and `p` end the mode first and then cut, copy or paste the range, so a refused clipboard step cannot leave the mode on.
- Escape ends the mode through the site-mode exit policy and sends no key that collapses the range. `page.clipboard` runs through the same per-page queue as `page.send_key`, so `l l x` typed fast cuts after both arrows, and pass `<C-a>`, `<C-x>` and `<C-v>` to the page so Select all, Cut and Paste work. A user Sheets row that sets `pass` replaces that pass column, so it must list all three to keep them.
- A row that sets `only` replaces it too, and keys left out of `only` go to the page, so it must leave `<C-a>` and `<C-x>` out. `only` always keeps `<C-v>` for the one-shot pass, so an `only` row cannot free the real Ctrl+V. The top-level setting `default_site_rows_off` lists the names of shipped rows to turn off. The popup and the settings page list the user's rows only, and which-key shows the shipped binds.
- The second is `maps`, two rows for `www.google.com/maps*` and `google.com/maps*`. Maps pans on arrow keys only while its map element (`div[role="application"][tabindex="0"]`, its localized aria-label left out) has focus, real or synthetic arrows alike, and Escape blurs it. So the row binds `h`, `j`, `k` and `l` to `page.send_key` arrows aimed at the map, guarded by `when_focus` on the same selector: with focus on the place panel or another element, the keys scroll as usual. A field puts the page in insert mode, so the binds do not apply there. Maps focuses its search box as it loads, so the row sets `focus_on_load` to the map, which takes the focus in place of the search box, and hjkl pan from the page as loaded. The binds also set `page.send_key`'s `focus` flag, so each key focuses the map before its arrow, and hjkl pan again after Escape blurs the map. The match patterns cannot name every `google.<country>` host, so the country domains keep the plain keys.
- The compiled keymap stores per row `{ site, origin, name, regex, off, keys, bind, modes, values }`, each column present only when the row sets it, with `keys` holding parsed sequences. `site` is the pattern as written, `origin` is `user` or `default`, and `name` is the shipped row's name. The site rules view (`site_rules_view.ts`) reads them: it lists the rows that fit one address in table order, the columns each sets and the keys each changes, marking what an earlier row already decides.
- The background resolves the columns for the sender's address (the top frame uses its own address only, because `sender.tab.url` can lag during navigation, and a subframe adds the tab address), prunes the normal tree with the shared `prune_tree`, marks the page all off when nothing is left, and sends the page that tree with `all_off` and the freed keys (`frees`, a list of keys and a flag that inverts it).
- The content script never sees `site_rules` and swaps the tree in before the matcher, so held keys replay against the right tree. An all-off page gets the whole normal tree, so `,i` still works. Which-key lists the same pruned tree through the same resolution. A key the rule frees (a passed `/`, `'` or digit, or any such key under `only`) matches nothing and is not cancelled or counted. Every `tree_updated` resolves the columns again, so a rule edit reaches open tabs at once.
- An install enters ignore mode only on the change into all-off, so a manual `,i` or `<S-Escape>` survives an unrelated edit. On the change out of all-off (removing the row, or setting `off = false` above it) a page in ignore mode returns to normal. A page that changes its address in place (pushState, replaceState, history traversal, a hash change) asks again on the Navigation API's `currententrychange`. `sender.url` stays the address the document loaded at, so each request that matches rows carries the page's own `location.href` (`url`): the keymap ask, `read_hint_selectors`, `editor_open`, `list_keys` and `quality_report`. The background matches on it (`sender_at`) and falls back to `sender.url` when it is missing, has another origin or has an opaque origin (an about:blank frame that wrote its document reports its parent's address, which must not give it the parent's rows). An answer identical to the last one installs nothing, so a running site mode survives a step within its row, while a `tree_updated` still installs. A step into or out of an `off` row enters or leaves ignore mode through the same rule as a rule edit.

#### Per-site settings

- Per-site settings: a row of `settings_table.ts` with `per_site: true` opts its setting in, and a `site_rules` row may then set it as a column. That setting's own check (`SETTING_SPECS`) checks the value, the editor schema lists it, and an unknown column is a typo. On the sites a row names, its value beats every global layer, `:set` and `:set --temp` included: the row names the site and `:set` does not. The compiled row keeps such values in `values`, and the background resolves them with the other columns (`site_columns_for` in `shared/site/site_columns.ts` and `site_value` in `page_keymap.ts`). A value about the whole tab resolves against the top frame's address: a frame's message passes through `top_frame_address_of`, and the zoom reads the tab's own address from `tabs.onUpdated`. A value about one frame's own content resolves against that frame's address. `zoom`, `blur_on_load`, `editable_add`, `editable_remove`, `editable_remove_unsized`, `escape_to_page`, `hint_add`, `hint_remove` and `strip_tracking` opt in (below). The settings that act inside one frame (`FRAME_SITE_SETTINGS` in `prefix_tree.ts`) resolve against the frame's own address only, never the tab address that key rules add for a subframe: a row for the top page says nothing about a frame of another site. `blur_on_load`, `escape_to_page` and the three `editable_` settings reach each frame as `site_values` in its page keymap reply. The hint selectors do not ride in that reply, so content.js does not grow: the hints bundle asks for them (below). A value at its default stays out of both answers. Their global values travel in the compiled keymap (`frame_site_globals`), which the background strips before it replies.

#### Zoom

- Zoom: `zoom` is a level from 0.3 to 5 (Firefox's range), set per site in a `site_rules` row or for every site at the top level. It has no default, so with neither a page keeps the zoom Firefox remembers. Firefox remembers zoom per host and `tabs.setZoom` writes that memory (see [Per-site zoom memory](../firefox-behavior.md#per-site-zoom-memory-and-tabssetzoom-per-site-settings)), so the background (`site_zoom.ts`) sets the level from `tabs.onUpdated` only the first time a tab reaches the host in a browser session. Firefox's memory then carries it to the host's later tabs. `storage.session` holds the level set on each host, with a separate record for the private windows that clears with the last private window. So a manual zoom sticks across reloads, pages of the site, new tabs and a round trip to another site. A level that changed since (a config edit, `:set`) is set on the next load. An add-on reload or update clears `storage.session`, so each host gets the level once more then. A zoom column acts per host: a row for one path also zooms the rest of the host, and two paths of one host with different levels set the zoom at each crossing, so give a host one level. The tab's address is its top frame's. The switch off sets nothing.

#### Escape to the page

- Escape to the page: `escape_to_page` (default off, per-site) lets a page keep Escape while a field is focused. In insert mode with a field focused, the content script passes the Escape keydown to the page, does not blur and stays in insert mode. The focus follower returns to normal mode once the page drops the field, as when Sheets parks its cell editor after a cancelled edit. A manual insert (`i`, no field) still ends on Escape. Set it only for sites whose editor handles Escape itself: on a plain input the field keeps the focus and so does insert mode. The shipped `sheets` rows turn it on. `<A-Escape>` in the insert keymap sends Escape to the focused element with `page.send_key` on any site, so a site with no row has a way to give the page its Escape.

#### Blur on load

- Blur on load: `blur_on_load` (default off, per-site) takes the focus away from a field that the page focuses as it loads, so keys work at once. The content script blurs a field already focused at its first install, and while the window is open it blurs any field that takes the focus, before the frame enters insert mode. A field focused before the reply came has already put the frame in insert mode, and the blur's focusout takes it back to normal. The window opens at the first install and ends about 1 s later. While the page has user activation (`navigator.userActivation.isActive`, set by a key or a click), nothing is blurred, so a field the user clicks keeps the focus. That also covers input from before the content script started, as in a subframe that starts on its first focus. A command that runs in the frame (`run_in_content`) closes the window, so `gi` in a macro replay right after a load keeps its field. A page that focuses a field after the window still gets insert mode. A page shown from the back-forward cache runs no install, so its focus stays as the user left it. A later `tree_updated` opens no new window.
- Focus on load: `focus_on_load` (a CSS selector, default empty, per-site) uses the same window. Where the blur takes a field's focus, or the first install finds nothing focused, the first match takes the focus instead. A row that sets it opens the window without `blur_on_load`. A selector that does not parse and no match leave the plain blur. The shipped `maps` rows set it to the map element.

#### Media quality

- Media quality: `media_quality` (default `auto`, per-site) is a rule that takes a site player to a quality level. The default leaves players alone, so a site gets the rule only from a global value other than `auto` and `off`, or from a site value. The values are `off` (leave the site alone), `auto` (the default: leave the choice to the site and touch nothing), `max`, `min`, or a height (144, 240, 360, 480, 720, 1080, 1440, 2160 or 4320, written as a bare number in TOML, the highest level at or below it). It is an enum setting, so any other height is refused with the value list.
- A `site_rules` row sets it for its sites, and a site value beats the global one. The background (`media_quality.ts`) listens to `tabs.onUpdated`, filtered to `url` and `status` changes: a changed `url` (a hard load, or a `pushState` such as a click on a related video) and a finished load each inject a small probe (`quality_probe.js`) into every frame, and so does a second pass 1 s later that adds `about:blank` frames. A frame whose probe finds a video (a `video` element, also inside the open shadow root of a custom element) or a known site player handle (the YouTube or hls.js one) reports once per address, and again when the background refused it (the rule was off), and the background then injects `quality.js` into that frame alone. A page or frame with no video never loads `quality.js`. A probe looks again for 10 s and wakes on a media event, as the bundle's rule does. Nothing is injected when the extension is off, or when the global value is `off` or `auto` and no site row sets a level. The `media quality auto` command still resets a player to adaptive, because the user asks for it there.
- That check reads the keymap once per trigger for the tab. A settings change that turns the rule from off to on injects the open web tabs at once. Each frame reports to the background (`quality_report`, with `has_video`). The answer to a report from a frame with a video is the rule for that frame's address, so a frame never asks for it and a page with no video costs no keymap read. A frame with no video ends at once, with no poll.
- The probe wakes on the first `loadstart`, `loadedmetadata` or `play` event of a `video` element that reaches its document (a capture listener sees them), and a local check every 2 s for 10 s also looks for a video or a known player, inside the open shadow roots of custom elements too, because their events do not cross the root. Either one reports, the background loads `quality.js` into the frame, and the bundle starts the poll with the answer. A report the background refuses (the rule is off) is sent again later. A frame with a video polls its driver every 100 ms, for 10 s at most, until the player lists its levels (YouTube answers "unknown" until it plays) and sits at the rule's level.
- A video that reaches the level and holds 3 s ends the poll. After a navigation inside a site the old video may already hold, so the poll ends early only for another video (YouTube's `video_id`, the address of the hls.js source) and otherwise runs to the 10 s deadline, and a new video restarts the watch. A player with no video identity keeps the plain 3 s watch.
- A new address in a frame is a navigation for it, and a second run at the same address (the load finishing, the about:blank pass, a media command that injects the bundle) is not: in a frame that already has a rule it only reports and changes no level. A settings change reaches a frame that has a video through `tree_updated`, which the background sends to every tab after each config or `:set` change: the frame reports again and a changed rule takes effect at once, and a switch-off stops the poll.
- A navigation to a non-web page cancels the work still pending for the tab. A newer start replaces the poll of an earlier one, so repeated navigations leave one poll. A `media quality` choice that took ends the poll and stands over a finished load, until the next navigation applies the rule again. A choice made in the site's own menu while the poll runs is not seen, so the poll can undo it for up to 3 s.
- A frame that loads after the tab's last event misses the rule, and so does an `about:blank` frame until the second pass, because the first injection leaves out `matchAboutBlank` (with it, a frame under an all-off site rule left ignore mode when the tab's insert hold ended). Pages that are not http or https, and the extension switched off, start nothing.

#### Editable rules

- Editable rules: `editable_add` and `editable_remove` (per-site lists of CSS selectors) decide what counts as a text field, so insert mode follows focus. A match of `editable_remove` is not a field, one of `editable_add` is, and remove wins. With `editable_remove_unsized` on, a remove match counts only while it has no width, which is how the shipped `sheets` rows drop the parked cell editor. A selector that does not parse matches nothing. The hints bundle reads the answer through `window.desertfox_host.is_editable_`.

#### Scroll target

- Scroll target: `scroll_selector` (default empty, per-site) is one CSS selector for the element that the scroll commands scroll, for an app with an inner scroll area. `scroll_target()` tries the first match before the focus chain, so every scroll uses it, bundle scrolls through `scroll_box_` too. A match that cannot scroll on the axis, a selector that does not parse and no match leave the usual order (focused element, page, largest scroller). The pick of that last scan is kept per axis, weakly, and reused while the box is connected and still scrolls on the axis. A `focusin`, a `pointerdown`, a failed re-check and a pause of 1 s between scroll keys drop it. The page keymap reply carries it, like `escape_to_page`.

#### Hint selectors

- Hint selectors: `hint_add` and `hint_remove` (per-site, default empty lists) are lists of CSS selectors. Each `hint.run` sends `read_hint_selectors` from the hints bundle, and the background answers with the frame's values (`frame_site_values_for` against `sender.url`). Keys typed during that ask are held, so they reach hint mode. A rapid session keeps what its run read. A settings edit or another address applies from the next run, and a new page loads a new bundle anyway. `hint_add` runs as a second query for the `all`, `clickable`, `every`, `draggable` and the internal `drop` filters, skips the filter's test, and its matches count as clickable, so a pointer wrapper around one gives way to it. The filters that promise an address or a kind (`links`, `images`, `inputs` and the rest) take nothing added. `hint_remove` drops every candidate that sits in a match (`closest`, so within its own document or shadow root, never across one) for every filter but `custom`. The run resolves the selectors for the frame that starts it, and elements in its same-origin frames use those too, not their own frame's rows. The check accepts any non-empty text, because only a page can parse a selector: the bundle skips one that does not parse, shows one notice for the run and applies the rest.

### Background files for the config build

Behavior of the `src/background` files for this area, moved here from `src/background/README.md`.

- `keymap_merge.ts`, `compile.ts` and `shared/config/config_load.ts`: the files config `config.reload` stored, default keymap under user keymap, and the args check per binding. `compile.ts` resolves the key edits with the config's aliases and engines (`config_entry_resolver`, which the site binds share) and merges them over the file keymap before the defaults, so an edit wins over both and drops a default it extends. The merge goes by key spelling (`spelling_of`), so a file's `<C-D>` gives way to an edit on `<C-d>`.
- `edit_layers.ts`: the browser edit layers other than settings, one `storage.local` key and one load check per kind in `EDIT_LAYERS`. Each kind is a text table: the key edits are mode to key sequence to command text, as keymap.toml writes it, with `""` to unbind. A stored entry that fails the check is dropped at load. A new kind is one table entry, its check and its merge where the config is consumed.
- `item_landings.ts`: `with_item_landings` gives a site row with an item selector (read from its `page.item` steps) the keys `I` (normal and item mode: pick a list, then land on it: normal mode offers only the row's items while they show (`row_only`), item mode offers the other lists too) `zt`, `zz` and `zb` (item mode: land, then `scroll.align`) and `}` and `{` (item mode: guarded section jumps, which a row's own `}` and `{` replace and a failed guard leaves to the default), under the binds the row already has. `compile.ts` applies it to user and shipped rows.
- `item_select.ts`: the `item_select` setting set to `arrows`. `item_select_keys` builds the four arrow steps through the validator, and `with_item_select` copies a page's item tree with each `page.item` step that names a selector turned into the site's own arrow keys, and each `hint.run` step with `items` gets `row_only`, because the arrows cannot walk another list.
- `default_site_rows.ts`: the site rows that ship with DesertFox, each with a name (`sheets` is two rows, one per Sheets address form, that bind hjkl, `gg`, the `G` chain, `<C-h/j/k/l>`, `x`, `y` and `p`, add the `visual` site mode behind `v` and `V` (the same keys with Shift held, and `x`, `y` and `p` that end it), pass `<C-a>`, `<C-x>` and `<C-v>`, and drop the parked cell editor from the fields with `editable_remove`, and `maps` is two rows, for `www.google.com/maps` and `google.com/maps`, that bind hjkl to arrow keys sent to the map, which they focus first, behind a `when_focus` guard and set `focus_on_load` to the map, because Maps focuses its search box as it loads and pans only while the map has focus, `kagi` passes j and k to the engine's own result highlight, and `brave` binds j and k to ArrowDown and ArrowUp, and `google_images` is two rows (the udm=2 address at an ampersand or at the end) that bind h, j, k and l to `page.item` on the Google image tab, ahead of `google`, and `google_videos`, `google_news`, `google_short_videos` and `google_shopping` do the same for those tabs, ahead of `google` too (`google_videos` binds j and k only), and `ddg_images` binds h, j, k and l to `page.item` on the DuckDuckGo image vertical, ahead of `ddg`, and `ddg_videos` and `ddg_news` cover those verticals, also ahead of `ddg` (`ddg_news` binds j and k only), and `ddg`, `google`, `bing`, `hackernews`, `wikipedia`, `lobsters`, `archwiki`, `startpage`, `arxiv`, `stackoverflow`, `tildes`, `amazon` (which binds h, j, k and l as a grid) and `reddit` bind j and k to `page.item` with the item and link selectors of each site; every `page.item` row but `reddit` also binds `gg` and `G` to its first and last item behind a `when_present` guard on its item selector). `compile_config` appends the rows the `default_site_rows_off` setting leaves on after the user's rows, so a user row decides each column first and `bind` merges key by key. A row whose command the registry lacks is left out without a warning.
- `site_keys.ts`: `answer_site_keys_request` checks the `site_keys` request. The rows it writes are in `shared/site/site_keys.ts`, and `config_setting_writes.ts` (`change_site_keys_in_file`) writes them into settings.toml the way `change_site_rule_in_file` does.
- `strip_patterns.ts`: answers `read_strip_patterns` and resolves `copy.tabs` per tab. The global `strip_tracking_params` list when the address's `strip_tracking` resolves on (`site_value`), else an empty list.
- `site_zoom.ts`: the `zoom` setting. On a tab's load it resolves the level for the tab's address (the site value, else the global one) and calls `tabs.setZoom` the first time the host gets that level in the browser session. The levels set per host sit in `storage.session`, the private windows apart, so Firefox's per-host memory carries a manual zoom to later tabs. A tab that moved on before the set is skipped, so another site's zoom memory stays.
- `engine_file.ts`, `engine_keys_file.ts`, `engine_message.ts`: the Engines page. Its engines live in `search_engines.d/zz-desertfox.toml` (`ENGINE_FILE`), one table each, and their key letters in `keymap.d/zz-desertfox.toml` (`KEYS_FILE`), one `[search_keys]` table. Each is written whole with `stringify` and deleted with its last entry. A name a hand search engines file defines is refused by name (`hand_file_defining`). `engine_message.ts` has `list_engines` and `change_engines` (add, remove, the starter set from `dist/starter_engines.toml`, a copy of `examples/engines.toml` that `tools/build.mjs` writes). Each change runs as a plan in `change_engine_file` in `config_setting_writes.ts`: in one queue turn it builds the planned file and engines layer (`trial`), refuses a files problem or a fresh layer drop, then goes through `change_folder_files`, and the host writes the engine file (kind `engines`) and the keys file (kind `search_keys`) in one batch. A change that moves an engine or letter out of the old layer stores the layer in the same `storage.local.set` as the files (`engines_after`). The form merges into the engine's table, so the label, children and params of a starter engine survive an edit. A remove takes the engine's key letters in the same write. A letter that a `keymap.d` file loading after the keys file sets is refused by name (`keys_file_after_setting`). Every caller sends one batch through `write_files` (in `config_file_writes.ts`): a `:set` its file, an Engines page change its two files, an import its files, and a start or `,r` every waiting file. The gate decides: before every batch, `folder_for_gate` reads the folder, and `write_breaks_folder` builds it with every file of the batch, once with the writes still out on top and once without them, so no order between the files matters and a batch never counts on another batch landing. A batch that adds a build problem answers `held` for each file and stays in the record, and the loop settles each other batch that is out (`settle_batch`) and tries again. With no batch out, a held batch takes every other waiting file of the record once and tries again. At a start or `,r` (`write_waiting_files`), a batch the host refuses over one file it names, or that the gate holds over files that break the folder on their own, goes once more without those files. A batch takes the write slot of each of its paths, so a write of one of them waits for the whole batch. The host lands a batch all or none, except for a file the rollback cannot put back and a host crash midway (see [host.md](host.md)). A refusal over a hand edit names the file (`refused_files`), which settles first through the replay or the question, and the other files go again. When `settings.toml` or the keys file goes to the question, each waiting file that drops what the folder's version names goes with it (`NAMING_PATHS`), so the folder keeps building. The page's files start with `PAGE_FILE_MARKER` and `KEYS_FILE_MARKER`. A file at either path without its marker is a hand file (`is_hand_file_at`).
- `engine_layer.ts`: the engines layer (`EDIT_LAYERS.engines`). It holds only the engines and key letters of an older version that the start could not move, which a start or a save moves into the files. `publish` builds the config with it through `build_config` over the stored files plus the layer written as the `.d` files an export writes (`layer_files` in `config_transfer.ts`), so one merge and check path serves the running config, the export and a re-import. The build is cached per layer in the load step and its config goes to `LAYERED_CONFIG_STORAGE_KEY` for the pages that read the config themselves. `change_layers` builds the new layer before it stores anything and refuses, with every problem, a save that makes the build drop something it did not drop before. A layer problem names the Search engines section, not the synthetic file. After a file edit a piece that now clashes is left out with a warning (`engines: <name> left out, ...`) and the rest stays. A key letter exports into the same `keymap.d` file as the key edits, as `[search_keys]`. Nothing of it goes to `autoconfig.toml`.
- `alias_message.ts`, `quickmark_message.ts`: the Aliases and Quickmarks sections. The aliases layer (`EDIT_LAYERS.aliases`, alias name to command id) goes through the same build as the engines: `build_layered` takes both layers, cuts each into pieces that stand alone (an alias is one piece, of kind `aliases`), and leaves out a piece the files now break, with a warning. A save refuses on a fresh drop, as for an engine. The quickmark messages edit the `M` store (`quickmark_store.ts`) of a normal window and list the `quickmarks.toml` entries beside it; the store is not a layer, so a reload, an import and a host start never touch it.
- `theme_message.ts`: the importer's messages (`list_imported_themes`, `change_imported_themes`). A save parses the scheme text itself with `parse_base16` and checks the name, so a page cannot store a theme the parser refuses. A save over an existing name answers `needs_replace` until the request says `replace`. A save and a remove go through `set_theme_file` in `config_setting_writes.ts`, which changes `themes/<name>.toml` in the browser copy and through the host as `set_in_settings_file` changes settings.toml. A remove also takes `theme` out of settings.toml and drops a saved or temp `theme` edit when they name the theme, and a `settings.d` file that names it refuses the remove. A theme file that shadows a built-in theme only loses the file: those two steps are skipped. The list is the theme files of the browser copy. `imports_moved_to_files` moves the imports an older version kept in `desertfox_imported_themes` into theme files at start (`reload_config_at_start`), once.
- `css_limits.ts`: the CSS rule of user CSS. `css_limit_breaches` finds `@import`, `@font-face`, `image-set(`, `src(` and a `url()` that is neither a `data:` address nor a `#` fragment reference in `style.css` and `style.d/*.css`, with the line. `read_import_source` and `build_files_config` (reload, edit and remove, not the layer rebuild) refuse on the first one.

### Config build files for the config

Behavior of the `src/shared/config_build` files, moved here from `src/shared/config_build/README.md`.

Builds the merged config from the user's config files. It takes raw file text and the command list, and uses no Node API. The extension and `tools/build-config` both run it. The tool reads the files from disk. `tools/build-config/README.md` lists what stays there.

- `build_config.ts`: `build_config(files, commands, warnings, options)`, the whole pipeline. `commands_of_registry` cuts the command list from the live registry, where the tool reads `dist/commands.json`. The `dir_label` option prefixes every path in a problem message and in the config's `origins`, so a tool run keeps absolute paths and the extension shows relative ones.
- `source_files.ts`: parses the file map into data layers, snippet files and CSS files, and reports unknown names. `files` maps a path relative to the config directory (`keymap.d/10-x.toml`) to its text. A directory entry has a trailing slash in its key and empty text, and is unknown, or a problem when a file name was expected. A known directory name that holds a file is a problem too. `autoconfig.toml` is skipped: the native host writes it and nothing reads it back.
- `theme_dir.ts`: parses theme files, one theme per `<name>.toml`.
- `merge.ts`: merges the layers of each data kind and records where each value came from.
- `snippet.ts`: turns a snippet file header into a registry entry.
- `check.ts`: builds the registry with the snippets and checks bindings, args, engines and settings.
- `resolve_binding.ts`: turns one binding as a config file writes it into invocations. The keymap, the site rows and the compile share it.
- `schemas.ts`: the editor schemas for the data files. Only the tool and tests call it.
- `errors.ts`: `ConfigErrors`, which collects every problem of one run.

`smol-toml` parses the TOML. A test fails when a file here imports a `node:` module. In the extension, only the background runs the build, because it pulls in `smol-toml` and `themes.ts`. No other folder imports it at runtime, and a test fails when one does. A page takes `KEYMAP_MODES` from `src/shared/keymap.ts` and `DATA_KINDS` from `src/shared/config_kinds.ts`.

### Engine files for the config

Behavior of the `src/shared/engines` files, moved here from `src/shared/engines/README.md`.

Search engines as named URL templates. Pure code with no browser calls. It sits outside the shared barrel, so the content script never bundles it.

- `slots.ts`: the slot table. An input slot is `query`. A page slot (`url`, `host`, `title`, `repo`, `subreddit`, `channel`) has a pure `read(page)` and the message shown when the page cannot fill it.
- `fill.ts`: parses and fills a template. `{a|b}` takes the first alternative with a value, `{name:raw}` skips escaping, `%s` reads as `{query}`. Slot values take `encodeURIComponent` whatever the position, and a space in the literal text becomes `%20`.
- `resolve.ts`: turns the TOML tree into a flat map keyed by the dotted name. `merge.ts` in `config_build` runs it for the extension and the tool, and the background engine files import it too. The rules (inheritance, params, generated children, `only`, reserved names) are in `docs/design/config.md`, "Engines".
- `reverse.ts`: the inverse of `fill.ts`. `read_query` reads the query out of an engine's results page address by its template or its `reverse` regex, and `engine_of_page` picks the engine that owns a page (longest fixed template start wins). The `search_query` context source calls it.
- `index.ts`: the exports.

The extension stores the resolved map and fills the page slots and the query at run time (`src/shared/url_build.ts`, `engine_url`). The availability check lives in `src/background/availability.ts`.

### Theme files for the config

Behavior of the `src/shared/theme` files, moved here from `src/shared/theme/README.md`.

Themes as role colors. A theme file maps its colors onto a fixed list of roles, and the extension turns the stored theme into CSS for each surface. Pure code, shared by the extension and `tools/build-config`. See `src/shared/README.md` for how the folder fits in `shared/`.

- `roles.ts`: the public role list. Adding a role is safe, renaming one breaks contributed themes.
- `derive.ts`: the one table of what a missing role becomes.
- `theme_file.ts`: checks one parsed theme file and fills it into a full theme. `just themes` and `tools/build-config` both use it, so they report the same errors.
- `base16.ts`: reads a base16 or base24 scheme and maps its slots onto the roles.
- `contrast.ts`: the fg_dim contrast clamp, shared by the Oasis build and the base16 importer.
- `tokens.ts`: the CSS custom property name of each role.
- `font_family.ts`: checks a font family list typed into a setting and returns canonical CSS text. It is the only guard before the value reaches a style sheet.
- `load.ts`: finds the theme a `theme` name stands for. The background, the command definitions, `config_build` and `tools/build-config` import it. No page or content bundle does, because it holds every theme table.
- `apply.ts`: turns the stored theme into CSS for one surface and keeps it current, with the `desertfox_theme` and `desertfox_user_css` storage keys. It runs in pages and lazy content bundles, never in `content.js`.
