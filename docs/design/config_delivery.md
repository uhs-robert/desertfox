# Config delivery

Area: how config reaches the browser and saved edits.
READMEs: `src/background/README.md`, `host/README.md`.
Source: `src/background`, `host`.

### Delivery

`config.reload` (key `,r`) asks the native host for the raw text of the files (`read_config`), builds the config in the background with `build_config` and swaps it in place. Nothing restarts, so the temp edits, the modes and open hints stay.

- The swap runs in the same queue as `set`, `toggle` and `unset`, so a reload and an edit never publish over each other. It replaces the snippet commands (the old ones leave the registry first), compiles and publishes the keymap, tells open tabs (`tree_updated`) and replaces the config the background runs on. Commands that arrive during the swap wait for it to commit. The toast counts every warning Help shows.
- The built config goes to `storage.local` (`desertfox_files_config`), with its build warnings, so Help still lists them after a restart. The raw file text goes beside it (`desertfox_files_source`) in the same write, so an import can rebuild it. A restart, the help page and the new tab page all read what the last reload or import built.
- An import (a zip or a picked folder) goes through the same swap (`apply_files`) and the same slot. It passes the zip guards, drops one top folder that every path shares, and refuses an empty result. Its config files replace the ones in the slot, the installed snippets stay, and the browser edits stay on top: the temp edits, the consent settings, the key edits and any value an older version saved in the browser that the start has not moved into `settings.toml`. Each imported snippet is stored only when the user accepts its exact code. The settings keys `bridge`, `bridge_share_tabs`, `host_auto_update` and `newtab_ip_info` are each a consent given on this machine, so an import drops them from its settings files. The review lists what the built import reaches (`src/background/import_reach.ts`): the search engine, new tab page, home page, new tab link, quickmark and fixed-address key addresses it adds, and the keys that read the clipboard, press keys or click on a page, change settings or use the native host, with at most 12 rows a list. It only informs. Import is the one consent, and a key that names a consent setting is shown and kept, not stripped. The settings page also exports the config as `desertfox-config.zip` (the config files, with the saved browser edits as `settings.toml`, or as the last file of `settings.d` when the config has settings files of its own, and the key edits in force as the last file of `keymap.d`, so an import elsewhere gives the same keymap) and the snippets as `desertfox-snippets.zip`. It lists the installed snippets, and Remove rebuilds the config without one through the same swap. A key that binds the snippet refuses the removal, in the files or as a key edit. The snippet returns on the next `config.reload` while its file stays in the config folder. A later `config.reload` replaces the whole import.
#### Start read

- The start read (`reload_config_at_start`) reuses the host call every start makes for the version check. It waits for the cached config and runs in the same queue as the swap, then compares the folder's files with the stored source (`desertfox_files_source`). The compare leaves out `autoconfig.toml`, which the host writes from the key edits and the build never reads, and the folder label, which an import or an editor save changes. An unchanged start builds and publishes nothing.
- Each swap to the folder's files (a start, Use the folder, `config.reload`) stores a digest of them (`desertfox_host_start_applied`), and a start that finds the copy equal to the folder stores it too. When the browser copy is empty, or still matches that digest, the start applies the folder with `apply_files`. Otherwise the copy holds browser changes, and the start replaces nothing (`host_start.ts`). A profile with no stored digest counts as changed, so it asks once rather than risk a loss.
- It stores the question (`desertfox_host_start_pending`: the folder, a digest of each side and the files the folder would replace, add or drop) and toasts once. The settings page shows it as a banner with Export config, Use the folder and Keep the browser copy. A choice reads the folder again in the change queue and runs only when the browser copy still matches what the page showed. Keep also needs the folder the page showed. Otherwise it refuses and stores the fresh question.
- Use the folder takes a folder changed since, because it drops only the browser copy: the user who unpacks the export into the folder clicks once. The export carries the saved edits in its settings file, so the folder then holds them too. Use the folder swaps through `apply_files`, so the edit layers stay on top, and a folder that does not build keeps the browser copy and the question. Keep the browser copy stores the folder digest (`desertfox_host_start_kept`), so the start asks again only when the folder changes.
- Any swap (an import, an editor save, a reload) drops the question, because its list no longer fits. The first answer wins, and a second page is told it is settled. A host start that cannot read the host drops it too, because no choice can run. Writing the whole browser copy into the folder stays manual: export the zip and unpack it. One setting at a time does reach the folder: a scalar or list setting changed by `set`, `toggle`, `unset`, the popup or the settings page is written into `settings.toml` (see Settings in the file). The host read and a waiting `settings.toml` write happen outside the queue, so a slow host never blocks a `:set`.
- A start reply is dropped when a config swap (reload or import) commits during the read, because the swap is newer. No permission, no host, a host error and a missing or empty config folder keep the stored config and only warn on the console. Empty means no file but `autoconfig.toml`, because the host creates the folder when it writes that file. The installer never creates the folder.
- A file that fails the build of a start that adopts keeps the stored config too, and a toast names the problem on every start until the file is fixed. `,r` stays the explicit replace: it applies the folder over any browser copy and refuses a missing or empty folder.
#### Failed reloads and managed storage

- A reload that cannot finish keeps the current config whole: config, snippets, keymap and stored files. Its toast names the cause and the fix: no permission or no host (run `:native.install`), a host error, a missing config folder, or the problems in the files (the first three, and a count).
- The load checks every setting in the files against `SETTING_SPECS`. It drops a setting with an unknown name or a value the check refuses, warns, and lets the layer below apply. `build-config` refuses both, but a stored slot from an older version can still hold one.
- Managed storage is removed. Firefox read its file once per extension load (see [firefox-behavior.md](../firefox-behavior.md), "Managed storage"), which is why `config.reload` uses the host. A fresh install starts on the defaults until the first start or `,r` that reaches the host.
#### Debug commands and the warnings list

- `debug.perf` (`:perf`, no key) copies the recent timings to the clipboard for a slowness report and toasts the slowest p95. It covers bundle loads (`load_log.ts`), command round trips (background commands only, timed in `router.ts` from the start of a step to its answer; content commands are left out because hint mode, find and caret wait on the user and the registry cannot tell which ones do) and hint build time (recorded by the `hints` bundle).
- There is no per-key timing, because `content.js` has little headroom and every frame pays for it. The timings are a ring of 300 in `storage.session`, summarized as count, median, p95 and max per name.
- `debug.restart` (no key) restarts the whole extension, for debugging. Firefox loads the content script into open tabs by itself after `runtime.reload`, so the reinjection step stays only as a fallback (see [firefox-behavior.md](../firefox-behavior.md), "Phase 1 measurements").
- The help page's Home shows the warnings. The settings page at `home.html#/settings` shows the config source and the steps to apply an edit, and has an input for each setting that `:set` takes. An Export and import section exports the two zips and `desertfox-sessions.json`, imports a zip, a folder or a sessions file, and lists the installed snippets. The sessions file holds the stored shape of the tab sessions (see Tab sessions). The add-on Preferences button opens the settings page, so no separate options page exists.
#### Saved edits

- `set`, `toggle` and `unset` write a scalar, list or `[[newtab_links]]` setting into `settings.toml` (see Settings in the file). With `--temp` they change only the temp edits and never touch the file. The four consent settings (`bridge`, `bridge_share_tabs`, `host_auto_update`, `newtab_ip_info`) stay in the browser, one choice per machine. `site_rules` changes one row at a time from the popup and is never set whole from the browser, and a Reset of the whole list drops every hand-written rule, so `unset site_rules` drops only a list saved in the browser. The settings in force come from four layers, and a later layer wins: the defaults, the config files, the saved edits and the temp edits. The saved edits live in `storage.local` (`desertfox_saved_settings`) and last until `unset`. Only the consent settings, and a `default_engine` that only the old engines layer defines (see Settings in the file), still go there. A `set` or `toggle` without `--temp`, the settings page and a `change_setting` message of any other setting never write there: the planner refuses it (`edit_with` in `src/commands/settings.ts`). An `unset` and a Reset still drop a value an older version left there. Each start moves the other saved edits into `settings.toml` (`saved_fold.ts`), so edits saved before the file writes existed reach the file. A saved value won over the file's, so it replaces the file's value, and a saved `site_rules` list adds only the popup's off rows and kept-keys rows the file lacks. The move runs only after the start read settled: the host answered, the folder exists and has files, and the copy took it, already matched it or differs only by a write still waiting. It then changes the browser copy, and the start's waiting writes send the file to the folder through the same record and base check as a `:set`. Without the host or a folder, while the copies-differ question waits, and for an imported copy, the saved edits stay on top as before, and a later start that settles moves them. A Use the folder answer drops values that sit only in the copy, so the move never runs ahead of it. The smaller layer goes in the same storage write as the files, so a stop at any point moves nothing twice and loses nothing. A start that moves something says so in a toast and in the Home warnings. A setting a `settings.d` file sets stays saved, as that file wins over `settings.toml`, and one Home warning names each such setting and its file. A value the files build refuses stays saved too, with a Home warning that gives the problem, and every start tries it again. The notes live in `storage.session` (`desertfox_saved_fold_notes`), and each start writes them anew. The temp edits live in `storage.session` (`desertfox_temp_settings`), and a browser restart clears them. `config.reload` keeps them.
- `debug.restart` clears them, because Firefox clears `storage.session` when an extension reloads. Both layers are global, private windows included. `set name value` saves a value, `set name` shows it and `toggle name` flips a true or false setting. With `--temp` (`-t`) the change goes to the temp layer. A saved change drops the temp edit of the same name, because that temp edit would keep winning and hide the save.
- `unset name` removes the key from `settings.toml` and drops both edits of the setting, so the default applies. It never writes the default value. A key only the browser edits set loses those edits and the file stays as it is. A key a `settings.d` file sets stays there: its browser edits go, and with none the unset is refused and names that file. `unset all` drops every browser edit and leaves `settings.toml` as it is. `unset --temp` drops only the temp edits. The settings page's Reset sends the same unset. A browser edit wins over the config file, as in qutebrowser, where `autoconfig.yml` holds the browser edits. `name` is a `strict` param of the known setting names, and `value` carries `value_of: "name"`, so `check_args` checks the value with that setting's entry in `SETTING_SPECS`.
- The two prefix settings are refused, because a live change could collide with other keys. The help page tags every value that differs from the default with its top layer: `settings.toml`, `saved` or `temp`. The `saved` tag, and the Saved here marker and Reset of the Your site rules box, show a consent setting or a value that stays saved after the start move.
- Settings in the file: `set`, `toggle` and `unset` without `--temp`, the popup's theme dropdown and its Disable and Enable on this site, and every settings page row of a scalar, list or link list setting (`FILE_WRITTEN_SETTINGS`) write `settings.toml`. The pages send `change_setting` with layer `file`, for a set and for a Reset. The background edits the browser copy of `settings.toml` (`set_top_level_key` and `remove_top_level_key`: only the key's lines change, and comments, blank lines, order, inline comments and line endings stay; a list or an inline table is written on one line, and an array written over several lines becomes one line, unless a comment sits inside it; a removal drops the whole value; a key that is missing goes after the last top-level line, above the comments that lead into the first table; a key inside a table, a multi-line string, an inline table and any edit a parse shows to touch another key are refused). A list of tables (`set_table_rows` in `toml_table_edit.ts`) keeps each `[[name]]` block whose row stays, byte for byte with its comments, drops the block of each row that leaves (from its header to its last line that is not blank or a comment, child tables included, and a blank line that led into it when a blank line or the end follows), and writes each new row as a block after the block of the row before it. The comment lines right over a header belong to that row only when the row before them in the same list comes next above, across blank lines at most. Those go with the row, and a row that moves takes its own lines along. A comment over the first row, or after a root key or another table, belongs to the list or the file and stays. A row added after the last row, where a blank line or the end of the file came next, and removed again leaves the file as it was. Between the rows the old and new lists share at the start and the end, the rows are paired one by one up to 250,000 pairs, and past that the rows in between are written anew. A list written as one inline array stays one. An empty list is written `name = []`, so a cleared list reads as cleared, and an unset or a Reset removes the key. The parse after the edit must hold exactly the new rows and every other key as before. A default engine that needs the current page (`site`, or a URL with a page slot) is refused by name, and the Settings page does not offer one. Any other value the files build refuses is refused, and nothing changes. The reply and the toast wait for the host write, so they say where the change went. It swaps the copy in through `apply_files` and drops the saved and temp edit of the setting, so no browser edit hides the file. One `storage.local.set` holds the files, their build, the saved edits and the record of a lagging folder, and a failure puts them all back. After that queue turn it sends the text to the host's `write_config_file` (kind `settings`) with the digest of the text the edit started from. A host from before that verb gets the text through its older `write_settings`. The host call runs outside the change queue, so a slow or hung host blocks no other change. The queue starts the write and applies its reply, one write at a time. A pick made while a write is out is written after it, from the text the first write left. `,r` holds the queue for its own host read, so it waits on a write that is out and writes in its turn. The host writes only while the file still has that digest, so a hand edit since is never overwritten: the write is refused and the folder is read again. When the hand edit left every key the browser changed at its base value, and the copy holds no other browser change, the copy takes the folder's files with those keys set again on its new `settings.toml`, and the write runs again from that text, so the hand edit, any other file saved beside it and the pick all stay (the record needs no list of its edits: a parse of the base and of the copy gives them back). The folder's files must pass the checks of a folder read first (CSS that loads only data: addresses, a folder with config files). After three such rounds in one write loop, or otherwise, the copies-differ question takes over. When the user kept the browser copy over that folder before, no question follows, and the reply says the change stays in the browser copy. When the folder cannot be read again, the record stays and the next start tries again. A pick never drops a pending question: after a write it reads the folder again and asks again or settles the question. The host is asked only when the browser copy came from the folder: a folder read is on record, and the copy is no import. The stored files carry `imported` apart from their label, so an import stays one through every browser edit until a folder read replaces it. Otherwise only the copy changes, and the reply says so. A setting a `settings.d` file sets, which wins over `settings.toml`, is refused and the reply names that file. `site_rules` is the exception: its files add up (see Site table), so a write to `settings.toml` is never hidden. A `default_engine` that names an engine of the Engines page's file is a normal file value. An engine that only the old engines layer still holds (one the first start could not move, see the Search engines section) is in no file, so a file that names it does not build: a `default_engine` that names one goes to the saved edits, and the reply says it is saved in the browser because the search engine is not in your files. The start moves that saved edit into `settings.toml` once the engine moves. A name that matches nothing is refused by name. Without the host, without the permission or with a host that knows neither write verb, the browser copy changes and the reply says the file updates when the native host connects, or once an old host is updated: `desertfox_settings_file_unsynced` keeps the base text, the next start and `,r` write the file first, and a start whose folder differs only by that edit asks nothing. The record maps each path the folder lags (`settings.toml`, and `themes/<name>.toml` and `search_engines.d/zz-desertfox.toml`, which the host writes too) to its base, and each path has its own write loop state: a refusal, a drop or a write out on one file never decides another file's outcome. A host that knows only `write_settings` still gets every `settings.toml` replacement. A theme write and a delete wait for an update there. A record stored as `{ base }` reads as `settings.toml`'s base until the next store writes the map. A start writes the waiting paths one after another. A file the copy no longer has is deleted through the same base check. A refused write of a whole file such as a theme is not put onto the folder's text, so the question takes over. A refusal whose folder read began before another file's write settled is sent again, so the merge never takes that file's old text. A refused `settings.toml` is put onto the folder's text only while each other waiting file in the folder still holds its base or the copy's text. An editor save or a snippet change (a removal, or an import of snippets alone) that leaves `settings.toml` as it was keeps the record. A reload, an import of config files or a save of `settings.toml` drops it, and the reply of a pick it drops names that swap and says whether the file got the pick before it. A refused write leaves a record that a later pick started after such a swap, even one with the same base, and that pick's write runs from its own base. An old file the host cannot read back after its rename goes back in place, and the reply says the file was not written and is tried again at the next start, not that it changed on disk. After a write the applied digest follows, unless the copy held other browser changes, so the next start does not ask.
- Key edits from the settings page form one more browser layer, in `storage.local` (`desertfox_keymap_edits`): per mode, a key sequence and the command text as keymap.toml writes it, with `""` to unbind.
- The Keys section of the settings page lists every binding by mode (generated bindings are not listed), checks a binding through `check_binding` and saves through `change_keymap`. A row keeps its draft across a refresh, and the page reloads the list on a write of the config status.
- The Search engines section of the settings page adds an engine (name, address, keyword) to its own file, `search_engines.d/zz-desertfox.toml`, and its key letter to a second file of its own, `keymap.d/zz-desertfox.toml`, as `[search_keys]` only, with a one-click starter set from `examples/engines.toml` that skips the names the files or the layer already hold. It never edits `search_engines.toml` or another `search_engines.d` file: an engine one of those defines stays the user's, and a save or a remove of it is refused and names that file. Each of the page's files starts with a comment line that marks it as the page's. A `zz-desertfox.toml` without that line, for example one the user wrote before this version, counts as a hand file: the page lists none of its engines or letters and refuses every change that would write it, naming the file. It never edits `keymap.toml` or another `keymap.d` file, and the key editor's own browser layer stays apart from the keys file. A letter a hand file binds to another engine moves to the page's engine when the keys file loads after that file, and the reply says which engine it searched before. A `keymap.d` file that loads after the keys file (a name that sorts later) would still win, so a save of that letter is refused and names the file. A letter the page's keys file gives another page engine moves to the saved one, since a letter searches one engine. A remove takes the engine's letter out of the keys file in the same change, and the keys file goes when its last letter goes. The page writes the whole file (`stringify` of one table per engine, `engine_file.ts`) and deletes it when the last engine goes. A save merges the four form fields into the engine's table, so the label, hosts, fallback, params and children of a starter engine stay. It changes the browser copy and goes through the host's `write_config_file` (kind `engines` and kind `search_keys`, fixed paths) the same way a `:set` writes `settings.toml` (see Settings in the file): one queue turn, the same record of a lagging folder, the same base check, so a file of that name made by hand since the last read is never overwritten and the copies-differ question takes over. The reply says where the change went. Before anything is stored, the files and the browser layer are built with the change, and a save that the build refuses, or that makes it drop a layer piece it did not drop before, changes nothing. The engine file goes to the host before the keys file, so a failure between the two leaves an engine without its letter in the folder, and the reply says the keys file waits or was not written. A host from before the `engines` or `search_keys` kind leaves that file in the browser copy, the record waits, and the reply says the file updates once the host is updated. A `settings.toml` whose `default_engine` names an engine of the page's file waits until that file reaches the folder, and a `settings.toml` that names it no more, or a write of it still out that names it, goes before the file that drops it. The keys file follows the same order: after the page's file when it binds a letter to an engine the folder's page file lacks, and before the page's file when the folder's keys file names an engine that file drops. When both hold at once (a new default engine or letter and the removal of the old engine), the page's file is first written as a bridge that holds the folder's engines and the copy's, then `settings.toml` or the keys file, then the page's file as the copy has it. That order only picks the next write. Before a write of `settings.toml` or either of the page's files, the host's folder is read and built as it would be after the write, with the writes still out on top. A write that adds a build problem (an engine or child a `default_engine` names in any settings file, a keyword held twice, a letter that names a missing engine) is not sent. It stays in the record, the reply says the file waits and why, and it is tried again after a write of the other file that is out lands, and at the next start. When no order builds, the reply says how to clear it: change the folder's files by hand, or `,r` to take the folder's files. A folder that cannot be read for the check holds the write too, and a missing host makes it wait as before. Engines and key letters that older versions kept in a browser layer (`desertfox_engine_edits`) move into the page's two files at the first start, and a saved `default_engine` edit moves into `settings.toml`. The layer loads after every engine and `keymap.d` file, and the page's files load after the usual numbered ones, so what ran before runs after. A layer table over a page engine of the same name is laid on it per engine path, so a child only the page's file holds stays, and an empty child table replaces the old child. The move changes the browser copy, and the start's waiting writes send the files to the folder through the same record, order and gate as a save. Without the host the files wait in the copy and the record. What is left of the layer goes in the same storage write as the files, so a stop at any point moves nothing twice and loses nothing. A piece the files build refuses, or one a hand file at the page's path blocks, stays in the layer, and every start tries it again and says why in a toast. The toast also names a later hand file that now wins over a moved engine path, and a later `keymap.d` file that rebinds a moved letter, which is dropped. A saved `default_engine` stays a saved edit while a `settings.d` file sets it or the build refuses it. A piece left in the layer stays listed and works as before. A save of one moves it into the files, and a remove drops it from the layer, in the same storage write as the files. The running config is `build_config` over the stored files plus the layer written as `search_engines.d` and `keymap.d` files, so the keyword, fallback and key checks are the ones the files get. After a file edit, a layer engine that now clashes is left out with a warning. The export carries the page's two files as they are, what is left of the layer as one more `search_engines.d` file that sorts after every engine file the config has (`zz-saved-edits.toml`, or a longer name after a file that sorts later), and the layer's key letters in `keymap.d` as `[search_keys]`.
- The Aliases section adds a command alias as a browser layer on top of `command_aliases.toml`. It goes through the same build as the engines (`build_config` over the stored files plus the layer as `command_aliases.d`), so a name with whitespace, a command name or an unknown target is refused at Save, and an alias that a file edit breaks (a removed snippet it targeted) is left out with a warning. The Quickmarks section lists the `M` store of a normal window over the `quickmarks.toml` table and edits that store, so `M`, the form and `go` never disagree. The export carries them as `command_aliases.d/zz-saved-edits.toml` and `quickmarks.d/zz-saved-edits.toml`. Neither goes into `autoconfig.toml`.
- It wins over keymap.toml and the defaults, as saved settings win over settings.toml, and it survives `config.reload`, an import and a files editor save. A key edit runs in the same queue as `set` and rolls back the same way when the publish fails. The export carries them too, and so does `autoconfig.toml` (next line).
- Each committed change to the key edits is mirrored to `autoconfig.toml` in the config folder through the host (`write_autoconfig`). Under the host's header the file holds one comment line, then every stored key edit in the keymap.d grammar (`[normal]`, `[browser]` and the other mode tables, `"" =` for an unbind), whether or not the edit is in force. No setting goes there: `settings.toml` holds the settings, and the consent settings stay on this machine. Older versions mirrored the saved settings there too. So the first start whose host finds the folder rewrites the file once, and a committed change to the saved settings rewrites it as well. A start whose saved layer is empty only sets the mark, as no setting sits in the file then, and the write would create the file for a user who never had one. The mark of that rewrite (`desertfox_autoconfig_key_edits_only`) waits for a write the host confirmed, so a failed write is tried again at the next start. A start without a folder writes nothing, as the host would create the folder for this file alone. Every write reads the key edits inside the change-queue turn, so write order is commit order. A rollback, a reload and an import write nothing. With no key edits the file holds the header and the comment line. The file is write-only: the build skips it and DesertFox never reads it back. A failed write never blocks or undoes the edit. Without the permission it is skipped quietly, and any other failure warns once in the background console.

The background compiles the keymap into a prefix tree and writes it to `storage.local` for the content scripts.
