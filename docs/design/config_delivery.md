# Config delivery

Area: how config reaches the browser and saved edits.
READMEs: `src/background/README.md`, `host/README.md`, `src/shared/README.md`.
Source: `src/background`, `host`, `src/shared`.

### Delivery

`config.reload` (key `,r`) asks the native host for the raw text of the files (`read_config`), builds the config in the background with `build_config` and swaps it in place. Nothing restarts, so the temp edits, the modes and open hints stay.

- The swap runs in the same queue as `set`, `toggle` and `unset`, so a reload and an edit never publish over each other. It replaces the snippet commands (the old ones leave the registry first), compiles and publishes the keymap, tells open tabs (`tree_updated`) and replaces the config the background runs on. Commands that arrive during the swap wait for it to commit. The toast counts every warning Help shows.
- The built config goes to `storage.local` (`desertfox_files_config`), with its build warnings, so Help still lists them after a restart. The raw file text goes beside it (`desertfox_files_source`) in the same write, so an import can rebuild it. A restart, the help page and the new tab page all read what the last reload or import built. `pick_config` picks the config to run: the one the files built, or the defaults when no usable build is stored (no build, a value that is not an object, or a `format_version` that does not match). `load_effective_config` (`src/shared/config/config_load.ts`) is for pages that read the config themselves: it returns that config with the saved edits and the temp edits on top, and prefers the layered build (`LAYERED_CONFIG_STORAGE_KEY`) when the engines layer holds something.
- An import (a zip or a picked folder) goes through the same swap (`apply_files`) and the same slot. It passes the zip guards, drops one top folder that every path shares, and refuses an empty result. Its config files replace the ones in the slot, the installed snippets stay, and the browser edits stay on top: the temp edits, the consent settings, the key edits and any value an older version saved in the browser that the start has not moved into `settings.toml`. Each imported snippet is stored only when the user accepts its exact code. The settings keys `bridge`, `bridge_share_tabs`, `host_auto_update` and `newtab_ip_info` are each a consent given on this machine, so an import drops them from its settings files. The review lists what the built import reaches (`src/background/import_reach.ts`): the search engine, new tab page, home page, new tab link, quickmark and fixed-address key addresses it adds, and the keys that read the clipboard, press keys or click on a page, change settings or use the native host, with at most 12 rows a list. It only informs. Import is the one consent, and a key that names a consent setting is shown and kept, not stripped. The settings page also exports the config as `desertfox-config.zip` (the config files, with the saved browser edits as `settings.toml`, or as the last file of `settings.d` when the config has settings files of its own, and the key edits in force as the last file of `keymap.d`, so an import elsewhere gives the same keymap) and the snippets as `desertfox-snippets.zip`. It lists the installed snippets, and Remove rebuilds the config without one through the same swap. A key that binds the snippet refuses the removal, in the files or as a key edit. The snippet returns on the next `config.reload` while its file stays in the config folder. With the native host and a config folder that holds config files, an import of config files also writes each config file it holds at another text than the folder's: every config file but a snippet has a host kind (see Native host), and a file whose name the host has no kind for (a theme named outside the theme pattern, a `.d` name over 233 bytes) stays in the browser only, and the review and the answer name it. The swap stores their record in its one storage write (see Settings in the file), and the writes run after it, outside the queue, so a later `config.reload` keeps them, and a stop before they land leaves the record for the next start. The files go to the host in one `write_config_files` batch, which lands all or none, except for a file the rollback cannot put back and a host crash midway (see [host.md](host.md)), and the gate builds the folder as it would be after the whole batch (see `write_files` in Config). The review names the files it writes, and the answer says what became of each. A file the import lacks stays in the folder as it is, and a snippet never goes there. The imported `settings.toml` takes the consent keys the folder's `settings.toml` sets, in the copy and in the folder, so a consent given on this machine stays. The import's own consent keys are still dropped. When the folder's `settings.toml` does not parse, or the imported text cannot take one of its consent keys, that file is not written, and the review and the answer say so. A folder `settings.d` file that sets a consent key, or does not parse, is not written either, and the review and the answer say which. A file with a write still out when the import reads the folder goes in the record even at the folder's text, so the import's text lands after that write. A refused write goes to the copies-differ question, and the import stays. Without the host, its permission or such a folder, the import stays in the browser, and the answer says the config folder was not updated. A host from before a file's kind answers outdated, and every file of the batch waits in the record until the host is updated. When every file the import sent landed, no file stayed out for consent or for its name, and every snippet of the copy is in the folder at the same text, the copy takes the folder's label and stops being an import (see Settings in the file).
#### Start read

- The start read (`reload_config_at_start`) reuses the host call every start makes for the version check. It waits for the cached config and runs in the same queue as the swap, then compares the folder's files with the stored source (`desertfox_files_source`). The compare leaves out `autoconfig.toml`, which the host writes from the key edits and the build never reads, and the folder label, which an import or an editor save changes. An unchanged start builds and publishes nothing.
- Each swap to the folder's files (a start, Use the folder, `config.reload`) stores a digest of them (`desertfox_host_start_applied`), and a start that finds the copy equal to the folder stores it too. When the browser copy is empty, or still matches that digest, the start applies the folder with `apply_files`. Otherwise the copy holds browser changes, and the start replaces nothing (`host_start.ts`). A profile with no stored digest counts as changed, so it asks once rather than risk a loss.
- It stores the question (`desertfox_host_start_pending`: the folder, a digest of each side and the files the folder would replace, add or drop) and toasts once. The settings page shows it as a banner with Export config, Use the folder and Keep the browser copy. A choice reads the folder again in the change queue and runs only when the browser copy still matches what the page showed. Keep also needs the folder the page showed. Otherwise it refuses and stores the fresh question.
- Use the folder takes a folder changed since, because it drops only the browser copy: the user who unpacks the export into the folder clicks once. The export carries the saved edits in its settings file, so the folder then holds them too. Use the folder swaps through `apply_files`, so the edit layers stay on top, and a folder that does not build keeps the browser copy and the question. Keep the browser copy stores the folder digest (`desertfox_host_start_kept`), so the start asks again only when the folder changes.
- Any swap (an import, an editor save, a reload) drops the question, because its list no longer fits. The first answer wins, and a second page is told it is settled. A host start that cannot read the host drops it too, because no choice can run. Writing the whole browser copy into the folder stays manual: export the zip and unpack it. An import writes its config files, never its snippets (see the import above). One setting at a time does reach the folder: a scalar or list setting changed by `set`, `toggle`, `unset`, the popup or the settings page is written into `settings.toml` (see Settings in the file). The start's host read and its waiting writes happen outside the queue, so a slow host never blocks a `:set`. `,r` holds the queue for its own host read and writes the waiting files inside it, settling any write still out itself.
- A start reply is dropped when a config swap (reload or import) commits during the read, because the swap is newer. No permission, no host, a host error and a missing or empty config folder keep the stored config and only warn on the console. Empty means no file but `autoconfig.toml`, because the host creates the folder when it writes that file. The installer never creates the folder.
- A file that fails the build of a start that adopts keeps the stored config too, and a toast names the problem on every start until the file is fixed. `,r` stays the explicit replace: it applies the folder over any browser copy and refuses a missing or empty folder.
#### Failed reloads and managed storage

- A reload that cannot finish keeps the current config whole: config, snippets, keymap and stored files. Its toast names the cause and the fix: no permission or no host (run `:native.install`), a host error, a missing config folder, or the problems in the files (the first three, and a count).
- The load checks every setting in the files against `SETTING_SPECS`. It drops a setting with an unknown name or a value the check refuses, warns, and lets the layer below apply. `build-config` refuses both, but a stored slot from an older version can still hold one.
- Managed storage is removed. Firefox read its file once per extension load (see [firefox-behavior.md](../firefox-behavior.md), "Managed storage"), which is why `config.reload` uses the host. A fresh install starts on the defaults until the first start or `,r` that reaches the host.
#### Debug commands and the warnings list

- `debug.perf` (`:perf`, no key) copies the recent timings to the clipboard for a slowness report and toasts the slowest p95. It covers bundle loads (`load_log.ts`), command round trips (background commands only, timed in `router.ts` from the start of a step to its answer; content commands are left out because hint mode, find and caret wait on the user and the registry cannot tell which ones do) and hint build time (recorded by the `hints` bundle).
- There is no per-key timing, because `content.js` has little headroom and every frame pays for it. The timings are a ring of 300 in `storage.session`, summarized as count, median, p95 and max per name.
- `debug.restart` (no key) restarts the whole extension, for debugging. Firefox loads the content script into open tabs by itself after `runtime.reload`, so the reinjection step stays only as a fallback (see [firefox-behavior.md](../firefox-behavior.md), "Phase 1 measurements").
- The help page's Home shows the warnings. The settings page at `home.html#/settings` shows the config source and the steps to apply an edit, and has an input for each setting that `:set` takes. An Export and import section exports the two zips and `desertfox-sessions.json`, imports a zip, a folder or a sessions file, and lists the installed snippets. The sessions file holds the stored shape of the tab sessions (see Tab sessions). The add-on Preferences button opens the settings page, so no separate options page exists.
#### Saved edits

- `set`, `toggle` and `unset` write a scalar, list or `[[newtab_links]]` setting into `settings.toml` (see Settings in the file). With `--temp` they change only the temp edits and never touch the file. The four consent settings (`bridge`, `bridge_share_tabs`, `host_auto_update`, `newtab_ip_info`) stay in the browser, one choice per machine. `site_rules` changes one row at a time from the popup and is never set whole from the browser, and a Reset of the whole list drops every hand-written rule, so `unset site_rules` drops only a list saved in the browser. The settings in force come from four layers, and a later layer wins: the defaults, the config files, the saved edits and the temp edits. The saved edits live in `storage.local` (`desertfox_saved_settings`) and last until `unset`. Only the consent settings, and a `default_engine` that only the old engines layer defines (see Settings in the file), still go there. A `set` or `toggle` without `--temp`, the settings page and a `change_setting` message of any other setting never write there: the planner refuses it (`edit_with` in `src/commands/settings.ts`). An `unset` and a Reset still drop a value an older version left there. Each start moves the other saved edits into `settings.toml` (`saved_fold.ts`), so edits saved before the file writes existed reach the file. A saved value won over the file's, so it replaces the file's value, and a saved `site_rules` list adds only the popup's off rows and kept-keys rows the file lacks. The move runs only after the start read settled: the host answered, the folder exists and has files, and the copy took it, already matched it or differs only by a write still waiting. It then changes the browser copy, and the start's waiting writes send the file to the folder through the same record and base check as a `:set`. Without the host or a folder, while the copies-differ question waits, and for an imported copy, the saved edits stay on top as before, and a later start that settles moves them. A Use the folder answer drops values that sit only in the copy, so the move never runs ahead of it. The smaller layer goes in the same storage write as the files, so a stop at any point moves nothing twice and loses nothing. A start that moves something says so in a toast and in the Home warnings. A setting a `settings.d` file sets stays saved, as that file wins over `settings.toml`, and one Home warning names each such setting and its file. A value the files build refuses stays saved too, with a Home warning that gives the problem, and every start tries it again. The notes live in `storage.session` (`desertfox_saved_fold_notes`), and each start writes them anew. The temp edits live in `storage.session` (`desertfox_temp_settings`), and a browser restart clears them. `config.reload` keeps them.
- `debug.restart` clears them, because Firefox clears `storage.session` when an extension reloads. Both layers are global, private windows included. `set name value` saves a value, `set name` shows it and `toggle name` flips a true or false setting. With `--temp` (`-t`) the change goes to the temp layer. A saved change drops the temp edit of the same name, because that temp edit would keep winning and hide the save.
- `unset name` removes the key from `settings.toml` and drops both edits of the setting, so the default applies. It never writes the default value. A key only the browser edits set loses those edits and the file stays as it is. A key a `settings.d` file sets stays there: its browser edits go, and with none the unset is refused and names that file. `unset all` drops every browser edit and leaves `settings.toml` as it is. `unset --temp` drops only the temp edits. The settings page's Reset sends the same unset. A browser edit wins over the config file, as in qutebrowser, where `autoconfig.yml` holds the browser edits. `name` is a `strict` param of the known setting names, and `value` carries `value_of: "name"`, so `check_args` checks the value with that setting's entry in `SETTING_SPECS`.
- The two prefix settings are refused, because a live change could collide with other keys. The help page tags every value that differs from the default with its top layer: `settings.toml`, `saved` or `temp`. The `saved` tag, and the Saved here marker and Reset of the Your site rules box, show a consent setting or a value that stays saved after the start move.
- Settings in the file: `set`, `toggle` and `unset` without `--temp`, the popup's theme dropdown and its Disable and Enable on this site, and every settings page row of a scalar, list or link list setting (`FILE_WRITTEN_SETTINGS`) write `settings.toml`. The pages send `change_setting` with layer `file`, for a set and for a Reset. The background edits the browser copy of `settings.toml` (`set_top_level_key` and `remove_top_level_key`: only the key's lines change, and comments, blank lines, order, inline comments and line endings stay; a list or an inline table is written on one line, and an array written over several lines becomes one line, unless a comment sits inside it; a removal drops the whole value; a key that is missing goes after the last top-level line, above the comments that lead into the first table; a key inside a table, a multi-line string, an inline table and any edit a parse shows to touch another key are refused). A list of tables (`set_table_rows` in `toml_table_edit.ts`) keeps each `[[name]]` block whose row stays, byte for byte with its comments, drops the block of each row that leaves (from its header to its last line that is not blank or a comment, child tables included, and a blank line that led into it when a blank line or the end follows), and writes each new row as a block after the block of the row before it. The comment lines right over a header belong to that row only when the row before them in the same list comes next above, across blank lines at most. Those go with the row, and a row that moves takes its own lines along. A comment over the first row, or after a root key or another table, belongs to the list or the file and stays. A row added after the last row, where a blank line or the end of the file came next, and removed again leaves the file as it was. Between the rows the old and new lists share at the start and the end, the rows are paired one by one up to 250,000 pairs, and past that the rows in between are written anew. A list written as one inline array stays one. An empty list is written `name = []`, so a cleared list reads as cleared, and an unset or a Reset removes the key. The parse after the edit must hold exactly the new rows and every other key as before. A default engine that needs the current page (`site`, or a URL with a page slot) is refused by name, and the Settings page does not offer one. Any other value the files build refuses is refused, and nothing changes. The reply and the toast wait for the host write, so they say where the change went. It swaps the copy in through `apply_files` and drops the saved and temp edit of the setting, so no browser edit hides the file. One `storage.local.set` holds the files, their build, the saved edits and the record of a lagging folder, and a failure puts them all back. After that queue turn it sends the text to the host's `write_config_files` (kind `settings`, in a batch with any other file the change wrote) with the digest of the text the edit started from. A host from before that verb reads as outdated, and the change waits for `:native.update`. The host call runs outside the change queue, so a slow or hung host blocks no other change. The queue starts the write and applies its reply, one write at a time. A pick made while a write is out is written after it, from the text the first write left. `,r` holds the queue for its own host read, so it waits on a write that is out and writes in its turn. The host writes only while the file still has that digest, so a hand edit since is never overwritten: the write is refused and the folder is read again. When the hand edit left every key the browser changed at its base value, and the copy holds no other browser change, the copy takes the folder's files with those keys set again on its new `settings.toml`, and the write runs again from that text, so the hand edit, any other file saved beside it and the pick all stay (the record needs no list of its edits: a parse of the base and of the copy gives them back). The folder's files must pass the checks of a folder read first (CSS that loads only data: addresses, a folder with config files). After three such rounds in one write loop, or otherwise, the copies-differ question takes over. When the user kept the browser copy over that folder before, no question follows, and the reply says the change stays in the browser copy. When the folder cannot be read again, the record stays and the next start tries again. A pick never drops a pending question: after a write it reads the folder again and asks again or settles the question. The host is asked only when the browser copy came from the folder: a folder read is on record, and the copy is no import. The stored files carry `imported` apart from their label, so an import stays one through every browser edit until a folder read replaces it, or until the import's own writes all land with nothing left that the folder lacks but the files the import did not hold. Then a swap in the change queue gives the copy the folder's label and stores its digest as the one last applied, so the next start adopts the folder without asking, and the folder files the import lacked come back. It runs only while the copy is still the import's files and no write waits. A stop before that swap leaves the flag, and the copy stays an import. Otherwise only the copy changes, and the reply says so. Such a change keeps the record of an import's files that still wait. A change to a file in that record is written with it, and the reply says what the write did. A change to any other file stays in the copy, and the reply says so. A setting a `settings.d` file sets, which wins over `settings.toml`, is refused and the reply names that file. `site_rules` is the exception: its files add up (see Site table), so a write to `settings.toml` is never hidden. A `default_engine` that names an engine of the Engines page's file is a normal file value. An engine that only the old engines layer still holds (one the first start could not move, see the Search engines section) is in no file, so a file that names it does not build: a `default_engine` that names one goes to the saved edits, and the reply says it is saved in the browser because the search engine is not in your files. The start moves that saved edit into `settings.toml` once the engine moves. A name that matches nothing is refused by name. Without the host, without the permission or with a host from before `write_config_files`, the browser copy changes and the reply says the file updates when the native host connects, or once an old host is updated: `desertfox_settings_file_unsynced` keeps the base text, the next start and `,r` write the file first, and a start whose folder differs only by that edit asks nothing. The record maps each path the folder lags (`settings.toml`, and `themes/<name>.toml` and `search_engines.d/zz-desertfox.toml`, which the host writes too) to its base, and each path keeps its own outcome: a drop or a pick of one file never decides another file's. A batch lands all or none, except for a file the rollback cannot put back and a host crash midway (see [host.md](host.md)), so a refusal of one of its files writes none of them. A hand edit to one file settles that file first, by the replay or the question, and the rest of the batch goes again without it. A file the host's rollback could not put back stays in the record, and its next write's base check finds out what the folder holds. A record stored as `{ base }` reads as `settings.toml`'s base until the next store writes the map. A start writes every waiting path in one batch. Those files wait for unrelated reasons, so when the host fails one file it names, or the gate holds one file that breaks the folder on its own, the start or `,r` sends the others once more without it, and that file keeps its own outcome. A file the copy no longer has is deleted through the same base check. A refused write of a whole file such as a theme is not put onto the folder's text, so the question takes over. A refusal whose folder read began before another file's write settled is sent again, so the merge never takes that file's old text. A refused `settings.toml` is put onto the folder's text only while each other waiting file in the folder still holds its base or the copy's text. An editor save or a snippet change (a removal, or an import of snippets alone) that leaves `settings.toml` as it was keeps the record. A reload, an import of config files or a save of `settings.toml` drops it (an import that writes the folder stores the record of its own files in its place), and the reply of a pick it drops names that swap and says whether the file got the pick before it. A refused write leaves a record that a later pick started after such a swap, even one with the same base, and that pick's write runs from its own base. An old file the host cannot read back after its rename goes back in place, and the reply says the file was not written and is tried again at the next start, not that it changed on disk. After a write the applied digest follows, unless the copy held other browser changes, so the next start does not ask.
- Key edits from the settings page form one more browser layer, in `storage.local` (`desertfox_keymap_edits`): per mode, a key sequence and the command text as keymap.toml writes it, with `""` to unbind.
- The Keys section of the settings page lists every binding by mode (generated bindings are not listed), checks a binding through `check_binding` and saves through `change_keymap`. A row keeps its draft across a refresh, and the page reloads the list on a write of the config status.
- The Search engines section of the settings page adds an engine (name, address, keyword) to its own file, `search_engines.d/zz-desertfox.toml`, and its key letter to a second file of its own, `keymap.d/zz-desertfox.toml`, as `[search_keys]` only, with a one-click starter set from `examples/engines.toml` that skips the names the files or the layer already hold. It never edits `search_engines.toml` or another `search_engines.d` file: an engine one of those defines stays the user's, and a save or a remove of it is refused and names that file. Each of the page's files starts with a comment line that marks it as the page's. A `zz-desertfox.toml` without that line, for example one the user wrote before this version, counts as a hand file: the page lists none of its engines or letters and refuses every change that would write it, naming the file. It never edits `keymap.toml` or another `keymap.d` file, and the key editor's own browser layer stays apart from the keys file. A letter a hand file binds to another engine moves to the page's engine when the keys file loads after that file, and the reply says which engine it searched before. A `keymap.d` file that loads after the keys file (a name that sorts later) would still win, so a save of that letter is refused and names the file. A letter the page's keys file gives another page engine moves to the saved one, since a letter searches one engine. A remove takes the engine's letter out of the keys file in the same change, and the keys file goes when its last letter goes. The page writes the whole file (`stringify` of one table per engine, `engine_file.ts`) and deletes it when the last engine goes. A save merges the four form fields into the engine's table, so the label, hosts, fallback, params and children of a starter engine stay. It changes the browser copy and goes through the host's `write_config_files` (kind `engines` and kind `search_keys`, fixed paths, in one batch) the same way a `:set` writes `settings.toml` (see Settings in the file): one queue turn, the same record of a lagging folder, the same base check, so a file of that name made by hand since the last read is never overwritten and the copies-differ question takes over. The reply says where the change went. Before anything is stored, the files and the browser layer are built with the change, and a save that the build refuses, or that makes it drop a layer piece it did not drop before, changes nothing. The engine file and the keys file go to the host in one batch. Once the batch settles, the folder holds both files or neither: a failure puts back the files written before it, unless one was edited since, which the refusal names. A host crash midway can still leave a mix. A `read_config` waits for a batch in flight, so a read never sees half of one. A host without the verb or without one of the kinds leaves every file of the batch pending until it is updated. A host from before the `engines` or `search_keys` kind leaves that file in the browser copy, the record waits, and the reply says the file updates once the host is updated. Before a batch, the host's folder is read and built as it would be after the batch, with the writes still out on top and without them, so a new default engine and the removal of the old one land together. A batch that adds a build problem (an engine or child a `default_engine` names in any settings file, a keyword held twice, a letter that names a missing engine) is not sent. Its files stay in the record, the reply says each waits and why, and it is tried again after a write out lands, and at the next start, which writes every waiting file in one batch. A `:set` or an Engines page change sends its own files. When the gate holds them and no other write is out, the batch takes every other waiting file once and tries again, so a pick that names an engine still waiting in the record (one an old host could not write) lands with it. When the folder does not build even so, the reply says how to clear it: change the folder's files by hand, or `,r` to take the folder's files. A folder that cannot be read for the check holds the write too, and a missing host makes it wait as before. Engines and key letters that older versions kept in a browser layer (`desertfox_engine_edits`) move into the page's two files at the first start, and a saved `default_engine` edit moves into `settings.toml`. The layer loads after every engine and `keymap.d` file, and the page's files load after the usual numbered ones, so what ran before runs after. A layer table over a page engine of the same name is laid on it per engine path, so a child only the page's file holds stays, and an empty child table replaces the old child. The move changes the browser copy, and the start's waiting writes send the files to the folder through the same record, batch and gate as a save. Without the host the files wait in the copy and the record. What is left of the layer goes in the same storage write as the files, so a stop at any point moves nothing twice and loses nothing. A piece the files build refuses, or one a hand file at the page's path blocks, stays in the layer, and every start tries it again and says why in a toast. The toast also names a later hand file that now wins over a moved engine path, and a later `keymap.d` file that rebinds a moved letter, which is dropped. A saved `default_engine` stays a saved edit while a `settings.d` file sets it or the build refuses it. A piece left in the layer stays listed and works as before. A save of one moves it into the files, and a remove drops it from the layer, in the same storage write as the files. The running config is `build_config` over the stored files plus the layer written as `search_engines.d` and `keymap.d` files, so the keyword, fallback and key checks are the ones the files get. After a file edit, a layer engine that now clashes is left out with a warning. The export carries the page's two files as they are, what is left of the layer as one more `search_engines.d` file that sorts after every engine file the config has (`zz-saved-edits.toml`, or a longer name after a file that sorts later), and the layer's key letters in `keymap.d` as `[search_keys]`.
- The Aliases section adds a command alias as a browser layer on top of `command_aliases.toml`. It goes through the same build as the engines (`build_config` over the stored files plus the layer as `command_aliases.d`), so a name with whitespace, a command name or an unknown target is refused at Save, and an alias that a file edit breaks (a removed snippet it targeted) is left out with a warning. The Quickmarks section lists the `M` store of a normal window over the `quickmarks.toml` table and edits that store, so `M`, the form and `go` never disagree. The export carries them as `command_aliases.d/zz-saved-edits.toml` and `quickmarks.d/zz-saved-edits.toml`. Neither goes into `autoconfig.toml`.
- It wins over keymap.toml and the defaults, as saved settings win over settings.toml, and it survives `config.reload`, an import and a files editor save. A key edit runs in the same queue as `set` and rolls back the same way when the publish fails. The export carries them too, and so does `autoconfig.toml` (next line).
- Each committed change to the key edits is mirrored to `autoconfig.toml` in the config folder through the host (`write_autoconfig`). Under the host's header the file holds one comment line, then every stored key edit in the keymap.d grammar (`[normal]`, `[browser]` and the other mode tables, `"" =` for an unbind), whether or not the edit is in force. No setting goes there: `settings.toml` holds the settings, and the consent settings stay on this machine. Older versions mirrored the saved settings there too. So the first start whose host finds the folder rewrites the file once, and a committed change to the saved settings rewrites it as well. A start whose saved layer is empty only sets the mark, as no setting sits in the file then, and the write would create the file for a user who never had one. The mark of that rewrite (`desertfox_autoconfig_key_edits_only`) waits for a write the host confirmed, so a failed write is tried again at the next start. A start without a folder writes nothing, as the host would create the folder for this file alone. Every write reads the key edits inside the change-queue turn, so write order is commit order. A rollback, a reload and an import write nothing. With no key edits the file holds the header and the comment line. The file is write-only: the build skips it and DesertFox never reads it back. A failed write never blocks or undoes the edit. Without the permission it is skipped quietly, and any other failure warns once in the background console.

The background compiles the keymap into a prefix tree and writes it to `storage.local` for the content scripts.

### Background files for config delivery

Behavior of the `src/background` files for this area, moved here from `src/background/README.md`.

- `config_main.ts`: `create_config_service` wires the services, store, swap, write modules and start, and the file exports the production instances. Tests build their own state through `fresh_config_service`.
- `keymap_message.ts`: the key editor's messages `list_bindings`, `check_binding` and `change_keymap`. The list tags each binding with the layer that decides it, and an edit or file binding the compile dropped with the warning. The check compiles with and without the candidate and reports the warnings it adds and the bindings it replaces or drops. For a `browser` chord it also plans the Firefox shortcut slots. A change goes through `change_layers`. A set the compile or the slots would skip is refused, and the change checks the set again in its own queue turn: `change_layers` hands `decide` the state of that turn, so two tabs that save the last free slot at once bind one chord and refuse the other. The check before the change is only a fast path. A change that changes nothing answers "Nothing to change". The export takes only the edits in force, not the ones the compile drops (`exportable_key_edits`), and a snippet removal is refused while a key edit runs the snippet (`key_edits_running`). Only a top-level extension page may send them.
- `engine_layer_move.ts`: the move of the engines layer into the Engines page's two files, and of a saved `default_engine` edit into settings.toml. `move_engine_layer` in `config_start.ts` runs it at every start until the layer is empty, before the waiting writes. It moves each engine with its letters, laid on a page engine of the same name per engine path (`merged_by_path`), and keeps in the layer a piece the files build refuses. What is left of the layer goes in the same `storage.local.set` as the files and the record (`engines_after`). The start toasts a piece left in the layer, a later hand file that now wins over a moved engine path, and a dropped letter a later `keymap.d` file rebinds.
- `saved_fold.ts`: the fold of the saved settings (`desertfox_saved_settings`) into settings.toml. `fold_saved_layer` in `config_start.ts` runs it after the start read settles (host, folder, no copies-differ question, a copy that came from the folder), then the waiting writes run again. Otherwise the layer stays on top until a later start. A saved value goes into settings.toml, as it won over the file before. A saved `site_rules` list adds only the popup's rows no file (settings.toml or `settings.d`) has, and a `settings.d` file that sets `site_rules` does not hold it, as the files add up. The consent settings stay saved, and so does a `default_engine` that only the old engines layer defines. A name a `settings.d` file sets stays saved, and so does a value the files build refuses: the next start tries again. The smaller layer goes in the same `storage.local.set` as the files and the record. A start that moves something shows a toast, and `storage.session` (`desertfox_saved_fold_notes`) carries that note and the reasons for what stays to the warnings of every publish.
- `settings_message.ts`: the settings page's messages `change_setting` and `list_settings`. A change takes a typed value, runs the setting's check and goes through the same planners and `change_edits` queue as `:set`. A change with layer `file` (every scalar and list setting, from the popup and the settings page) goes to `set_in_settings_file`, or for a reset to `unset_in_settings_file`, instead, and its reply says whether settings.toml was written, waits for the host, or changed on disk. Only a top-level extension page may send them.
- `config_reload.ts`: the pure build behind every swap: raw files to the slot to store and the config to run, and every refusal as a `ConfigRefusal` whose message names the cause and the fix. Apart from `shared/config/config_load.ts` because the build pulls in `smol-toml`, and the help and new tab pages import `config_load.ts`.
- `config_import.ts`: the pure part of an import from the settings page. `read_import_source` reads the zip or folder through the zip guards, drops one shared top folder and refuses an empty result. `preview_import` lists the config files, the files the import writes to the folder (`import_folder_record`: each file the host writes that the import holds at another text), and each snippet's code, `matches` and `requires`, the build problems and what the built import reaches (`import_reach.ts`), storing nothing. `checked_consent` keeps only the snippets accepted with their exact code, and `plan_import_files` puts the import's config files over the slot's, keeping the installed snippets and dropping `bridge`, `bridge_share_tabs`, `host_auto_update` and `newtab_ip_info` (`CONSENT_SETTINGS` in `src/shared/settings_schema.ts`) from the imported settings files (each is a consent given on this machine, and the review warns for each dropped key). `answer_config_import` answers the `preview_config_import` and `commit_config_import` messages.
- `import_reach.ts`: pure. `import_reach` walks the config an import builds and lists what it can reach: addresses (engines, `new_tab_page`, `home_page`, `newtab_links`, quickmarks, fixed-address keys and modifiers) and key rows by group (clipboard or page, settings, native host), over every mode, every site row bind and site mode bind, and aliases. A command is classified by an id list, and a test checks it against the registry. A list keeps 12 rows and counts the rest.
- `config_transfer.ts`: the settings page's export, snippet list and snippet removal. `export_files` splits the slot's files into the config files and the snippets, and adds the saved browser edits as `settings.toml` (as a file of `settings.d` that sorts after every file there, when the config has settings files of its own), and the key edits as the `keymap.d` file that sorts last. `installed_snippets` parses each installed snippet's header. `layer_files` also writes the aliases layer as `command_aliases.d` and the `M` store of a normal window as `quickmarks.d`. `answer_config_transfer` answers `export_config`, `list_snippets` and `remove_snippet`. A removal runs through `apply_files` in the change queue, so a key that binds the snippet refuses it.
- `config_files.ts`: the answer to the files editor's `config_files` message: the stored files out (without `autoconfig.toml`), one save in. A save is `save_config_file` in `config_swap.ts`, beside `remove_snippet`: in the change queue it replaces or deletes one path of the stored files and calls `apply_files` with the action `edit`. Saves and reloads therefore run one after the other, and a failed build writes nothing. The refusal carries every build problem, not only the three the message names. Editor saves are the user's own config, so the import guards do not run. A snippet is stored only when `accepted` equals its text, else the answer is the consent preview. `shared/config_file_path.ts` holds the path and size rules the page shares.
- `host_start.ts`: what a start does with the host's config folder. `classify_host_start` compares the folder's files with the browser copy, both without `autoconfig.toml`: a missing or empty folder and equal files change nothing, a browser copy that is empty or still the files last taken from the folder takes the folder, and a copy with browser changes stores a question for the settings page. `settle_host_start` answers it in the change queue after a fresh read, only while the browser copy is the one the page showed. `answer_host_start_choice` is the `host_start_choice` message.
- `settings_file.ts`, `toml_key_edit.ts`, `toml_table_edit.ts`: a setting written into, or removed from, settings.toml. `settings_file.ts` also holds the toasts that answer a write (`outcome_kind`, `unset_toast`) and the `UnsetResult` type. `set_in_settings_file`, `toggle_in_settings_file`, `unset_in_settings_file` and `change_site_rule_in_file` (the popup's Disable and Enable on this site) in `config_setting_writes.ts` (`:set`, `:toggle` and `:unset` without `--temp`, and the pages) share `change_setting_in_file`. A `[[name]]` list goes through `set_table_rows`, which keeps the block of every row that stays and changes only the blocks of rows that leave or arrive. An empty list is written `name = []`, and `remove_table_rows` removes the key. It edits the browser copy with `set_top_level_key` or `remove_top_level_key` (only the key's lines change, a list or an inline table is written on one line, every comment, blank line and line ending stays, and a parse before and after refuses any edit that touches another key), swaps it in through `apply_files` with the action `setting` while it drops the saved and temp edits of the name, then sends the text to the host's `write_config_files` outside the queue. The queue only starts a batch and applies its reply, one write at a time per path, so a hung host blocks no change, and a pick during a write is written after it. The host writes only while the file still has the digest of the text the edit started from. `desertfox_settings_file_unsynced` maps each path the folder lags to that base text (no host, no permission, an older host), and each path keeps its own outcome. A record of the older `{ base }` shape reads as `settings.toml`. The next start and `,r` write it first. A start whose folder differs from the copy only by that edit asks nothing. The record goes into the same `storage.local.set` as the files and the saved edits. A refused write (the file changed on disk) reads the folder again. When the folder kept the base value of every key the copy changed, and the copy holds no other browser change, `replayed_on_folder` sets those keys on the folder's text, the copy takes the folder's files with that text and the record moves to it, and the write runs again, at most three times per write loop. The folder's files pass the CSS and empty-folder checks of a folder read first. Otherwise it stores the copies-differ question and drops the record, or keeps the record when the folder cannot be read. A record a later pick started after a swap dropped the old one stays, whatever its base, and the loop writes it from its base. A pick's reply says `replaced` when a swap dropped its record, with the swap and whether the file got the pick first. A pick keeps a pending question and classifies the folder again after its write. Only a copy that came from the folder (a folder read is on record, and the stored files are not `imported`) is written to the folder. `imported` stays through browser edits until a folder read. After a write the applied digest moves with it when the copy held no other browser change, so the next start does not ask. An editor save or snippet change (a removal, or an import of snippets alone) that leaves settings.toml as it was keeps the record. Any other swap drops it. A default engine that only the old engines layer holds, which no file can name, goes to the saved edits instead, and the start moves it into settings.toml once the engine moves. A theme or engine name that matches nothing is refused. `set_theme_file` shares the same path (`change_folder_files`): one queue turn for every file a change touches, one pick per path, and one host batch for all of them, so the folder never names a theme or engine it lacks. `change_engine_file` shares the path too. A setting a `settings.d` file sets is refused, and an unset of it drops only its browser edits.
- `autoconfig_mirror.ts`: writes a comment line, then all stored key edits as keymap.d mode tables, to `autoconfig.toml` through the host, one write at a time. No setting goes there. DesertFox never reads the file. A failure never reaches the edit. It warns once per kind of failure, and not at all without the permission.
- `timing_log.ts`, `timing_summary.ts`, `timing_browser.ts`: the last 300 timings in `storage.session` (command round trips from `router.ts`, `hint.build` from the `hints` bundle through the `record_timing` message), and the pure count, median, p95 and max per name that `debug.perf` copies. The bundle loads come from `load_log.ts` at read time. A tick of records is one write, writes run one at a time and a storage failure is dropped.

### Shared files for config delivery

Behavior of the `src/shared` files for this area, moved here from `src/shared/README.md`.

- `zip.ts`: `read_zip` and `write_zip` for config export and import. The reader takes stored and deflated entries and returns a path-to-text map. It skips `__MACOSX/` and dot-file entries and drops `.` path segments. It fails the whole archive on an unsafe path (absolute, `..`, backslash), an exact duplicate, a symlink, overlapping entries, a size or count overrun, a bad checksum or text that is not UTF-8. `read_folder` puts a folder the page read (`webkitdirectory`) through the same path, junk, duplicate, count and size rules. The writer is store-only. The byte caps (1 MiB) equal the host's reply cap. Pure, so the background and help pages can both use it.
- `storage_watch.ts`: `watch_stored` (a `storage.local` key, now and at each change), `touches_settings` (a `storage.onChanged` event that says the settings in force changed: a write of the config status key `CONFIG_STATUS_STORAGE_KEY`, which every settings edit ends with, or of `FILES_CONFIG_STORAGE_KEY`, the last write of a reload) and `follow_settings`. Pages use `follow_settings(draw)` to redraw from the current settings: it calls `draw(true)` at once and `draw(false)` at each change, one at a time, and puts the scroll position and focus back after each redraw. The page keeps its own timers and listeners out of the DOM and stops the old ones in `draw`.
