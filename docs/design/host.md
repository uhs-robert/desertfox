# Native host

Area: the native host.
READMEs: `host/README.md`, `src/background/README.md`.
Source: `host`, `src/background`.

## Native host (optional)

### Config host (built)

A Python 3.9 stdlib-only host in `host/` (see `host/README.md`). The extension calls it with one-shot `runtime.sendNativeMessage`, and the host exits after its reply. It has nine verbs:

- `read_config`: the raw text of every config file under `~/.config/desertfox/`, keyed by relative path. One reply carries all files, and the host returns a clear error above Firefox's 1 MB reply cap. Nothing is parsed host-side. The host reads only regular files of at most 1 MiB, following links, and opens them without blocking, so a FIFO in the folder cannot hang it. A file it will not read (not a regular file, or larger than 1 MiB) is refused with an error that names the file and the reason, so `config.reload` keeps the current config.
- `write_autoconfig`: writes the key edits to `~/.config/desertfox/autoconfig.toml`, atomically. Nothing loads that file back. Browser storage stays the only source of key edits.
- `write_config_file {kind, name?, text, base_sha256}`: writes one file of a fixed kind table, `settings` (`settings.toml`, no name), `engines` (`search_engines.d/zz-desertfox.toml`, no name), `search_keys` (`keymap.d/zz-desertfox.toml`, no name) or `theme` (`themes/<name>.toml`). The host builds the path and checks the theme name again, so a request never carries a path and no name leaves the `themes` folder. A `null` text deletes the file, only while it still has `base_sha256`. A linked file loses only its link. `write_settings {text, base_sha256}` is kind `settings` under its older name. Either replaces the file with the text the extension edited, atomically (a temporary file renamed over it), only while the file's SHA-256 is still `base_sha256` (`null`: no file). Otherwise it refuses with `changed on disk` and writes nothing. Host writers take a lock file in the folder, so two writes never pass the check against one base. Just before the rename it checks the digest again and that the link still points at the same file, and it hard-links the old file aside. After the rename it compares that old file's bytes with the base again, and an edit an editor saved into it in the meantime goes back and refuses with `changed on disk`. An old file it cannot read goes back too and refuses with `could not be read back`. An old file whose size differs from the base is an edit found without reading it. A filesystem without hard links refuses every write, because a copy could not see an edit saved after it. It follows a symlink so the link stays, keeps the target's mode, refuses a file that is not UTF-8, and never creates the config folder. The request names no path. See Settings in the file.
- `self_update {version, sha256}`: replaces the installed host with GitHub release `v<version>`. The request carries the version and the SHA-256 of each script, which the extension takes from its signed build (`host_sha256.json`). It carries no URL, channel or path. The host accepts only `x.y.z` or `x.y.z.N`, builds every URL from this repo's releases, fetches over HTTPS only with size and time caps, and refuses a downgrade. Each file must match both the release `.sha256` and the extension's hash, so a replaced release asset fails. It then writes the five paths `install.sh` writes, each as `<path>.new` renamed over the old file: the bridge, the `desertfox` command line, both manifests, and the config host last. A development host (`release_version` `dev`) never updates itself.
- `editor_start {text, ext?, insert?, private?}` and `editor_collect {job}`: run the user's editor on a scratch file and return the edited text. The command comes from `editor.toml` in the config folder, which only the host reads and `read_config` skips, so the request carries no argv. `editor_start` returns a job id and `editor_collect` long-polls for 20 s, so no call outlives a native-message timeout. See `host/README.md`.
- `open_firefox_page {page}`: opens one Firefox page (`about:preferences`, `about:config` and others) that no extension API can open. `page` is a key of a fixed table in the host, never a URL. The host runs its parent Firefox as a remote client with that profile and URL, argv only, and kills it after 10 s. `browser.open_firefox_page` (`:firefox`, the `,f` keys, `bridge: false`) calls it. Without the host, the command copies the address and the toast says to press Ctrl+L and paste. The first such toast also names `:native.install`. See `host/README.md`.
- `list_fonts`: the installed font family names, from one `fc-list` run (argv only, 5 s timeout), deduplicated, sorted, cut to 2000, with every name that `parse_font_family` refuses dropped. The extension uses them alone when the host answers, and falls back to a canvas probe otherwise (see Styles). See `host/README.md`.

Every reply carries `release_version`, which `just release` stamps into the shipped hosts. The bridge sends it in its `ready` frame. Apart from `self_update` and the editor scratch files, the host writes only these files in the config folder: `autoconfig.toml` (a copy of the key edits), `settings.toml`, `themes/<name>.toml`, `search_engines.d/zz-desertfox.toml`, `keymap.d/zz-desertfox.toml` and the empty lock file `.settings.lock`. `nativeMessaging` is an optional permission, requested from a button on the Help page that `:native.install` opens, the same panel `:permissions.grant nativeMessaging` opens (Firefox grants it only from a click). The page also shows a one-line command that runs `host/install.sh`, with a Copy button. For a release build it downloads `install.sh` of its own version from the GitHub release to a temp file, checks it against `install_sh` in the signed build's `host_sha256.json`, then runs it with the hash of each script from the same file, and `install.sh` refuses a script that does not match. A development install, and a build with no `host_sha256.json`, gets `curl ... | sh` from `main` with no checksum, and the page warns that it is for development only. `--channel main` forces main. `just release` uploads both hosts, the `desertfox` command line, their checksums and the script. `config.reload` reads the files through it, and each change to the key edits writes `autoconfig.toml` (see [Delivery](config_delivery.md#delivery)).

### Host updates (built)

Firefox updates the extension. DesertFox then updates its own native hosts and the `desertfox` command line to match, so a user installs the host once with `:native.install`.

- Channels. A stable extension (`x.y.z`) gets the stable release of its own version from AMO and the matching GitHub release. A beta extension (`x.y.z.N`, a self-hosted signed build; AMO refuses letters in a version, so the number counts up from the last stable release and 0.1.23.2 ranks above 0.1.23 and below 0.1.24) gets the GitHub prerelease of its own version. A development install (`installType` `development`) has no release and never updates its host, and a host with `release_version` `dev` refuses to update too. The channel is read from the fourth number, in `src/shared/host_version.ts`.
- When it checks. The extension reads `release_version` from the bridge's `ready` frame, from every reply of the config host, ok or error, and from one `read_config` request at start (only with the `nativeMessaging` permission), so a host is checked even with `bridge` off. A missing field, as in a host from before the updater, counts as older. The extension compares the numeric `x.y.z` parts, and a beta sorts after the release it counts from and before the next one. It sends nothing when the host is equal or newer, so with two Firefox profiles the newest host wins and none downgrades another.
- Consent. The `host_auto_update` setting is off by default. The "Install and keep the host updated" button on the `:native.install` page saves it as a browser edit and installs nothing itself, because Firefox cannot run the install command. With consent, an older host updates on connect and a toast says so. Without it, the extension shows one line per version that names `:native.update`, which runs the same update on demand and ignores consent and the limits below.
- Trust anchor. The first install checks `install.sh` and each script against the signed build only (see above). The update has two checks. The release carries a `.sha256` per script, and the signed extension build carries the hashes of the same stamped scripts in `host_sha256.json` (`just release_stamp` writes it and the build copies it into `dist/`). The host accepts a file only when it matches both, so a swapped release asset fails against the signed build, and a broken signed build fails against the release. The request holds the version and those hashes and no URL, so a page or a bridge client cannot point the host elsewhere. A build with no hashes sends no update. The update runs only in the config host, and there is no socket verb for it.
- Lock. The updater and `host/install.sh` take a non-blocking `flock` on `update.lock` in the data folder (`~/.local/share/desertfox/`), which both already write to, so both compute one path whatever the environment. They hold it from the first staged `.new` file to the last rename. The second caller fails with `update running`, so two writers never stage the same file.
- Reconnect. After an ok reply the extension closes the bridge port and connects again. The running bridge still holds the old code in memory, and it exits when its stdin closes. The new bridge waits up to 3 s for the old one to release `bridge.lock`. If it loses that race, it exits and the usual backoff connects again. The bridge never replaces its own file.
- Retry and toasts. The extension tries a version once per 24 hours (the time of the last attempt lives in `storage.local`, written before the call). A failure shows one toast per version, "Host update failed: <reason>. Run the command from :native.install", and is logged each time. A checksum mismatch blocks that version until a new extension build, which carries other hashes. Each success shows one toast. While the host is older, an error from it reads `host_outdated` and says whether it is updating or the update failed.
- Bootstrap. A host from before the updater has no `release_version` and no `self_update` verb. The extension treats it as any outdated host: the update fails with the host's "unknown cmd" refusal, and the failure toast names the manual `:native.install`. `INSTALL_HINT` stays for `host_missing` and `no_permission`, because a missing host cannot update itself.

### Bridge host

One long-lived host, `desertfox_bridge` (`host/desertfox-bridge`), serves everything on the desktop that needs to talk to DesertFox. It is generic: it assumes no particular shell, bar or window manager. It sits beside the one-shot config host and does not change it.

The same script serves DesertBird, the Thunderbird extension, through a second manifest, `desertbird_bridge`, which allows only `desertbird@uhs-robert`. A fourth manifest, `desertbird_host`, starts the config host for the same extension id, so DesertBird reaches `editor_start` and `editor_collect`. The installer and the updater write both beside the other two in `~/.mozilla/native-messaging-hosts`. The app passes the host the manifest path and the extension id, and the host takes its app from them. A manifest name or id it does not know, or a pair that names two different apps, stops the host before it takes a lock, so a guess can never put one app's host on the other's socket. A host run with no arguments is Firefox's, as before. Each app has its own runtime folder, `$XDG_RUNTIME_DIR/desertfox/` for Firefox and `$XDG_RUNTIME_DIR/desertbird/` for Thunderbird, each with its own lock, socket, state file and kept theme. So both hosts run at once and never contest one lock, and the second-host rule below holds per folder. The rest of this section names the Firefox folder. The tab verbs, the tab events and the tab caches belong to Firefox alone: the Thunderbird socket refuses the tab verbs with `tab verbs need --app firefox`, and a Thunderbird host drops tab events and never prunes or deletes the caches. A Thunderbird host also refuses a `run` with a `tab_id` the same way, and refuses `theme` with `theme needs --app firefox` and replays no kept theme, because DesertBird takes no theme. The mail reads belong to Thunderbird alone, and the Firefox socket refuses them with `mail reads need --app thunderbird`:

- `folders {}`, `messages {folder, limit?, unread_only?}`, `message {id}` and `attachments {id}`. The host checks the fields (`folder` is the opaque folder id from `folders`, 1 to 1024 characters; `limit` is 1 to 200; `id` is a whole number), counts each read against the rate limit, sends only the checked fields, and passes the add-on's reply on as it came. The add-on checks its share settings, which are off by default, and builds each reply, so the host checks no setting. A reply frame over 1 MiB is skipped unread, so that read fails as unanswered. A body arrives marked `untrusted: true`. The command line that prints it wraps it in a nonce envelope (see below).
- The mail writes, `draft {to, cc?, subject, body, from?, reply_to_id?}` and `act {action, ids, folder?}`, belong to Thunderbird alone too. The Firefox socket refuses them with `mail writes need --app thunderbird`. The host checks the shapes: `to` holds 1 to 10 addresses (0 to 10 with `reply_to_id`), `cc` at most 10, an address at most 320 characters, the subject at most 998, neither with a control character, and the body at most 64 KiB of UTF-8 with no control character but tab, newline and carriage return, so its JSON stays under the request cap. `action` is `archive`, `trash` or `move`, `ids` holds 1 to 50 different whole numbers, and only `move` takes a `folder`, which it needs. The host sends only the checked fields, counts each write against the rate limit, and cuts the reply to `ok`, `message` and an act's `count`, so no draft id or mail data leaves through it. The add-on checks its settings (`bridge_allow_drafts`, `bridge_allow_actions`, and `bridge_share_folders` for a move), the address shapes and the identity, never sends, and shows a person a y or n prompt for each act. The add-on gives up saving a draft after 30 s with `timed out`, so a draft waits 40 s. A person answers an act, so an act waits 70 s, past the add-on's 30 s prompt timeout, and the host holds one act at a time: a second one gets `busy` and never reaches the add-on. The slot frees on the reply, the timeout, the port closing and the client closing its connection, which the host checks every 0.5 s while it waits. A client that closes only its write side still gets its answer. The add-on has no cancel, so a y on the prompt still moves the messages after the client has left, and nobody hears the result. The other verbs keep working while an act waits.

The extension opens one `connectNative` port to it when the `bridge` setting is on and the optional `nativeMessaging` permission is granted. With either missing there is no port and no socket. A host that is missing or exits before its first message leaves nothing changed, and the extension reconnects with a growing pause (1 s up to 60 s). The host says `ready` once it holds its lock, and the extension trusts the port only after that. Firefox keeps the background awake while the port is open, which also helps a later move to MV3.

Two things come out of the host, both under `$XDG_RUNTIME_DIR/desertfox/` (a folder with mode 0700).

- `state.json`, written for a bar to read: the mode, the host's pid and start time, and `private`. The host writes it atomically (a temp file renamed over it). A reader treats a dead or reused pid as no state. A private window leaves only its mode and `private: true`: no window or tab id, no URL, no title.
- `bridge.sock`, a Unix socket with mode 0600, because a desktop program cannot open a channel into the extension. The first host to start owns the socket and the state file through a lock on `bridge.lock`. A second host waits 3 s for the lock, then exits with an error, so two Firefox profiles share one bridge and the second one gets none. The socket takes one JSON object per line and answers each with one line. A request over 192 KiB is refused (the size lets a 64 KiB draft body through as JSON), an idle connection closes after 5 s, and at most 16 connections are open at once. A connection from another user is closed.

The built verbs are `ping`, `state` (the latest snapshot, the same shape as the file), `list`, `run` and `theme`. Each verb has a fixed name, so there is never a shell or eval verb:

- `list`: the commands the bridge allows, as registry entries with their params, for completion.
- `run`: one command line from outside. The host forwards it to the extension, which refuses it unless the command's `bridge` field is true. A hard-coded never-list wins over the field: the `config`, `settings`, `session`, `copy`, `register`, `debug`, `native` and `permissions` groups, `page.reload` (it can clear cookies and site data), `page.save_pdf`, the hint picker, `visual.act`, `open.clipboard`, `command.repeat`, `macro.play`, every snippet, and an address that is not http or https. A handler refusal comes back as fixed text (`<id> failed`), because it can hold a tab title. An `open.url` address is resolved the way the handler resolves it (trim, scheme, bare host, search) and refused unless the result is http or https, so `localhost:3000` opens and `vscode://x` does not. A command that passes goes through the one validator (`check_args`) and then the router, with no command line to open, so a missing value is a refusal. The reply carries success or failure and a message, never data. The host cuts a run reply to those two fields.
- The tab verbs, all behind the separate `bridge_share_tabs` setting (off by default, and it needs `bridge`), because a tab list leaks browsing. With it off, each answers `tab sharing is off, set bridge_share_tabs to true`, and so does a `run` that names a tab. The extension sees every id and checks it itself.
  - `tabs {current?}`: the tabs of normal windows, each with `tab_id`, `window_id`, `title`, `url`, `active`, `audible`, `discarded`, `last_accessed`, `pinned`, `hidden`, `fav_icon_url` and, from the host's caches, `fav_icon_path`, `thumbnail` and `thumbnail_at`. A tab of a private window or a popup never appears. With `current: true` the list holds only the active tab of the last focused window, for a capture tool, and is empty when that window is private or a popup.
  - Icons: Firefox gives tab icons of web pages as data URLs (measured on loaded, restored and discarded tabs) and `chrome:` icons to `about:` pages. A list of the data URLs would outgrow one native message. So `fav_icon_url` is blank for a data URL icon, and the row carries the SHA-256 of the data URL instead. The host keeps that key to itself. For a key it has no file for, it asks the extension for that tab's icon (a `favicon` request the socket does not offer), within 3 s for the whole list, and saves the image in `$XDG_CACHE_HOME/desertfox/bridge-favicons/` (mode 0700) under the key with the suffix of its type. `fav_icon_path` names the file, or is empty. Tabs with the same icon share one file.
  - `activate {tab_id, preface?}`: selects the tab and focuses its window. The optional `preface` (letters and digits, 32 at most) goes in front of the window title, so a program that raises the window itself can find it by title. DesertFox does not raise windows through a window manager, because it assumes none. It clears itself after 10 s, and `clear_preface {window_id, preface?}` clears it early, but only when the preface is still the one DesertFox set. Activations run one after another, so two at once cannot swap each other's title. The reply is `window_id`, `focused` and `preface_set`.
  - `close {tab_id}`.
  - `capture {tab_ids?}`: renders each tab (all loaded ones without ids), one at a time, and the host saves a JPEG per address in `$XDG_CACHE_HOME/desertfox/bridge-thumbs/` (mode 0700), pruned after 7 days once no open tab has that address. The host asks only for ids in a fresh tab list from the extension, so it never saves the image of a tab the extension did not list as a normal one.
  - A tab id that is stale, private, in a popup or not a whole number gets the same refusal, `no such tab` (`no such window` for `clear_preface`), so an id cannot be used to probe for private tabs. Failures carry fixed text and never a title.
  - `run` takes an optional `tab_id` and runs the command in that tab, where a run otherwise uses the active tab of the focused window. Every rule of a plain run applies first, with the same refusal text, and the tab is looked up only after they pass.
- `theme {theme}`: the desktop tells DesertFox which theme it uses, and DesertFox maps the name onto its own roles. It changes the theme and nothing else: no other setting has a verb. The host checks the shape (a letter or digit first, then letters, digits, `_` and `-`, 1 to 64 characters), keeps the last name in `theme.json` beside the state file (it is the one file that outlives a host, and a host that dies mid-write leaves the old file) and forwards it. It forwards the kept name again right after each `ready`, in the same step that opens the link, so a push never overtakes the replay and a connection gets the name once. The extension accepts only a built-in theme name (`desktop` is not one), logs and ignores any other name, and keeps the current theme. The host deletes the kept name when the extension refuses it, in a push and in the replay, so a typo is refused once. While no host runs (the browser is closed), `desertfox theme` writes `theme.json` itself, atomically and under the `bridge.lock` flock, and exits 0, so the next host replays it. It needs `bridge` on to take effect, because no host starts otherwise. It stores the name in `storage.local` (key `desertfox_desktop_theme`: per machine, not Firefox Sync, so a browser restart keeps it) and publishes again only while `theme` is `desktop`. The name stays whether the bridge is later turned off or not. `light` or `dark` and `light_intensity` are not part of the push.
- `subscribe`: turns the connection into a one-way event stream. The host answers `{"ok": true}`, then the current mode if it has one, then one line per event, each with a `seq` that rises by one, so a reader can tell it missed one. A reader that also wants to send requests opens a second connection. The events:
  - `mode`: the same fields as the state file, so a private window gives only its mode and `private: true`. The host makes it from the mode it gets, and it needs no `bridge_share_tabs`.
  - `tab_activated {tab_id, window_id}`, `tab_updated {tab_id, window_id, title, url}`, `tab_audible {tab_id, window_id, audible, title, url}` and `tab_removed {tab_id}`: only while `bridge_share_tabs` is on, and only for a tab of a normal window. Title and address changes of a tab within 250 ms go out as one `tab_updated` with the values at the end, because some pages change their title every second. `tab_audible` and `tab_removed` go out at once. A closed tab can no longer be looked up, so the extension sends `tab_removed` only for a tab an earlier event named, and the host passes it only to a reader that an earlier event told about that tab. Each reader remembers its last 1024 tabs. The host cuts a title to 512 characters and an address to 2048.
  - `tabs_off`: `bridge_share_tabs` is off. The extension sends it when the setting goes off and again each time the port comes up with the setting off, so a host that missed it still hears it. A reader forgets its tabs, and no tab event follows until the setting is on again. A tab reply whose request came before the setting went off goes out as the sharing-off refusal.

  At most 4 readers stream at once, inside the 16 connections, so stuck readers cannot starve the command line. A fifth gets `too many subscribers`. Each reader has its own queue of 64 events and its own writer. A reader that falls 64 events behind, or does not take a write within 2 s, is dropped and can reconnect, so a slow reader never holds up the port, the requests or another reader. A stream is not closed for being idle. `subscribe` counts once against the rate limit and its events do not count. The extension sends tab events whether or not anyone reads, and the host drops them when nobody does.

A `run` targets the active tab of the last focused normal window, not the window Firefox thinks is current. It never toasts and never touches `.` or the macro recorder, so a script cannot change what the user repeats. A run that opens an address is refused when that window is private.

The host limits all connections together to 10 `run`, `list`, tab and mail requests per second (`theme` is not limited), because the CLI opens a connection per call (an excess request gets an error line and does not reach the extension), keeps the cap of 16 connections, and keeps at most 16 requests waiting on the extension. A request the extension does not answer in 10 s fails, and so do all waiting requests when the port closes, so a client never hangs on a reconnect. Each request carries an id and the reply that carries the id goes to the connection that asked.

The extension is the trust boundary. It drops everything from a private window before it reaches the host, so a host bug cannot leak it. The host writes only the socket, its lock, the state file and the kept theme (`theme.json`), all on tmpfs, and the thumbnail and icon caches in `$XDG_CACHE_HOME`. It prunes each cache at start (files over 7 days old, then the oldest beyond 500), prunes the icons again after each full tab list (an icon no open tab uses, once 7 days old), and deletes both caches when the extension says `bridge_share_tabs` is off: in a reply, or with the `tabs_off` event. A write and a delete never overlap, and an image the extension sent before a delete is dropped, so a deleted cache does not come back.

`host/desertfox` is the command line for the socket, a stdlib Python script: `desertfox run [--tab <id>] <command> [args]`, `desertfox list`, `desertfox state`, `desertfox theme <theme>`, `desertfox events` (prints the stream, one JSON line per event), `desertfox tabs [--current]`, `desertfox activate <id> [--preface <nonce>]`, `desertfox clear-preface <window id>`, `desertfox close <id>` and `desertfox capture [id...]`, and for Thunderbird `desertfox --app thunderbird mail folders|list <folder id>|read <id>|attachments <id>`, `mail draft --to A [--cc B] --subject S [--from EMAIL] [--reply-to ID] --body-file PATH|-` and `mail archive|trash <id>...` and `mail move <folder id> <id>...`. The draft body comes from a file or stdin, never from an argument, so neither the shell history nor `ps` holds mail text. A write prints one short line with no mail text, and a refusal prints the add-on's text on stderr and exits 1. `--app firefox` or `--app thunderbird` in front of the verb picks the socket. Without it the command line always talks to Firefox, so a desktop call written before Thunderbird never lands in Thunderbird. `theme` is Firefox's alone, and `mail` without `--app thunderbird` is a usage error. Mail is text from strangers, and a reader of the output can be a language model that follows instructions. So every sender field (from, to, subject, the message's content type, the body, attachment names and types) prints only between `<<<UNTRUSTED mail <what> nonce=<n>>>>` and `<<<END <n>>>>`, in plain and in `--json` output alike. The command line draws the nonce with `secrets.token_hex(16)` for each print, after the reply came, and draws again while the text holds it, so a guessed or an old END line in a body cannot close the envelope. The folder list prints inside an envelope as well, because feed titles, newsgroups and shared IMAP folders let third parties name folders. It prints plain text and exits 0 when done, 1 when refused or failed, 2 for bad usage and 3 when the bridge is not running (`theme` keeps the name and exits 0 instead). `-h` or `--help` after a verb prints the usage and sends nothing. The installer puts it beside the hosts and links it into `~/.local/bin`.

### Background files for the native host

Behavior of the `src/background` files for this area, moved here from `src/background/README.md`.

- `native_client.ts`: the client for the native host. `create_native_client(deps)` gives `read_config`, `write_autoconfig` and `list_fonts` (the installed family names), each one `sendNativeMessage` behind a permission check. Every failure is a `NativeHostError` (`no_permission`, `host_missing`, `host_failed`, `bad_reply`) whose message says what to do. `config.reload` and the autoconfig mirror call it. `open_firefox_page` turns an `unknown cmd` reply into `host_outdated` with an update hint, because a `dev` host never reports outdated. `write_config_file` names a file by the host's kind and name (`host_file_of`), never by path, falls back to `write_settings` for `settings.toml` on a host from before it, reads a host whose kind table lacks the kind as `host_outdated`, and reads `changed on disk` as `file_changed` and `could not be read back` as `file_not_read_back`.
- `host_update.ts`, `host_update_browser.ts`: the host updater. A host older than the extension (from the `release_version` in a config host reply or the bridge `ready` frame) is replaced through `self_update` (the background also sends one `read_config` at start, so a host is checked with the bridge off), with the hashes of the signed build (`host_sha256.json`). It needs `host_auto_update` consent, else shows a line that names `:native.update`. One attempt per version per 24 h, one failure toast per version, a block on a checksum mismatch. An ok update reconnects the bridge. See `docs/design/host.md`, "Host updates".
- `bridge.ts`, `bridge_browser.ts`, `bridge_run.ts`: publish the mode to the bridge host (`desertfox_bridge`) over one `connectNative` port and answer its `run`, `list` and `theme` requests (`theme` stores the theme the desktop pushed, see `set_desktop_theme` in `config_store.ts`, and only a built-in theme name passes), when the `bridge` setting is on and the `nativeMessaging` permission is granted. `bridge.ts` holds the logic with injected browser calls, `bridge_browser.ts` wires it to the browser and registers the listeners. The port counts as up only after the host's ready message, and a drop reconnects with a growing pause. The bridge publishes that state as `HOST_CONNECTED_STORAGE_KEY` in `storage.session` (set on ready, cleared on a drop, a disconnect and every start) for the popup's host dot. A private window sends its mode and `private: true` and no id. The in-page badge and which-key panel are not affected. `bridge_run.ts` is the one path for a run from outside: parse, the command's `bridge` field and the hard-coded never-list, the one validator, a private-window check, then a router of its own that targets the focused normal window, or the normal-window tab a `tab_id` names, and records nothing for `.` or macros. It answers success or a refusal text, never data. `tab_switch.ts` holds the tab verbs (`tabs`, `activate`, `clear_preface`, `close`, `capture`, and `favicon`, which only the host asks for). `activate`, `close`, `capture` and `favicon` start from `normal_tab`, which refuses a private-window tab with the text of a missing id. `tabs` filters the windows and tabs of normal windows directly, and `clear_preface` refuses a window that is not normal ("no such window"). `bridge.ts` answers them (and a `run` with a `tab_id`) only while `bridge_share_tabs` is on. `bridge_events.ts` builds the tab events the host streams to subscribers (activated, title and address, audible, removed, and `tabs_off`), gated by `bridge_share_tabs`. Every event but two starts from a `normal_tab` lookup. `tab_removed` goes only for a tab the subscribers heard of, and `tabs_off` goes when sharing turns off, with no lookup. Title and address changes of a tab are settled over 250 ms.
