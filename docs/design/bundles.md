## Bundles and loading

- `background.js`: the registry, the handlers, keymap validation and the shortcut slots.
- `content.js`: the key listener, the prefix tree, the modes and scrolling. Kept under a guard of 22 KB minified (see [Content script size](../design.md#content-script-size)).
- Hints, which-key, caret and visual mode are separate files. Each has its own limit in `MAX_BYTES` in `tools/build.mjs`. Snippets run as their own code. The background injects one with `tabs.executeScript` on first use in a tab.
- A site mode is a named set of binds in a site row (`modes.<name> = { label, bind }`) that `mode.site <name>` lays over normal mode, and `mode.site off` ends. It is not a `Mode`: the mode stays `normal`, so the matcher, `key_flow.ts` and `mode_state.ts` do not change. The page reply carries, per mode, the label and the top-level children of the tree that differ from the normal tree (binds go on after `pass` and `only` prune, and the matcher does not free a key the running mode binds, so a mode key wins over both). The content script swaps the matcher's tree to normal plus those children, and shows the label in the badge, even under `mode_indicator = not_normal`. The first matching row that has a mode name decides that mode whole. One exit policy holds for every mode: Escape, any keydown DesertFox does not cancel (a replayed key that the keymap passes too), a mousedown, any mode change (focus moving into a field too) and any keymap update. A mode with `sticky = true` is the exception: a mousedown and a keydown the page keeps do not end it, so a widget can be opened and picked from. The shipped `arrow` row defines one, labeled ARROW, that `<A-l>` (a `browser` chord) starts and ends through `mode.site arrow` with `toggle`. A start from a text field blurs the field first, and a start from caret, visual, media or another mode leaves that mode first, because a mode change ends a site mode. It also ends on Escape, a mode change and a keymap update. Its Escape bind ends the mode first and then sends Escape to the page once, so a page that cannot take the key never leaves the mode on. Its h, j, k and l call `page.arrow` on the deepest focused element, through shadow roots. A select steps over disabled options, a range steps up or down (by one percent of its span when it has no step), and a radio gets a click on the next radio of its group, which a script framework reads. With nothing focused the keys scroll as the normal keys do. Any other element gets an ArrowLeft, ArrowDown, ArrowUp or ArrowRight keydown and keyup, and the page scrolls when it did not cancel the keydown, so a clicked link or button does not strand the keys. A count spaces its steps one `KEY_PAIR_GAP_MS` apart. A number input is a text field, so focusing it ends the mode and the real arrows step it. The key test piece `p28_arrow_mode` proves it. A macro recording starting or stopping is a keymap update, so it ends the mode. The mode report to the background, which-key listings inside a mode and a badge for a mode in a child frame are not built. The compiler warns on a `mode.site` bind that names a mode no row defines. The key test piece `p28_site_modes` proves it on the `/grid` stand-in.

- The `drive` row (`drive.google.com/drive/*`, which leaves the docs editors and a file preview out) binds plain `page.item` moves in its `item` column and sets `item_select = "arrows"` (see the next bullet), because Drive keeps its own selection and Enter opens the selected file. The page gets j and k as `page.item` `current` plus ArrowDown or ArrowUp over the grid view (`[role="grid"] [role="gridcell"][data-id]`, every file a cell of one row) and the list view (`[role="grid"] [role="row"][data-id]`, one table row per file), so Drive moves its selection, scrolls its panel and draws more rows. In the grid view h and l send ArrowLeft and ArrowRight. In the list view h and l keep the plain sideways scroll, which a narrow window needs. gg and G are the `first` and `last` of `page.item` on the files of both views, which scroll Drive's panel to its end and follow it while Drive draws more rows (Drive ignores a sent Home and End), and send no arrow. In Drive, gg and G move Desert Fox's focus but not Drive's selection. Enter after gg or G opens the file Drive had selected, not the one Desert Fox boxed. Each key is guarded by `when_present` on the files of its view, so a page with no file keeps the plain keys. Known gap: in a folder with one file, or a grid of one line, no arrow can move, so the file gets the box and no selection, and Enter opens nothing. The roles were read on a live Drive page, and `default_site_rows_off` turns the row off.
- `item_select` (per site: `off`, the default, or `arrows`) is for a site that keeps its own selection. The background rewrites the item tree it sends a page (the page reply and which-key both, through `page_mode_trees_for`), so item.js and content.js carry nothing for it; the compile only builds the four arrow steps once through the validator (`item_select_keys`). It rewrites only `page.item` steps that name a selector, at every choice of a guarded bind, and never the finder keys, so a page with no file keeps the plain scroll. A move (`down`, `up`, `left`, `right`) becomes `current` plus the site's arrow, and the arrow keeps the count rule of `page.send_key`, so a count sends it that many times. `first`, `last`, `current` and the section jumps keep themselves and send no arrows, since Drive drops an arrow that follows another within about 100 ms. With no file selected, I focuses a file and selects none until j or k. The `current` step before a move's arrow puts the focus back on the item when the site redrew it, and ignores the count. A key that item mode binds, pressed while G follows the end, stops the follow, and that key then runs on the item reached. The row binds Enter to a sent Enter, guarded by `when_present` on the files, so an Enter typed right behind G or gg waits for the end key like any bound key and opens the file Drive has selected, which gg and G do not change. The guard also fails while a `[role=dialog]` holds focus (`body:not(:has([role="dialog"]:focus-within))` in front of the file selector) and while focus sits on a `button`, `a[href]` or `[role=button]` inside a file (`:not(:has(<file> :is(button, a[href], [role="button"]):focus))`, where Tab in item mode puts it). The bind says `otherwise = "page"`, so a dialog's focused button, or a file's focused button or link, gets the real Enter, which a sent Enter cannot give since the page does not trust it. A hidden mounted dialog holds no focus and does not disable the bind. With no file shown the guard fails and the page gets Enter too, not the mode's `page.item_action` open. A pointer press or the wheel during the follow also stops it. The setting is resolved against the frame's own address.
- `page.item` (bundle `item.js`) takes an item selector, an optional `link` selector and a direction. Down and up go to the nearest item on another row below or above, and left and right to the nearest item that overlaps in height, so one bind set serves a list and a grid. Items whose span across the direction overlaps the current one come first (so a masonry tile keeps its column and a left-aligned list of unequal widths goes to the next line). Among them, the nearest one sets the next row or column, which is every item that shares its extent along the direction, and the largest overlap across picks from it, a tie going to the nearer. With none overlapping, the smallest gap across stands in for the overlap. The start is the item that holds the focus while it is on screen (a focus left behind after a scroll far away gives way), else the last item it moved to while that is on screen (a weak reference, so nothing is stored), else the first item in view. The list is read again on each press. Down and up scroll the page by 50 px per count, in place of the move, while the current item runs past the view edge in that direction (a long comment is read to its end first) and when the current item is the last one (the page below the results stays reachable). Where the selector matches nothing (a Hacker News text page), every direction scrolls the same way and shows no error. Left and right show a notice at the last item. `first` and `last` go to the first and last shown item, whatever has focus, and ignore a count. They scroll the list's scroller to its top or bottom first: the nearest ancestor of the items whose `overflow-y` is `auto` or `scroll` and that holds more than it shows (an overflow box that holds no more than it shows is skipped), else the page. They land on the end item, by `aria-rowindex` where the list numbers its rows, else in document order: at once when the scroll did not move, else at the next read, because the items drawn before the scroll would pull the list back. Then they follow the end while the page draws or loads more rows (polled every 50 ms, `END_POLL_MS`): each time the scroll height grows they scroll to the end again, and each new end item takes the focus and the box, after a check that it is still on the page. They stop when the end stays the same for 1 s (`END_STALL_MS`), after 10 s (`END_MAX_MS`), or when the user leaves (`watch_user_left`, a key, a pointer press, the wheel or a hidden tab). A last drawn row below `aria-rowcount` keeps `last` going past the stall time. A match does not end it, because Drive gives `aria-rowcount` as the rows it has loaded, not the whole folder. With no item they do nothing, and every shipped `page.item` row binds `gg` and `G` to them guarded by `when_present` on the row's item selector, so a page that shows no item keeps the plain scroll to the top and bottom. Like j and k, these binds replace the user's own `gg` and `G` from the keymap on those pages while items show. A user who made `G` a prefix (`Gx` keys) loses those keys there, because a bind over a branch replaces the whole branch and keeps no fallback. A user row that binds `gg` or `G` on the same sites wins, as the first row decides a key, and `default_site_rows_off` with the row's name turns the shipped row off. A count moves that many items and stops on the last one, and a left or right move with nowhere to go shows a notice. `current` focuses the item a move would start from (the focused item, else the last one moved to while on screen, else the first in view) and goes nowhere, so a key sent next lands on an item. It ignores a count and does nothing with no item. The item or its link takes focus with `preventScroll`, and the page scrolls it to the centre only when it is not fully in view, or to its top when it is taller than the view. An item that is not focusable gets `tabindex="-1"`. DesertFox draws a box around the item in a shadow root, because sites often remove the focus outline. The box follows scroll and resize with the follower the hint labels use, and clears when focus leaves the item (Escape too), when the mode is no longer normal (read on a 100 ms timer, which also moves the box after a layout shift, because a bundle cannot subscribe to mode changes) and when the item leaves the page. The same box is the shared focus mark: `item.mark` draws it on the element that `]l`, `[l`, `]i`, `[i` and the `;ff` hint action focus, only when the page's own focus style is invisible (the element's computed outline, box-shadow, border, background and text colour read the same focused and unfocused, so a site that marks focus by colour or border shows no second mark), never for an element in a frame, and with no setting. It does not use the shared surface code, which would have taken the bundle over 10 KB: the box has the default colours, takes no user theme and sits in the page's stacking order, not the top layer.
- Item mode is a real mode (`item`) with its own keymap section `[item]`, and the tab holds it, as it holds media mode. `I` hints every list and grid of the page (`hint --lists`, no height rule) and starts the mode on the pick, which makes that list the one j and k walk and lands on its current item. With one list it picks at once, and with none it shows a notice and stays in normal mode. `f` and the `;` hints label the whole page. When the mode is item, the hints bundle asks the item bundle's `item.current` (the item that holds the focus, else the last one moved to while it is on the page) and puts that item's targets first in the label order, so they get the shortest labels, one letter on a page with few targets and two on a busy one. All labels keep one color, and hints across frames stay unranked. A grab's drop pass stays page-wide, and Escape in item mode, then a hint key, labels the page again. `<Space>` and `<Enter>` are `page.item_action` (`toggle` and `open`, the `item_act` bundle, `item_act.js`, loaded on the first press). Both ask the item bundle for the current item and its link (`item.current`) and click with the hint click, the full pointer and mouse sequence. Toggle clicks the first shown native checkbox of the item, else the first shown element with role=checkbox, or what a site row's `target` selector finds in its place (`page.item_action --action=toggle --target=.star` on `<Space>` in the row's `item` column). A checkbox that ignores the hint click needs a `target`. The click is not checked. Open clicks the element that `page.item_focus` last focused while it still has the focus, else the item's link (the row's `link` selector, which finding nothing means no link, else the finder's link, else for a row with no `link` the item itself when it is a link or its first link), and it does not record the page in the jump list. `<Tab>` and `<S-Tab>` are `page.item_focus` (`next` and `prev`, same bundle): they focus the next or previous shown focusable element inside the current item (the item root counts when it takes focus) and wrap at its edges, so the focus stays in the item and the box stays on it. An item with a single focusable element (its link) steps on through the page's focusable elements in document order from the focus, as the browser's Tab does, and one with none refuses with "Nothing to focus". The ring skips text fields (what `is_editable_element` takes for typing: text inputs, textareas, contenteditable), because focusing one starts insert mode, which ends item mode. Checkboxes, radio buttons, buttons, links and selects stay in it. Each refuses with a notice when it has nothing to act on: "No current item", "No checkbox in this item" or "This item has no link". Visual item mode (`item_visual`, badge `VISUAL`) has its own section `[item_visual]`. `v` in item mode enters it, with the current item as both ends of the selection. `j`, `k`, `h`, `l`, `gg`, `G`, `}` and `{` move the cursor end (`page.item` with `extend`) and `o` swaps the ends. A row that names its items (`selector`, `link`, `section`) keeps them: every visual move reads the list of the item mode move before it. `I` ends the selection and picks a list as in item mode, with the finder's lists (a row's own `I` is not bound there). `<Space>` (`page.item_action` `toggle_range`, `item_act.js`) sets every native or role checkbox of the range to the opposite of the anchor item's state, skips items with none, refuses when the anchor has none and shows how many it changed. It reads the range again before each click, so a page that draws its list again on a click still gets every box set. It ignores a row's `target`. `<Enter>` and the other keys are unbound there. Each item of the range gets a mark (an outline in the item colour), and the badge says `VISUAL 3` with the size of the range, also when the list sits in a child frame. The selection keeps item keys (link address, else `data-id`, else row index), so it follows its items when the page draws the list again. An end whose item left the list takes the item now at its place, and an empty list ends the mode with the notice "Selection gone". `v` or Escape in the mode returns to item mode, and a second Escape goes to normal mode. The tab holds it as it holds item mode: a frame that reports `item_visual` keeps the hold, and only the frame that entered it is in the mode, so the other frames stay in item mode and a frame that loads later joins as item mode. A key typed behind the pick waits until the whole leaf of `I` has ended (content.js hands the hints bundle the end of the leaf that ran last), so a key typed behind it moves on from the landing. A page that goes away ends the wait. Escape in the picker leaves normal mode as it was. In a frame, only the keyboard frame's lists are labeled. Inside the mode `I` picks another list. While a site row's items show, `I` in normal mode offers only the row's list (`row_only`), so it starts at once. `I` inside the mode offers the row's list first, then the lists the finder found that share no item with it. Picking one of those pins it: the row's j, k, gg, G and the landings walk it as the finder's keys do, with no row selector, until a pick of the row's list, `item.start`, an address change or the list leaving the page. A row that selects with arrows (Drive) offers the row's list alone in both modes, because the arrows cannot walk another list. DesertFox gives every site row with an item selector, a user row too, `I` for the row's own items, and `zt`, `zz` and `zb` in item mode (`item_landings.ts`, at compile time, under the row's own binds). The section binds j, k, h, l, gg and G to `page.item` with no selector, `zt`, `zz` and `zb` to the current item followed by `scroll.align` top, center or bottom, and copies of the keys of normal mode that stay useful in the mode: `J`, `K`, `gt` and `gT` for tabs, `<C-d>`, `<C-u>`, `<C-f>` and `<C-b>` for page scroll, `:` for the command line, `?`, `<A-?>`, `<F1>` and `g?` for help, `f`, `F` and the whole `;` hint group (its modifier variants too) as hints that rank the current item first (below), except `;fF` and `;fe`, which stay in normal mode, `/` for find, `<Space>` and `<Enter>` (below), `]]` and `[[` for the page series, `<C-o>` and `<C-i>` for the jump list, `H` and `L` for history, `gi`, which focuses a field and so leaves the mode, `aa` and the rest of the `a` media group with `A`, `i`, `V` and `gV` to start insert, caret and visual mode, `n`, `N`, `*` and `#` for find, `<S-Escape>`, `<S-Insert>`, `<AC-Escape>`, ``<AC-`>`` and `,i` for ignore mode, and `<C-v>`. Of these, `aa`, `i`, `V`, `gV` and the ignore keys end item mode, since they start another mode. `v` is not a copy: it starts visual item mode (below). Escape in media mode that began in item mode goes back to item mode in every frame, and a media step takes a frame in item mode as an item step takes a frame in media mode, so either order of the two steps ends in item mode. A fullscreen that starts in item mode starts media mode, and its end goes to normal mode. Counts work as in normal mode. A key the section does not bind goes to the page. With no list on the page, j, k, h, l, gg and G scroll as the plain keys do, so the mode costs nothing on a page without one. Entering the mode writes no setting. The hold is `src/background/tab_item.ts`, in `storage.session`, and follows the media hold: the first frame to report item starts the mode in every other frame of the tab (a `MediaStep` with `item` set, which a frame in normal mode or media mode takes and a frame in a field, a hint or the command line ignores). A frame of the hold that reports any mode but item, hint or command line ends the mode for every frame, so Escape in any frame, or a field taking the focus, ends it for the tab. A frame that loads late joins through the reply to its first keymap read (`join: "item"`, after the insert and media holds). A child frame of the hold that reloads or navigates keeps the mode: `webNavigation.onCommitted` marks it before its new document reports, the report of normal that the new document sends first is ignored, and the reply to its keymap read puts it back in the mode. A load of the tab ends the hold, and an address change the page makes itself keeps it. A step that reaches a frame after the hold ended is a stepped report, and the background sends that frame back to normal, as in media mode. In a field the mode ends the way media mode does: the frame goes to insert and, since it left item mode, the tab leaves it. The shipped result rows (`default_site_rows.ts`) bind their item keys in their `keymap.item` column, so on those pages j and k scroll in normal mode and walk the items in item mode. A user row can do the same with `[site_rules.keymap.item]`. The `item_hover` setting still fills the `hover` arg of the shipped item keys and rows (`src/background/compile.ts`). The `item_navigator` setting means "list pages start in item mode". It takes three values: `shipped` (the default) starts the sites of the shipped rows, `true` every page with a list, and `false` none. It is also a per-site setting. The shipped rows with a `keymap.item` column set it to `shipped`, which follows the global value unless that is false. A user row with its own value comes first in the table and decides its site. With no row value only a global `true` starts a page. When a tab finishes loading and the setting is on for its address (`item_start_for` in `src/background/page_keymap.ts`, the site row first and the global value as the fallback), and no row binds or passes j or k there in normal mode, the background reads the top document that completed (`webNavigation.getFrame`) and sends `item.start` to that document alone (`tabs.sendMessage` with its `documentId`), so a reload meanwhile, even at the same address, does not take the start. The start carries the item selectors of every item key and guarded choice the page's rows bind. The item bundle then waits for an idle moment and looks for the rows' items, again every 250 ms until 5 s after the ask, by the clock, while the site draws them (Drive draws its files late), or with no selector runs the finder once. It enters item mode only if it finds a list, the frame is in normal mode with no field focused, and the user has not pressed a key or clicked in the page since it loaded (the key count of content.js, since user activation misses Escape and the other keys that type nothing). Each look reads that gate again right before it enters, and a key, a click, a field or another mode ends the wait. A box drawn in item mode clears when the frame leaves the mode by any route. It asks once per document, so a page that the user left item mode on never starts it again. The hold sends its steps without waiting for them inside its queue, which every tab shares, so a frame that never answers holds up no other report, join or keymap reply. `page.item` with no selector reads the item finder (`src/content/item/finder.ts`), which answers a list, a grid or `none` from the boxes and links of the page. It gives a list only when it is sure: three or more items in three rows (two rows when the block starts in the left half of the main column, so a top-stories block counts and a side rail does not) that each hold a title link, spanning most of a screen (for the first list and for the start on load, a shorter list is kept as a short list that only a pick makes active), and no great body of prose around them. A page with several such lists (a feed and its side rails, a video and its related videos and comments) keeps all the top-level ones. A widget that declares itself a `listbox`, `grid`, `feed` or `tree` (a web app's inbox, channel list or post feed) is a short list too: `src/content/item/aria_lists.ts` offers it to the `I` picker whatever its items hold, so rows with no title link count, and it never starts item mode on load or wins a hand-over. Its items are the `option`, `row` (a `tr` with no role in a grid counts), `article` or `treeitem` elements it shows. A tree is flat: a branch is an item and stands for its own label. The link of each item is the item itself, so Enter clicks the row. A widget in a dialog (native, `role=dialog`, `role=alertdialog` or modal) or a menu, a combobox popup, a grid whose rows all hold under 16 characters (a calendar), or one that shares items with a finder list is left out. A widget that names its active row with `aria-activedescendant` keeps the focus: item mode draws the box and moves nothing. The pass stops at the finder's time budget, adds nothing then, and leaves the lists found before it in the answer. One is active: the first press takes the list with the most area in view, and the larger list wins a tie. The active list stays while any of its items shows. Once none shows, the next press takes the list with the most area in view, so scrolling alone changes nothing and a held j never crosses from the end of one list into the next. With no list in view the active one stays, and the page is read again once the answer is 500 ms old. With `none`, and with no item shown, the four keys scroll 50 px per count as the plain keys do, h and l do so on a list too, and content.js scrolls the same way when the item bundle cannot load. The first press moves only to an item in view, else it scrolls. The answer is kept per document and read again when the active list's first item has left the page or the address changed, and, at the end of the list, when a down move or a poll of gg and G finds something new after the last item. A `none` answer stands for 500 ms. The first read at an address stops at 400 ms, so a long page answers once, with a pause on that press: a press past the budget scrolls, and the next press reads the page again. A `none` read again at the same address stops at 40 ms and keeps the old `none` when it runs out, so a held j on a long text page scrolls without stalls. A second timeout in a row stands for 500 ms like a `none`, and puts the address on 40 ms for 10 s. gg and G go to the first and last item as on a bound row, but land on the end item only when it is in view after the scroll, so a list that starts screens down gets a plain scroll and the next j does not jump back. With no item they refuse, and content.js scrolls to the top or bottom, as it does when the bundle cannot load. `]]` does not carry the box onto the items a load adds. With a row selector it does, in normal and item mode alike. Article pages answer `none` until the article kind exists. `}` and `{` jump to the first item of the next section and to the start of the current section, then of the previous one, using the sections the finder records for front pages. A row names its own with `section` on its own `}` and `{`, and a row with item selector and no keys of its own gets the finder's sections. A page with none shows a notice. A thread row binds `}` and `{` to its sibling comments with a guard, and a failed guard runs this default.
- Item mode carries across a same-tab load to the same host. When the top frame starts a load while the item hold is on (`tabs.onUpdated` with `status: "loading"` and no `url`), `tab_item.navigated` writes a resume mark for the tab in `storage.session` (`ITEM_RESUME_STORAGE_PREFIX`) with the address the load leaves (`tab.url`, still the old page then), and ends the hold. The top frame's `webNavigation.onCommitted` keeps the mark only for `transitionType` `link` or `form_submit` without the `forward_back` or `from_address_bar` qualifier, at an address on the same host and port. So Enter on an item, `]]`, `f` and the site's own links and forms keep it, and a reload, Back, Forward, a URL bar address or bookmark, and a link to another host drop it. No helper knows the registrable domain, so a subdomain counts as another host. Firefox reports Back and Forward as `link` with `forward_back` (measured in `p49_item_start`). A load that DesertFox starts in the tab commits as `link` too, so `:open`, quickmarks, the home page and the mark and jump moves to another page end the hold and drop the mark before their `tabs.update` (`end_for_own_load`, wired into `open_target.ts` and the `navigate` deps). A toolbar or menu bookmark also commits as `link` with no qualifier, so it keeps the mode on the same host. A commit more than 30 s after the load began drops the mark, and so does a later load that starts with no hold while the mark has no commit, so a load that never commits (a download, a 204) carries nothing. A kept mark survives a redirect of the new page before it completes. Child frame commits leave the mark alone. When the load completes, `take_resume` spends the mark, and a kept one asks `item_start_for` with `resume`, which starts any page with a list whatever `item_navigator` says, unless the page's own site row sets it to `false`, turns the keys off or claims j or k. The content side is the usual start, so a page with no list stays in normal mode and the mark is gone. A list page left while it still loads also resumes (measured). Closing the tab clears the mark.
- Thread trees. `page.tree` (the `tree` bundle, `tree.js`, loaded on the first press) moves through items that nest, by depth. A site row names the item selector and where the depth sits: an attribute of the item, of an element inside it (`depth_from=inside`, `depth_at`), or of the closest ancestor (`depth_from=above`). `parent` goes to the nearest item above with a lower depth, `child` to the next item when it is one level deeper, `next` and `prev` to the nearest sibling in that direction without leaving the parent, and a count repeats a move. Items that the page hides drop out of the list, so a folded thread has no children and its siblings stay reachable. `child` on a folded item unfolds it and stays. `fold` folds the item with its replies, or its parent when the item is a leaf or folded already. `unfold` and `toggle` act on the item itself. A fold clicks the row's own fold control (`fold`, a selector in the item) with the hint click, reads the state from the row's `folded` selector (matching the item, an ancestor or an element inside it), and checks nothing after the click. A move lands through `page.item` with the current-item direction, so focus, scroll, the box and the last move match j, and it starts from the item that holds the focus, so each run takes the focus first. A run holds the keys behind it until it lands (`hold_keys_until_`), so a key typed during the first load, a second `l` or a `j`, starts from the item the run leaves. A failed call to the item bundle refuses with its message. Failures show a notice: "No parent", "No next sibling", "No previous sibling", "No child", "Nothing to fold", "No current item" and "No fold control in this item". The Hacker News row binds `h` parent, `l` child, `}` and `{` next and previous sibling, `za` toggle, `zc` fold and `zo` unfold in its `item` column, each guarded by `when_present = "tr.comtr"`, so on a page with no comment h and l keep their scroll. Item mode starts on its pages through `item_navigator`. The Reddit thread rows (`/r/*/comments/*`) bind the same keys on the head of a comment (`shreddit-comment > details > summary`), with the depth on the closest `shreddit-comment`, the head as the fold control and `details:not([open])` as the folded state. They keep item mode off: the user presses `I`. Replies the page has not loaded are not items. On Reddit the item is the author line only, so the long-item rule does not apply there: `j` moves on to the next author line even when the text of a comment runs past the window. Measuring the author line and the text as one item is a planned follow-up. Item mode's default `h`, `l`, `{`, `}`, `za`, `zc` and `zo` are guarded in the default keymap: they run `page.tree` with `preset = "aria"` while the focus is inside a `[role=tree]` (`when_present = "[role=tree]:focus-within"`, which body focus never matches, so a page that shows a tree keeps the plain keys until the focus is in it), and otherwise run the step they had (`fallback`, which only the default keymap may set), so on a page with no tree h and l still scroll sideways. The preset walks the treeitems of the tree that holds the current item, reads the depth from `aria-level` (or, when a nested tree leaves it out, from the count of treeitems around the item) and the folded state from `aria-expanded=false` on the item itself, takes the parent as the closest treeitem around the item (a `role=none` or `role=group` wrapper is not one, and a tree whose items do not nest falls back to the depth), and folds by `fold_by = "keys"`: ArrowLeft and ArrowRight through `page.send_key` with both `key` and `key_code`, to the focused treeitem, because tree widgets read the key code. `l` on a folded item only opens it, since a lazy tree fills its children later. `za` on an item that cannot fold (no `aria-expanded`) refuses with "Nothing to fold" and sends no key. A tree with `aria-activedescendant` holds the focus itself, so the tree step runs and refuses with a notice. The landing picks the deepest item that holds the focus, and a focused treeitem stands for the label the finder lists for a branch, so j and k go on from it. `I` stays the way into the tree.
- Recipes for sites on any host, which no shipped row can match. Discourse has its own j and k, so a user row hands them over: `[[site_rules]]` with `site = "https://forum.example.org/*"` and `pass = "j k"`. phpBB has none, so a row binds them to `page.item`: `bind = { j = { id = "page.item", args = { selector = "ul.topiclist li.row", link = "a.topictitle", direction = "down" } }, k = { id = "page.item", args = { selector = "ul.topiclist li.row", link = "a.topictitle", direction = "up" } } }` (and `.post` for a topic page).
- `site_actions.js` holds the handlers of `page.send_key` and `page.clipboard`, which site rows bind to keys and which share one per-page queue. `page.clipboard` focuses its target and calls `document.execCommand` for cut, copy or paste, so the page gets the browser's own trusted event (a synthetic Ctrl+X or Ctrl+V keydown does nothing). A paste that fires no event falls back to reading `navigator.clipboard` and dispatching an untrusted `paste` event with that data. The shipped Sheets rows bind `x` and `p` to it and pass `<C-a>`, `<C-x>` and `<C-v>` to the page. A site bind of `x` or `p` replaces the default `xx`, `xp` and `pp`, `pt`, `pw` sequences on that site. The content script loads it on the first press, with the other bundles.
- `next_page.js` holds `page.follow` (`]]`, `[[`) and loads on the first press. A pure detector decides and answers follow, click, scroll or nothing. It reads the page through an interface of boxes and layout flags, so the suite in `test/fixtures/next_page/` runs it on saved pages. A `rel` link wins. Then the best next word, matched as a whole word in a text of at most five words, skipping controls in carousels, in video players and inside one item of a repeated list. `]]` in place then tries the load step. It finds the page's main list (the repeated block with the most area) and clicks the lone control right after its last item, with the load words only breaking ties. With no control, it scrolls to the end of the list, but only when the list ends within half a screen of the page end, so an article does not jump. After a click or a scroll it watches up to 3 s for added content and shows "Nothing loaded" when none came. One load runs at a time: `]]` during a pending load does nothing. A page that hides during the wait shows no toast when Back restores it. A load click on a link that leaves the page is a move for the jump list. When a `page.item` box shows at the press, the box moves to the first item that follows the old last item in document order, once one arrives within the same 3 s. It follows the element, not the old count, because a page that drops or virtualizes the items above shifts every index. With the old last item gone, the last old item still on the page stands in. The box stays put when the user moved it to another item or the frame left the mode of the press (normal or item mode) during the wait, which another frame can also end. `more` left the `next_patterns` default for the load step, and a list that still holds it has it dropped when the settings are read.
- `grab.js` holds keyboard drag (see "Grab" below): the `grab.mode` pick handler, `grab.move`, `grab.drop` and `grab.cancel`, and the sink of grab mode. It loads on the first grab pick.
- `editor.js` holds `text.edit_external` (see "External editor" below). It loads on the first press.
- `media.js` and `quality.js` are the bundles the content script does not load. The background injects them into every frame of the tab for each `media` command (see the `a` group below).
- `cmdline.html`: an extension page in an iframe. It has its own bundle with completion and fuzzy matching.
- Imports between `src` folders run one way, so a file's runtime shows from its path. `src/shared` imports only itself. `src/content`, the page folders (`help`, `newtab`, `popup`, `devtools`, `cmdline`) and `src/commands` import their own folder and `src/shared`. `src/commands` also imports `src/background`, `src/cmdline/host.ts` also imports `src/content` (it is a content bundle), and `src/background` imports `src/commands` only in `command_modules.ts` and `main.ts`. Within `src/content`, a bundle folder imports only itself, the content root files, `src/content/lib` and `src/shared`. `lib` imports the root and `src/shared`. The root imports no bundle folder. `src/cmdline/host.ts` stays the one other importer. `src/content/handlers/` is core content code, so the root can import it. `media` imports `quality` as the one permanent exception. `test/import_boundaries.test.ts` enforces both rules, type-only imports included, and `test/import_boundaries.ts` lists the exceptions that remain.

### Content script root files

Behavior of the files in `src/content` itself, moved here from its README. The README keeps one line per file. The key, mode and badge files are under "Key flow and mode reports in the content script" in `keys.md`, the which-key files under "Which-key content files" in `interfaces_pages.md`.

The content script. It runs at `document_start` in every frame. A subframe starts on its first focus (`start_content_once` in `handlers/focus.ts`). Until then its loaded flag `desertfox_content_loaded` holds the start, so `hint --all-frames` can start the frame from the hints bundle. This costs content.js 28 bytes, under admission clause C. Every frame asks the background for its keymap, already trimmed for the page's site rule, so the content script holds no rule logic.

A property name that ends in `_` is internal, and the build (`tools/build.mjs`, esbuild `mangleProps`) shortens it in every bundle with one shared cache. Add the `_` only to a name that stays inside the extension scripts. Never to one that crosses storage, a runtime message, a port, the manifest, a DOM attribute or CSS, a page or browser API, or a file on disk. The key test reads `desertfox_host.get_mode()` through the debugger, so that one method of the bundle API, `get_mode`, stays unmarked.
- `main.ts`: the capture listener, messages and mode wiring, and the `blur_on_load` window that blurs a field the page focuses as it loads, or hands its focus to the `focus_on_load` match (`p24_site_blur` and `p25_site_maps` test it). It keeps the promise of the leaf that ran last and gives it to a bundle as `leaf_end_` on the page host, which never rejects: the hints bundle holds the keys typed behind an `I` pick until it settles. Not unit tested, it needs a DOM.
- `strip_setting.ts` and `shared/copy/strip_tracking.ts`: the `strip_tracking_params` copy rule. `strip_tracking` drops the listed query parameters from a web address and leaves the rest byte for byte. Pure and import-free, used by the page and hints bundles and the background, never `content.js`. `strip_setting.ts` asks the background (`read_strip_patterns`) for the names to drop on a page address: the global list when the site's `strip_tracking` is on, else none.
- `shared/copy/link_list.ts`, `shared/copy/link_escape.ts`: the lines of a copied link list (Markdown, Org, plain, title) and the bracket escaping they use. Pure and DOM-free, shared by `hints/yank_links.ts` and the background `copy.tabs`; `is_web_address` is the one rule for which addresses count.
- `ask_keymap.ts`: asks the background for the page's keymap at start and on `tree_updated`. A rejected ask (the background has not registered its listener yet) is retried 30 times, 100 ms apart, and then the page gets the empty tree. The newest ask wins. Pure.
- `item/`: the `item` bundle, `page.item` and visual item mode, see its README.
- `item_act/`: the `item_act` bundle, `page.item_action` (Space and Enter in item mode), see its README.
- `tree/`: the `tree` bundle, `page.tree` (h, l, { and } through nested items, and the fold keys), see its README.
- `bundle_calls.ts`: the type map of the handlers bundles call in each other, or the background relays to (the ids that are no registry command, and the registry ids a bundle calls by hand): id to the bundle that registers it and the args it takes. `register_handler_` and `run_command_` read it, so a wrong bundle name or a wrong arg shape fails `tsc`. An id outside the map takes `Record<string, unknown>`. Types only, so it costs no bytes. `test/bundle_handlers.test.ts` checks each entry against the bundle that registers it.
- `bundle_host.ts`, `bundles.ts`: load bundles on first use and keep what they register. A bundle is a script the background injects into this frame (every name in `BUNDLE_NAMES` in `src/shared/bundles.ts`). `media.js` is not one of them: the background injects it itself and it talks to the background alone (`media/README.md`). It registers a sink per mode and a handler per command, and enters its mode with `set_mode_`, through `window.desertfox_host`. A bundle can also call a handler of another bundle with `run_command_`, which loads that bundle first (search does this between `caret.js` and `cmdline.js`). The host also gives a bundle `scroll_box_`, the box the vertical scroll keys move, after it ends a smooth scroll in flight (that state lives in `content.js`). `run_command_` answers an `Outcome` (`src/shared/messages/content.ts`), the handler's real one, which stays pending while the handler waits on the user. `bundles` is the one instance. A bundle may run twice, for example after a missed deadline, so its setup must be safe to repeat. `sink.exit()` may run after the sink has already cleaned up. A mode with a sink is set only once its sink is in: the hints and cmdline bundles set their own modes, and a caret mode is set by the caret bundle's `caret.mode` handler, which `set_mode_` in the host calls when `caret.js` is not in yet. While `caret.js` loads, every other mode change (a focus move, a `set_mode` message, a bundle's `set_mode_`) waits behind it in order (`in_mode_order_`), so a sink sees enter and exit in the order the changes came. The badge, `get_mode` and the `mode_changed` report show a caret mode only once `caret.js` has set it.
- `player_box.ts`: the element that goes fullscreen for a media element, shared by the `fullscreen` hint action and the `media fullscreen` command. Pure.
- `align_target.ts`: which element `scroll.align` moves into place. Pure, the DOM side builds the candidates.
- `badge_hosts.ts`: marks every badge host so a cleanup never touches page elements. A reload of the extension leaves the old host behind, and this removes it.
- `shadow.ts`: `shadow_root_of`, which reaches a closed shadow root through `openOrClosedShadowRoot`.
- `relay.ts`: a bundle in a subframe asks the background to run one of its handlers in the top frame or in another frame of the tab. The allow list and the direction of each handler are in `src/shared/relay.ts`. The command line, which-key and the toasts use it, so they draw in the top frame for a subframe that holds the keys.
- `hidden_frame.ts`: the size test for a hidden input frame, a child frame the user cannot see, which a page keeps to take typed text. In normal mode such a frame hands the focus to the document that holds it (`hand_focus_to_parent` in `handlers/page.ts`, called one tick after each mode report, and at once after Escape blurs the field), and `gi` in that document finds the frame's field (`page/focus_input.ts`). Pure.
- `invocation_args.ts`: applies a command's count rule. Pure.
- `scroll_target.ts`, `editable.ts`: helpers for scroll choice and focus. `editable.ts` holds the frame's `editable_add`, `editable_remove` and `editable_remove_unsized` rules, which `main.ts` sets from the page keymap reply. `pick_scroll_target` takes the frame's `scroll_selector` match first (`handlers/scroll.ts` holds the selector). The scan of the whole page that finds the largest scrolling box does not run on every key: `scroll_target` keeps its pick per axis in a weak reference and reuses it while the box is connected and still scrolls on that axis. A `focusin`, a `pointerdown` or a 1 s pause between scroll keys drops it. A bundle asks the host's `is_editable_` instead of its own copy.
- `smooth_behavior.ts`: `"smooth"`, or `"instant"` while the page asks for reduced motion. The page scroll keys and the grab bundle's snap swipe use it, and it checks the media query on every call.
- `scroll_box.ts`: whether an element is a box that scrolls (`candidate_of`), used by the scroll keys and the `scrollable` hint filter.
- `run_content.ts`: runs one invocation, or a list in order, and answers an `Outcome` that never rejects: nothing returned is done, a throw is failed, and `cancelled` means the user left a wait. The caller shows a failure once. `run_content_steps` runs a leaf of content steps in order, each after the one before has finished. A leaf with any background step skips it and goes to the router whole (`run_leaf_` in `main.ts`), which reads the active tab per step. A leaf of content steps sends a `record_step` message with its outcome when it ends (not for a held key's repeats), which the background keeps for `.`.
- `leaf_for_page.ts`: `leaf_for_page` picks the leaf under a site bind's guards first: the bind while its `when_focus` holds (nothing has focus, or the focused element sits on or inside a match) and its `when_present` holds (the page shows a match, `shown.ts`), else the next leaf of its `otherwise` chain (the next choice, then the leaf it replaced), else nothing. The which-key bundle shares it (through `whichkey/guarded_rows.ts`), so `run_leaf.ts` stays out of that bundle.
- `shown.ts`: `is_shown`, the visibility rule that `page.item`, `page.click` and the `when_present` guard share: a box, and not hidden by `visibility` or opacity.
- `pointer_events.ts`: the pointer and mouse events of a real mouse, shared by the `;h` hover pick (`hints/hover.ts`) and the item box hover (`item/hover.ts`): `dispatch_mouse_event` sends one event (pointer type mouse, primary, composed where the event bubbles, with `relatedTarget`), `enter_events` and `leave_events` send the enter and leave sides of a move along the ancestor path (shadow hosts included).
- `user_left.ts`: `watch_user_left` marks the user as gone when the tab hides or a trusted key (not a repeat or a bare modifier), wheel or pointer press comes. A scroll and a window blur alone do not count. The wait starts the watch after the press and stops it when it ends. The `next_page` bundle reads it during a load wait and the `item` bundle while `page.item` follows the end of a list for `first` and `last`.
- `handlers/`: one plain function per content command. `handler_map.ts` is the only id-to-code link. The count rule is not on the handler. The command definition in `src/commands` holds it, and the background compiler puts it on each `LeafStep` as `count_rule`.
- `surface.ts`, `toast.ts`: the closed shadow root in a top-layer popover host (above modals) and the message surface, for refusals and for error, warning, info and success notices. `surface.ts` also fills each surface with its theme and user CSS sheets after the built-in style (see `shared/theme/apply.ts`), one storage read and one change listener per bundle. The lazy bundles import it, never `content.js`.
- `ui_proxy.ts`, `ui/main.ts`: `show_toast_` and `show_mode_label` as the rest of the script calls them. They ask the `ui` bundle (`ui.js`), which holds the toast and the badge, and a call made before it loads waits and runs after. Neither holds keys. While the document is still loading, a plain NORMAL badge (no pass-next, site label or recording) waits for the `load` event, because drawing it earlier measurably slows the page load. Any other state, a hide or a later call draws at once and cancels the waiting draw. A page whose `load` never fires gets the badge after 2 s. In a subframe, `ui/main.ts` sends each toast to the top frame, and draws it in the subframe only when the top frame does not answer. In the top frame, `ui/frame_hide_watch.ts` checks the child frame that holds the focus every 300 ms while the background says one does (`frame_mode`), and takes the focus back when that frame turns transparent or shrinks. content.js turns it on through `ui.frame_watch`, so the bundle loads when a child frame first takes the focus. A frame of another site cannot see its own frame element, so the child cannot watch itself. The help page loads `ui.js` by script tag, because `executeScript` is refused there.

`data-desertfox-tree-read-ms` on the document element is the one test hook allowed in `src/`. The key test reads it as the signal that the content script is ready. The badge's `data-desertfox-mode` and the which-key panel's `data-desertfox-whichkey*` attributes are the same kind of hook. A page can read all of them, so they exist only in the key-test build (`KEY_TEST_BUILD` from `src/shared/key_test_build.ts`, set by an esbuild define in `tools/build.mjs` with `KEY_TEST_BUILD=1`) and the release bundles carry none. `data-desertfox-layer` stays in the release build.
