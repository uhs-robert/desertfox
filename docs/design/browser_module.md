# The browser module

Area: the browser module, the optional second tier beside the native host.
READMEs: `browser_module/README.md`.
Source: `browser_module`. The channel it reads is in [host.md](host.md#browser-module) and `src/shared/browser_module_protocol.ts`.

## What it is

A content script never runs on Firefox's own pages, the restricted sites, the PDF viewer or Reader View. It also misses a tab that has not committed its page (see [Constraints from Firefox](../design.md#constraints-from-firefox)). The browser module takes DesertFox's tab and scroll keys there. It is a set of plain script files that Firefox loads with browser privileges from a drop-in folder. It is not in the xpi, and the extension and the host never install, download or load it.

- The user installs it with `sudo browser_module/install.sh`, and removes it with `--uninstall`. The script copies every `desertfox-*.js` file of the folder into `chrome.d` in the Firefox install folder (`DESERTFOX_FIREFOX_DIR`, default `/usr/lib/firefox`) as root, mode 0644. It refuses a folder that is missing, a link, not owned by root, or writable by group or others. It never creates the folder or touches `mozilla.cfg`. A loader must already read the folder. Oasis Dots ships one.
- The loader contract: a regular `*.js` file in `chrome.d` runs once per browser window, after `browser-delayed-startup-finished`. Files run in name order, each in its own `try`, with the window as the global. The loader skips a link and a file the browser user can write.
- Two switches. The Firefox pref `desertfox.browser_module.enabled` is the kill switch. It is unset (off) by default, so the user sets it to `true` in about:config. The setting `browser_module` is the extension's consent to write the state. Both must be on.

## Files

- `desertfox-browser.js` is the core. It reads and checks the state, says the hello and reads and writes the message lists. It decides whether a key is DesertFox's to take on this page. Its frame script reports each document.
- `desertfox-statusbar.js` draws the status bar (see the next section). It is not a command feature.
- Each feature is its own file that sorts after the core (`desertfox-tabs-scroll.js` runs `tab.next`, `tab.prev`, `scroll.lines`, `scroll.pixels`, `scroll.pages` and `scroll.to`, `desertfox-panes.js` answers the pane kinds, `desertfox-cmdline-panel.js` opens the command line panel, `desertfox-devtools.js` takes the tree keys and runs hints in DevTools, see [DevTools](#devtools), `desertfox-popup-walk.js` walks menus and panels, see [Popup walk](#popup-walk), and `desertfox-chrome-hints.js` hints Firefox's own UI, see [Hints over Firefox's own UI](#hints-over-firefoxs-own-ui), and `desertfox-firefox-pages.js` opens Firefox's own pages, see [Firefox pages](#firefox-pages), and `desertfox-selection.js` reads the page selection of an about: page, see [Selection on locked pages](#selection-on-locked-pages)). A later feature adds a file and touches no other.
- `desertfox-commands.js` is generated: `tools/build_browser_module.ts` (`just browser-module`) bundles `browser_module/sources/commands.js` with the extension's matcher (`src/shared/keys/matcher.ts`), token (`src/shared/keys/token.ts`) and tree check, so both sides read keys with one code. The file is committed, because `install.sh` copies the checkout and runs no build. `test/tools/build_browser_module.test.ts` fails when it differs from a fresh build, so a change to the bundled code needs `just browser-module` in the same PR.
- `desertfox-whichkey.js` is generated the same way, from `browser_module/sources/whichkey.js` with the page panel's sheet, layout, element tree and timer (`src/content/whichkey/style.ts`, `layout.ts`, `render.ts`, `timer.ts`). It draws the which-key panel on locked pages, see [Which-key on locked pages](#which-key-on-locked-pages).
- The core lives in a system sandbox that the first window builds by loading the core file into it, once per process. A listener the process keeps then holds no closed window alive. In a window, the core file only attaches the window, and a feature file only asks the core to load it into the sandbox (`adopt`). The core loads only files from its own folder.
- The surface for feature files, on `Services.desertfox_browser_module`: `define_command(id, { args, run })`, `add_frame_script(fn)`, `register_kind(kind, handler)`, `send(kind, args, on_reply)`, `claim_devtools_keys(fn)`, `on_hello(fn)`, `watch_session(keys, fn)`, `log_once(text)`, `set_hello_flag(name, on)`, `take_keys(taker)`, `run_command(id, args, context)`, `module_pending(win)`, `watch_pending(fn)`, `take_held_keys(win, end)`, `may_act(win)`, `on_shut_down(fn)`, `sidebar_row(win, keys)`, `chrome_hint_keys(win)`, `token_of(event)`, `is_field(element)`, `deep_active(doc)`, `focused_element(win)`, `ime_in_field(win)`, `type_key(win, key, still_holds)`, `hold_keys(win, owner)`, `release_keys(win, owner)`, `keys_held_by(win)` and, in a window, `adopt(file_url)`. `args` names the shape of each arg (`int`, `number`, `enum` with `values`), and the core runs `run({ window, browser, tab, args, repeat })` only for a row whose args fit. The header of the core file documents each call.
- A feature file ends a failed start in one of two ways, and a feature that started halfway never takes keys. It lets the error throw, and the core turns the whole module off for the session. Or it catches the error, undoes what it registered, logs one line with `log_once` and stays off alone, so the rest of the module keeps running. The popup walk and the chrome hints take the second way, because a menu walk that fails to start is no reason to drop the tab and scroll keys.

## When the module takes a key

All of these must hold, checked on each keydown in the capture phase of the browser window. Otherwise the key goes on as if the module were not there.

1. The event is trusted, not part of an IME composition and not prevented. The pref is `true`.
2. The key is for a tab's page. A key in the browser UI, DevTools (docked toolbox or any panel), a sidebar or a popup is not. Its document is no content document of a tab browser. So DevTools' own keys keep working. The one exception is the DevTools feature's table, below.
3. DesertFox is running, and in a private window it has private window access.
4. The state is valid: the right `v`, `enabled` true, unknown fields ignored. The module applies the protocol's limits (32 key rows, 1024 tabs) and checks each field it reads, so a state past them claims nothing. An extension reload empties `storage.session`, so the module takes nothing until the new extension writes the state again.
5. The key's token (the same normalization as `src/shared/keys/token.ts`) has a row whose command a feature defined, with args of the right shape. With the commands feature loaded, the feature decides instead, after checks 6 to 8 (see [Keys on locked pages](#keys-on-locked-pages)).
6. The focus is not in a field. A page in the parent process is read directly: the deep active element, the event's own target and design mode. A remote page is read from its frame script's report. A key can come before the report. The window's input state (`windowUtils.IMEStatus`) covers it, because Firefox sets it when a text field takes the focus.
7. The tab is in normal mode. A tab the state does not list is normal and not live.
8. DesertFox is not live in the shown document. No report for the current inner window counts a DesertFox keydown listener, and the tab has no live mark. A report from an older document of the tab does not count.

The module runs the command first, then prevents and stops the key in the parent, so the page and the content script never see it. A command that throws leaves the key to the page. Tab keys run `advanceSelectedTab`, which wraps. Scroll keys go to the feature's frame script. It scrolls the focused element's scrolling ancestor, else the page when it scrolls. Else it scrolls the largest scrolling box, such as the settings pane of about:preferences or the PDF viewer's pages. In the PDF viewer DesertFox's keys win, so pdf.js loses its own `j` and `k`.

## Browser sidebar keys

`desertfox-sidebar.js` takes keys in Firefox's own sidebar: the vertical tab strip (with `sidebar.verticalTabs` on) and the history, bookmarks and open tabs panels. It never takes a key in another panel, such as an add-on's sidebar, whose page it does not know. It attaches its own keydown listener to each browser window's root, because a key there is not for a page and the core leaves it alone.

- The keys come from `sidebar_keys` in the state, built from the keymap's `sidebar` mode: rows of one or two key tokens, each naming one `sidebar.*` command. A bad table is left out whole, and the other keys stay. The module holds the first key of a two-key row (`gg`) per window. Escape, a focus move or a window blur drops it. Any other key tries the pair, then itself alone.
- A key is taken only with the focus in one of those places, the module allowed to act there (`may_act`) and no menu or walking panel open (the popup walk owns those keys). In a text field, such as a panel's search box (a field in a shadow root included), only the `sidebar.leave` row is taken.
- In a panel the moves, open, expand and collapse type arrow keys, Home, End or Enter through the core's `type_key`, so Firefox keeps its own selection, scrolling and folding. `type_key` types only those keys, after the current key event, and never with the focus in a text field or DevTools. A typed key passes the feature's own listener untouched, so a typed Enter never runs `sidebar.open` again. In the strip they move the strip's own keyboard focus (`ariaFocusedItem`), select the tab or fold its group.
- `sidebar.close_item` closes the open tabs row's tab or the strip's tab. It is not taken in history or bookmarks, where a close would delete data. `sidebar.filter` focuses the panel's search box, and in the strip opens Firefox's all tabs panel.
- `sidebar.leave` (Escape) from the search box goes to the list. Elsewhere it gives the focus back to the page region that last had it in the window, the page, the split partner or a docked DevTools, while it still shows. Else it goes to the selected tab's page. The module remembers that region from focus events, in memory per window.
- An action that meets a missing or changed Firefox internal leaves the key to Firefox. A start that fails leaves the sidebar keys off and the rest of the module on.
- The keys live in the keymap's `sidebar` mode: `j k gg G <Enter> l h d / <Escape>`, each bound to one `sidebar.*` command. The mode never runs in a page. The extension writes its rows into the state (`sidebar_rows_of`) and a user rebinds them like any other mode. A key with a count, a prompt, a guard or more than two tokens is left out of the table.
- The `sidebar.*` commands are defined once in the registry, with command line names such as `sidebar_down`, and hidden from completion. The extension has no focus in the sidebar, so its handler of each refuses with "Works only with focus in the sidebar". Only the module runs them.
- `,e` focuses the sidebar. It is the same `pane.focus` command with region `sidebar` that `ES` runs, and it needs the module. With a panel open, the focus lands in the panel's search box, so a letter types there. With vertical tabs and no panel, it lands on the selected tab in the strip, where the keys above work at once. With only the launcher showing, it lands on the launcher buttons, and with nothing showing the last used panel (else Bookmarks) opens first. In a panel's search box, the first <Escape> moves into the list, where the keys above work, and the next <Escape> goes back to the page. In the strip, the first <Escape> goes back to the page. The same holds after `ES`.
- In which-key the `g` group of this mode is the `Go` group of the normal mode. `,e` sits in the `DesertFox` group.

## Popup walk

`desertfox-popup-walk.js` makes `j`, `k`, `h` and `l` move in Firefox's own popups. It takes the letter and types the matching arrow key into the same window once the letter's event is over, through the core's `type_key`. Firefox then does all its own moving: subviews, submenus, trees, radio groups and the Picture-in-Picture seek and volume keys. The letters are fixed and are no key rows of the extension, since a menu has no DesertFox mode or keymap. The walk adds no protocol kind.

- It takes a letter only where an open popup or a walking window owns the keys: an open menu, the app menu or the downloads panel open, the Library, Page Info or a Picture-in-Picture window, or a list with the focus in a settings sub-dialog. A permission prompt and another extension's popup never count, because an arrow key there goes to the page or to that extension.
- A field keeps its letters, except under an open menu: a menu opened over the focused address bar keeps the letter out of the field, so walking there steals no typing.
- Escape also closes the Library from one of its trees when the search box is empty, since Firefox binds no Escape there.
- The core's `type_key` refuses a key with the focus in a field. The walk passes `menu_owns_keys` for an open menu, which skips only that check, and only while the core itself sees an open menu popup that does not ignore keys. The DevTools refusal stays: a context menu over DevTools belongs to the DevTools feature, and the walk attaches to no DevTools window.
- The arrow key is dropped when the popup closed, the window closed or the focus moved into a field before it goes out, so it never lands on what was under the popup.
- The listener sits on the window root, which hears a key before the core's window listener. Else the core takes `j` as a scroll key on a locked page under a context menu.
- The feature reads no state of its own. It gates every key on the core's `may_act(win)`, as the other features do. Its start error leaves it off alone.
- A key the [key hold](#key-hold) gives to another feature is left alone, so the letters of hint labels never walk a menu. A key that begins a `hint.browser` binding waits for the window's own listeners where chrome hints can start (the Library, Page Info, a dialog frame, or inside an open panel), and the walk acts only if chrome hints left it alone.

## Hints over Firefox's own UI

`desertfox-chrome-hints.js` and the command `hint.browser` (`gB`) label the controls of Firefox itself, in the style of the page hints. The user types the label to pick the control. The surfaces are the nav bar buttons, the tab strip, the bookmarks toolbar, the sidebar buttons, the menu bar, the rows of an open app menu, permission prompts (doorhangers), the downloads panel, the controls of a tab's prompt, the settings sub-dialogs, the Library and Page Info. A pick clicks the button, runs its command, selects the tab or opens the menu or folder.

The work splits by the thin-executor rule:

- The module collects the targets and sends only ids and boxes (`chrome_hints.targets`, at most 400 targets, in parts of at most 4 KB and at most 32 parts). It sends no page content and no label text.
- The extension makes the labels from the `hint_letters` setting, narrows them as the module reports each typed key (`chrome_hints.key`, one key per message, with a counter so a key read twice runs once) and names the id to pick (`chrome_hints.pick`). It stores the session in `storage.session`.
- The module draws the labels it is told (`chrome_hints.draw`) in a closed shadow root that links one fixed sheet. Theme colors travel as checked hex values. A draw replaces the one before only when all its parts came. A target inside an open panel gets its label inside the panel's own DOM, because the window layer does not cover a popup.
- A pick names an id of the module's own table for the current session. The module refuses an id of an older session, a target that is gone and one that moved more than 2 px since its label was drawn. Each target kind has one fixed action.
- A session ends on Escape, a key with Ctrl, Alt or Meta, a click, a resize, the window leaving the front or closing, the pref going off, the module shutting down, or no labels within 2 s of the start. Each end removes the layers, the listeners and the timer.

### Start token

The content script hears `gB` only with the focus in a page. With the focus in a dialog, the Library, Page Info or an open panel, the module starts the hints itself:

- The extension lists the key token lists of the `hint.browser` bindings in the optional state field `chrome_hint_keys` (at most 4 bindings of at most 4 tokens, none beginning another). A bad table is left out whole and the rest of the state stays. The module never knows the binding is `gB`.
- The module matches those tokens only with the focus in one of those places, never in a field and never with a menu open. The first keys of a longer binding are held while they wait for the rest.
- A whole binding makes the module hold the window's keys and push `chrome_hints.want` with a random start token. The extension answers with `chrome_hints.collect_here`, which names no window. The module takes its own token once, within 3 s of the key, and only in the window where the key was typed. So a start in chrome focus never opens where the user typed no binding. An older or cancelled token gets the refusal "The hint key is stale", which shows no toast.
- Keys typed before the first labels show (at most 16) wait for them.
- A start from a page or the toolbar goes the other way: the extension asks with `chrome_hints.collect`, which names the window, and the module refuses it unless that browser window is in front and the module can act there. Both starts refuse with a short text while a menu is open or the focus is in a field. A start that lost to a newer one sends nothing. A collect that labels a grant control also needs the user's start key (see [Grants wait for the user's Enter](#grants-wait-for-the-users-enter)). While the downloads panel is open, a plain collect refuses with "Type the hint key in the panel" whatever its targets are, because a pick there opens a downloaded file. Only the binding typed in the panel labels it.
- A plain collect on a surface with no grant control (the nav bar, the tabs, the bookmarks toolbar) opens a session with no user key. This is the limit of the rule above, which holds for `collect_here` and for grant surfaces. The keys the user types while the labels show then go to the add-on (`chrome_hints.key`) until Escape, a click or a pick.

### Key hold

Two features can see the same key in one window, and listener order cannot settle who goes first: Firefox calls the newest window watcher first. So the core keeps one owner per window. `hold_keys(win, owner)` claims every key of the window and returns false while another owner holds it (a feature that gets false does not start), `release_keys(win, owner)` ends the owner's hold and `keys_held_by(win)` names it. A feature leaves a key alone while another owner holds its window. The hints hold the keys from the binding's last key to the end of the session, a pending grant holds them until its Enter, and the popup walk stands aside for both.

### Grants wait for the user's Enter

A plain `chrome_hints.collect` (the extension's start for `gB` typed in a page) labels a control that grants only after the user's own start key. The module keeps the window's last keys that went on to the page, as many as the longest binding. They count as a start key when they end in a whole `hint.browser` binding, each key at most 3 s after the one before. A key typed in a field, or a repeat, never counts, and a key typed in a field empties the list, so `gB` typed as text does nothing. The collect must come at most 1 s after that key, and it spends the key, so one key starts one such session. A collect whose targets include a grant control and has no fresh start key refuses with "Type the hint key to label the prompt". A plain collect with no grant control still runs, but its session is not keyed, and a pick of a grant control in it refuses with "Type the hint key to pick this" and shows no Enter mark. So a control that comes to grant after the collect, as a ticked Remember box makes a Block do, is gated at pick time too. A start in chrome focus is keyed by its start token instead.

Known limit: the binding comes from the extension's state, so a compromised extension can rebind it. A grant still needs the user's own Enter on a visible mark.

Some picks give something away: they allow a permission, unblock a held-back download, open a downloaded file, send a client certificate or send a login. The extension names every pick, so a compromised extension can swap the user's Block for Allow. The module therefore never clicks such a control on a pick. It marks the control with a frame and the word "Enter", holds the window's keys and waits for an Enter that the user types in that window. The extension has no kind that confirms, and the module decides from the real key event alone.

What counts as a grant is a fixed table in the module, keyed by Firefox's own ids, classes and attributes. The table sits in the module and not in the extension because the extension is the party it guards against. On a surface that can grant, a control the table does not name counts as a grant, so a button that a later Firefox adds waits as well.

- A doorhanger's main button and any control but its close button, its link and its drop-down. Its second button clicks at once only on a prompt of a known deny (location, XR, persistent storage, MIDI, storage access, the two local network prompts, and camera and microphone). It waits when the Remember box is ticked, because Firefox then stores the deny for good. Notifications' second button is Always Block, so it waits too.
- The downloads panel and list: opening a file, and a held-back download's unblock and open buttons. Cancel, retry, the arrow to the blocked-download view and Show in folder on a clean row click at once. A Library row pick only chooses the row, and the user's own Enter there opens the file.
- Page Info's permission rows, except the Block and Always Ask radios.
- The external protocol dialog and the client certificate dialog: every control but Cancel and a drop-down, which only opens.
- The Exceptions and site permissions dialogs: only Block, Cancel and a drop-down click at once. Remove, Remove All, Add and Save Changes wait, since a removed Block entry lets the site do what the default allows.
- A tab prompt's OK when it sends a login (a user name and password or a password prompt), and a tab prompt's checkbox, which stops the site's prompts or on a prompt from a background tab lets the site take the focus to its tab.

An Enter confirms only when all of these hold:

- The key is trusted, so a script's key does nothing. It has no modifier and is not a repeat, so a held-down Enter does nothing.
- It was pressed after the mark showed, and at least the dwell later. The dwell is Firefox's own doorhanger delay, the pref `security.notification_enable_delay`, but never under 500 ms, so a pref of 0 removes no dwell. A key inside the dwell ends the confirm, so tapping Enter through a page never carries over to a grant the user did not see marked. Times are in ms since the epoch on the key target's own clock, because a dialog's window starts later than the browser window that shows the mark.
- The window is still in front, the module can still act there and the hold is still the confirm's.
- The target is the same: the same prompt, the same download, the same control and row state, visible and where it was drawn. Else the confirm ends.
- The control is ready. A doorhanger button and a dialog's accept button ignore a click for a moment after they show. Enter then does nothing, and the next Enter tries again.

Any other key or a click ends the confirm without a grant. So do the window leaving the front, a resize, a tab switch, the prompt closing, the page under the mark going away, the download changing and the module turning off. A timer ends it after 15 s. Every end clears the mark and releases the held keys.

The mark sits in a layer of its own with no sheet: its frame and the "Enter" note carry fixed colors in inline style. The extension's label sheet and theme colors never reach it, so a compromised extension cannot hide the note or make it unreadable over a grant.

### Hints on Firefox's own pages

The hint keys (`f`, `F` and the rest of the tree's `hint_keys`) also work on a fixed list of Firefox's own pages that run in the parent process: about:preferences (and about:settings), about:addons, about:downloads and about:config. No content script reaches them, so `desertfox-chrome-hints.js` labels them as it labels a dialog. Every other about: page keeps the notice (see [Keys on locked pages](#keys-on-locked-pages)): about:support, about:profiles, about:debugging and about:processes, whose buttons reset, delete profiles or end processes, and the privileged pages in a content process (about:protections, about:newtab, about:logins, about:certificate and the error pages), which the parent cannot read. The list is an allowlist, so a page a later Firefox adds stays unlabelled.

- Start: the key taker (`desertfox-commands.js`) turns a hint key path into a page hint leaf where the locked page rule says `page_hints`. The rule says so only on a page of the list, under the system principal and in this process, and only once the state carries `page_hints: true` (the extension's word that it answers the start). An older extension keeps the notice. Each press calls the start chrome hints lend through `share_page_hints`. It takes the key only when the key event is trusted, holds the window's keys, and pushes `page_hints.want` with a random start token, the leaf's keys and the count.
- The extension matches the keys against its own normal tree. Only a lone `hint.run` step maps to an action of the fixed list `PAGE_HINT_ACTIONS`: a plain click (`follow`), a tab or a background tab (`tab`, `background`) and a copy of a link's address (`yank`), with the filter left at its default or `links` for the link actions. Any other action, filter, text, rapid mode or register refuses with "This hint does not run on this page", and the error reply ends the module's start at once. Else the extension answers with `page_hints.collect`, which hands the token back with the action. The module takes its own token once, within 3 s, only with the same page still shown in that tab and window. A page token opens nothing through `chrome_hints.collect_here`, and a chrome token nothing here.
- Targets: `follow` labels the controls, the links, the newer link and button rows and the text fields of the page, through its shadow roots. The other actions label only links to an `http` or `https` address. The labels sit in the browser window's own layer, never in the page's DOM, built from text by the module. That layer takes no sheet and no theme from the extension: each label carries the hint view's default look in inline style, so a compromised extension cannot move, hide or swap labels over a control that changes a setting. Draw, key, pick and clear then go on the `chrome_hints.*` kinds.
- A pick must name the label the user's own keys spelled. The module keeps the labels of the first whole draw, none the start of another, and drops a later draw that changes one. It follows each key it forwards by the rule of `key_step`: a letter that continues a label is kept, Backspace takes one back, any other key changes nothing. A key counts only after the user pauses 300 ms with the labels shown: a key typed before that, or a held key's repeat, spells nothing and starts the pause again. A pick runs only when the target's label equals that text and the last key came within 2 s. So an extension that names another target clicks nothing.
- Actions: `follow` focuses a text field and clicks anything else, as a dialog pick does. A download row of about:downloads is only chosen, as in the Library. `tab` and `background` open the link's address in a new tab next to the page, with a null triggering principal, and `yank` copies it through Firefox's clipboard helper. The module reads the address from the page, so no address crosses to the extension.
- Grants wait for the user's Enter as above. On about:addons: the private windows choice, the sites with restrictions choice, an add-on's optional permission toggles, its enable toggle, Remove, Undo of a removal and a plugin's Always Activate. On about:config: every write to a pref (toggle, edit, save, reset, delete, add). The risk warning's button there never gets a label, since it is the user's own consent.
- The bar shows HINT while the page's labels or a mark show. A pick that focuses a field ends the session first, so the bar then shows INSERT and Escape blurs the field ([Escape in a field](#escape-in-a-field)). While a session or a start holds the window's keys, Escape ends it and never reaches a field.
- A session there also ends on a tab switch, a click in the page and the page going away.

## DevTools

`desertfox-devtools.js` gives the DevTools trees j, k, h and l: the Inspector markup, the Debugger sources, Storage, Network rows and any other tree that takes the arrow keys. f shows hint labels on the DevTools tabs, buttons, rows and panes. v starts visual mode in a DevTools text area, and y copies. It works in docked DevTools and in a DevTools window. The Browser Toolbox is a separate Firefox process with no DesertFox, so it gets nothing.

- The core's DevTools guard takes no key row there. A feature that calls `claim_devtools_keys(fn)` (only the first one counts) sees each key whose focus is in DevTools, and only while the module may act in the window: the pref, DesertFox running, private window access and the toolbar switch. The consent setting off removes the state, so the feature takes nothing then. The focus is in DevTools when the key's document sits under a frame of class `devtools-toolbox-iframe`, or the window's type is `devtools:toolbox`.
- The loader runs the module in browser windows only, so once a feature claims DevTools keys the core also attaches each DevTools window, those open at that time and each one that opens later, after its document loads.
- The extension pushes the key table with the kind `devtools.keys` after each new matched hello, since the module keeps it in memory only. A row is a one-character key and an action: `tree.down`, `tree.up`, `tree.collapse`, `tree.expand`, `hints.start` or `visual.start` (at most 8 rows). The defaults are j, k, h and l, f for `hints.start` when the hello says `devtools_hints`, and v for `visual.start` when it says `devtools_visual`. A module before hints refuses a table with an action it does not know, so without that flag it would lose the tree keys too. A one-character key carries no modifier, so the table can never take Escape or a DevTools shortcut. The newest valid table wins, and a bad one is dropped whole. Each new hello empties the table first. A hello rewritten for a flag change keeps it. So a reloaded or older DesertFox that pushes no table gets no DevTools key. The push may be read up to a day late (its `max_age_ms`), since it sets a table and presses no key.
- The feature passes a key with Ctrl, Alt or Meta, a key with no row, a key whose target is editable (an input, a textarea, a select, editable text, a code editor) and a key whose target is a frame element. So the console input and the markup view's inline editors type, and so does a field in an extension's DevTools panel, which runs in another process and shows only as its frame. Escape stays DevTools' (it opens the split console).
- A taken key becomes an arrow keydown, dispatched on the key's own target, and the real key stops in the parent. Chrome code makes it, so Gecko marks it trusted. It passes the core's listener, the popup walk, the sidebar keys and chrome hints like a real arrow, and none of them takes an arrow there: a table row is one character, the walk takes letters only, and the sidebar and chrome hints never act with the focus in DevTools. With a DevTools context menu open, that arrow moves the menu.
- No DesertFox page code runs in a DevTools document: they all have the system principal. The feature reads no DevTools internals and the extension sends it no selector.
- An open DevTools context menu takes the keys ahead of the tree. Docked, it opens in the browser window, and in a DevTools window in that window. The DevTools feature moves those menus with the arrow it makes for j and k.
- In the markup view `h` collapses, so DevTools' own `h` (hide the node) needs the context menu there.

### Hints in DevTools

The flow is that of chrome hints (`hint.browser`), and the extension's session in `src/background/chrome_hints.ts` serves both. The module collects the targets and sends only ids and boxes, the extension makes the labels and names the pick, and the module draws and runs one fixed action.

- The hint key (`hints.start`) sends `devtools_hints.ask` with a fresh random token and takes the key. The ask is a call with a reply, as `chrome_hints.want` is, so an ask read twice after a background restart runs once. The extension answers with `devtools_hints.collect`, which hands the token back with the session number and the theme's label colors. The module spends the token at once and refuses one that is unknown, older than 2 s, from a window no longer in front, or with the focus no longer in DevTools.
- From the hint key until the first labels show (at most 2 s for the ask, then 2 s for the first draw), every letter, Backspace, Enter and Tab in that window is dropped, so a fast `fh` never hides a node. Escape ends the ask or the session and stops there, so it never opens the split console. Any other key (a key with Ctrl, Alt or Meta, an arrow, F5, F6, the context menu key) ends them and goes on, since it can move the focus out of DevTools, where no key would end them. The ask and the session hold the window's keys in the core, so the popup walk and the sidebar leave them alone. An ask nobody answers (a busy or restarted background) gives the window its letters back after 2 s.
- The targets come from a fixed table per DevTools document address: the tool tabs and toolbar buttons of the toolbox, the Inspector's tabs, buttons, search field and rule view, one per markup line, the Console's buttons, input and output, the Debugger's tree rows, tabs, buttons and editor, Network's rows, buttons and tabs, Storage's rows and buttons, and a generic row for any other panel. Only the documents that show are read: the toolbox and each visible panel frame of this process, the markup view inside the Inspector too. An element inside a row already labelled gets no label of its own. A target shows at its point (`elementFromPoint`) or gets no label.
- Each target's action is fixed: a click, a mouse press (`mousedown`, `mouseup`, `click`, for the tool tabs and the markup lines, which act on mousedown) or the focus (a field, or an area such as the rule view, where the focus goes to its first focusable element). A target that moved since its label was drawn is refused.
- The labels sit in a layer per DevTools document, since DevTools has its own zoom. An area's label sits at its middle, a markup line's label left of the line so the tag name shows, an icon button's label over its middle so a row of them keeps apart, and any other at its top left corner. The labels drop most of their padding, as DevTools rows are dense. The layer, the label checks and the assembly of a draw are chrome hints' own, which they lend through the core (`share_hint_drawing`). The layer is a closed shadow root with the extension's `chrome_hints.css` and the theme colors in a constructed sheet, because the toolbox and Storage documents ignore an inline style ([measured](../firefox-behavior.md#hints-in-devtools-devtools-keys)). The boxes the extension gets are in the top window's pixels, to sort the labels in reading order.
- The session's draw, pick and clear come on `devtools_hints.draw`, `devtools_hints.pick` and `devtools_hints.clear`, apart from the chrome hint rows, because the core gives each kind one handler and chrome hints hold theirs. The targets, the keys and the end go on the chrome hint rows. A click in the window, the window leaving the front, a resize, a panel document hiding, the pref off, the consent setting or the toolbar switch turning the module off and a new hello end the session.
- The module says `devtools_hints` in its hello once the hint kinds are registered.
- An area with nothing to focus in it, such as the console output, takes the focus out of the field that held it, so the next keys reach the area's document. A click in the console output gives the focus to the console input, so this label is the way into the output.

### Visual mode in DevTools

`v` (`visual.start`) selects one character in the focused DevTools text area, and the mode's keys move the end of the selection. The extension pushes those keys as `devtools.visual_keys` with the key table, before it: at most 16 rows of a one-character key and an op, `char.back`, `char.forward`, `line.down`, `line.up`, `word.forward`, `word.back`, `line.start`, `line.end` or `copy`. The defaults are h, l, j, k, w, b, 0, $ and y. It is a push of its own, so a module before visual mode, which refuses the kind, keeps its tree table. Each new hello empties it, as it empties the key table.

- The areas come from a fixed table per document address. Plain DOM areas: the console output, the rule view and the Network headers. Code areas: the Debugger source and the Network response, CodeMirror editors that DevTools shows read-only. The console input is a CodeMirror editor too, and has no row, so `v` types there. So does every other field. The computed view is out, since its text is `user-select: none`. The markup view is out, since `Selection.modify` stops at the edge of each span of a tag line, so a selection never grows past the `<` ([measured](../firefox-behavior.md#visual-mode-in-devtools-devtools-keys)). `v` there goes to DevTools.
- A DOM area starts at the first text that shows under the focused element, else anywhere in the area. Each op is a `Selection.modify` extend. A move whose end leaves the area goes back, so the selection never takes in a toolbar or the next pane. The console takes no line moves: it draws only the messages near the view, so a line move skips the rest ([measured](../firefox-behavior.md#visual-mode-in-devtools-devtools-keys)). `copy` puts `selection.toString()` on the clipboard with `nsIClipboardHelper`.
- A code area gets CodeMirror's own keys: a Shift+arrow, Shift+Ctrl+arrow, Shift+Home or Shift+End keydown made by chrome code on its `.cm-content`. CodeMirror draws only the lines near the view, and keeps the selection of the rest in its own state, so `Selection.modify` would lose it. Those keys come back to the core's listener as trusted keys, and the feature lets its own through. `copy` runs `cmd_copy` on the editor's document, and CodeMirror fills the clipboard from its selection.
- A copy over one million characters copies nothing. In a code area a `copy` listener that runs after CodeMirror's empties it.
- `copy` ends the mode and keeps the selection, so it shows what was copied. Escape ends the mode, drops the selection and stops there, so it opens no split console. Every other one-character key outside a field does nothing in the mode, `f` and `v` too. A key in a field ends the mode and goes to DevTools, Escape included, and the selection stays. A field inside the Debugger source, the breakpoint condition or its checkbox, counts too. A key with Ctrl, Alt or Meta, or a named key (an arrow, Tab, F6), ends the mode and goes on. So do a click, the window leaving the front, the panel document hiding, the pref off, the consent setting or the toolbar switch turning the module off and a new hello. The mode holds the window's keys in the core, as the hints do.
- No text, selector or range crosses the channel. The extension never learns what was copied.
- The module says `devtools_visual` in its hello once the kind is registered.

## Liveness

The core's frame script runs in every tab. For the top document it reports the inner window id and whether the focus is in a field. It also counts the keydown listeners of DesertFox's content script, from each listener's sandbox metadata, with no help from the extension. It reports at its start, on DOMContentLoaded, pageshow, 500 ms after load, focusin and focusout. The live mark in the state covers the time before the first report.

## blur_on_load

Like web pages, about:preferences and about:config put the focus in their search box as they open. With the setting `blur_on_load` off (the default), a key there types into the box, as it does on a web page. With it on, the extension adds `blur_on_load: true` to the state. The frame script marks a report whose field the page focused within 1 s of DOMContentLoaded or load, or of the top document's `visibilitychange` to visible (the tab shown again). A key that is no repeat and no modifier, a mouse press and the document going hidden end the window. Such a key or press also keeps any later load window of that document shut, so DOMContentLoaded and load cannot reopen one after the user clicked. User activation plays no part: `hasBeenActive` never resets, and the repeats of a held Shift+J give each tab they pass activation. A field that holds the focus as the tab is shown gets a report at once. A window blurs at most five times, and then a page that takes the focus back keeps the field, so no blur and refocus loop runs. An older module blurs on load only. The core sends a blur back only where it would take a key: the pref, the state, the toolbar switch, private access, normal mode and DesertFox not live. The frame script then blurs the field if that is still true for the same document. The window and its input rule are those of `blur_load_focus` in `src/content/main.ts`.

## Escape in a field

On a page the module handles (about:preferences, about:config and other pages with no DesertFox script), a plain Escape in a text field blurs the field and stops the key, so the page's own Escape (clearing a search box) does not run. It acts only where the module would take a key. It leaves Escape alone while a feature holds the window's keys and in a tab ignored with `<S-Escape>` (the taker's optional `ignores(browser)`). It acts only on the tab's own document, so a subdialog such as Manage Exceptions keeps its Escape, and on a field the page's report names, so a field in an iframe of a remote page leaves Escape to the page. A document in design mode keeps its Escape, since it has no focused element to blur. A page in this process is blurred directly. A page in a content process gets the blur message with `escape: true`, which skips the load-window rule of `blur_on_load`. The key is hard-coded to plain Escape and follows no remap.

## The status bar

`desertfox-statusbar.js` draws one bar under the page area of each browser window, below the tab box and the sidebar. It shows, by the settings `browser_bar_left` and `browser_bar_right`, the mode, the half-typed keys with a typed count, the macro register, the container, the scroll place, the tab place and the address. The setting `browser_bar` and the Firefox pref `desertfox.browser_module.statusbar` (true unless set) turn it off. The pref is the kill switch of the bar alone.

- It is not a feature of the core. It runs in the window itself and never adopts into the sandbox, so a fault in it cannot reach the key path. It reads only that the core is on, and the state the extension writes, as foreign input: it checks the version, the lists and each field of the shown tab again. A state it cannot read draws nothing.
- Text reaches the bar only through `textContent`, and the label of a field is cut and stripped of control characters. A theme color reaches a style only when it is `#` and 3, 4, 6 or 8 hex digits. A name that the bar does not know (a widget, a mode, a container color) is not drawn.
- The bar rewrites the core's hello with `bar: true` while it can draw, and takes the flag out when its pref turns off. It writes no hello of its own, so a missing hello stays missing. The extension then hides the corner badge of the page and sends the per-tab fields (see [host.md](host.md#browser-module)). With the bar off, absent or broken, the badge shows as before.
- Every trigger only marks the bar dirty, and one animation frame draws it. A resize is the one place that reads layout: it gives the width in characters and the height. A narrow bar drops the url, then the container, scroll, tab place, macro register and pending keys, in that order. The mode is never dropped.
- The bar sets `--desertfox-statusbar-height` on the window root to its height with its margins, and to 0 while it is hidden, so a later piece can reserve the space. It hides in fullscreen (Firefox's `inFullscreen`, which F11 and a video share) and while customizing.
- On a page with no tab record, no DesertFox listener and a focused text field, the bar shows INSERT, because the module's keys type there. It reads the core's existing report (the field boolean, the listener count and the document id) and asks every tab for a fresh one when it starts. A tab with a record keeps the mode the record names.
- The scroll place comes from a frame script that reports only for pages the extension cannot reach (about: and add-on pages, view-source, the PDF viewer, Reader View). A web page sends no message. It stays in the browser process and is not written to storage.
- The tab, container, address and security parts are read in the browser itself. Reader View shows the address of the page it holds. A private window shows no address and no site label.
- Look: flat, in the colors of Firefox's toolbar, with the mode badge in the theme's mode color. When a TextFox style is present (`--tf-bg`), the bar is one more pane of it: its border, margin, font, hover color and radius. `browser_bar_border` sets the corner. `none` is the default and draws no border, diagonal or clip, only padding around the badge and the info. `auto` reads the panes of the window once: a radius above zero is round, a bevel on the navigation bar is a chamfer, and no TextFox variable is square. The bevel is drawn by the bar itself. A Firefox restart is needed for a corner change in the panes, because their style loads at start.
- The bar needs `#browser`. A window without it (a popup) gets no bar. A Firefox release that moves it leaves the corner badge in place, because the bar says nothing in the hello when it cannot build.

## Messages

The core reads the extension's requests and writes its own list (the channel is in [host.md](host.md#browser-module)).

- One storage listener (`extensionStorageSession.registerListener`) per DesertFox extension object, in the core sandbox. A reloaded DesertFox is a new object with an empty bucket, so the core listens to the new one on its `ready` and stops the old listener. Shutting down for the session stops it too.
- Each change of the from-extension list carries the whole list in `newValue`. The core checks it once, as `validate_message_list` does, and never reads it again. A list past 16 messages or the list's byte cap (`message_list_bytes`) is dropped, and a message over its kind's `max_bytes` is refused. A request older than its kind's `max_age_ms` (2000 when absent) is dropped, with an error reply when its kind expects one. A request with no `sent_at` is accepted. Ids already handled, kept per extension object, are skipped.
- A feature file answers a kind with `register_kind(kind, handler)`, for a kind on the core's copy of `EXTENSION_TO_MODULE_KINDS`. The handler gets the checked args and returns `{ ok, error?, value? }` or a promise of it. The reply copies `ok`, the error cut to 120 characters and a text `value`. A reply over the kind's `max_bytes` becomes the error "the answer is too large". A kind no feature answers gets "no handler for this kind". A reply error loses control and bidi characters, as on the extension side. A handler that throws or rejects gives the fixed error "the request failed", never its own text. A push (`reply: false`) gets no reply.
- `send(kind, args)` starts a call to the extension, for a kind on the copy of `MODULE_TO_EXTENSION_KINDS`. It sets `sent_at`. Requests and replies go to the from-module list, the newest within its caps. The core writes nothing there while the pref is off or after DesertFox reloaded, so a reply that settles late goes nowhere.

## Keys on locked pages

Status: built. The background side is `src/shared/browser_module_scope.ts` and `src/background/browser_module_run.ts`. The module side is `desertfox-commands.js`.

Beside the single-key rows, the state carries `tree`: the normal tree pruned to the keys a locked page can run, so the module takes sequences (`gg`, `xx`) and counts too.

- The set is derived, never listed: a command that runs in the background and does not need `content`, minus a deny list (`media.act`, `frame.exit`, `macro.record`, every `mode.*`). A page swaps the record key for `macro.stop` while a macro records, and the stored tree has no such swap, so `q` stays with the page. `test/browser_module_scope.test.ts` lists the result, so a new command shows in review. `docs/keymap.md` marks the keys in its Locked pages column, from the same derivation.
- A leaf stays when every step is in the set and it has no guard. A bare `cmdline.open` leaf (`:`) stays too, as a forward leaf, because the background opens the line itself (see [The command line panel](#the-command-line-panel)). One that types text in (`A`, `tM`) does not, since its commands mostly need a page. A key that leads only to other leaves is not in the tree, so `f` and `/` stay with the page or Firefox. Site rules do not apply: a locked page matches none.
- The root also lists the key paths of the `hint.run` leaves in `hint_keys`. Where hints cannot run now, the module claims them, after the field, DevTools and liveness guards: on the PDF viewer and Reader View while `browser_module_pages` is off, and on an about: page (not `about:blank`, a srcdoc frame or a DevTools toolbox in a tab). The locked pages feature lends that rule through `share_locked_page_rule`. On a page chrome hints label themselves the rule says `page_hints` instead, and every hint key starts them (see [Hints on Firefox's own pages](#hints-on-firefoxs-own-pages)). The first hint key per document goes out as a `run`, and the background refuses it with a notice: "Hints here need :set browser_module_pages true", or "Hints do not run on this page". Later hint keys there do nothing. A tree binding on a hint key's path wins. A web page, an extension page and a sidebar get no claim, and the setting turning on gives the keys back at once.
- A leaf is `forward` or native. A native leaf is one command of the protocol's list (`tab.next`, the scroll commands, `page.stop`) with its args and count rule, which the module runs itself. A forward leaf holds no command id.
- The tree is rewritten with every state write, so a keymap change, the toolbar switch and the setting follow. It is left out when the switch is off and when it is over `MAX_TREE_BYTES` (32 KB). The default tree is about 4 KB. The module then keeps only the single-key rows, as a module that predates the tree does.
- For a forward leaf the module sends a `run` request: the tokens of the path joined by spaces, and the typed count or 0. Chrome sends no tab id. The background matches the tokens again against the stored tree with `create_matcher`, never the module's copy, so a stale or forged tree runs nothing the keymap does not bind now. The tokens must end on a leaf of the set, with no count, register or hold typed among them. The binding then runs through the router in the active tab, in normal mode, with `may_prompt`. The router refuses a count over a step's `repeat_limit` before any step runs, as for a key on a web page.
- A refusal the user caused (a key the keymap no longer binds, a key that needs a page, a count over the limit) shows as a desktop notification, as any refusal with no page does. Junk keys text and a bad count are refused with no notification.
- The module matches with the extension's own matcher against the tree, one matcher per window, in the keydown's tick, so a prefix key (`g`, `x`) and a count digit are stopped before the page sees them. A key that ends no sequence goes to the page. A key on another tab or document, or a new tree, starts a fresh walk, so a half-typed `g` never finishes on another tab. A state rewrite with the same tree keeps the walk. There is no timeout, as in DesertFox's own key flow. A key a guard refuses (a field, a live or non-normal tab, the browser UI or DevTools, no state) ends the walk, and so does the pref or the toolbar switch going off, so a half-typed `x` never finishes after a trip into a field.
- A native leaf runs through `run_command`, with the count as its count rule says. A `repeat` count runs the command at most 100 times.
- A hold Space (a group's hydra hold) needs run semantics the walk does not have, so the walk resets and the Space goes to the page. A register typed before a binding (`"a`) means nothing here, so the keys run nothing.
- With no tree, or a tree that fails `validate_scope_tree` (bundled in), the single-key rows decide, as before.
- `module_pending(win)` gives the keys half typed in the window's selected tab and the count, for the which-key panel. `watch_pending(fn)` calls `fn(win)` after each key the walk saw and each reset, with no window for a reset of every window. The module never sends the keys. The status bar does not read them: on a locked page it shows no half-typed keys.
- The tree's root lists the forward leaves that open the command line in `line_keys` (`:`, and the keys that ask for a value: `o`, `T`, `ww`). After one of them the module holds every key of that window and runs none, because the line takes a few hundred milliseconds to get the focus and a fast `:undo` would otherwise run `u` on the page. It keeps the printable text typed meanwhile (32 characters at most). The hold ends when the panel shows and takes the focus, when the address bar opens, on a tab switch, when the window loses the focus, on Escape and after 1.5 s. An older module ignores the field and holds nothing.
- The module keeps two keys of its own, because the tree carries no mode leaves and an older extension's tree has no command line leaf: `<S-Escape>` and `:`. Each works only while no sequence is under way and the tree does not bind it, so a user binding wins. `<S-Escape>` follows no remap of DesertFox's own key.
- `<S-Escape>` is the ignore toggle. The module keeps the flag per tab, in memory, for the document it was turned on in, so a load ends it. While it is on, every other key goes to the page, so pdf.js gets its `j` and `k` back.
- `:` opens the address bar with `df `, the backup command line, when the tree has no `:`. A current extension's tree binds it, so the module forwards it like any other leaf and the background opens the panel. With no tree, a single-key row for `:` or `<S-Escape>` wins over the module's own key.
- A key that asks for a value (`o`, `T`) opens the command line through `open_cmdline`. A tab with no content script gets the panel, and when the module refuses it, `address_bar.open` instead: the module opens the address bar of the focused window with `df ` and the printed command typed in, and the omnibox runs it when the user presses Enter. The module never submits it, and it sets the field without starting a query, so the text (which can hold the selection or clipboard text) reaches no search suggestion provider until the user edits it. The request names the tab that asked (`tab_id`), and the module refuses when that tab is no longer the selected tab of the focused window. The handoff ends the binding as a line the user left does, so a later step of the binding never runs while the bar is still open. The text loses control and format characters and is data in an input field, never code or an address to load. A private window counts only with DesertFox's private window access. A module that cannot answer leaves the refusal "needs a page DesertFox runs on".

## Which-key on locked pages

Status: built. The background side is `which_key_table_of_keymap` in `src/background/browser_module.ts`. The module side is `desertfox-whichkey.js`.

After a prefix on a locked page, the module shows the which-key panel: the keys that can follow, in the page panel's look. It draws in the browser window from a table the extension writes. No DesertFox page code runs for it, so it works where page code cannot run at all, such as about:preferences, about:addons and about:support in the parent process.

- The state carries `which_key`: `delay_ms`, `skip` and `border` from the settings `which_key_delay_ms`, `which_key_skip` and `which_key_border`, and `panels`, one per branch of the scope tree, keyed by its path (the tokens joined by one space). Each panel is the title and rows `panel_after_prefix` (`src/background/list_keys.ts`) gives over the compiled normal tree cut to the keys of the scope tree. So the panel lists only keys that run on a locked page, with the labels, group names and order of the page's panel. A row has no description, because the panel takes no pointer.
- The table is left out when which-key is off (a delay of 0), when DesertFox is switched off, and when it is over a limit: 64 panels, 80 rows a panel, 60 characters a label, 48 KB in all. The builder strips control and format characters from each label and cuts it to the limit. The default table is about 8 KB.
- The module reads the table as foreign input, as the extension's validator does: known fields only, every text checked, the paths in a Map. A bad table draws nothing. It reads the state when a sequence starts, so a table change shows at the next sequence.
- The file runs in each browser window and never adopts into the core's sandbox, as the status bar does. The core calls it through `watch_pending` and it reads `module_pending`. It sends nothing and writes nothing, so the half-typed keys stay in the module.
- It uses the page panel's timer: the panel opens after `delay_ms`, a prefix in `skip` waits for no delay of its own, and a panel that is up follows the next prefix key at once. It checks at draw time that the walk still holds the keys.
- It hides on every change of the walk (a leaf, a key that ends no sequence, Escape, a guard reset such as a field, a new tree, the pref, the toolbar switch, the consent setting), on a tab switch, a load of another document in the tab, the window losing the focus, the window closing and the module shutting down. The walk has no timeout, so neither has the panel.
- Drawing: one host on the window's root, a closed shadow root, `pointer-events: none`, a constructed sheet of the page panel's `STYLE` and two rules of its own: chrome's own font, as the status bar has, and the corner above the status bar (`--desertfox-statusbar-height`). The text goes in with `textContent` only. The theme colors `bg_core`, `fg_core`, `primary` and `secondary` come from the state's `bar_theme` for the window's color scheme, each only as `#` and hex digits. The footer reads `ESC close`, because the walk has no Backspace and no hold.
- With `browser_module_pages` on, the PDF viewer and Reader View run DesertFox's page code, which draws its own panel. The module's liveness guard keeps the walk out there, so the module never draws a second panel.
- DevTools takes only its single-key table, so no prefix is pending there and no panel shows. The `?` and `<A-?>` first-keys panel is not shown on a locked page.

## The command line panel

Status: built. The module side is `desertfox-cmdline-panel.js`, the background side `src/background/cmdline_panel.ts`, and the page the same `src/cmdline/page.ts` as on web pages.

On a locked page `:` and a key that asks for a value open DesertFox's own command line in a panel over the page. The address bar is the backup.

- The background sends `cmdline_panel.open { tab_id }`. When the module opens the panel, the background records it in `storage.session` (`desertfox_cmdline_panel`): the tab, its window, whether it is private, the mode, the text to type in and the page's address. When the module refuses or has no handler, the background records nothing and sends `address_bar.open`. Opens, the page's claim and every forget run one at a time, so no step deletes or overwrites a record written after it read.
- The module's reply carries, as JSON text, a random key it put in the page's address (`cmdline.html?panel=<key>`) and the keys held since the line was asked for. The background checks both as foreign input and adds the typed text to the line. Keys typed between the reply and the panel taking the focus are dropped. The page focuses its input at once and keeps what lands there before its data arrives.
- The module refuses when the tab is no longer the selected tab of its window, when it may not act there (the pref, private access, the switch), when a panel is already open and when Firefox has no `mainPopupSet`. Otherwise it opens a XUL panel at the bottom of the page, the page's width.
- The panel holds a remote `<browser>` built as Firefox builds a toolbar popup (`ExtensionPopups.sys.mjs`): DesertFox's browsing context group and remote type, `extension-browser-inserted`, Firefox's own popup content script and the fixed address `cmdline.html` with DesertFox's principal as the loader. The page runs in DesertFox's process with DesertFox's principal, never the system principal. The extension names only the tab.
- Traps: the browser joins the panel only on `popupshown`, because a remote browser appended before `openPopup` crashed the parent process. Its message manager exists one microtask after `XULFrameLoaderCreated`.
- The page grows the panel upward with its list: Firefox's popup content script measures the page and sends `Extension:BrowserResized`, and the module sets the height, capped at the page's height, and moves the panel.
- The panel closes on the page's `window.close()`, on a tab switch (`TabSelect`), when its tab loads another page, on Escape and when the module shuts down. The focus then goes back to the page it opened over, if that tab is still selected. A page that failed to load makes the module refuse every later panel in the session, so `:` opens the address bar.
- The record goes when the line ends (Enter, or Escape through `close_panel_cmdline`), when its tab closes or loads, when another tab of its window comes up and when another window or no window takes the focus.
- The page sees it has no parent window and asks `open_panel_cmdline` in place of a ticket. The background answers only its own `cmdline.html` with no sender tab at the recorded address, key included, and only once per record. A copy a web page frames or opens in a tab, a copy another extension frames or a sidebar shows, and the toolbar popup get nothing: Firefox gives a sender with no tab no frame id, so only the key tells the panel's page apart. It then opens the line through the command line service with frame id -1 as the opener, so the opener checks of completion, the tab rows, help and the ports admit the panel and no frame of the tab.
- One helper, `asker_of`, gives every later message of the page the recorded tab: `run`, `record_cmdline` (no history from a private line), `complete_items`, `tab_rows_action`, `open_help` and the tab model and rank ports. A private window's panel loads as a private browsing context, so its line lists private tabs only.
- The page stands in for its host: Enter sends `run` with `from_line` and closes the window, a close closes the window, and the line has no page search.
- The module's keys stay out of the panel: its browser is no tab browser, so the core's key guard leaves every key there to the page.

## Firefox pages

Status: built. The module side is `desertfox-firefox-pages.js`, the extension side `src/commands/firefox_page.ts`, and the page list `src/shared/firefox_pages.ts`.

`browser.open_firefox_page` (`:firefox`, the `,f` keys) opens one of Firefox's own pages that no extension API opens. It tries three routes in order: the module, the native host (`open_firefox_page`, see [host.md](host.md)), then the clipboard.

- The list: settings, its sections `settings-general`, `settings-home`, `settings-search`, `settings-privacy` and `settings-sync` (`about:preferences#<section>`), add-ons, downloads, about:config, profiles, support, debugging, passwords (`logins`), processes, memory, policies, crashes and protections, and `addons-shortcuts`, the add-on shortcuts view. That view has no address, so only the module opens it. The host and the module each keep a copy of the names and addresses, and tests keep the copies equal.
- Left out: about:reader (it needs `?url=`, so the request would carry an address), about:newtab and about:home (DesertFox has its own new tab page and `page.home`), about:privatebrowsing (a private window opens it), about:sessionrestore and about:welcomeback (their buttons restore or drop the session), and the state pages that need a query or a browser state (about:certificate, about:neterror, about:blocked, about:tabcrashed). Niche pages such as about:telemetry can join later as one more value.
- The request is `firefox_page.open { page, where?, tab_id? }`, sent only to a module whose hello says `firefox_pages`. `where` is `tab` (the default) or `here`. `tab_id` names the tab that asked. A module without the flag gets nothing, and the host is asked at once.
- The extension goes on to the host only when the module never got the request (no matched module, or the request was not written) or answers the core's fixed wrong-shape text, which an older module gives for a page or `where` value it does not know. Every other refusal stands, because the host opens the page in the most recent window and steps around the module's checks. A request that got no answer within 2 s, or whose module went away before it answered, stands too, with a report: the module can have opened the page already. The request is taken back so it never runs late.
- `here` needs the module, because the host and the clipboard only add a tab. The passwords page stays off the module route: it opens through the host or the clipboard, in a new tab only.
- The module finds the address in its own frozen table by the name. Nothing else of the request reaches the load. It opens in the window of the asking tab, or the focused window with no tab, and refuses when the tab is gone or it may not act in that window (the pref, private access, the switch). For `here` it also refuses when that tab is no longer the selected tab of its window.
- It opens through Firefox's own entry points. A tab: `switchToTabHavingURI` with the system principal and container 0, which switches to a tab that already shows the page, in the asking window first and then in any other window. Only a new tab is sure to open in the asking window. Firefox keeps the switch within the same privacy for every page but about:addons, which it switches to across private and normal windows, as its menus do. For settings it first looks for an `about:settings` tab, as `openPreferences` does, but in the asking window rather than the most recent one. A section moves an open settings tab to that section. The shortcuts view opens through `BrowserAddonUI.openAddonsMgr`, which reuses any open add-ons tab. `here`: `openTrustedLinkIn(address, "current")` with container 0. In a container tab Firefox then opens a new tab instead, because a system page belongs to no container. The shortcuts view here loads about:addons and shows the view once the add-on manager in that tab, or in the new tab Firefox opened for a container tab, says it loaded.
- The same page in the same window within 1 s opens nothing more and answers ok, so a double press opens one tab. That holds only while the tab the first open left selected still shows the page or is still loading it. Once the user closed that tab or moved it on, the page opens again. At most 5 pages open per 10 s in the process. More are refused with "Too many Firefox pages opened at once".
- `:open about:addons` and any typed text that equals an address of the list (`about:settings` counts as `about:preferences`) runs `:firefox` here or in a tab. A background tab, a window or a container is refused. The mapping applies to typed text only. On a web page it runs for a request the command line submitted. The content script that hosts the line sets `from_line` on that request, and a page cannot send a message of its own, so the flag is as strong as the page-sent mark. A link a page wrote, followed by hints, `]]` or item mode, never maps and keeps the allow-list refusal. A page never reaches about:logins: a request from a page for it is refused in every placement, typed or not. The bridge refuses every about: address before the command runs. Another about: address keeps the refusal of the one allow-list, which then names `:firefox`. `.` replays a mapped open from one of DesertFox's own pages, and a macro records it, although `:firefox` itself never repeats. On a web page `.` does not map it, because the replay is not a line submit. That is harmless: every listed page is safe to open, and the module's rate limit holds.

## Selection on locked pages

Status: built for parent-process about: pages. The module side is `desertfox-selection.js`. The extension side is `ask_selection` in `src/background/selection_ask.ts`. Pages in a content process (about:protections, error pages, about:reader) follow once a frame script can read them.

A command that reads the `@selection` source (the command line prefill, yank, search, `open` with text) asks the tab's content script. A parent-process about: page has none, so the extension asks the module instead.

- The request is `selection.read { tab_id }`, and the reply value is the selected text. The module reads on demand, so nothing leaves it unasked. It serves every `@selection` source, because the router has one chain, not only the command line.
- The extension asks the module only after the content script gave no answer, and only for the top frame. A module that has no such kind refuses it, and the extension reads no selection, as before. The hello has no flag for it.
- The module refuses unless the tab is still the selected tab of its window, `may_act` allows the window and the tab shows an about: address whose page has a window in the parent process. A selected range in the focused field wins, then the page selection, found through the frames that hold the focus. A field with no selected range leaves the page selection.
- Input fields count, as on a web page. A private tab is read when the module may act in its window, and the line records no history for it, as for any private line.
- The module strips control and format characters and cuts the text at 1000 characters. The extension does both again on the reply, because the reply is foreign input. The text is data: it is typed into a line or a query and never run or used as an address.

## Page code on locked pages

Status: built, off by default. The module side is `desertfox-locked-pages.js`. The extension side is `src/content/locked_shim.ts` and `src/background/browser_module_rpc.ts`. The kinds and snapshots are in `src/shared/browser_module_protocol.ts`. What Firefox does there is measured in [firefox-behavior.md](../firefox-behavior.md#locked-pages-locked-page-modes).

With the setting `browser_module_pages` on, DesertFox's own `content.js` and bundles run inside the PDF viewer and Reader View, so the keys that work on a web page work there too (hints, caret, which-key, the command line). The exception is a route that `LOCKED_PAGE_ROUTES` refuses on a locked page, such as snippets. The module's key tree (above) still covers about:addons, about:preferences and every other locked page.

What runs where:

- In the extension: the background answers each page call through the same router as a content script's message. It refuses a type the route table (`LOCKED_PAGE_ROUTES`) does not list for a locked page, such as snippets.
- In the module core: the attach rule, the calls and pushes, and the snapshots. Chrome code never parses a page message.
- In the page's process, a sandbox: `locked_shim.js` (the `browser` global, a typed surface over the module's transport), then `content.js`, then bundles. The module loads files only by name from a fixed list.

Trust boundary and principal:

- The sandbox runs under the expanded principal `[page, extension]`, as Firefox gives a content script on a web page. It never runs under the system principal, so the feature adds no privilege over a content script. For this reason about:addons and about:preferences are out of scope: they work only under the system principal. Chrome hints label them instead ([Hints on Firefox's own pages](#hints-on-firefoxs-own-pages)).
- A page script sees nothing of the sandbox. The transport sits on the sandbox global, not on the page window.
- Chrome relays the JSON text of a page message as it came. The extension reads it, checks it against the route table and a size cap, and answers. The shim checks the same list, but the background never trusts it. `tab_id` and `document_id` are facts chrome reads, never fields of the page's message.

Channel kinds (all JSON text with a size limit and an age limit, in both kind tables):

- `page_call`, from the module: a page message for the background, with a reply.
- `page_push`, to the module: a background message for the page, in place of `tabs.sendMessage`, with a reply. A push settles when the page answers or its attach ends.
- `page_gone`, from the module: chrome says an attach ended, on pagehide and when the page's window goes away. The background marks a document left only on this word. A same-address load event does not end a lock, because the PDF viewer sends a second one with no new document.

Both calls name a `document_id`, one id per attach, so a call from a document that a load replaced is refused. A page that Back restores from the cache attaches again under a new id.

Snapshots carry the read-only data a message is too small for: the keymap with its site rules, the config status, the theme and the which-key panel of normal mode. The extension writes one session storage key per part with its own cap and rewrites it when the part changes. The module checks each part once (`validate_snapshot`) and hands the shim a copy. A missing, invalid or over-cap keymap or config snapshot leaves the page code stopped and the module keys in force. Site rules on a locked page match the tab's address, which the background reads.

Lifecycle:

- The module attaches a page only when the kill switch pref, `browser_module` and `browser_module_pages` are on, the snapshots are present with the protocol version (`BROWSER_MODULE_PROTOCOL_VERSION`), the tab is not private (unless DesertFox has private access), and chrome reads the page kind as the PDF viewer or Reader View.
- A pagehide settles every open call and push with an error and sends `page_gone`. A pagehide of a page that goes into the back-forward cache keeps the sandbox, and the page attaches again under a new id when it returns. Any other pagehide destroys the sandbox. Turning either setting off, the kill switch, a version mismatch or a failed start does the same and takes the page code out. Tab close clears the tab's lock.
- The setting is on by default and works only with `browser_module` on. While it is off, such as after `:set browser_module_pages false`, a hint key on these pages shows a notice that names it (see [Keys on locked pages](#keys-on-locked-pages)).
- A snapshot part over its cap is removed, and the background logs one console warning per part per session with its size and the cap. [privacy.md](../privacy.md) states what it writes and relays.

## Safety

- Startup: every step at load and per window runs in a `try`. A failure logs one line, turns the module off for the session (all windows lose their listener) and never throws into the loader.
- A Firefox internal that throws on a key leaves that key to the page and logs one line per distinct error.
- With the pref off the module loads no frame script, says no hello and handles no message. It turns on at once when the pref does. Turning the pref off takes the hello back. The frame scripts stay loaded for the session once loaded, so they check the pref and do nothing while it is off. Turning it on again asks each tab for a fresh report.
- The module makes no network request and runs no code it reads. A key row or tree leaf names a command a feature file defines, and a request names a kind on a fixed list, each with checked args. It writes the extension only the hello and the from-module list. The hello has one writer, the core: a feature sets a flag on its fixed list (`bar`) with `set_hello_flag`.
- A request may name a Firefox page from the module's own list (`firefox_page.open`). The module builds the address from its table, and the request carries no address, query or fragment. A page joins the list only when opening it changes nothing: no listed page acts on open. about:config shows its warning page when the pref asks for it, and the actions of about:support, about:profiles, about:processes, about:crashes and about:debugging each need a click, most with a confirm. The passwords page, the one that shows private data on screen, stays off the module route.
- A finished match is the only key data the module sends: the tokens of a forward leaf and the count, never raw key events or the keys of an unfinished sequence. There are two exceptions. One is the text held after a key that opens the command line (at most 32 characters), which goes to the line in the `cmdline_panel.open` reply or into the address bar. The other is the hint keys: while chrome hint labels show, each key the user types goes to the add-on in `chrome_hints.key` (any single character, Backspace, Enter or Tab), so the add-on can narrow the labels. A page hint start sends the tokens of its hint leaf and the count in `page_hints.want`.
