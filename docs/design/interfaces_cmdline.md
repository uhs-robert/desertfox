# Command line and invocations

Area: the command line, completion and invocations.
READMEs: `src/cmdline/README.md`, `src/shared/completion/README.md`, `src/shared/README.md`, `src/background/README.md`.
Source: `src/cmdline`, `src/shared/completion`, `src/shared`, `src/background`.

## Invocations and prompts

Every caller produces one shape:

```ts
type Invocation = { id: string; args?: Record<string, unknown>; count?: number };
```

- A key binding is one invocation, or an array of invocations that run in order. Pipes have no replacement, because context sources cover the cases the config uses. If a binding ever needs one command's result, a command declares `returns` with a type, and a later step in the array takes it with `{ from: "previous" }`. The keymap loader checks the types. This is not built.
- A binding asks for input only through an explicit `prompt`. If a binding leaves a required param out and sets no `prompt`, the loader warns and skips the key. The prompt opens the command line with completion for that param's type. A binding with a `prompt` compiles to a background step, and the router opens the command line with the text typed in. A binding can prefill the prompt from a context source, for example the current URL for editing.
- A binding that leaves a required `key` param out captures it: the next key press fills the param. The compiler checks the other args at load, stores the step on the background side, and moves the leaf under a branch of its own, in the child `ANY_KEY` (the empty token). The matcher takes one printable key there and fills the param in a copy of the leaf. So the captured key is a value even when it is a prefix elsewhere (`g` after `m`), and a count typed before the binding reaches the command (`5@q`); a command decides whether to use it. Escape, a chord or a named key ends the wait, and the key gets one more try as a first key, as after a stray prefix. Backspace drops the wait like any prefix key. A binding in `browser` mode cannot capture. A character find (`caret.find`) also gets a second child, `LIVE_KEY`, holding `caret.move` with `unit=find_repeat`, in the direction of the binding (`forward` for `f` and `t`, `back` for `F` and `T`). While the caret sink reports a live find, the key flow feeds `LIVE_KEY` in the same key press, so the find key repeats at once and a typed count reaches the repeat. Which-key shows the wait as a group with one `<key>` row and skips `LIVE_KEY`. The `only` form of a site rule matches the capture by its first key and not by the captured one.
- A binding that starts with `:` carries `prompt: { param, prefill? }` in the stored file. The key types its command into the command line and waits, and the user edits it and presses Enter.
- The command line and the config parse the same grammar into an invocation, as described below. Keymaps and the native host also accept the `args` object.

### Command line syntax

One grammar covers the command line and every binding in the config. The text is what the user types and what a `:` key shows. `search arch -b "rust lifetimes"` becomes:

```json
{ "id": "open.search", "args": { "engine": "arch", "where": "background", "query": "rust lifetimes" } }
```

- The first word is a `name`, an alias or a full id. The config uses the same words, and the build tool maps them to the id.
- Flags come first, then the subject. `--value` sets an enum (`hint --background --links`), `--name` turns a switch on (`hint --rapid`), and `--name=value` sets any param, split at the first `=`: `scroll.pixels --dx=-50`. This is the way to turn a switch off (`--rapid=false`). A declared short letter does the same as the long flag: `-b`, `-r`, and `-c=Work` for a valued param. A hyphen in a flag reads as `_` in the name (`--word-end`).
- There are no `--no-` flags, no space-separated values (`-c Work`) and no clusters (`-tb`). An unknown dash word before the subject is an error, so a typo never becomes a query. `-h` and `--help` show a usage line.
- The subject is the `main` param. The first word that is not a flag starts it, and the rest of the line joins into it: `search arch pacman mirrors` gives the query `pacman mirrors`. After the subject starts, everything is text, so `open https://a.example -b` opens that whole string. Write `--` to end the flags early when the subject starts with a dash: `open -- -b`, `search -- -std c++`.
- Quoted words are never flags, engines, values or `@source`s: `open '-b'` opens the text `-b`. Quote a value that has spaces or `=` with shell rules: `open -t "https://a.example/?q=a b"`.
- A `main` param marked `verbatim` (the `selector` of `hint`) takes the raw typed text from its first word to the end of the line, end-trimmed. Quotes, backslashes and inner spacing stay, and a leading `@name` is text, not a source: `hint --custom a[href="x"] > b` gives `a[href="x"] > b`. The usual rules for flags and `--` still apply before it. A verbatim param must be a `string`, `main`, and not `value_of`. The printer writes its value raw, and completion reads quotes inside it as plain text.
- A required `strict` string param that is not the subject is positional. The first bare words fill the positional params in schema order, then the subject takes the rest: `set hint_letters asdf` gives `name` then `value`. A positional param takes its word whatever it says, so a typo reads "name expects one of ...". It shows as `<name>` in the usage line.
- When a command has exactly one number param, and no `main` param, a bare number is its subject: `tab.goto 1`, `zoom.set 1.5`. A negative number is a value, never a flag. A command with two number params needs `--name=value` for them. When the command has a `main` param, a leading number is part of the main text, even when the command also has a number param: `tab.unload 3 GitHub` picks the tab `3 GitHub`, and the count is `--count=2`. A negative number word there is text too: `tab.move -1`.
- A command whose only argument is a required value takes it as the bare subject: `mode ignore`, `cmdline.history prev`, `visual.act yank`. `mode --ignore` works too.
- An enum whose values come from a runtime list, the search engine, is the first bare word, and only when it names an engine: `search arch pacman`. An engine name can hold dots (`search github.repo.issues foo`). `--engine=arch` also works, and the printer writes it only when the bare word would not read back. `--` stops the engine check, so `search -- arch maps` searches the default engine for "arch maps". Build time knows the resolved engine names from `search_engines.toml` plus the built-in `duck`, and the command line from the loaded engines. `tools/build-config` warns about an engine name that starts with `-`, because only `--engine=` can name it.
- An unquoted `@current_url`, `@selection`, `@clipboard`, `@bookmark_title` or `@search_query` is a context source. The router fills it in when the key is pressed. It works as the subject or after `=`.
- A leading `:` (config only) makes the binding type its command into the command line and wait. `gO = ":open -t @current_url"` shows `open -t https://this.page/...`. The stored file names one param to fill: the one that holds a `@source` (which becomes the prefill), else the `main` param, else the first param. A command with no params cannot take a `:`.
- Unknown flags, a param set twice and an unknown source are errors with a message.
- A param whose `when` condition does not hold is an error with a message, for example "container needs where tab, background or window".
- The printer writes the shortest text that reads back as the same args, with short flags: the engine, then flags in param order, then the subject. It leaves out args equal to the default and adds `--` when the subject would read as a flag. `gO` prefills `open -t `. Docs and the help page use the long form.
- Wording says before, after, previous and next, never left or right, because vertical tab layouts exist.
- The `desertfox run` script uses the same parser.

Completion reads the same definition:

- A command word completes by fuzzy match on the dotted id.
- A `-` lists that command's flags with their descriptions, from `short` and the long names. Flags already set drop out.
- A `--name=` prefix completes that param's value from its source, for example the containers.
- Any other word completes the subject by its type, for example engine names, tabs or bookmarks, then the query.

### Command line and completion

The address bar keyword `df` (the `omnibox` manifest key, `src/background/omnibox.ts`) runs a command on a page where no key reaches DesertFox. You type `df`, a space and the command text, for example `df tab.next`, and press Enter. The text takes the command line's path: the same parser, then the router, whose check is the one validator. Every router command runs. A command that needs the page, such as a scroll, refuses on a page with no content script, as it does anywhere else. Nobody can type a missing value into a prompt there, so a command with a missing value refuses with its usage, and so does text that is no command (`df rust`). Refusals reach the user as a notification when the page has no content script to draw a toast. Enter in a new tab or a background tab sets `where` on a command that has that param. A parsed line is added to the command line history, except from a private window. A line typed while DesertFox is off is refused and not added to that history. Command aliases from the config work after `df`, as on the command line. The keyword is fixed in the manifest, so it cannot change at run time. The address bar shows the hint "Type a DesertFox command" as its first row. Below it come up to nine suggestions from the command line's own completer (`onInputChanged`), built from the loaded commands, configured aliases and the setting and engine lists. A row's content is the full command text, and its description is the command name, the summary and the keys. The completer has no live source here, so no tab, bookmark or history row appears, in any window. An answer that finishes after a newer keystroke is dropped. The description is plain text (see `docs/firefox-behavior.md`).

The command line is an extension page in an iframe, so page scripts and CSS cannot reach it. It reads the stored keymap itself and asks the background for everything else. Keys typed while it opens are buffered and replayed.

The list opens with the line and shows every command, so the line is never an empty list. Each row has a name, the first sentence of the intent, the args (flag names and the subject) and the keys. In a narrow window the description shrinks first, then the args collapse to "…". The name never drops. The list shows up to 10 rows of 26px, with no scroll bar, and the host grows the frame upward to fit.

The cursor word decides what the list offers. A first word completes command names, fuzzy over the whole dotted name: `tab.` lists the tab family and `tc` finds `tab.close`. A word that starts with `-` lists the flags of that command with their descriptions, and the value after `=` lists the values of that param. Any other word lists the subject candidates. A quoted word never completes, and after `--` only the subject candidates show. One fuzzy scorer ranks every source: a name hit beats a description hit, a dot is a word break, an exact name ranks first and a tie goes to the shorter name.

Tab previews the selected row in the line and cycles. The list keeps ranking the text the user typed, and typing starts over. A single match goes in at once. Up and Down move and preview like Tab while the list is open, and stop at its ends. On a fresh line, before any typing or Tab, and with the list closed, they walk the history, so `:` Up Enter reruns the last command. Escape closes the list first and the line second. Enter runs the line as shown. The note row shows the usage of the selected row, or "no match".

Completion sources load only when the param being completed needs them: commands, open tabs, bookmarks, search engines, containers, headings, sessions and enum values.

`heading` lists the headings of the page, and `sh` opens the line with `heading ` typed. Jumping to a heading is a reading task, not a hint task, so it uses the list and the line's own typing, with no labels. The rows come in page order, each indented by its level counted from the shallowest level on the page (a page without an h1 loses no width) and tagged `h2`, `h3` in the description column. The indent is padding, so the highlight of a fuzzy match still counts the letters of the heading. Typing ranks by the one fuzzy scorer, best match first, and Enter with text and no selected row jumps to the best match. A pick puts `3 Heading text` in the line, and the leading number wins over the text. The heading goes to the top of the view, instantly, and focus, caret and address stay. A page with no heading shows the usual "no match" row. Which headings count is the rule of the hints bundle (`src/content/lib/headings.ts`): h1 to h6 and `role=heading`, by the aria level. A hidden, empty, tiny or clipped heading, and one in a closed `<details>`, gets no row. A heading in a same-origin frame is listed unless the frame is hidden or clipped, and the jump scrolls the frame too. Row text is the rendered text. The headings sit in the page, so the host script answers: the page sends `list_headings` over the port, the host runs `heading.list` in the hints bundle and sends the rows back, with no trip through the background. The bundle keeps the list as a snapshot of elements. The line drops it when it closes, except after Enter, when it drops it once the submitted command has run. A reply that arrives after the line closed is ignored. If the chosen element has left the page at Enter, `heading` refuses with "That heading is gone".

`copytabs` (`yT`) copies the open web tabs of this window as a list in the same formats, one line per tab, and `scope=all` adds the other windows, a blank line apart. It runs in the background and drops tracking parameters like `copylinks`. `copylinks` copies the web links of the page as a list, one line per link. `yL` takes the whole page and `yl` only what is in view, both as Markdown. The `scope` param (`page`, `viewport`) and the `format` param (`markdown`, `plain`, `org`) reach the rest from the command line. Only http, https, ftp and file addresses count: mailto, tel, javascript, data and links to a fragment of the same page are dropped. A link counts once, by its absolute address, in page order, and a hidden link is skipped. Its text is the visible text, else the aria-label, the title, the image alt, then the address. The list stops at 500 links. A same-origin frame and a shadow root count, a cross-origin frame does not (`copylinks` has no `--all-frames`). The toast says "Copied N links", and an empty list refuses with "No links on this page". The code sits in the hints bundle (`src/content/hints/yank_links.ts`), because the content script has no room for it.

`]i` and `[i` (`page.focus_field`) focus the next or previous form control: text fields, `contenteditable`, selects, checkboxes, radios and every kind of button, in page order. Disabled controls, hidden inputs and controls with no box are skipped, and off-screen ones count. The start is the focused control, else the last one Escape left, else the top of the view (the first control not above it). A count moves that many controls and stops on the last. Past the last or before the first the key shows a notice and leaves focus alone, and it does not wrap. The control takes focus without a scroll and is then centered if it is not fully in view, in each frame that holds it. Insert mode follows the existing `focusin` rule, so a checkbox or a button gets focus and the mode stays normal. The code is in the hints bundle (`src/content/hints/focus_fields.ts`), which reaches shadow roots and same-origin frames. The content script passes the last blurred field along, because the bundle cannot see it. `gi` keeps its own text-field rule in the content script.

`]l` and `[l` (`page.focus_link`) walk the links with an address the same way and only focus them. Enter then follows the focused link. Known limit for `]i` and `]l`: when a key focuses an element inside a same-origin frame, the next step walks only that frame, until Escape or a click leaves it.

`]h` and `[h` (`page.heading`) scroll the next or previous heading to the top of the view, instantly, as the heading search does, and leave focus, caret and address alone. Which headings count is the rule of `heading` above. The start is the heading the last `]h` or `[h` jumped to while it is still on screen, so a heading near the page end, which cannot scroll to the top, is passed and not picked again. The bundle keeps that heading as one weak reference. `zt`, `zz` and `zb` (`scroll.align`) align that heading, and its frames innermost first, when it is the newest of the heading jump, a focus change and a selection change: a focus or selection change after the jump empties the slot, so the field or selection wins. A heading that left the page, or whose frame navigated away, is skipped for the next candidate. `sh` picks fill the same slot. Otherwise the start is the view and not the caret: next is the first heading whose top is below the view top, previous the last one above it, and `.` keeps going. A count moves that many headings and stops on the last. Past the last or before the first the key shows a notice ("No next heading", "No previous heading") and does not wrap. Every jump of `]h`, `[h`, `}`, `{` and the `sh` pick leaves the target just below a fixed or sticky bar that covers the top of the view. The bundle finds the bar with one `elementFromPoint` at the top edge and walks up to the element whose `position` is fixed or sticky. A bar over a third of the view is no header and counts as no bar. The bar bottom is also the top line of the next pick, so the next press passes the block just placed. The code is in the hints bundle (`src/content/lib/headings.ts`). `]H` and `[H` go to the last and first heading of the page, take no count, set the same align slot (so `zt` works after them) and show "No headings" on a page with none. `}` and `{` (`page.heading` with `next_block` and `prev_block`) step the same way over a wider set: headings plus `p`, `pre` and `blockquote` of at least 40 characters (a blockquote counts once, not its paragraphs), minus page chrome (navigation, footer, aside, form and dialog, by tag or role, and every header that no article, aside, main, nav or section holds). They show "No next section" or "No previous section" at the ends and "No sections" on a page with none. `li`, `dt`, `figure` and tables are no stops.

Tabs and bookmarks come from the background, because it knows the window and privacy of the line's tab. A string param asks for them with `values: { from: "tabs" }` or `{ from: "bookmarks" }`. The page asks once per kind, keeps the answer for the line and ranks it with the shared scorer on every key. The row list shows "loading" in the note row until the answer lands. Each kind has its own fetch in flight, so kinds do not drop each other. A reply is dropped when the line has closed. The background answers only the frame whose line redeemed a ticket, until the tab closes or navigates or the next line redeems. The frame matters, because any frame of the page can embed its own copy of `cmdline.html`. A normal line lists only normal tabs and a private line only private tabs. Bookmarks list in both.

- A tab row reads `3: GitHub`: the number is the tab's place in its window's tab bar, counted from 1, so it stays while the user types. Picking it puts the number and title in the line. `tab` reads a leading number as that place, and the number wins over the title. Other text is a fuzzy match on title and address, and an equal tie is refused with both tabs named. The `completion_all_windows` setting (default false) lists the tabs of every window. The same number then exists once per window, so the title picks one, else the line's own window.
- The `cmdline_prompt` setting sets the text before the input. `caret` (the default) shows `> `, bold, in the `secondary` theme role. `colon` shows `:` in the `primary` role, normal weight, with a small gap. Any other value is custom text in the caret style and holds its own trailing space. Every value is 1 to 8 characters on one line.
- The `statusbar_widgets` setting (default `url, scroll, tabs`) lists the widgets on the right of the open command line, in list order. An empty list hides the area. `url` shows the host and path without the scheme, query or fragment, in the `ok` token for https and the `warn` token for http. The label is cut to 30 characters with an ellipsis, so a long path can be partly or fully hidden. The full address is the title. Other schemes get no color, and the widgets do not use the `error` token. `scroll` shows `Top`, `N%` (kept between 1 and 99, so the edges read `Top` and `Bot`, never 0% or 100%), `Bot` or `All` for the page's `scrollingElement`. `tabs` shows `[n/m]`, the tab's place in its window. Each value is a snapshot taken when the line opens and does not change while the user types. The widgets are hidden on `/` and `?` search lines, whose note row shows the match count, and on a line narrower than 30rem.
- A bookmark row shows the title and the address. With no word typed, the list shows the 20 newest. Picking one puts the address in the line. A typed word ranks by use as well as text. `bookmark` takes an exact address first, then the best fuzzy match with the same use boost, and refuses an equal tie. The answer is `{ rows, folders }`: the folder paths go once and each row holds indexes into them, newest copy first. A dim cell shows the last part of the row's newest folder, and `+N` when more folders hold the address. `bookmark` and `bookmark.remove` take `--folder=` (the `folders` list), which keeps the rows filed in that folder or any subfolder. The folder matches as filing does: an exact path, else a fuzzy match, and an equal tie or a shared path is refused. The list shows no row for text that picks no folder, and Enter refuses it. `bookmark.remove --folder=X` removes only the copies at that address inside X. `open` rows and the new tab page keep the flat list with no folder cell.
- A tab row leads with fixed-width cells, in this order: a status cell (`%` the current tab, `#` the alternate tab, which is the tab the user was on before, then small icons for pinned, audible, muted and discarded), a container mark, a favicon, then the name, the address and the keys. The icons are CSS masks, so they take the text color. The container mark is Firefox's own container icon in the container color, and a colored dot when the icon cannot load. The default container and private tabs have no mark. The favicon is sent only as a data: URL of at most 32768 characters (Firefox gives loaded, restored and discarded tab icons as data: URLs, measured on six sites in Firefox 160 with lengths from 1306 to 23682, and gives `chrome:` icons to `about:` pages, which are dropped), and a failed load shows a plain glyph. The favicons load from the data: URL, so the list opens with no network request. The tab model port sends each row's favicon in every snapshot and patch, so 100 tabs with a Reddit-size icon send about 2.4 MB per command line open. `#` is the tab the window was on before its current one, which the background tracks from `tabs.onActivated` in `storage.session`. The `contextualIdentities` lookup fails quietly when containers are off, and then no row has a mark.
- `open` and its tab variants complete from bookmarks and history (`values: { from: "open" }`, `kind: "open"`). The background answers every row, tagged `bm` or `hist`, in the group order of the `open_completion` setting (default `["bookmarks", "history"]`, a source left out is not read), and drops a history row whose address is a bookmark. History comes from a cache of the 20000 newest visited addresses that the rank Worker holds (`history_cache.ts`), minus `about:`, `moz-extension:` and `data:` addresses. A private line lists no history. With no word typed the page shows the 20 newest bookmarks and `history_completion_max` history rows (default 10), a cap that rides in the answer. A typed word ranks every row as one list, raised by use, and an equal score keeps the group order of `open_completion`. Site rows (tag `site`) follow the rules in "Ranking by use" and come last on an equal score. A dim `bm`, `hist` or `site` cell tells the rows apart. Enter on text that matches no row still opens the address or searches with the default engine. The `history` permission adds an install prompt on update.
- The `p` group is Page. `pp`, `pt` and `pw` open the clipboard here, in a new tab and in a new window, and `P` stays the one-key paste in a new tab. `pr` (`page.print`) calls `tabs.print`, which opens Firefox's print window on the active tab and returns no result. `ps` (`page.save_pdf`) calls `tabs.saveAsPDF`, which asks for a file name: a cancelled picker is silent, and a failed write shows a notice. Both run in the background, so the content script grows by nothing, and neither is repeatable: `.` skips them, but a macro records and replays them. Neither takes a tab id, so `:page.print` from another tab still acts on the active one. `gr` (`page.reader`) calls `tabs.toggleReaderMode` on the active tab and runs in the background. It refuses with a message when the tab is neither an article (`isArticle`) nor already in Reader View, and when Firefox rejects the call. On a Reader View tab the same key returns to the page. A typed `about:reader` address is refused with a message that points at `gr`.
- `history` lists only history (`values: { from: "history" }`, `kind: "history"`), newest first, from the same fetch as `open` and with no dedup against bookmarks. A private line gets no rows, and Enter there refuses with "no history in a private window". The answer carries the `history_list_max` cap (default 20) for an empty word, and a typed word ranks every cached row, so history older than the 20000 newest addresses is not reachable by typing. The cache fills from one `history.search` when the background starts and stays current from `onVisited`, `onTitleChanged` and `onVisitRemoved` (`allHistory` clears it). Events that arrive during the fill apply after it, in order. A page the cache has not seen enters only after a one-row `history.search` lists it, since `onVisited` also fires for hidden pages such as redirect sources. Past 50 such pages waiting, one full search refills the cache instead of the one-row checks. Firefox sends no event when only some visits of a page are deleted, so such a page can keep a too-new last visit until the background restarts. Until the fill ends, a line gets the 1000 newest entries from `history.search` and never waits, and it ranks again over the whole cache once the fill ends. The rows of `open`, `history` and the finder rank in a Worker the background starts, which holds the only copy of the cache, and the page gets the top 100 rows of each word over a port (`background/rank_service.ts`). Keys typed during a rank collapse into one rank of the newest word. Tab, Up, Down, the row keys and the finder's Enter wait up to 1 s for rows on their way, then run in order. Typed keys and keys bound to those row commands wait behind them in order. Any other key acts at once: a bound key such as Ctrl+U runs, and a browser key such as a paste or Shift with an arrow keeps its action. With no word typed, a list shows at most 100 rows, whatever its cap. The cap is 20000 because the Worker ranks off the page: a first key over that many rows takes tens of milliseconds there and blocks no key. The page no longer ranks, which at 20,000 rows took 70 to 100 ms in Node. A typed word ranks by use as well as text. A pick puts the address in the line. Enter takes an exact address first, then the best match on title and address with the same use boost, so it opens the row the list shows first, and refuses an equal tie. It has no default key and no container flag.

- Ranking by use. `open`, `history`, `bookmark` and the finder raise a text match by how much a page is used, and never lower one: score times (1 + boost), with the boost from 0 to 0.6, added before the exact-name bonus, so an exact name still leads. The background computes the boost once per line and list. Half of it comes from the visit count (by its log, full at 50 visits) and half from the last visit (it halves every 14 days). Firefox gives only those two numbers per page, not the visit list its own frecency reads. A bookmark, quickmark or closed tab takes the boost of its address's history row, so a bookmark opened daily ranks as a page visited daily, though the history row drops out as a duplicate. An open tab gets 0.3 plus its page's boost, within the same cap. A private line reads no history, so in `open` and the finder only its tabs get a boost. The `bookmark` list and its Enter read the boost on every line, so they agree. Site rows: in `open` and the finder, a typed word of at least 2 characters with no space that starts a label of a visited web host (`git` finds `github.com`, not `digital.com`) offers that host's home page, at the scheme of its newest visit, as a row of its own. Up to 3 hosts show, the most used first, and each ranks with the summed visits of all its pages. A host whose home page is already a row (a bookmark, history row, quickmark or tab) gets no site row. A private line gets none. Site rows rank by the same scorer on the host name.
- Engines ride the same fetch (`kind: "engines"`) for the first word of `search`, `--engine=` and `engine.show`. A row shows the engine name and its label. The background marks each engine with a yes or no for whether the line's tab page can fill its slots, and sends no page data. A row the page cannot fill is dimmed and reads "unavailable" in the args column; `engine.show` marks none. A word that ends in a dot (`github.`) lists every engine under that prefix, deeper ones included. The parser still reads a hidden engine, so a picked or typed one runs and the router refuses it.

#### How the completion code works

Code map: `src/shared/completion/README.md`. The rules the lines there leave out:

- `ranked_client.ts` asks the background for the rows of `open`, `history` and the finder, which rank there because they rank the history (`background/rank_service.ts`). It sends the word over the rank port with one request in flight per line, keeps only the newest word waiting behind it, drops a reply it no longer waits for, keeps the last 4 answers, clears them on `stale` and ends with the line. While an answer is on its way the list keeps the last ranked rows and reads `loading`.
- `anything.ts` builds the finder's rows (`,,`, `open.anything`) from the tabs, the background's answer and the engines. It ranks the tabs here, drops an answer row whose address a tab holds, and merges the rest in by score, so every group ranks as one list, raised by the use boost each row carries. An equal score keeps the group order, and the search rows come last.
- A finder row carries a `ref` (`shared/anything_ref.ts`) and the completion carries `highlight_first`, so `session.ts` highlights the first row while a query is typed and submits that row's reference in place of the text. `cmdline.submit` takes an optional `where` (`<S-Enter>`), which `session.ts` sets on a submitted command that has a `where` param.
- `live.ts` and `model_client.ts` are pure: the page passes in the asking and the redraw. The tabs come from `model_client.ts`, not from `live.ts`.
- `set`, `toggle` and `unset` complete setting names, then the values a setting lists, from the generated `shared/setting_completion.ts`. The page imports no setting rules, so it checks only the shape of a line (`check_args_shape`) and the background refuses a bad `:set` value at Enter.

### Background files for the command line

Behavior of the `src/background` files for this area, moved here from `src/background/README.md`.

- `omnibox.ts`: the `df` address bar keyword. `create_omnibox` takes the text of Enter, parses it with the command line grammar and runs it through the router, so the one validator checks the args. It never prompts: a command with a missing value refuses with its usage, and so does text that is no command. A modified Enter (new tab, background tab) sets `where` on a command that has the param. `changed` answers `onInputChanged` with up to nine rows from the command line completer (`create_completer`, no live source, so no history rows in any window) and drops an answer that a newer keystroke passed. A parsed line goes into the command line history, except from a private window. `main.ts` wires it only when `browser.omnibox` exists.
- `cmdline_service.ts`: what the command line page asks for. `issue_cmdline_ticket` gives the host a one-time ticket for its tab, kept in `storage.session`. `open_cmdline` takes that ticket once and returns the line tab's window id, the all-windows setting, the history, the engine and container lists, the registry's commands (snippets included), the configured aliases, the font names for `set font_family` and the user CSS, and `record_cmdline` adds a parsed line to the history (last 100, newest last, a repeat moves to the end, nothing from a private tab). Redeeming a ticket also marks the tab as an opener in `storage.session`, with the redeeming frame's id as the value, so only that frame is an opener (`is_opener(tab, frame)`) and the next line replaces it. Tab close and the start of a navigation remove the marker. A ticket asked for a subframe's keys also stores that frame as the line's target (`target_of`): `run` messages with `from_line` run there, and the marks list reads that frame's address. A new line, the frame's navigation and the tab's close forget it, and so does the frame being gone.
- `font_names.ts`: `create_font_names(deps)`, the font names that `set font_family`, `set font_family_mono` and the Settings page suggest. `refresh` takes the host's `list_fonts` answer alone, or, when the host does not answer, a canvas probe of `FONT_CANDIDATES` (`shared/font_candidates.ts`), and stores `{ host, names }` under `desertfox_font_names`. `read` answers from that cache, or from a probe-only list it stores on the first ask, and never waits on the host. Reads and writes queue, so a probe-only write never lands after a host answer. `main.ts` refreshes at startup, after a host update, on a permission grant and on each `list_font_names` message from an extension page. The cache refills when it is absent or malformed. The probe runs here and nowhere else, so `cmdline_page.js` gets ready names in the `open_cmdline` answer.
- `history_cache.ts`: the 20000 newest history rows, newest first, kept for history completion. It lives in the rank Worker (`rank_index.ts`), and fills from `history.search` at each start of the Worker (the browser history is the truth, so nothing is stored). It applies `onVisited`, `onTitleChanged` and `onVisitRemoved`, which `rank_service.ts` forwards in order, and holds events that arrive during the fill until it ends. `when_ready` resolves when the first fill ends. An address it has not seen enters only after a one-row `history.search` lists it, because `onVisited` also fires for hidden pages (redirect sources, framed links). Past 50 such addresses waiting, one full search refills the cache in place of the checks. Firefox sends no event when only some visits of a page go, so a page can keep a too-new last visit until the next start. Under a future event page the first line after a wake gets the fallback. Before the fill ends `read` gives nothing and the lists rank the newest 1000 pages instead. It holds only normal visits, because Firefox fires no event for a private one.
- `complete_items.ts`: `complete_items` answers the command line page with the bookmarks (one row per address with indexes into the folder paths, sent once), windows, bookmark folders, sessions (none for a private line), registers (those of the line's privacy) or engines it lists for `bookmark`, `tab.attach` and `search`. `rank_inputs` reads what the rank Worker needs for `open`, `history` and the finder besides the history: the bookmarks, quickmarks, closed tabs, open tabs and settings. `bookmark_usage` gives the bookmark list its use boosts from the Worker's `usage_for`, or from the newest 1000 rows when the Worker gives no answer. The `tab` list does not ask: it reads the tab model. The engines come in config order, each with its label and a yes or no for whether the line's tab page can fill it (`available_engine_names`). The page URL stays in the background. It answers only an opener tab, checks the marker again after the browser call, lists only tabs of the line's privacy, and gives an empty list when the browser call fails. The tab handler lists through the same code. The pure row readers (`listed_tabs`, `bookmark_items`, `closed_tab_rows`) are in `shared/completion/tab_rows.ts`. The use boost and the site rows of those lists come from `completion_rank.ts`. `tab_rows_action` (the row keys of the list) closes, mutes, pins, unloads or loads the tab ids the page captured at the key press, through `tab_actions.ts` and `tab_discard.ts`. It skips ids with no tab and refuses the whole message when one id is a tab of the other privacy. `reopen` also takes a store id and reopens the tabs through `reopen_tabs_in_container`: it leaves out the line's own tab and tabs already in that container, skips a tab that fails and goes on, and refuses a private line or an unknown store id. The answer holds only a refusal text, which for a reopen names what moved and what stayed.
- `rank_service.ts`, `rank_worker.ts`, `rank_index.ts`, `completion_rank.ts`: the lists that rank the history (`open`, `history`, the finder) rank in a Worker that holds the only copy of the history rows. `rank_service.ts` starts the Worker (`rank_worker.js`), forwards the history events to it in the order they fire, answers its questions (the history search, the one-row check of a new address, the 1000-row fallback) and relays each line's rank port (`shared/rank_port.ts`). It admits a port only from the line's page in the opener frame (`is_opener`), checked once at connect, reads the line's inputs once per list, keeps one request per line in the Worker and only the newest one waiting (an older one gets `skipped`), and frees the line on disconnect. A Worker that fails is ended and started again, at once if it ran 5 s or more, else after a wait that doubles from 250 ms to 30 s. Each line's request in flight goes to the new one with the line's inputs, and each line that ranked gets `stale`. The background asks the Worker two questions on the same channel and never copies its 20000 rows: `usage_for` (the use boost of each bookmark address, for the bookmark list) and `pick_history` (Enter on `history <text>` runs the `pick_entry` rule over the Worker's rows and answers one row or the refusal text, which the handler throws again as a `RuntimeRefusal`). Each answers undefined while the fill runs, when the Worker fails or when it is silent for 2 s, and the caller then reads the newest 1000 rows from the browser, with no second wait on the Worker. A request that throws in the Worker gets an empty answer marked `failed`, and a word over 1000 characters an empty answer, so a line never waits on a request. `rank_index.ts` is the Worker's state, pure: the history cache, each line's inputs and snapshots, and the rank. A snapshot copies the rows once per line and list, so events never change it under a rank. A snapshot built before the fill ended uses the fallback rows, is dropped when the fill ends, and its line gets `stale`. `completion_rank.ts` builds the rows of each list from the inputs and the history (the use boost `usage_boost` from visit count and last visit, joined by address, and the visited hosts as site rows `site_items`) and ranks them per word into the top 100. The finder's tab rows rank in the page, so the finder answer leaves the tabs out, sends as many more rows as there are open-tab addresses, the site rows unranked and the tab boosts and use times.

### Shared files for the command line

Behavior of the `src/shared` files for this area, moved here from `src/shared/README.md`.

- `rank_port.ts`: the port between the command line page and the background for the lists that rank the history: the request (a word, a sequence number and the finder's over-fetch), the reply of at most 100 ranked rows with their scores, and the `stale` push.
- `folder_pick.ts`: `pick_by` (exact key, then best fuzzy match, a tie refused), `pick_folder` (the filing rule for a folder path), `in_folder` and `rows_in_folder` (the subtree test). The `bookmark` handlers and the command line page share them, so a typed `--folder=` filters by the rule that filing uses.
- `url_build.ts`: pure URL math. `parent_url` and `root_url`, `url_target` (text to a URL) and `config_url_target` (the same under a config's engines), the two engine fillers: `engine_search_url` for typed text and `engine_url`, which follows `fallback` when the page cannot fill the slots, and `own_pages`. The slot table and the template filler are in `src/shared/engines/`.
- `font_candidates.ts`: the built-in font names (`FONT_CANDIDATES`), `probe_fonts` (keeps the names whose canvas width differs from `monospace` or `serif`), `canvas_measure` and `merge_font_names` (dedupe, drop names `parse_font_family` refuses, sort, cap 2000). Extension pages only: the background page runs it (`src/background/font_names.ts`).

### Command line files for the command line page

Behavior of the `src/cmdline` files, moved here from `src/cmdline/README.md`.

- `host.ts`: the `cmdline` bundle (`cmdline.js`). The first `:` injects it into the page. It mounts the iframe in a closed shadow root inside a top-layer popover that `mount_surface` shows last, so toasts and which-key draw below it. When a surface mounts and shows the popover again, the host gets `desertfox-restacked`, refocuses the frame and sends `refocus` so the page refocuses its input. It sets the `cmdline` mode, keeps the keys typed before the page is ready, and sends the parsed command to the background as a `run` message from the page's own frame. It closes itself if the page has not opened in 3 s, if the page removes the bar or sends the frame elsewhere, and on Escape even when the frame is gone. However the line ends, the host first moves the focus to the page itself, never back to a field or link that had it before, and holds the page's keys that can bind (`hold_keys_until_`). It sends `drain`, and the page answers `drained` with the keys it got after the end, once its window has lost the focus. The host replays those keys ahead of the held ones, then removes the frame, or after 1 s when the page never answers. A replayed key acts only through a DesertFox binding: its keydown was cancelled in the frame, so the page never sees it.
- Lines for a subframe: the top frame draws the line, so it shows where the user looks. In a subframe, `cmdline.open` sends the line to the top frame (`relay("top", "cmdline.open")`, see `src/shared/relay.ts`), stays in the `cmdline` mode and sends each key it gets up as `cmdline.token`. The top frame mounts the line with the subframe's mode and scroll place, asks for a ticket that names the subframe (`target_frame`), and the background runs the submitted command in that subframe. The headings and the page search run in the subframe (`cmdline.headings_ask`, `cmdline.find_text`, `cmdline.find_end`), which sends its results back up. When the line ends, the top frame hands the focus back (`cmdline.focus`) and then sends `cmdline.end`, with the late keys when the subframe took the focus and none when it refused. The subframe replays the keys the top frame did not take at the end. A top frame under 120 px tall refuses, and the subframe draws the line itself. A subframe that never hears the end leaves the mode after 2 s.
- Focus loss in a subframe: the line's frame takes the real focus, so the subframe gets `blur` and `focusout`, and a popup that closes on them would close (#634). While a subframe is the remote end of a line, it holds capture listeners for both events on its window that call `stopImmediatePropagation`. `open_remote` adds them. Every end removes them: `end_remote`, the mode leaving the line, and the no-room fallback. The page sees no focus loss, and DesertFox's own `blur` report for the frame (`src/content/main.ts`) is skipped for the same time. A page listener that ran before the bundle loaded, or a page that polls `document.hasFocus()`, still sees the loss.
- `style.ts`: the page's sheet (`CMDLINE_STYLE`). Pure text with no imports, so DesertBird can vendor it. `tools/build.mjs` puts it into `cmdline.html` at the `<!--cmdline-style-->` marker, so the built page is unchanged.
- `page.ts`, `cmdline.html`: the page in the iframe (`cmdline_page.js`). It reads the stored keymap and runs its own matcher on the `cmdline` mode, because the content script's keys cannot reach into the iframe. Enter parses the line with `parse_command_line` (flags first, then the subject; see the command line syntax in `docs/design/interfaces_cmdline.md`), over the commands and aliases that `open_cmdline` returns, through `word_lookup.ts` (`src/shared/completion/`), because the registry cannot load in a page. It loads the user CSS and the `cmdline_prompt` preset (`caret`, `colon`) or custom text from the same answer after its own styles.
- Search flavor: `/` and `?` open the same line with a search prompt (`start.search`). Its text is a pattern, so the page parses nothing, offers no list and keeps no history. Each edit goes to the host as `find_text`, the host calls the caret bundle's `find.live`, and the answer ("3 of 17") comes back as `find_status` into the note row. Enter sends `find_commit`. Whatever way the line ends, the host calls `find.end` with `keep` set only after Enter.
- `session.ts`: the text, the inline message, the completion list and the history walk, apart from the DOM. `source_ready` ranks the text again when tabs or bookmarks arrive. A parse error keeps the line open and shows the error. Tab, Up and Down preview a row in the line, Escape closes the list before the line. `pick(index)` takes a clicked row like Tab does. `cmdline.help` (`<C-h>`) gives a `help` effect for the selected command row, else for the typed command word, else a note. Pure.
- `list.select` (`<C-Space>`) marks tab ids in `session.ts`. The marks survive filtering and drop out when the tab leaves the model. `list.act` (`<A-u>`, `<A-x>`, `<A-m>`, `<A-p>`) gives a `tab_rows_action` effect for the marked tabs, else the highlighted tab row, with the ids fixed at the key press, or a note on any other row. `<Esc>` clears the marks before it closes the list. `list.act` with `reopen` (`<A-c>`) opens a container prompt in the same session: the text and caret of the tab list wait in `picking`, the rows are the line's containers ranked by name, and `<Esc>` brings the tab list back with the marks and the highlighted tab. Enter fixes the ids at that moment and gives a `reopen` effect with the container's store id, or a note when no container is chosen, there are no containers or no tab is left. `page.ts` sends the message and shows only the refusal. The rows change when the model's patch arrives: `source_ready` ranks the text again and keeps a previewed tab row on the same tab by id, and a tab that is gone ends the preview. A tab row accepted by a click or a single-match Tab stays tied to its tab until the next edit, so the number in the line follows it.
- `list.ts`: draws the rows, ten at most, as a window that follows the selection. A tab row leads with a status cell (`%`, `#` and flag icons), a container mark and a favicon, then a dim window number when the list spans more than one window. Then come the name, description, args, then the keys cell, which never shrinks and shows `keys` from the `open_cmdline` answer (see [Mode parents](keys.md#mode-parents)). An unloaded tab row has the class `desertfox-cmdline-item-discarded`, which dims its name. Its widths are CSS in `style.ts`. Each item carries its absolute `data-index`, and the name of a built-in command row is a help link (`data-help`, from `help_ids` in the `open_cmdline` answer). `page.ts` delegates clicks on the list: a link click sends `open_help` to the background and closes the line, a click elsewhere picks the row.
- `status.ts`: the labels and the security state of the status widgets (`statusbar_widgets`): the address by scheme, the scroll text and the `[n/m]` tab place, and `status_widgets`, which orders them by the setting. The background sends the address and the tab place in the `open_cmdline` answer. The host reads the scroll place of the page's `scrollingElement` before it mounts the frame and sends it in `start`. The page draws the widgets once, on the right of the line, so each value stays what it was at open. `url` takes the ok or warn token by scheme and carries the full address as its title. A search line shows none, and so does a line under 30rem wide. Pure.
- Keys while rows are on their way: Tab, Shift-Tab, Up and Down over the list, the row keys and, in the finder, Enter act on rows, so while the list reads `loading` the page holds such a key and runs it once the rows land. Typed keys and keys bound to row commands that come after it wait behind it, in order. Any other key acts at once, as a bound Ctrl+U does. The finder's Enter then opens the row that landed. After 1 s they run anyway, so a lost answer never stalls the line.
- `protocol.ts`: the message shapes between the host and the page. Only `ready` and `start` use the page's window. The rest travels over a `MessageChannel` port handed over with `start`, so page scripts cannot read or forge it. The host gets a one-time ticket from the background and sends it in `start`, to the extension origin only. The page trades it for the history and commands, so a copy of `cmdline.html` that a site embeds on its own gets nothing.

The history lives in `storage.local`, kept by `src/background/cmdline_service.ts`. The page measures its panel and tells the host the height it needs with a `resize` message, so the list grows upward. The bookmark, window, session and engine rows read from the background (`complete_items`), and the open, history and finder rows from the rank port. Both answer only the frame whose line redeemed a ticket. Before it submits, `page.ts` runs a pre-check with `check_args_shape`: a missing value shows the error under the line and keeps it open, and nothing goes to the background.

The heading rows read from the page: the page sends `list_headings` over the port, the host calls `heading.list` in the hints bundle and answers with `headings`. `heading.go` runs from the snapshot that call took, so the host drops it (`heading.clear`) when the line closes, or after the submitted command ran. A row carries `indent`, which `list.ts` draws as padding on the name, so the highlight positions stay right.
