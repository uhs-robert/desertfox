# DesertFox design

DesertFox is a keyboard-first Firefox extension. It has a small scope and one command registry. Every command is defined once. Keys, the command line, completion, help, the palette and which-key all read that definition.

The extension works on its own. Oasis Dots adds an optional native host. Through it, a desktop shell can show the mode, and later list and run the same commands.

Status: phase 1 is built on the `feat/phase-1-core` branch. [firefox-behavior.md](firefox-behavior.md) holds the measurements this design rests on, and [keymap.md](keymap.md) maps every binding in the current browser config to a command here.

## Constraints from Firefox

Phase 0 measured these on Firefox 159 with real key presses. They shape every choice below.

- A content script catches plain keys such as `Shift+J` on web pages only. It catches nothing on about: pages, addons.mozilla.org, view-source, reader view, the PDF viewer, or while the address bar has focus. The address bar keyword `df` runs commands on these pages (see "Command line and completion").
- `moz-extension://` pages do not match `<all_urls>`, so no content script runs on them by itself. The help page loads `content.js` with a script tag, and `tabs.sendMessage` reaches it like any other tab.
- The `commands` API (Firefox shortcuts) catches a modifier chord such as `Alt+J` everywhere except on a page that cancels the key first. Firefox rejects bare keys and Shift plus a letter there.
- A `document_start` listener is ready 11-58 ms (median 27) after the first byte of a page. Keys before that moment are lost. Navigating from a live page keeps the old listener until the new page commits.
- A message from a content script to the background and back takes under 1 ms. So does a round trip to a native host over an open port.
- Firefox still supports Manifest V2 with a persistent background page. MV3 in Firefox uses event pages that sleep after 30 s.

## Decisions

- Manifest V2 with a persistent background page. No state lives only in memory, so a later move to MV3 changes the manifest and little else.
- TypeScript, bundled with esbuild. No framework. No runtime dependency in the content script.
- No Rust and no WASM. The slow parts are DOM work and messages between processes, not computation. WASM also adds load cost to every page.
- No ex-command language. The command line parses text into the same typed invocation that a key produces. Snippets are the only user code. They come from the user's own config folder, or from an import the user accepts snippet by snippet.
- No shell access. The native host has a fixed set of verbs.
- Native tab groups and the parked sidebar stay separate layers. A native group is the user's own, named and collapsed by keys. The sidebar groups tabs by site on its own, and a future sidebar shows `group_id` only as a badge.

## Registry

The registry lives in the background page. A command is plain data plus a handler:

```ts
define("tab.close", {
  label: "Close tab",
  intent: "Close the current tab and focus the next one, or close the tabs around it.",
  params: [
    { name: "side", type: "enum", values: ["none", "all_before", "all_after", "focus_previous"],
      default: "none", short: { all_before: "B", all_after: "A", focus_previous: "P" },
      value_labels: { focus_previous: "and focus previous" } },
  ],
  runs_in: "background",
  count: "repeat",
  run: async (ctx, { focus }) => { /* ... */ },
});

define("open.search", {
  label: "Search",
  intent: "Search with a keyword engine from the search engine list.",
  name: "search",
  params: [
    { name: "engine", type: "enum", values: from_engines },
    { name: "query", type: "string", main: true, default: { from: "selection" } },
    { name: "where", type: "enum", values: WHERE, default: "here",
      short: { tab: "t", background: "b", window: "w" } },
    { name: "container", type: "string", values: from_containers, short: "c",
      when: { where: ["tab", "background", "window"] } },
  ],
  runs_in: "background",
  run: async (ctx, { engine, query, where, container }) => { /* ... */ },
});
```

The fields follow the Oasis action library (`home/hypr/.config/hypr/lib/act/init.lua`) so the two lists have one shape:

- `id`: `group.name`, lowercase with underscores. Same pattern as Oasis actions.
- `name`: the command line name, set by hand. It is optional, and it holds no `.`. The full id always works on the command line, and it is the name of most commands: you type `tab.close`, `window.new`, `tab.pin`. Only two kinds of command get a name. The one-word commands are `open`, `search`, `paste`, `copy`, `hint`, `heading`, `find` and `github`. The family words are `tab` (switch), `bookmark` (open), `history` (open), `zoom` (set), `scroll` (lines), `mode` (set) and `help` (open), one per group, for the main action. Names are never derived from the id, because derived names collide (`tab.close` and `window.close`).
- `aliases`: more command line names. The defaults ship none.
- `label`: a short title in sentence case ("Close tab"). Which-key, the palette and completion show it. A key shows this label plus a phrase for each arg its binding sets, see [Which-key](#which-key).
- `intent`: plain text on one line. Its first sentence is the summary that the completion list shows: it starts with a verb, takes at most 60 characters and names no other command. Later sentences are detail. Help, the status page and which-key hover show all of it. The registry rejects an empty or multi-line one, and a test holds every built-in command to the summary rule.
- `params`: typed and named. The types are `int`, `float`, `string`, `bool` and `enum`. `key` is one key press (one character, so `a`, `Z`, `'`). It takes `pattern` for the set a command accepts and no `optional`, `values` or `strict`. A command has at most one `key` param. On the command line a required `key` param is a bare word (`markadd a`), and one with a default is a flag (`--slot=a`). A param with no `default` that applies, no `optional` and no `when` is required. The order is for display only.
- Value rules, plain data that travels in `commands.json`: `min` (the smallest value of an `int`), `pattern` (the source of a regular expression that a `string` must match), `format` (`"url"`: a `string` must be an absolute address, as `URL.canParse` reads it), `strict` (a `string` with a static `values` list accepts only those values, where `values` alone is completion only) and `optional` (a `string` or `enum` may be left out or empty and then reads as `""`, in place of `default: ""`) and `value_of` (a `string` holds the value of the setting named by a sibling `strict` param, and `check_args` checks it with that setting's entry in `SETTING_SPECS`, an empty value passing). `strict` compares exactly, like an enum value. `check_args` applies them. The registry checks at define time that each sits on a param type that can carry it.
- `value_labels`: on an `enum` param with a fixed value list, a short phrase for each value ("and focus previous"). Which-key adds the phrase to the label when a binding sets that value, and completion shows it beside the value. Every key must be one of `values`, and a value that is the default in every context has no phrase. A value with no phrase reads as the raw value with spaces for underscores. The registry checks this at define time.
- `description`: one sentence for a flag, under the same rule as the first sentence of an `intent`. A string on a bool or valued param. A map from value to sentence on an enum with a fixed value list, with no entry for a value that is the default in every context. Completion shows it beside the flag. Every flag of a built-in command has one, and a test checks it. The registry checks the sentence at define time when one is present.
- `main`: the one `string` param that config and the command line take as the subject, for example the URL of `open` or the query of `search`. At most one per command.
- `short`: the one-letter flag of a param. A string for a bool or a valued param (`short: "r"` gives `-r`, `short: "c"` on a string gives `-c=Work`). A map from value to letter for an enum with a fixed value list (`{ tab: "t" }` gives `-t`). Never on `main`, `rest` or an enum with a runtime list. `-t -b -w` mean where (tab, background, window) and `-c` means container on every command that has those params. A default value gets no letter, because the printer leaves it out.
- `rest`: marks a `string` param as text with spaces. The grammar already lets the `main` value run to the end of the line.
- `when`: the param is valid only if one other param has one of the listed values. For example, `container` needs `where` to open a new tab or window, because Firefox cannot change the container of an open tab. This is the only kind of condition, apart from the default list, `value_when` and `pattern_arms` below. A command that needs more is split into two commands. A new window with no `container` keeps the container and private state of the tab that opened it, and a private tab refuses a named container.
- Default list: `default: [{ value, when }, ..., plain]`, an ordered list of arms with an optional plain value last. Each arm uses the `when` syntax, and unlike a param's own `when` it may name several params, which must all have a listed value (AND). The first arm that holds wins, else the plain value applies, else the param has no default and is required. This holds for a param with `when` too: when its `when` holds and no arm does, the param is required, so `media seek percent` needs its count while `media seek up` defaults to one. `open.url` sets `default: [{ value: "", when: { where: ["tab", "window", "background"] } }]` on `url`, so `open` with no URL is an error for `here` and opens the new tab page elsewhere. A hint `action` can default to `play_pause` for the `media` filter and to `here` otherwise. An arm may name a param that has a default list itself, the define check refuses a cycle and names its path (`action -> filter -> action`), and an arm that names several params makes the param depend on each of them. The list travels in `commands.json`. Help prints the plain value first, then each arm: `here; play_pause when filter is media`, and `background when filter is links and rapid is true` for an arm with two params. A value that is the default under only some arms keeps its flag, short, phrase and description, because it is a choice elsewhere. Flag completion hides the value that is the default for the flags already typed. The printer drops an arg equal to the default that the other args give, so `.` replays the same value. The key compiler stores the resolved default in the leaf.
- `value_when`: on an `enum` param, `{ value: { sibling: [values], ... } }`. The value is allowed only while every named sibling has a listed value (AND, as in a default arm). A value with no entry is allowed everywhere, so a new sibling value gets no restricted enum value until someone lists it. `check_args` checks the final value, explicit or default, so a combination that makes no sense is an error on the command line and never compiles into a key. A hint `action` of `background` needs a `filter` that has an address, and `mute` needs `media`. The define check refuses a key that is not one of `values`, a bad sibling, and a default arm whose value its own condition does not allow (the arm must name every sibling the rule names). The rules travel in `commands.json`.
- `pattern_arms`: on a `string` param, `[{ pattern, when }, ...]`. The final text must match the pattern of the first arm whose `when` holds (several siblings allowed, AND). Each value of a sibling, such as the `action` of `media`, so takes its own value set, which one `pattern` cannot give. With no arm holding, the plain `pattern`, if any, applies instead. A `when` param may also carry a default list: when its `when` holds and no arm of the list does, the param is required, so `media seek percent` needs its count while `media seek up` defaults to one. The arms travel in `commands.json`.
- Every static argument rule lives in the param schema, and one `check_args` applies it for the command line, key map compile, `tools/build-config` and the router. A context source (`@selection`) passes the check as a marker, so the router runs `check_args` again on the expanded text. `help` takes a page name (`quick_start`) or a command id, matched exactly. A command handler never judges argument values. It reports only runtime failures, such as a tab that is gone, a refusal from Firefox or an empty selection, and throws them as `RuntimeRefusal`. `test/registry/handler_static_rules.test.ts` fails when a background handler throws anything else on args the schema accepts.
- `default`: a value, or a context source (`{ from: "current_url" }`, `"selection"`, `"clipboard"`, `"bookmark_title"`, the title of the current page's bookmark, `"search_query"`, the query of the search results page, read back through the engines' URL templates). A context source can carry `then`, a second source read when the first has nothing: `{ from: "selection", then: "search_query" }` is the default of the `query` of `search`. The router fills a context source where it is available, so a background command can ask for the page selection.
- `runs_in`: `background` or `content`. The router sends the invocation to that side. A command never runs in both.
- `needs`: what must be true to run it. `content` means a content script in the tab. A permission name means an optional permission. The router refuses with a message instead of failing silently. A command that needs a permission only for some args (`page.reload` with `clear`) checks it in the handler and throws `RuntimeRefusal`. Either way the message names `:permissions.grant <permission>`, which opens the grant panel.
- `count`: what a numeric prefix does. `repeat` runs the command that many times. A param name fills that param, for example `tab.goto` takes the count as its `index`. `ignore` drops it.
- `repeat_limit`: the largest count prefix the router accepts, for a command whose repeats are hard to undo. It needs a `count` rule other than `ignore`. A bigger prefix is refused with a toast (`A count of 100 is over the limit of 20 for tab.close`) before any step of the request runs, so `.`, `3.`, macro replay and snippets refuse the same way and a sequence never runs half. A typed param count (`tab.unload --count=100`) is not a prefix and is not limited. `tab.close` and `tab.unload` carry 20. A yes/no confirmation line, so a big count can still run, is a possible follow-up.
- `bridge`: whether a program outside the browser may run the command through the bridge socket (see [Bridge host](#bridge-host-in-progress)). Every built-in command states it with `bridge: true` or `bridge: false`, and a test fails when one does not. The tab commands that move between tabs (not `tab.switch`, which matches a title or address and so tells a caller which tabs exist, and not `tab.close`, which closes whole sides of the tab bar: the id-addressed `activate` and `close` verbs behind `bridge_share_tabs` do both), `tab.mute`, `open.url`, `media.act`, the `scroll.*` commands and the mode commands (`mode.set`, `mode.insert`, `mode.escape`) say true. The rest say false. A hard-coded never-list wins over a true.
- `repeatable`: whether `.` can replay the command. The default is true. These commands opt out: `command.repeat`, `browser.close_all`, `browser.focus_page`, `config.reload`, `debug.perf`, `debug.restart`, `page.print`, `page.save_pdf`, `frame.exit`, `help.open`, `help.key`, `native.install`, `native.update`, `permissions.grant`, `engine.show`, `settings.set`, `settings.toggle` and `settings.unset`, and the page commands that only change a mode or open a prompt: `mode.set`, `mode.escape`, `mode.pass_next`, `hint.key`, `find.open`, `help.whichkey`, every `cmdline.*` and `list.*` command, `caret.move` and `visual.act` (a motion replays in normal mode, where it does not apply). One command opts out by its args: `page.reload` is not repeatable with `clear` set to `all`, so `.` and a macro never run a clear of every site. The `repeatable` field takes a function of the checked args for this.
- `jumps`: whether a successful run moves the view in the tab it ran in, so the router records the place it left in the jump list. Absent means false, and a command without it pays nothing. The field takes a function of the checked args: `open.url`, `open.search`, `open.anything`, `open.clipboard` and `page.follow` jump only with `where` set to `here`. `scroll.to`, `find.next`, `find.prev`, `heading.go`, `page.heading` and `mark.jump` always jump. Reading and recording are in the jump list paragraph under Marks.
- `modes`: the modes where a key can run the command. The default is normal.
- `completion`: where the command line list offers the command. Absent means always. `hidden` means never, and a list of modes means only when the line was opened from one of them. Typing the name still runs the command.
- `advanced`: `true` for a rarely used command (`config.reload`, `debug.restart`, `native.install`, `native.update`). Only the help Commands page reads it: the cards stay hidden until `#/commands?advanced` (the "Show advanced commands" button sets it), and a `#command=<id>` link still shows its card. Completion, keys and which-key ignore it.
- `run`: the handler. It gets the context (tab, frame, mode) and the checked args.

Validation is strict and happens in one place, the same as `Act.resolve` in Oasis. The command line, keys, the native host and the palette all pass through it.

Define-time checks cover names and params too:

- `name` and `aliases` are unique across all commands, snippets included.
- At most one param is `main`, and it is a `string`.
- A long flag names at most one param of a command: no two enum params share a value, and no bool name repeats a value. `_` reads as `-` in a flag, and no value or bool is called `help`. Names and values are lowercase with underscores.
- A short letter is one ASCII letter, never `h`, and unique within the command.
- A `when`, and every param named in the `when` of a default arm, is a param that exists, with valid values, and never the param itself.

A set of options where at most one can apply, for example open, background tab or copy link for a hint, is one `enum` param with a value per option. Two flags from the set both set that param, so the command line rejects them together. No list of exclusions exists. This turns the hint command into five params: `action`, `filter`, `selector` (with `when: { filter: "custom" }`), `text` and the `rapid` switch.

A build step writes `commands.json` from the registry: id, name, aliases, label, intent, params, count, repeat_limit, modes, completion and advanced. Help, the palette, which-key and the native `list` verb read it. The content script does not load it.

## Invocations and prompts

Every caller produces one shape:

```ts
type Invocation = { id: string; args?: Record<string, unknown>; count?: number };
```

- A key binding is one invocation, or an array of invocations that run in order. Pipes have no replacement, because context sources cover the cases the config uses. If a binding ever needs one command's result, a command declares `returns` with a type, and a later step in the array takes it with `{ from: "previous" }`. The keymap loader checks the types. This is not built until a binding needs it.
- A binding asks for input only through an explicit `prompt`. If a binding leaves a required param out and sets no `prompt`, the loader warns and skips the key. The prompt opens the command line with completion for that param's type. A binding can prefill the prompt from a context source, for example the current URL for editing.
- A binding that leaves a required `key` param out captures it: the next key press fills the param. The compiler checks the other args at load, stores the step on the background side, and moves the leaf under a branch of its own, in the child `ANY_KEY` (the empty token). The matcher takes one printable key there and fills the param in a copy of the leaf. So the captured key is a value even when it is a prefix elsewhere (`g` after `m`), and a count typed before the binding reaches the command (`5@q`); a command decides whether to use it. Escape, a chord or a named key ends the wait, and the key gets one more try as a first key, as after a stray prefix. Backspace drops the wait like any prefix key. A binding in `browser` mode cannot capture. A character find (`caret.find`) also gets a second child, `LIVE_KEY`, holding `caret.move` with `unit=find_repeat`, in the direction of the binding (`forward` for `f` and `t`, `back` for `F` and `T`). While the caret sink reports a live find, the key flow feeds `LIVE_KEY` in the same key press, so the find key repeats at once and a typed count reaches the repeat. Which-key shows the wait as a group with one `<key>` row and skips `LIVE_KEY`. The `only` form of a site rule matches the capture by its first key and not by the captured one.
- A binding that starts with `:` carries `prompt: { param, prefill? }` in the stored file. The key types its command into the command line and waits, and the user edits it and presses Enter.
- The command line and the config parse the same grammar into an invocation, as described below. Keymaps and the native host also accept the `args` object.

### Command line syntax

One grammar covers the command line and every binding in the config. The text is what the user types and what a `:` key shows. `search arch -b "rust lifetimes"` becomes:

```json
{ "id": "open.search", "args": { "engine": "arch", "where": "background", "query": "rust lifetimes" } }
```

- The first word is a `name`, an alias or a full id. The config uses the same words, and the build tool maps them to the id.
- Flags come first, then the subject. `--value` sets an enum (`hint --background --links`), `--name` turns a switch on (`hint --rapid`), and `--name=value` sets any param, split at the first `=`: `scroll.pixels --dx=-50`. This is the way to turn a switch off (`--rapid=false`). A declared short letter does the same as the long flag: `-b`, `-r`, and `-c=Work` for a valued param. A hyphen in a flag reads as `_` in the name (`--word-end`).
- There are no `--no-` flags, no space-separated values (`-c Work`) and no clusters (`-tb`). An unknown dash word before the subject is an error, so a typo never becomes a query. `-h` and `--help` show a usage line.
- The subject is the `main` param. The first word that is not a flag starts it, and the rest of the line joins into it: `search arch pacman mirrors` gives the query `pacman mirrors`. After the subject starts, everything is text, so `open https://a.example -b` opens that whole string. Write `--` to end the flags early when the subject starts with a dash: `open -- -b`, `search -- -std c++`.
- Quoted words are never flags, engines, values or `@source`s: `open '-b'` opens the text `-b`. Quote a value that has spaces or `=` with shell rules: `open -t "https://a.example/?q=a b"`.
- A `main` param marked `verbatim` (the `selector` of `hint`) takes the raw typed text from its first word to the end of the line, end-trimmed. Quotes, backslashes and inner spacing stay, and a leading `@name` is text, not a source: `hint --custom a[href="x"] > b` gives `a[href="x"] > b`. The usual rules for flags and `--` still apply before it. A verbatim param must be a `string`, `main`, and not `value_of`. The printer writes its value raw, and completion reads quotes inside it as plain text.
- A required `strict` string param that is not the subject is positional. The first bare words fill the positional params in schema order, then the subject takes the rest: `set hint_letters asdf` gives `name` then `value`. A positional param takes its word whatever it says, so a typo reads "name expects one of ...". It shows as `<name>` in the usage line.
- When a command has exactly one number param, and no `main` param, a bare number is its subject: `tab.goto 1`, `zoom.set 1.5`. A negative number is a value, never a flag. A command with two number params needs `--name=value` for them. When the command has a `main` param, a leading number is part of the main text, even when the command also has a number param: `tab.unload 3 GitHub` picks the tab `3 GitHub`, and the count is `--count=2`. A negative number word there is text too: `tab.move -1`.
- A command whose only argument is a required value takes it as the bare subject: `mode ignore`, `cmdline.history prev`, `visual.act yank`. `mode --ignore` works too.
- An enum whose values come from a runtime list, the search engine, is the first bare word, and only when it names an engine: `search arch pacman`. An engine name can hold dots (`search github.repo.issues foo`). `--engine=arch` also works, and the printer writes it only when the bare word would not read back. `--` stops the engine check, so `search -- arch maps` searches the default engine for "arch maps". Build time knows the resolved engine names from `search_engines.toml` plus the built-in `duck`, and the command line from the loaded engines. `tools/build-config` warns about an engine name that starts with `-`, because only `--engine=` can name it.
- An unquoted `@current_url`, `@selection`, `@clipboard`, `@bookmark_title` or `@search_query` is a context source. The router fills it in when the key is pressed. It works as the subject or after `=`.
- A leading `:` (config only) makes the binding type its command into the command line and wait. `gO = ":open -t @current_url"` shows `open -t https://this.page/...`. The stored file names one param to fill: the one that holds a `@source` (which becomes the prefill), else the `main` param, else the first param. A command with no params cannot take a `:`.
- Unknown flags, a param set twice and an unknown source are errors with a message.
- A param whose `when` condition does not hold is an error with a message, for example "container needs where tab, background or window".
- The printer writes the shortest text that reads back as the same args, with short flags: the engine, then flags in param order, then the subject. It leaves out args equal to the default and adds `--` when the subject would read as a flag. `gO` prefills `open -t `. Docs and the help page use the long form.
- Wording says before, after, previous and next, never left or right, because vertical tab layouts exist.
- The `desertfox run` script uses the same parser.

Completion reads the same definition:

- A command word completes by fuzzy match on the dotted id.
- A `-` lists that command's flags with their descriptions, from `short` and the long names. Flags already set drop out.
- A `--name=` prefix completes that param's value from its source, for example the containers.
- Any other word completes the subject by its type, for example engine names, tabs or bookmarks, then the query.

## Keys and modes

The keymap is data, not code. It maps a mode and a key sequence to an invocation:

```json
{
  "normal": {
    "J": { "id": "tab.next" },
    "D": { "id": "tab.close", "args": { "side": "focus_previous" } },
    "sa": { "id": "open.search", "args": { "engine": "arch" } },
    "ca": { "id": "tab.reopen_in_container", "args": { "container": "Family" } }
  },
  "browser": {
    "<A-j>": { "id": "tab.next" },
    "<A-k>": { "id": "tab.prev" }
  }
}
```

- The extension ships a default keymap. The user config overrides it, as described in [Config](#config).
- The background checks each entry against the registry when it loads. A bad entry logs a warning and is skipped, so one typo does not break the rest. The help page lists the warnings.
- Key notation is vim style: `<C-x>`, `<A-j>`, `<S-Escape>`. Sequences match through a prefix tree. A complete match runs at once, with no timeout.
- The modes are normal, insert, ignore, hint, cmdline, caret, visual, line visual and media. See [Caret and visual](#caret-and-visual). Insert mode follows `focusin` and `focusout` on editable elements. Each keydown and keyup also re-reads the focused element and follows a change in whether it takes typing, because a page can change that with no focus event. A key that finds no change leaves the mode alone, so Escape holds in a frame whose body is the editor and keeps the focus. The case that needs the re-read: the Google Sheets cell editor holds the focus all the time and counts as a field only while a cell is being edited (see [Firefox behavior](firefox-behavior.md#the-google-sheets-cell-editor-sheets-cell-editor)). `i` enters insert mode with no field, in every frame of the tab, and a frame that loads later joins it. The background sends one message to the tab with no frame id and keeps only a flag for the hold, never a list of frames, so the extension needs no `webNavigation` permission. A frame under an all-off site rule drops the message and stays in ignore mode, in both directions. Focus leaving a field does not end it. Escape in any frame returns all frames to normal, and so does a navigation. With no field focused, insert mode handles only Escape, so `<C-r>` and the other insert keys go to the browser. `I` is `gi`: it focuses the first field. A hidden input frame is a child frame of the page's own origin that the user cannot see: under 4 px on one side. Where the frame sits does not count, so an editor in a full-size frame that is scrolled out of view is not one. A page such as Google Docs types into one. While such a frame is in normal mode it blurs its own frame element, so the document that holds it gets the keys and every command, sink and panel works there. It hands off on each change into normal mode and when it gains the focus in normal mode, and no rule names a site. Escape hands off in the key's own turn. Every other hand-off waits one tick, so a focus move that leaves the frame for a field of the page is not cancelled. A mouse press that focuses the frame's field returns to insert mode, and so does `gi`, which picks a field in one of the page's hidden input frames ahead of the page's own visible fields. A frame that gains the focus again within 500 ms of a hand-off, with no insert mode between, keeps it, so a page that fights for the focus does not loop. While the page holds the focus, keys the page's editor handles in the frame (arrows and PageDown in Docs) do nothing.
- `,` is the built-in leader for DesertFox's own commands (`,r` reload, `h` help, `s` settings page, `t` toggle a setting, `i` ignore mode, `b` blur, `?` all keys, `"` registers). `<A-?>` lists the first keys in every mode except ignore and the command line (which keeps its own `<C-h>` help). In insert mode with no field focused the chord goes to the page. Space stays with the page, so pause on video sites and Space-to-scroll keep working. `,` alone runs nothing, because a key cannot be both a binding and a prefix. The which-key panel shows the group after the pause, and a key outside the group starts a new sequence, so `,j` scrolls. A lone `,` in normal mode no longer reaches the page. `pass = ","` in a site rule gives it back on one site, and `<C-v>,` passes one comma. DesertFox reserves no user leader: `\` and `<Space>` are unbound by default, and a user who binds Space as a leader loses Space on the page.
- In every mode except insert, ignore, hint and cmdline, DesertFox cancels a `/` or `'` keydown that no binding takes, when focus is not in a field. Shift does not matter, but Ctrl, Alt or Meta do. Firefox starts Quick Find on these keys in page content (see [Firefox behavior](firefox-behavior.md#firefox-defaults-not-measured)), and Quick Find competes with DesertFox's own [page search](#page-search). Insert and ignore mode give keys to the page, and hint and cmdline mode own theirs. Every other mode is covered, so a new mode is covered without a change.
- In caret, visual and line visual mode, DesertFox also cancels every other unbound key without Ctrl, Alt or Meta, outside fields. These are reading modes, and a site shortcut (a letter in a mail app, a digit in a video player) moves the user away from the caret. Tab and Shift+Tab, the function keys, Escape, Page Up, Page Down, Home and End still reach the page. So focus moves, Firefox's own keys work, a page dialog closes and the page scrolls. Space and Backspace stay blocked. Every chord passes too, so Ctrl+C copies a selection. Normal mode passes unbound keys, apart from `/` and `'`.
- A mode badge sits in the bottom right corner, 8 px above the bottom edge. The `mode_indicator` setting controls it: `always` (the default), `not_normal` or `off`. The `palette` setting names a theme (default `oasis_moonlight`), see [Themes](#themes). Light or dark follows the system theme.
- A toast is one short message in the bottom right corner, framed in the color of its kind (error, warning, info or success). It disappears after `toast_error_ms` (default 6000) for an error and `toast_ms` (default 3000) for every other kind, whole milliseconds from 500 to 30000. The compiled keymap carries both values, as it does `which_key_delay_ms`, and the content script hands the one that fits the kind to the `ui` bundle with each toast.
- The which-key panel is a floating frame with a 1 px tinted border and its title set into the top border. The `which_key_border` setting picks the corners: `square` (the default), `round` or `chamfer`. The `which_key_skip` setting lists key prefixes, in keymap notation, whose panel does not open after the delay (exact match, global, checked with the key parser). An instant redraw still shows it: Backspace back to the prefix, or a key typed while a panel is already up. `?` lists only the first keys of the mode. A footer names the exit keys. Below them a `.` line shows the step `.` would repeat, as the command line that does the same (a command with no name shows its label), while the panel is open. A saved count shows too: a count that maps to an argument shows as that argument, and a repeat count, which the command line cannot spell, shows as a prefix such as `5× :scroll`. A label has no argument, so a command with no name shows either kind of count as that prefix. The `which_key_repeat` setting (default on) turns it off. The panel bundle asks the background with `read_repeat_preview` and the background reads the normal slot of the repeat memory only, so a private tab gets no line.
- The `bridge` setting (default off) opens the native bridge, and `bridge_share_tabs` (default off, needs `bridge`) lets it list, activate, close and capture tabs, see [Bridge host](#bridge-host-in-progress). Neither changes the badge or the which-key panel: both stay in the page.
- `browser` mode holds the chords for the Firefox shortcuts. The manifest reserves a fixed number of shortcut slots, and the background assigns the chords to them with `commands.update`. The content script also catches these chords. If it cancels a chord, Firefox does not fire the shortcut as well, which the phase 0 key-blocking page showed.

## Config

The user config is a directory of files, one file per kind of setting. `config.reload` reads them through the native host, and the extension merges and checks them with the same code `tools/build-config` runs. Each start rereads the files through the host once and applies them when they differ from the stored build, so an edit made while the browser was closed needs no `config.reload`. When the browser copy holds changes made in the browser (an import, an editor save, a snippet change), the start asks on the settings page first. Without the host or its permission the extension runs on the stored build, and on the built-in defaults before the first load. `just build-config` only lints the directory and writes nothing Firefox reads. The native host is optional: browser edits cover casual use, and only the config files (TOML, snippets and CSS) need it. A stale `~/.mozilla/managed-storage/desertfox@uhs-robert.json` from older versions is ignored and safe to delete.

### Source files

The tool reads `~/.config/desertfox/` by default. Every data file is TOML. A leftover `.jsonc` file is an unknown file.

| File | Holds |
| --- | --- |
| `keymap.toml` | Every key: bindings per mode, plus the `search_keys`, `container_keys`, `site_keys` and `modifiers` shortcuts. `""` removes a default binding. |
| `search_engines.toml` | Search engines: a tree of named URL templates with slots (`{query}`, `{repo}`, and others). `%s` still reads as `{query}`. Data only, no keys: the letters of the `s/` group live in `[site_keys]` in `keymap.toml`. The built-in `duck` and `site` need no entry, and an entry with their name replaces them. See [Starting engines](#starting-engines). |
| `command_aliases.toml` | Extra command line names, for example `g = "open.search"`. |
| `quickmarks.toml` | Quickmarks: one letter or digit mapped to an address, for example `g = "https://github.com"`. `M<key>` adds entries in browser storage on top of these, and the stored entry wins for the same key. |
| `settings.toml` | Settings such as the which-key delay and the new tab page. |
| `snippets/*.js` | One custom command per file. See [Snippets](#snippets). |
| `themes/<name>.toml` | A local theme that `palette = "<name>"` picks. See [Themes](#themes). |
| `style.css` | Custom CSS for the DesertFox surfaces. See [Styles](#styles). |

Each data file can also have a matching directory, for example `keymap.d/`. The tool merges the main file first, then the files in the directory in name order. A later entry wins for the same key. This is how private config joins without editing public files: a private repo links `keymap.d/50-private.toml` and `snippets/` files into place.

Every key lives in `keymap.toml`. The other files hold only data. A binding is one line of command text, in the grammar of [Command line syntax](#command-line-syntax), or a list of them that run in order, or a table `{ run = "...", label = "...", intent = "..." }` that names the key for which-key and can replace its hover text (`run` is a string or a list). TOML quotes any key that has symbols, so `"<C-[>"` and `"$"` are quoted and `gx` is not. Two shortcut sections remove most repetition:

```toml
# keymap.toml
[search_keys]                   # sa/Sa, sb/Sb
a = "arch"
b = "brave"

[site_keys]                     # s/i, S/i: the engine of the page's site
i = ["github.issues", "gitlab.issues"]
I = ["github.repo.issues"]

[container_keys]                # ca/Ca, cc/Cc, cp/Cp
a = "Family"
c = "Client"
p = "Personal"

[normal]
J = "tab.next"
b = "bookmark.open"
gO = ":open -t @current_url"    # types the command into the command line and waits
y = ""                          # removes a default binding
ww = { run = ":open -w @current_url", label = "New window, edit current URL" }
```

- `sa` searches with the `arch` engine in this tab, and `Sa` in a new tab.
- `ca` reopens the current page in the Family container, and `Ca` opens a prompt, set by an explicit `prompt` on the generated key, prefilled with the current URL in a new Family tab.
- `s/` is the group for the page you are on. Each `[site_keys]` letter lists engines of different sites. On a page the first listed engine whose `hosts` include the page host and whose page slots the page fills runs. Which-key shows a letter only when such an engine exists, so on a GitHub repo page `s/` offers GitHub-wide search and search in this repo, on a user page the GitHub-wide ones, and on an unrelated site nothing. `S/` does the same in a new tab. A member key behaves like `sa`: it searches the selection at once, or opens the command line with the engine typed in. A letter is one key, not `/`, and lists only engines whose `hosts` do not overlap (an engine with no `hosts` overlaps all). `tools/build-config` refuses the rest, and a `search_keys` letter `/` unless the user unbinds both `s//` and `S//`. A row reads the label of the engine the page selects, and which-key hides a letter it cannot resolve. A typed key on a site that fits none refuses with a toast, "No <letter> search for this site".
- `s//` and `S//` search the current site with the built-in `site` engine: the default engine's URL with `site:{host}` added to the query. They show on every page that has a host. The shipped keymap sets the letter `/`, which the build refuses in a user file. If the default engine needs a page slot, `site` uses DuckDuckGo and the load warns. `site` is built when the config loads, so a live `:set default_engine` does not change it.
- `[modifiers]` maps a key inside a group to the args it adds, for example `";r" = { rapid = true, label = "Rapid" }`. The key becomes a group that holds a variant of every other key of the group, with those args added. The `label` names the group. A variant exists only when the command's param schema accepts the args, so an invalid combination is never bound or shown. A key that sets its own `action` gets no variants, and modifiers do not stack. An explicit key at the modifier key wins and the load warns. An explicit key under it wins silently. Normal mode only.
- Containers themselves need no file. Firefox lists their names, colors and icons through `contextualIdentities.query()`, and completion and the `container` param use that list. A name in `container_keys` that does not exist gets a warning at load and is skipped.
- The prefixes for generated bindings (`s` and `S`, `c` and `C`) are settings. An explicit binding in the keymap wins over a generated one.
- A key cannot be both a binding and the start of a longer one, so a user key that extends a default binding (default `sg`, user `sgg`) takes its place: the build drops the default binding and warns once per mode, naming the user keys. A default that a user key replaces includes a binding made by a modifier. The default stays when no extending user key passes the registry check. The build does not check the mode of the extending key, so a user key whose command does not run in its mode still drops the default. This holds for keys from `search_keys` and `container_keys` too. The reverse needs no rule. A user binding shorter than a default group (user `g`, default `gg`) keeps the user key and skips the longer default keys. Two user keys that clash, or two default keys, still skip the longer one with a warning. A vim-style wait on the shorter key is not built, because it adds a pause to every such key.

#### Starting engines

DesertFox has one built-in engine, `duck` (DuckDuckGo), and the `default_engine` setting defaults to it. So clipboard search works with no config. It is added when the config loads and when `tools/build-config` checks names, so the merged file stays as written. An entry named `duck` in `search_engines.toml` replaces the built-in whole. Nothing hides or removes it.

[`examples/engines.toml`](../examples/engines.toml) resolves to 69 engines, `duck` among them, and teaches the tree rules in two worked trees (GitHub and YouTube). Copy it to `~/.config/desertfox/search_engines.toml` and edit it. A TOML file cannot include another file. A `search_engines.d/` file also works, and a later file replaces the table at the same dotted path (a later `[github.repo]` replaces only that node and leaves `github` alone).

#### Engines

An engine is a named URL template. It replaces the former site commands. No provider is built in except `duck`.

- Slots. `{query}` is the typed or selected text, and `%s` means the same. Page slots read the current tab: `{url}`, `{host}`, `{title}`, `{repo}` (GitHub), `{subreddit}` and `{channel}` (YouTube). Each page slot is a small pure function in `src/shared/engines/slots.ts` with its own message for a page that cannot fill it. `{a|b}` takes the first slot that has a value, so `{query|url}` is the typed address, else this page. `{name:raw}` skips escaping, for a path such as `/web/{url:raw}`. Every other value takes `encodeURIComponent`.
- Tree. A table inside an engine is a child, named with a dot (`github.repo.issues`). A child inherits every field and overrides by name. `label`, `keyword` and `reverse` do not inherit: the label is the chain of labels on the path ("GitHub: this repo: issues"), and a `label` field sets one link. A `keyword` names one engine, so a child sets its own. A child cannot be named `url`, `label`, `params`, `fallback`, `hosts`, `keyword` or `reverse`, or like a field or param of its parent. `reverse` is an optional regex that reads the query back from a results page address (see `docs/search_engines.md`, "Reading the query back"); without it the reader comes from `url`. A later file replaces the table at one dotted path.
- Params. `[github.params.type]` declares `default`, `values` (name to URL text) and `children = true`, which generates one child per value. A field set to a value name picks it, and `type = { only = [...] }` narrows the values below that level. A hand-written child beats a generated one. A query pair whose whole value is one empty param (`&type=`) is left out.
- Hosts. `hosts = ["github.com"]` lists the host names of the sites an engine belongs to, and children inherit it. A host matches only itself, so `gist.github.com` needs its own entry. It gates only the generated `s/` and `S/` keys: explicit keys and completion ignore it. The build refuses a `hosts` that is not a list of lower-case host names, and one on a node with no url on it or above it.
- Availability. An engine is available on a page only when every page slot in its URL can be filled. Which-key hides the keys of an unavailable engine, and a group left empty. A key still works when typed, and shows the slot message. An engine with `fallback = "<engine>"` never hides and runs the fallback when its slots cannot fill. Snippets can require slots with a `// requires: repo` header. The background filters the key list, so the content script is unchanged.
- Resolution. `tools/build-config` resolves the tree into a flat map keyed by the dotted name and the extension stores the result, so it only fills page slots and the query. `tools/build-config` runs the same resolution as a lint and writes no engine file. It rejects an unknown slot, a param no URL uses, a field that is neither a known field nor a var some URL reads, a value outside the declared list, a fallback to a missing engine, a fallback loop and a default engine that needs a page slot.
- Help. `help` lists the resolved tree with each engine's URL, slots and the file and level that set each field. `engine.show <name>` opens it at that engine.
- Which tool. A result that is a URL is an engine. Page DOM or several steps is a snippet. Browser APIs (tabs, windows, bookmarks, containers) is a built-in command. A fuller real example: [https://github.com/uhs-robert/oasis-dots/blob/main/home/desertfox/.config/desertfox/search_engines.toml](https://github.com/uhs-robert/oasis-dots/blob/main/home/desertfox/.config/desertfox/search_engines.toml).

### Merge and checks

The merged file has one section per kind: `keymap`, `search_engines`, `command_aliases`, `quickmarks`, `settings`, `snippets` and `css`, plus a format version. The stored keymap holds invocations, so the extension never parses command text. The tool:

- rejects unknown files and unknown sections with a message, so a misspelled file name does not vanish silently. A TOML syntax error names the file, line and column.
- parses every binding string with the registry grammar, then checks it, every alias and every snippet against `commands.json` and reports errors before the extension loads.
- reads snippet code and CSS as text and escapes it, so nobody edits code inside JSON.
- generates a JSON Schema for each data file from `commands.json`, so an editor with TOML schema support (Taplo) completes command names and setting names.

The TOML parser (`smol-toml`) is a dev dependency of the tool only. None of it reaches the extension bundles.

### The settings table

Each setting is one row of data in `src/shared/settings_table.ts`: its kind (true or false, a word from a list, a number, text, a list, a table), the values the kind takes and its default. The check, the expectation text in a problem message, the values the command line offers, the editor JSON Schema, the `Settings` type and the defaults all follow from the row, so a new setting takes one row and one description. A row of kind `custom` (`hint_letters`, `palette`, `new_tab_page`) has its check and expectation written in `settings_schema.ts`. `settable: false` marks a setting that `:set` refuses. `per_site: true` lets a `site_rules` row set the setting for its sites (see roadmap item 6). The one row of kind `site_table` (`site_rules`) takes each such setting as an extra column, checked by that setting's own check. A table field of kind `site_modes` (the `modes` column) holds named site modes, each `{ label, bind }`, where `bind` follows the rules of the `bindings` kind. A table field of kind `bindings` (the `bind` column) holds a table from a key sequence to a binding in the formats of a keymap entry (a command string, a list of steps, `{ run, label, intent }`; the stored form is an invocation table `{ id, args }`). Every setting has a default except `home_page`, because `page.home` refuses without one, and `zoom`, because without one Firefox keeps the zoom it remembers for each site. The editor descriptions live in `settings_docs.ts`, which only the tool imports: the prose is large and no page needs it. The content script reads `src/shared/default_settings.ts`, which `just settings-defaults` writes from the table with one constant per setting, so the content script carries only the defaults it reads. The command line page reads `src/shared/setting_completion.ts` the same way, one row per setting with its name, flags, expectation text and listed values (theme names as of generation), so it bundles neither the table nor the setting rules. The page checks the shape of a line only (`check_args_shape`), and a bad `:set` value shows its error at Enter, from the background. `just test` fails when either generated file is stale, and `just themes` changes the theme names in the second.

### Delivery

`config.reload` (key `,r`) asks the native host for the raw text of the files (`read_config`), builds the config in the background with `build_config` and swaps it in place. Nothing restarts, so the temp edits, the modes and open hints stay.

- The swap runs in the same queue as `set`, `toggle` and `unset`, so a reload and an edit never publish over each other. It replaces the snippet commands (the old ones leave the registry first), compiles and publishes the keymap, tells open tabs (`tree_updated`) and replaces the config the background runs on. Commands that arrive during the swap wait for it to commit. The toast counts every warning Help shows.
- The built config goes to `storage.local` (`desertfox_files_config`), with its build warnings, so Help still lists them after a restart. The raw file text goes beside it (`desertfox_files_source`) in the same write, so an import can rebuild it. A restart, the help page and the new tab page all read what the last reload or import built.
- An import (a zip or a picked folder) goes through the same swap (`apply_files`) and the same slot. It passes the zip guards, drops one top folder that every path shares, and refuses an empty result. Its config files replace the ones in the slot, the installed snippets stay, and the browser edits stay on top. Each imported snippet is stored only when the user accepts its exact code. The settings page also exports the config as `desertfox-config.zip` (the config files, with the saved browser edits as `settings.toml`, or as the last file of `settings.d` when the config has settings files of its own) and the snippets as `desertfox-snippets.zip`. It lists the installed snippets, and Remove rebuilds the config without one through the same swap. A key that binds the snippet refuses the removal. The snippet returns on the next `config.reload` while its file stays in the config folder. A later `config.reload` replaces the whole import.
- The start read (`reload_config_at_start`) reuses the host call every start makes for the version check. It waits for the cached config and runs in the same queue as the swap, then compares the folder's files with the stored source (`desertfox_files_source`). The compare leaves out `autoconfig.toml`, which the host writes from the saved edits and the build never reads, and the folder label, which an import or an editor save changes. An unchanged start builds and publishes nothing. Each swap to the folder's files (a start, Use the folder, `config.reload`) stores a digest of them (`desertfox_host_start_applied`), and a start that finds the copy equal to the folder stores it too. When the browser copy is empty, or still matches that digest, the start applies the folder with `apply_files`. Otherwise the copy holds browser changes, and the start replaces nothing (`host_start.ts`). A profile with no stored digest counts as changed, so it asks once rather than risk a loss. It stores the question (`desertfox_host_start_pending`: the folder, a digest of each side and the files the folder would replace, add or drop) and toasts once. The settings page shows it as a banner with Export config, Use the folder and Keep the browser copy. A choice reads the folder again in the change queue and runs only when the browser copy still matches what the page showed. Keep also needs the folder the page showed. Otherwise it refuses and stores the fresh question. Use the folder takes a folder changed since, because it drops only the browser copy: the user who unpacks the export into the folder clicks once. The export carries the saved edits in its settings file, so the folder then holds them too. Use the folder swaps through `apply_files`, so the edit layers stay on top, and a folder that does not build keeps the browser copy and the question. Keep the browser copy stores the folder digest (`desertfox_host_start_kept`), so the start asks again only when the folder changes. Any swap (an import, an editor save, a reload) drops the question, because its list no longer fits. The first answer wins, and a second page is told it is settled. A host start that cannot read the host drops it too, because no choice can run. Writing the browser copy into the folder stays manual: export the zip and unpack it. The host read happens outside the queue, so a slow host never blocks a `:set`. A start reply is dropped when a config swap (reload or import) commits during the read, because the swap is newer. No permission, no host, a host error and a missing or empty config folder keep the stored config and only warn on the console. Empty means no file but `autoconfig.toml`, because the host creates the folder when it writes that file. The installer never creates the folder. A file that fails the build of a start that adopts keeps the stored config too, and a toast names the problem on every start until the file is fixed. `,r` stays the explicit replace: it applies the folder over any browser copy and refuses a missing or empty folder.
- A reload that cannot finish keeps the current config whole: config, snippets, keymap and stored files. Its toast names the cause and the fix: no permission or no host (run `:native.install`), a host error, a missing config folder, or the problems in the files (the first three, and a count).
- The load checks every setting in the files against `SETTING_SPECS`. It drops a setting with an unknown name or a value the check refuses, warns, and lets the layer below apply. `build-config` refuses both, but a stored slot from an older version can still hold one.
- Managed storage is removed. Firefox read its file once per extension load (see [firefox-behavior.md](firefox-behavior.md), "Managed storage"), which is why `config.reload` uses the host. A fresh install starts on the defaults until the first start or `,r` that reaches the host.
- `debug.perf` (`:perf`, no key) copies the recent timings to the clipboard for a slowness report and toasts the slowest p95. It covers bundle loads (`load_log.ts`), command round trips (background commands only, timed in `router.ts` from the start of a step to its answer; content commands are left out because hint mode, find and caret wait on the user and the registry cannot tell which ones do) and hint build time (recorded by the `hints` bundle). There is no per-key timing, because `content.js` has little headroom and every frame pays for it. The timings are a ring of 300 in `storage.session`, summarized as count, median, p95 and max per name.
- `debug.restart` (no key) restarts the whole extension, for debugging. Firefox loads the content script into open tabs by itself after `runtime.reload`, so the reinjection step stays only as a fallback (see [firefox-behavior.md](firefox-behavior.md), "Phase 1 measurements").
- The help page's Home shows the warnings. The settings page at `home.html#/settings` shows the config source and the steps to apply an edit, and has an input for each setting that `:set` takes. An Export and import section exports the two zips and `desertfox-sessions.json`, imports a zip, a folder or a sessions file, and lists the installed snippets. The sessions file holds the stored shape of the tab sessions (see Tab sessions). The add-on Preferences button opens the settings page, so no separate options page exists.
- `set`, `toggle` and `unset` change a setting from the browser, with no file edit. The settings in force come from four layers, and a later layer wins: the defaults, the config files, the saved edits and the temp edits. The saved edits live in `storage.local` (`desertfox_saved_settings`) and last until `unset`. The temp edits live in `storage.session` (`desertfox_temp_settings`), and a browser restart clears them. `config.reload` keeps them. `debug.restart` clears them, because Firefox clears `storage.session` when an extension reloads. Both layers are global, private windows included. `set name value` saves a value, `set name` shows it and `toggle name` flips a true or false setting. With `--temp` (`-t`) the change goes to the temp layer. A saved change drops the temp edit of the same name, because that temp edit would keep winning and hide the save. `unset name` drops both edits of a setting, so the config file value applies, and `unset all` drops every edit. `unset --temp` drops only the temp edits. A browser edit wins over the config file, as in qutebrowser, where `autoconfig.yml` holds the browser edits. `name` is a `strict` param of the known setting names, and `value` carries `value_of: "name"`, so `check_args` checks the value with that setting's entry in `SETTING_SPECS`. The two prefix settings are refused, because a live change could collide with other keys. The help page tags every value that differs from the default with its top layer: `settings.toml`, `saved` or `temp`.
- Each change to the saved edits is mirrored to `autoconfig.toml` in the config folder through the host (`write_autoconfig`). The file is write-only: the build skips it and nothing reads it back. A failed write never blocks or undoes the edit. Without the permission it is skipped quietly, and any other failure warns once in the background console.

The background compiles the keymap into a prefix tree and writes it to `storage.local` for the content scripts.

### Styles

Every surface (which-key, the command line, hints and the mode indicator) draws from CSS custom properties, for example `--desertfox-bg-core`, `--desertfox-fg-core`, `--desertfox-primary` (titles and groups), `--desertfox-secondary` (keys), `--desertfox-font` and `--desertfox-radius`. The variables are the stable way to restyle DesertFox. Documented class names use the same `desertfox-` prefix.

- The defaults are declared on an inner element of each surface, not on the shadow host. The host sits in the page, so page CSS can match the host, but a variable set on the host or on `:root` does not reach the inner element, which sets every role token itself. The long prefix and the inner element together keep page CSS out.
- User CSS must name the inner class of a surface to change a variable there, for example `.desertfox-whichkey { --desertfox-primary: #ff6ec7; }`. Variables on `:root` or `:host` alone do not reach inside a surface. The help page lists the classes.
- `style.css` and `style.d/*.css` load after the built-in styles in the shadow roots (hints, which-key, toast, badge) and in the command line, help and new tab pages, after the theme sheet, and follow a reload. Those pages stay hidden until the theme and the user CSS have both been read. Variables set outside DesertFox, on `:root` or in a browser user stylesheet, stay unsupported.
- The background resolves the theme at startup and at every `set`, and stores it as `desertfox_theme` (`{ dark, light }`, the light set already picked by `light_intensity`) in `storage.local`. Each surface turns it into one style block on its inner element, after the built-in styles and before user CSS, and follows `storage.onChanged`, so a `set palette` reaches open pages at once. A surface stays hidden until the first read of the theme and of user CSS returns, and a page stays hidden until the theme read returns, so the default colors never show. A failed read counts as returned. The first hint or which-key panel on a page appears a few ms later, once per page. Light or dark is a `prefers-color-scheme` block.
- Setting variables covers colors, fonts and sizes. Full selectors can change layout. The documented class names on each surface are part of the public format, and the help page lists them.
- In Oasis Dots, the theme switcher writes `style.d/00-oasis-theme.css` with the variables for the current Oasis theme, then runs the reload. Without Oasis, the built-in defaults apply.
- CSS cannot run code. Imported CSS may not load remote addresses: an import that holds `@import`, `@font-face`, `image-set(`, `src(` or a `url()` that is not `data:` in `style.css` or `style.d/*.css` is refused, with the file and line. CSS from the user's config folder and from the files editor is not checked. The import review and the permission grant panel show no user CSS.

### Themes

A theme file maps colors onto a fixed public list of roles. The theme's own color names never reach DesertFox. A file is TOML with a `[dark]` table, a `[light]` table or both, and a file with one table serves both system settings. Each table maps a role to a color: `#rgb`, `#rrggbb`, `rgb()`, `rgba()` with alpha 1 or `hsl()`, stored as `#rrggbb`. Named colors are not accepted.

The 25 roles: `bg_core`, `bg_mantle`, `bg_crust`, `selection`, `fg_core`, `fg_comment`, `fg_dim`, `fg_muted`, `primary`, `secondary`, `accent`, `border`, `error`, `warn`, `ok`, `info`, `mode_normal`, `mode_insert`, `mode_ignore`, `mode_caret`, `mode_visual`, `search_bg`, `search_fg`, `search_current_bg` and `search_current_fg`. `fg_core` is the text, `fg_comment` is secondary text, `fg_dim` is hints such as the command line usage line, and `fg_muted` is disabled text, which has no contrast floor. `error`, `warn`, `ok` and `info` color the toast kinds. A mode badge is its `mode_*` role with `bg_core` as the text. `selection` also paints the selection in visual mode, and caret mode paints one cell in `mode_caret` with `bg_core` text. `mode_caret` is the Neovim cursor color, so the badge and the cell match. The `search_*` pair colors every match of a `/` search and the `f`, `t`, `F` and `T` targets, and the `search_current_*` pair colors the current match. They come from the Neovim `Search` and `CurSearch` groups without the bold, because a CSS `::highlight()` rule cannot set it. The page document has no tokens, so the caret bundle reads these colors from the stored theme. `bg_core`, `fg_core`, `primary` and `accent` are required. Every other role derives from them when missing, by the one table in `src/shared/theme/derive.ts`. A role's CSS variable is `--desertfox-` plus the role with hyphens, for example `--desertfox-bg-mantle`. The list is a contract: a later rename breaks contributed themes, an addition does not. An old name such as `bg`, `fg` or `muted` in a theme file is an unknown role, and the error lists the valid ones.

`palette = "<name>"` looks in `<config dir>/themes/<name>.toml` first, then in the built-in themes. The default is `oasis_moonlight`, and a bare name such as `moonlight` is a config error that lists the known names. A local file wins over a built-in theme of the same name.

`palette = "desktop"` follows the palette the desktop pushed over the bridge (the `theme` verb, see [Bridge host](#bridge-host-in-progress)). The background resolves it at every publish to the last stored push, or to `oasis_moonlight` while none was stored, with the bridge off too. `:set palette <name>` stops the following until `:set palette desktop`. A push stores its name either way and changes the theme only while `palette` is `desktop`. The default stays `oasis_moonlight`, so following is off until chosen. A built-in theme name is what a push can carry, so a local theme is not reached through it. Light or dark and `light_intensity` stay as they are.

The 16 Oasis themes are not TOML. `themes/oasis/` holds byte copies of the oasis.nvim CSS files, one dark file and five light files per theme (`just oasis-themes <oasis.nvim dir>` copies them). `tools/build_themes.ts` reads each role from one named `--oasis-*` variable, with no mixing, and the table of which variable fills which role is at the top of that file. The `light_intensity` setting (1 to 5, default 3) picks the light set of an Oasis theme. Other themes have one light set. `tools/build-config` checks every local theme file and rejects an unknown role (the error lists the valid ones), a missing required role and a bad color, each with the file, table and key. `just themes` compiles `themes/oasis/*.css` and the contributed `themes/*.toml` into `src/shared/themes.ts`, and `just test` fails when that module is stale. The stored theme sets every role token on every surface.

`primary` is the brand color: links, titles, groups, the hint labels (a filled label with `bg_core` text and a 1px primary border). `secondary` colors the keys in which-key and the new tab clock second hand. `accent` marks highlights. A `style.css` that sets or reads `--desertfox-accent` for the brand color moves to `--desertfox-primary`.

## Snippets

A snippet is a user command written as page code. It is how users add behavior that DesertFox does not ship, for example helpers for one private web app. DesertFox has no plugin system: snippets are the only extension point.

A snippet file has a header with the command fields, then the code:

```js
// id: myapp.toggle_ids
// label: Toggle IDs
// intent: Show or hide record IDs in My App.
// matches: https://app.example.com/*
// name: ids
// modes: normal, visual
// param: query string main default=selection
// param: all bool short=a
window.wrappedJSObject.my_app.toggle_ids(args.query);
```

- `default=selection` reads a context source. `default=selection,search_query` is a chain: the selection, else the query of the results page. `short=` gives a bool or a valued param its flag letter (`short=a`). An enum maps values to letters: `short=tab:t,window:w`. The letter rules are the define-time checks above.
- `modes` is optional. It lists the modes where a key can run the snippet, from `normal`, `caret`, `visual` and `visual_line`. The default is `normal`. Any other name is a build-config error.
- `tools/build-config` turns the header into a normal registry entry. Snippet commands get keys, which-key rows, help, completion and prompts (through an explicit `prompt`) the same as built-in commands.
- The router checks args, then runs the code in the tab's content script with `tabs.executeScript`, with `args` defined. `window.wrappedJSObject` reaches the page's own functions.
- `matches` limits where the command runs. On other pages the router refuses with a message.
- Errors from the code are caught and shown as a message, with the snippet id.
- Snippets have no storage of their own. The code runs in the content script world, so the body's scope hides `browser` and `chrome`. That guards against accidents and is not a sandbox: `globalThis.browser` still reaches the extension APIs, and the code is the user's own.
- A snippet runs other commands with `desertfox.run(command_text)`, which takes the same text as the command line, for example `await desertfox.run("open -t https://example.com")`. It rejects when the command fails. Snippets can call snippets up to 5 levels deep.
- A relative URL in `fetch` resolves against the extension, not the page. Build the address from `location.origin`, for example `fetch(location.origin + "/api/items")`.
- Snippet ids cannot use a group name that DesertFox uses.

The config file is code, so whoever can write it can run code on pages. The file lives in the user's home directory and only the user's own tools write it, so this adds no new access. An import through the settings page shows each snippet's code, `matches` and `requires`, and stores only the snippets the user accepts. Its consent screen says a snippet can use every DesertFox permission. An import that carries CSS loading a remote address is refused, and the consent views show no user CSS. The import asks on every import and remembers no trust.

## Routing

1. The content script catches a trusted `keydown` in the capture phase on `window`, at `document_start`.
2. It walks the prefix tree for the current mode. On a match it cancels the key and its keypress and keyup. It also cancels a trusted keyup whose keydown this frame never saw, so a page never acts on half a press that began in another frame or in the browser's own UI. This rule runs in normal, insert and the other modes. In ignore mode, on a site that is off and with DesertFox switched off, a lone keyup passes, but a key whose keydown was cancelled still swallows its keyup.
3. It runs a `content` command itself. It sends a `background` command to the background page.
4. The background resolves context sources, checks args and runs the handler. Tab commands act on the tab that is active when they run, never on the tab that was active when the key arrived.

A Firefox shortcut enters at step 4 through `commands.onCommand`.

Every command that opens an address checks it against one allow-list, `openable_url` in `src/commands/url_build.ts`: http, https, ftp, mailto, tel, magnet, `about:blank`, `view-source:` of an http or https address, and DesertFox's own `moz-extension:` pages. Typed text, hints, the clipboard, bookmarks, quickmarks, history and session restore all pass it. Text that names an address off the list is refused, not searched. A request from a page's content script carries `from_page` in its command context, and typed text in it may not open DesertFox's own pages, nor may clipboard or register text from any sender, so a link a page offers cannot reach the grant panel of the help page. Config and stored addresses, such as `home_page` and quickmarks, may open them.

`.` (`command.repeat`) replays the last request that ran to the end. Every finished request or leaf passes `record_step` (`src/background/record_step.ts`), which stores the repeatable steps in `storage.session` when every step succeeded, with the count it had. The router calls it for background commands and for replays, before it answers. The content script calls it, through a `record_step` message, when a leaf of content commands ends, so `j` then `.` scrolls again. A held key sends its first press only. The background checks the message like any page message: content commands only, args through the one validator, at most 16 steps. A failed, cancelled, prompted or `skip_repeat` request never overwrites the slot. A private window has a slot of its own, which Firefox's own rule for private data clears: the background clears it when the last private window closes. A `.` that follows a page record waits for the write. A request that opens the command line stores nothing until the typed command runs. A hint start records itself from the `hints` bundle at the pick start, because a pick that opens the link in this tab can end the page before the leaf ends. So `.` after a hint pick shows hints again with the same action and filter. `3.` replaces the stored count and `.` keeps it. With nothing stored, `.` shows "Nothing to repeat". A pick that opens a link runs as `open.url` marked `from_hints`, which the router does not store, so `.` shows hints and does not reopen the address. A replay re-reads context sources such as the selection and the clipboard, so it uses their values at that time.

Local marks keep a scroll position per page. `m<a-z>` stores the offset of the box the vertical scroll keys move (the page, or an inner box that has the focus or most room), and `'<key>` or the backtick jumps there with an instant scroll, which ends a smooth scroll in flight. The page is its address without the hash. Only whole pixels are kept, and a page that fits the window stores 0. A jump stores the position it left under `'`, so `''` and the backtick twice toggle between two spots. Only mark jumps set it: `gg`, `G` and search do not, because the jump list owns that history. Marks sit in the background, in `storage.local` (`desertfox_marks`) for a normal window and in `storage.session` (`desertfox_private_marks`) for a private one, which the background clears when the last private window closes. Writes run one at a time. The store keeps at most 500 pages, drops the page written longest ago, and refuses an address over 2048 characters. A mark works in the frame that has the focus. The code sits in the `page` bundle, and the which-key rows under `m`, `'` and the backtick list the page's marks with their offsets in px. A mark remembers an offset, not the box: set with the focus in an inner box, it later scrolls whichever box the keys move. "Clear all history" in Firefox (`history.onVisitRemoved` with `allHistory`) drops every mark of the normal windows, global ones too, and the command line history, because both hold page addresses. Registers, macros, quickmarks and sessions stay, and so do the private marks. A clear of a time range sends no `allHistory`, so it drops nothing.

Global marks (`m<A-Z>`, jumped to by `'<A-Z>` or the backtick) keep an address and an offset, in the same value as the local marks (`globals`, which a value stored before them lacks and reads as none). Only a top frame on an http or https page sets one, with the address of its tab, and a jump from a frame works: on the tab itself the top frame does the jump, so a frame never scrolls its own box. A normal and a private window keep separate sets, and a jump never uses a tab of the other kind. A jump goes to the tab on that address (the hash ignored, the container ignored): the current tab, then the newest accessed tab of the current window, then the newest of the other windows, and with none it opens the address in the current tab. The background answers the key press once the switch or the navigation has started, so the old tab does not hold keys while the user looks elsewhere. It then waits up to 10 s for the page (`src/background/page_ready.ts`) and runs `mark.jump` in the top frame of the target tab, which scrolls there. The scroll is not retried when a page builds its height late, and a refused wait (timeout, a page with no content script) shows a toast on the target tab. A page that redirected still scrolls, because the arrival jump uses the stored mark whatever address the tab ended on. `''` stays per page: the arrival scroll stores the offset the target page had under that page's `'`, and nothing is stored for the page left, so a return across tabs belongs to the jump list. Which-key lists the page's marks, then the global marks with their address (no scheme, 36 characters) and offset.

The jump list (`<C-o>` back, `<C-i>` forward, `page.jump` with a `direction` and a count that moves that many places) keeps the places that big jumps left, one list per window with a cursor, in `storage.session` (`desertfox_jumps`, and `desertfox_private_jumps` for private windows, which the background clears when the last private window closes). A closed window drops its list. An entry is an address without the hash and an offset in whole pixels. The list holds 100 entries, and a place within 4 px of the last one on the same page, on both axes, is the same place. Stepping back from the present first adds the place you are on, so `<C-i>` comes back to it. A new place after a step back drops the entries after the cursor. A step past either end refuses with "No older jump" or "No newer jump", moves nothing and does not wrap, and a count past the end refuses whole. A step to a place on the page you are on scrolls instantly. A step to another address goes to the tab on it, found as for a global mark (the same privacy, the hash and the container ignored) but only in the current window, because another window has its own list. It opens the address in the current tab when no tab of this window has it, even if another window does, and scrolls after the page is ready (`src/background/address_arrival.ts`, shared with global marks). The cursor moves before the switch, so a target that never loads leaves the cursor on it. A step from a child frame runs in the top frame. The keys work in normal mode only. `g;` is dropped, because a page keeps no history of edits. Two things record into it. The router records for a command that has the `jumps` flag. The key compiler marks such a step (`jump`), so a first press of a key like `gg` goes through the router, one round trip more than a plain scroll, and the keys typed right after it wait until it has run, as they do after `m`. A held key's repeats run in the page and record nothing, and `$` and `^` (`scroll.to` on the x axis) are no jumps. Before the command runs the router asks the top frame's `page` bundle for the scroll offset (the box the scroll keys move, through `scroll_target`), which loads `page.js` on the first use in that page, then runs the command and, only when it succeeded and was not cancelled, puts the place it left in the window's list. So a refused command, a bad argument and `5j` (not flagged) record nothing, and `50%G` does. The read ends before the command starts, so the command cannot move the view first, and a page that gives no answer within 1 s runs the command and records nothing. A command typed in a child frame records nothing, because an entry holds no frame. A global mark jump records apart from the router, in `global_mark_jump.ts`, because only the background knows where it lands: the top frame's place goes into the list of the window the jump lands in, so after a jump to a tab in another window `<C-o>` there comes back. That holds for a jump a child frame asks for too. The second source is the page changing in a tab, from any cause that loads a new document (a click, a typed address, a script): the `page` bundle reports its offset as the page hides, and the background records that place once the tab shows another page. Each event (the report, the address change, the end of the load) judges against the tab as it is then, so their order does not matter: another page records, the same page loaded to the end is a reload and records nothing, and a hash change neither records nor ends the wait. An address change inside the same document (a single-page app's `pushState`, and back or forward between its entries) hides no page, so the leave watch (`src/content/page/leave_watch.ts`) records it. It reads the address left and the offset on `navigate`, before the app scrolls, and records when the change commits (`currententrychange`). So a change the page cancels records nothing, a link the app intercepts records, and one that loads another document is left to the page hiding. It records only in the top frame of a visible tab and not within 1 s of its last record or of a jump or step that scrolled the page (the router's offset read counts as one), so a burst records once and a page that changes its address as it scrolls does not record the list's own moves. A hint pick ends that window, so a follow right after a jump records. The same commit ends hint mode in the frame that holds the session (not a `replaceState`, and not a change the session's own pick makes, such as a table-of-contents anchor in rapid mode), as a page hiding does. These changes record through the Navigation API, which every supported Firefox has. `replaceState` and a hash change record nothing. The background drops such a push while a step is arriving in the tab and refuses one for another site. A step back to an earlier address of the same app loads it again in the tab, because the step opens addresses with `tabs.update`. A redirect after the first change records nothing more. A step of the jump list that opens its address in the current tab marks the page it leaves before the navigation starts, so that page's report records nothing, however late it comes. The Navigation API cannot classify the leave in the page, because Firefox fires `navigate` only for navigations the page starts (see [firefox-behavior.md](firefox-behavior.md), "The Navigation API in a content script"). The `page` and `hints` bundles both arm the leave watch, which also sends the report as the page hides. A page where neither bundle loaded (only scrolled with `j`, left by a plain mouse click) has no offset to report, so a navigation from it records nothing. Hint picks record through that navigation, not at the start of the pick.

`mark.clear` takes a `scope`. `page` clears the page's marks with its `'` slot and every global mark, and `all` clears every page and every global mark. A private window clears only its own set, and quickmarks stay. It has no default key and no confirmation, so typing the command is the confirmation, and `.` never replays it. With no marks to clear it refuses, as `mark.delete` does.

Quickmarks bind a key to an address. `M<key>` saves the address of the current tab, `go<key>` opens a quickmark in this tab and `gn<key>` in a new tab (`quickmark.add` and `quickmark.open`, with the shared `where` flag, so a user can bind a window variant). The table is `quickmarks.toml` as the base, with the entries `M` saved in `storage.local` on top: the saved entry wins for the same key, as saved settings win over the settings file. A private window saves into `storage.session` and loses those entries with its last private window, and it reads the normal entries too. A key is one letter or digit. The URL edit prompt that `go` and `gO` held moved to `ge` and `gE`. Which-key under `go` and `gn` lists the keys with their addresses. Counts do nothing.
`:marks` and `:quickmarks` (`mark.list`, `quickmark.list`) take one picked row from the command line list and show no summary: the key, with the same text as the which-key rows (the address, no scheme and 36 characters, and for a mark the scroll offset). `:marks` lists the page's marks first, then the global ones, and leaves `'` out. Enter on a row jumps to the mark (the top frame of the line's tab runs `mark.jump`, so a global mark switches tabs as `'<A-Z>` does) or opens the quickmark in this tab. `mark.delete` and `quickmark.delete` pick a row the same way and have no default key. `quickmark.delete` lists only quickmarks saved with `M` in its own layer (`saved_quickmarks`): a private window lists and deletes only private ones, never changes `storage.local`, and refuses a normal one with where to delete it. An entry of `quickmarks.toml` is not listed and stays. When a deleted key still has an address from `quickmarks.toml`, the toast says what it opens now. The lists are the completion sources `marks`, `quickmarks` and `saved_quickmarks` (`values: { from: "marks" }`, `kind: "marks"`), which the background fills from the line tab's page and privacy.

`,,` opens the finder, `open.anything` (`anything`): one fuzzy list over open tabs, quickmarks, bookmarks, history, recently closed tabs, visited sites and search rows. A query ranks all of them but the search rows as one list with the one scorer, raised by use (see "Ranking by use" below), so a strong history hit leads a weak tab hit. An equal score keeps the group order tabs, quickmarks, bookmarks, history, closed tabs, sites. An address shows once, in the first group that holds it, so a page open in a tab shows as the tab. A closed tab wins over the history row of its address, so Enter restores the tab. The list covers every window of the line's privacy, whatever `completion_all_windows` says, and a private line lists private tabs, quickmarks and bookmarks only: no history, closed tabs or sessions. With no query it shows every quickmark, then the 8 most recently used tabs (the line's own tab left out, ordered by `lastAccessed` read once when the line opens), `history_completion_max` history rows and 5 closed tabs, and no bookmarks or search rows. Search rows come last and show only with a query: when the first word equals an engine's `keyword` (case-sensitive) and a space and more text follow, that engine's search row goes first in the whole list and is the highlighted one, and the last row always searches the default engine with the whole query by the rule of `o`. With a query typed the first row is highlighted and Enter opens it. The line submits a reference to the highlighted row (kind plus tab id, session id, engine name and query, `shared/anything_ref.ts`) in the `query` argument, so a repeated address or title cannot pick the wrong row. Enter switches to a tab row (and focuses its window), restores a closed-tab row, and opens any other row here. `<S-Enter>` is `cmdline.submit` with `where = "tab"`: the optional `where` argument of `cmdline.submit` replaces the `where` of the submitted command when that command has one (`open`, `bookmark`, `history`, `search` and the finder) and is ignored otherwise. On a tab or closed-tab row it acts as Enter. Tab rows keep their marks, so the row keys (`<C-Space>`, `<A-x>`, `<A-m>`, `<A-p>`, `<A-u>`, `<A-c>`) work on them. The page reads the rows from the tab model and one `complete_items` fetch of kind `anything`.

Typed text repeats too. A lazy recorder (the `text` bundle) builds one insert session from `input` events: the text typed in one field, never in a secret field (`is_secret_field`: a password input, an autocomplete of `current-password`, `new-password`, `one-time-code` or any `cc-*` token, and a field that was once one). The session ends on Escape, on focusout, on page hide and before any command is sent from the field, so the text is stored before that command. It is stored as a `text.insert` step through the same `record_step` message, led by the command that focused the field (`gi`, `]i`, `[i`, a hint pick on a field) when there was one. `.` runs the entry, then types the text through one field writer; a field focused by a click has no entry, and the replay types into the field the last Escape left, or refuses with "No text field to type into". `3.` types the text three times. The text stays in `storage.session`, in the slot of the window it was typed in.

The content script must have the keymap before the first key. At start it sends `read_keymap` to the background, which reads the compiled prefix tree from `storage.local`, trims it for the page's site rule and replies with the tree as a JSON string. The page keeps every key until the reply arrives, then replays them against the trimmed tree. A held key that the tree leaves unbound goes back to the page as a synthetic keydown on the element it was pressed on, so page scripts see it, and a keyup follows when the real one was already swallowed. Its default action (scroll, Tab focus) is lost, and so is the key when its element has left the page. A rejected ask (the background has not registered its listener yet) is retried every 100 ms, 30 times, and then the page installs an empty tree. The next `tree_updated` asks again and heals it. An ask answered after a newer one started is dropped. Phase 1 measured the old direct storage read at 6-10 ms (median 8); the ask through the background keeps the median under 12 ms (see [firefox-behavior.md](firefox-behavior.md), "Phase 1 measurements").

## Bundles and loading

- `background.js`: the registry, the handlers, keymap validation and the shortcut slots.
- `content.js`: the key listener, the prefix tree, the modes and scrolling. Kept under a guard of 19 KB minified (see "Content script size" below).
- Hints, which-key, caret and visual mode are separate files. `hints.js` has a guard of 46 KB minified in `tools/build.mjs`, raised from 42 KB for hints across frames, the tracking-parameter strip and the jump list's leave watch. Snippets run as their own code. The background injects one with `tabs.executeScript` on first use in a tab.
- A site mode is a named set of binds in a site row (`modes.<name> = { label, bind }`) that `mode.site <name>` lays over normal mode, and `mode.site off` ends. It is not a `Mode`: the mode stays `normal`, so the matcher, `key_flow.ts` and `mode_state.ts` do not change. The page reply carries, per mode, the label and the top-level children of the tree that differ from the normal tree (binds go on after `pass` and `only` prune, and the matcher does not free a key the running mode binds, so a mode key wins over both). The content script swaps the matcher's tree to normal plus those children, and shows the label in the badge, even under `mode_indicator = not_normal`. The first matching row that has a mode name decides that mode whole. One exit policy holds for every mode: Escape, any keydown DesertFox does not cancel (a replayed key that the keymap passes too), a mousedown, any mode change (focus moving into a field too) and any keymap update. A macro recording starting or stopping is a keymap update, so it ends the mode. The mode report to the background, which-key listings inside a mode and a badge for a mode in a child frame are not built. The compiler warns on a `mode.site` bind that names a mode no row defines. The key test piece `p28_site_modes` proves it on the `/grid` stand-in.
- `site_actions.js` holds the handlers of `page.send_key` and `page.clipboard`, which site rows bind to keys and which share one per-page queue. `page.clipboard` focuses its target and calls `document.execCommand` for cut, copy or paste, so the page gets the browser's own trusted event (a synthetic Ctrl+X or Ctrl+V keydown does nothing). A paste that fires no event falls back to reading `navigator.clipboard` and dispatching an untrusted `paste` event with that data. The shipped Sheets rows bind `x` and `p` to it and pass `<C-a>`, `<C-x>` and `<C-v>` to the page. A site bind of `x` or `p` replaces the default `xx`, `xp` and `pp`, `pt`, `pw` sequences on that site. The content script loads it on the first press, with the other bundles.
- `editor.js` holds `text.edit_external` (see "External editor" below). It loads on the first press.
- `media.js` and `quality.js` are the bundles the content script does not load. The background injects them into every frame of the tab for each `media` command (see the `a` group below).
- `cmdline.html`: an extension page in an iframe. It has its own bundle with completion and fuzzy matching.

### Content script size

`content.js` loads in every frame of every page, so its size has two numbers and one admission rule. The measurements behind them are in [firefox-behavior.md](firefox-behavior.md), "content.js size".

#### Admission rule

Code goes in `content.js` only if one of these holds:

- A. It runs before the first key or decides what happens to a key: the capture listeners, the matcher, modes, focus tracking, the blur-on-load window, held-key replay.
- B. It serves a key that is pressed on most pages in most frames, so a lazy load saves nothing and adds a round trip to nearly every page: scrolling.
- C. The bundles cannot load without it: the bundle host and the proxies that queue calls.
- D. It must work while the page navigates, when Firefox can leave a bundle injection unanswered until the loader times out: `xp` (`page.stop`) and `<A-,>` (`focus_page`). Both matter most on a page that is still loading, so a bundle would fail them where they are needed. A command that only needs a loaded page does not qualify.

Everything else goes in an on-demand bundle. The price of a bundle is a first use that is 11 to 16 ms slower, once per frame. A second test for code admitted under A or B: keep only the part that must be instant. A rare branch of an instant feature goes behind the bundle host.

#### Two numbers

- Guard: 19 KB (19456 bytes). A step past it fails the build and someone has to decide.
- Ceiling: 32 KB (32768 bytes). The guard never passes it, and the build fails when the guard is set above it. Passing it needs an owner decision and a fresh run of the measurements in `tools/measure/` on the Firefox of that day.

The reason for 32 KB: size does not delay the first key below about 64 KB. Probe runs at 0, 4, 16, 32 and 64 KB mostly put the key listener 5 to 7 ms after the response starts. A few runs were slower (54.5, 17.3 and 11.8 ms) and did not repeat in the second pass. What size costs below 64 KB is memory, about 2.4 KB of heap per KB of script in every frame, including frames that never start DesertFox. At 32 KB that is about 8 MB for a typical session (about 100 frames) and 31 MB for a heavy one (about 400 frames). The frame counts are estimates, not measurements. The ceiling sits at half the point where timing starts to count, and it keeps the memory cost bounded.

#### When the guard may rise

1. The new code passes the admission rule, and the commit says which clause.
2. Code that fails the rule has been moved out first. A raise is the last step, not the first.
3. The raise is the smallest step of 512 bytes that fits the feature.
4. The commit that raises it names the feature that needs the room.
5. The guard never passes the ceiling.

## Interfaces

### Command line and completion

The address bar keyword `df` (the `omnibox` manifest key, `src/background/omnibox.ts`) runs a command on a page where no key reaches DesertFox. You type `df`, a space and the command text, for example `df tab.next`, and press Enter. The text takes the command line's path: the same parser, then the router, whose check is the one validator. Every router command runs. A command that needs the page, such as a scroll, refuses on a page with no content script, as it does anywhere else. Nobody can type a missing value into a prompt there, so a command with a missing value refuses with its usage, and so does text that is no command (`df rust`). Refusals reach the user as a notification when the page has no content script to draw a toast. Enter in a new tab or a background tab sets `where` on a command that has that param. A parsed line is added to the command line history, except from a private window. A line typed while DesertFox is off is refused and not added to that history. Command aliases from the config work after `df`, as on the command line. The keyword is fixed in the manifest, so it cannot change at run time. The address bar shows the hint "Type a DesertFox command" as its first row. Below it come up to nine suggestions from the command line's own completer (`onInputChanged`), built from the loaded commands, configured aliases and the setting and engine lists. A row's content is the full command text, and its description is the command name, the summary and the keys. The completer has no live source here, so no tab, bookmark or history row appears, in any window. An answer that finishes after a newer keystroke is dropped. The description is plain text (see `docs/firefox-behavior.md`).

The command line is an extension page in an iframe, so page scripts and CSS cannot reach it. It reads the stored keymap itself and asks the background for everything else. Keys typed while it opens are buffered and replayed.

The list opens with the line and shows every command, so the line is never an empty list. Each row has a name, the first sentence of the intent, the args (flag names and the subject) and, in a later piece, the keys. In a narrow window the description shrinks first, then the args collapse to "…". The name never drops. The list shows up to 10 rows of 26px, with no scroll bar, and the host grows the frame upward to fit.

The cursor word decides what the list offers. A first word completes command names, fuzzy over the whole dotted name: `tab.` lists the tab family and `tc` finds `tab.close`. A word that starts with `-` lists the flags of that command with their descriptions, and the value after `=` lists the values of that param. Any other word lists the subject candidates. A quoted word never completes, and after `--` only the subject candidates show. One fuzzy scorer ranks every source: a name hit beats a description hit, a dot is a word break, an exact name ranks first and a tie goes to the shorter name.

Tab previews the selected row in the line and cycles. The list keeps ranking the text the user typed, and typing starts over. A single match goes in at once. Up and Down move and preview like Tab while the list is open, and stop at its ends. On a fresh line, before any typing or Tab, and with the list closed, they walk the history, so `:` Up Enter reruns the last command. Escape closes the list first and the line second. Enter runs the line as shown. The note row shows the usage of the selected row, or "no match".

Completion sources load only when the param being completed needs them: commands, open tabs, bookmarks, search engines, containers, headings, sessions and enum values.

`heading` lists the headings of the page, and `sh` opens the line with `heading ` typed. Jumping to a heading is a reading task, not a hint task, so it uses the list and the line's own typing, with no labels. The rows come in page order, each indented by its level counted from the shallowest level on the page (a page without an h1 loses no width) and tagged `h2`, `h3` in the description column. The indent is padding, so the highlight of a fuzzy match still counts the letters of the heading. Typing ranks by the one fuzzy scorer, best match first, and Enter with text and no selected row jumps to the best match. A pick puts `3 Heading text` in the line, and the leading number wins over the text. The heading goes to the top of the view, instantly, and focus, caret and address stay. A page with no heading shows the usual "no match" row. Which headings count is the rule of the hints bundle (`src/content/hints/headings.ts`): h1 to h6 and `role=heading`, by the aria level. A hidden, empty, tiny or clipped heading, and one in a closed `<details>`, gets no row. A heading in a same-origin frame is listed unless the frame is hidden or clipped, and the jump scrolls the frame too. Row text is the rendered text. The headings sit in the page, so the host script answers: the page sends `list_headings` over the port, the host runs `heading.list` in the hints bundle and sends the rows back, with no trip through the background. The bundle keeps the list as a snapshot of elements. The line drops it when it closes, except after Enter, when it drops it once the submitted command has run. A reply that arrives after the line closed is ignored. If the chosen element has left the page at Enter, `heading` refuses with "That heading is gone".

`copytabs` (`yT`) copies the open web tabs of this window as a list in the same formats, one line per tab, and `scope=all` adds the other windows, a blank line apart. It runs in the background and drops tracking parameters like `copylinks`. `copylinks` copies the web links of the page as a list, one line per link. `yL` takes the whole page and `yl` only what is in view, both as Markdown. The `scope` param (`page`, `viewport`) and the `format` param (`markdown`, `plain`, `org`) reach the rest from the command line. Only http, https, ftp and file addresses count: mailto, tel, javascript, data and links to a fragment of the same page are dropped. A link counts once, by its absolute address, in page order, and a hidden link is skipped. Its text is the visible text, else the aria-label, the title, the image alt, then the address. The list stops at 500 links. A same-origin frame and a shadow root count, a cross-origin frame does not (`copylinks` has no `--all-frames`). The toast says "Copied N links", and an empty list refuses with "No links on this page". The code sits in the hints bundle (`src/content/hints/yank_links.ts`), because the content script has no room for it.

`]i` and `[i` (`page.focus_field`) focus the next or previous form control: text fields, `contenteditable`, selects, checkboxes, radios and every kind of button, in page order. Disabled controls, hidden inputs and controls with no box are skipped, and off-screen ones count. The start is the focused control, else the last one Escape left, else the top of the view (the first control not above it). A count moves that many controls and stops on the last. Past the last or before the first the key shows a notice and leaves focus alone, and it does not wrap. The control takes focus without a scroll and is then centered if it is not fully in view, in each frame that holds it. Insert mode follows the existing `focusin` rule, so a checkbox or a button gets focus and the mode stays normal. The code is in the hints bundle (`src/content/hints/focus_fields.ts`), which reaches shadow roots and same-origin frames. The content script passes the last blurred field along, because the bundle cannot see it. `gi` keeps its own text-field rule in the content script.

`]h` and `[h` (`page.heading`) scroll the next or previous heading to the top of the view, instantly, as the heading search does, and leave focus, caret and address alone. Which headings count is the rule of `heading` above. The start is the heading the last `]h` or `[h` jumped to while it is still on screen, so a heading near the page end, which cannot scroll to the top, is passed and not picked again. The bundle keeps that heading as one weak reference. Otherwise the start is the view and not the caret: next is the first heading whose top is below the view top, previous the last one above it, and `.` keeps going. A count moves that many headings and stops on the last. Past the last or before the first the key shows a notice ("No next heading", "No previous heading") and does not wrap. The code is in the hints bundle (`src/content/hints/headings.ts`). `]H` and `[H` stay free for first and last heading.

Tabs and bookmarks come from the background, because it knows the window and privacy of the line's tab. A string param asks for them with `values: { from: "tabs" }` or `{ from: "bookmarks" }`. The page asks once per kind, keeps the answer for the line and ranks it with the shared scorer on every key. The row list shows "loading" in the note row until the answer lands. Each kind has its own fetch in flight, so kinds do not drop each other. A reply is dropped when the line has closed. The background answers only the frame whose line redeemed a ticket, until the tab closes or navigates or the next line redeems. The frame matters, because any frame of the page can embed its own copy of `cmdline.html`. A normal line lists only normal tabs and a private line only private tabs. Bookmarks list in both.

- A tab row reads `3: GitHub`: the number is the tab's place in its window's tab bar, counted from 1, so it stays while the user types. Picking it puts the number and title in the line. `tab` reads a leading number as that place, and the number wins over the title. Other text is a fuzzy match on title and address, and an equal tie is refused with both tabs named. The `completion_all_windows` setting (default false) lists the tabs of every window. The same number then exists once per window, so the title picks one, else the line's own window.
- `tab.unload` and `tab.load` free and restore a tab's memory (default keys `tu`, `tU`, `tH`, `tL`). They take a subject like `tab`, a `side` and a `count`. Unloading the current tab switches to the alternate tab first, else the next loaded tab, else the previous one. Audible tabs and the active tab of another window are refused, and a side or a count skips pinned tabs. The site of a tab is its site key (`src/shared/site_key.ts`): the host in lower case, with one trailing dot and one leading `www.` dropped and the port ignored, so `www.github.com` is `github.com` and `docs.github.com` is another site, because no public suffix list is used. An IP address and `localhost` are their own keys. All `file:` pages are one site, all `about:` pages are one site (`about:reader` and `view-source:` take the key of the page they wrap), each extension is one site, and `blob:`, `data:`, `javascript:` and unparsable addresses are one `other:` site. `--side=site` (short `S`, on `tab.close`, `tab.unload` and `tab.load`, with no default key) acts on the tab and every unpinned tab of the same site in the line's window. `tab.close` first moves focus to the nearest tab outside the site. A count is invalid with `site` on `tab.unload` and `tab.load`. A count prefix with `tab.close --side=site` is a known gap (it repeats the close), tracked in #187. `tab.load` reloads in place and keeps focus. Both report one line, such as "unloaded 3 tabs, skipped 1 (audible)". In the list, `<C-Space>` (`list.select --action=toggle`) marks or unmarks the highlighted tab row and moves down. The marks are tab ids kept in the line, so filtering keeps them and the actions include hidden marked tabs. A tab that closes drops out, `<Esc>` clears the marks before it does anything else, and they end with the line. `list.act` runs on the marked tabs, or on the highlighted row when none is marked: `<A-x>` closes (the highlight then goes to the first row below the closed rows, else above), `<A-m>` mutes and `<A-p>` pins (any off turns all on, else all off), and `<A-u>` unloads the loaded tabs, or loads all when none is loaded. The ids are fixed at the key press and go to the background in a `tab_rows_action` message that needs the line's ticket, skips ids that no longer name a tab and refuses ids of the other privacy. The list stays open and the rows show the change, with a name dimmed while unloaded. The line's own tab cannot unload this way, because the line lives in it. `<A-c>` (`list.act --action=reopen`) swaps the line to a `container:` prompt over the same line, ranking the containers by name with `default` as one entry. Enter reopens the marked tabs, or the tab that was highlighted when none is marked, in the previewed container, or in the one whose name was typed in full. `<Esc>` returns to the tab list with the marks, filter and highlight kept, and the `<Esc>` order above holds after that. The ids are read when Enter is pressed, so a tab that closed meanwhile drops out. The message carries the container's store id, because names can repeat. The background refuses a private line, an id of the other privacy and a store id it does not know. It leaves out the line's own tab and the tabs already in that container, skips a tab that fails to reopen while the rest go on, and opens no new tab as the active one, because hiding the line's tab ends the line. The note names what moved and what stayed, such as "reopened 2, 1 already there, line tab left out". A private line has no containers, so the prompt refuses there.
- The `cmdline_prompt` setting sets the text before the input. `caret` (the default) shows `> `, bold, in the `secondary` theme role. `colon` shows `:` in the `primary` role, normal weight, with a small gap. Any other value is custom text in the caret style and holds its own trailing space. Every value is 1 to 8 characters on one line.
- The `statusbar_widgets` setting (default `url, scroll, tabs`) lists the widgets on the right of the open command line, in list order. An empty list hides the area. `url` shows the host and path without the scheme, query or fragment, in the `ok` token for https and the `warn` token for http. The label is cut to 30 characters with an ellipsis, so a long path can be partly or fully hidden. The full address is the title. Other schemes get no color, and the widgets do not use the `error` token. `scroll` shows `Top`, `N%` (kept between 1 and 99, so the edges read `Top` and `Bot`, never 0% or 100%), `Bot` or `All` for the page's `scrollingElement`. `tabs` shows `[n/m]`, the tab's place in its window. Each value is a snapshot taken when the line opens and does not change while the user types. The widgets are hidden on `/` and `?` search lines, whose note row shows the match count, and on a line narrower than 30rem.
- A bookmark row shows the title and the address. With no word typed, the list shows the 20 newest. Picking one puts the address in the line. A typed word ranks by use as well as text. `bookmark` takes an exact address first, then the best fuzzy match with the same use boost, and refuses an equal tie. The answer is `{ rows, folders }`: the folder paths go once and each row holds indexes into them, newest copy first. A dim cell shows the last part of the row's newest folder, and `+N` when more folders hold the address. `bookmark` and `bookmark.remove` take `--folder=` (the `folders` list), which keeps the rows filed in that folder or any subfolder. The folder matches as filing does: an exact path, else a fuzzy match, and an equal tie or a shared path is refused. The list shows no row for text that picks no folder, and Enter refuses it. `bookmark.remove --folder=X` removes only the copies at that address inside X. `open` rows and the new tab page keep the flat list with no folder cell.
- A tab row leads with fixed-width cells, in this order: a status cell (`%` the current tab, `#` the alternate tab, which is the tab the user was on before, then small icons for pinned, audible, muted and discarded), a container mark, a favicon, then the name, the address and the keys. The icons are CSS masks, so they take the text color. The container mark is Firefox's own container icon in the container color, and a colored dot when the icon cannot load. The default container and private tabs have no mark. The favicon is sent only for http, https and data: URLs up to 2048 characters, and a failed load shows a plain glyph. The favicons load from the network when the list opens, for each listed tab, in the command line's tab context (its container and private state), not the listed tab's. `#` is the tab the window was on before its current one, which the background tracks from `tabs.onActivated` in `storage.session`. The `contextualIdentities` lookup fails quietly when containers are off, and then no row has a mark.
- `open` and its tab variants complete from bookmarks and history (`values: { from: "open" }`, `kind: "open"`). The background answers every row, tagged `bm` or `hist`, in the group order of the `open_completion` setting (default `["bookmarks", "history"]`, a source left out is not read), and drops a history row whose address is a bookmark. History comes from a background cache of the 8000 newest visited addresses (`history_cache.ts`), minus `about:`, `moz-extension:` and `data:` addresses. A private line lists no history. With no word typed the page shows the 20 newest bookmarks and `history_completion_max` history rows (default 10), a cap that rides in the answer. A typed word ranks every row as one list, raised by use, and an equal score keeps the group order of `open_completion`. Site rows (tag `site`) follow the rules in "Ranking by use" and come last on an equal score. A dim `bm`, `hist` or `site` cell tells the rows apart. Enter on text that matches no row still opens the address or searches with the default engine. The `history` permission adds an install prompt on update.
- `rc` (`page.reload --site`) clears one site and reloads. `rC` opens the line with `page.reload --all`, and Enter runs it, so no key press clears every site. `site` clears the cookies of the page's exact host in the tab's container, plus the parent-domain cookies the page sends (`cookies.getAll` for the page URL), then the whole HTTP cache, then asks the page to clear its own localStorage, sessionStorage, IndexedDB, Cache Storage and service workers through a fixed `tabs.executeScript` string (not a content-script message, because the content script is near its size limit). Firefox ignores `browsingData` `hostnames` for the cache and localStorage (see [firefox-behavior.md](firefox-behavior.md), "browsingData hostnames"), which is why the cache goes whole and the page clears itself. A database the page holds open blocks its own delete and `browsingData` `indexedDB` ignores `hostnames` too, so that delete stays pending until the reload closes the connection, and the notice names IndexedDB. `all` clears every type for every site and container with one `browsingData` call. The cache call never carries a `cookieStoreId`, which Firefox rejects for it. The clear finishes before the reload (`bypassCache`), and a failed cookie or cache clear stops the reload. A page the extension cannot script (addons.mozilla.org, an error page) or a step that stalls past 3 s still reloads, and a notice names what stayed. A `file:` or `about:` page refuses a site clear before anything is cleared. `browsingData` is an optional permission, and `cookies` stays required because the container option of `tabs.create`, `windows.create` and `downloads.download` needs it. Without `browsingData`, `rc` and `rC` refuse before they clear anything and name `:permissions.grant browsingData`. That opens a Help panel, and its Allow button asks for the permission (see [Permissions](firefox-behavior.md#permissions)). The keys work at once after the grant, and a plain reload never needs them.
- The `p` group is Page. `pp`, `pt` and `pw` open the clipboard here, in a new tab and in a new window, and `P` stays the one-key paste in a new tab. `pr` (`page.print`) calls `tabs.print`, which opens Firefox's print window on the active tab and returns no result. `ps` (`page.save_pdf`) calls `tabs.saveAsPDF`, which asks for a file name: a cancelled picker is silent, and a failed write shows a notice. Both run in the background, so the content script grows by nothing, and neither is repeatable: `.` skips them, but a macro records and replays them. Neither takes a tab id, so `:page.print` from another tab still acts on the active one.
- The `a` group is Media. `am` mutes the tab (`tab.mute`, also `<A-m>`). The rest run `media` (`media.act`) with an action: `ap` play or pause, `as` and `aS` speed up and down by 0.25x (0.25x to 4x), `ar` speed back to 1x, `av` and `aV` volume up and down by 10 points, `al` and `ah` seek 10 s forward and back, `aP` picture-in-picture on or off, `af` fullscreen (`src/content/media/fullscreen.ts`): it clicks the site player's own fullscreen button when one inside the player box carries a label, title or class that names fullscreen, relying on the key press's activation. Otherwise it requests fullscreen on the player box (the same box as the `;F` hint, `src/content/player_box.ts`, so the site's controls stay). A fixed pixel height inside the box can then leave the video short of full screen, because Firefox allows one fullscreen request per key press (see [firefox-behavior.md](firefox-behavior.md), "Fullscreen requests per key press"). The key again leaves every nested level, since `exitFullscreen` leaves one. `media mute`, `media loop`, `media info`, `media quality` and `media skip` have no key. `mute` and `loop` toggle the element (the tab stays unmuted), and `info` shows the time, speed, quality and volume. `A` opens the line with `media ` typed. On the line the value of `speed`, `volume` and `seek` is `up`, `down`, `reset` (1x, 100% or the start), `end` (the top of the range, the media end for `seek`), `percent` (the count as a percent of the range, so `50` goes to the middle of the media and `volume` to 50%), a signed number that moves by it (`media seek -10`) or a bare number that sets it (`media speed 1.5`, `media volume 60`). Each action takes its own values, as `pattern_arms` keyed on `action`, so the schema refuses `media speed end`, `media volume percent` and any value on an action that takes none. `percent` is for `seek` only, and it needs its count: `media seek percent` with no count is refused as `missing <times>`. A value outside the range is set to the nearest end, not refused: speed stays within 0.25x to 4x, volume within 0 to 100 and seek within the media. Without a value the notice shows the current one and nothing is written. A count fills `times`, which the schema allows only with `up`, `down` or `percent`, so `3as` moves three steps in one press and `2ap` is refused. Speed is not kept: a new video starts at its own rate.
- `media quality` and `media skip` reach the site's own player, not the media element, because a video element has no quality control. `quality.js` (`src/content/quality/`) holds one driver per site player and no host list: each driver probes the page for its handle. The background injects the bundle into every frame, each frame reports whether it has a player and whether the player lists its levels, and the background sends the one `quality_apply` request to a single frame: one that lists levels first, then the top frame, then the lowest frame id. So a page with several embeds changes or skips one player. A frame that refuses the script does not stop the others, and the whole request ends after 1.2 s without sending anything late. The bundle reaches the handle through `window.wrappedJSObject`, the way `hints/inspect.ts` does, so a site CSP does not matter and no script is injected into the page. The drivers use player calls only and write no cookie or storage. The YouTube driver reads the `#movie_player` element's unofficial calls (`getAvailableQualityData`, `setPlaybackQualityRange`, `nextVideo`, `previousVideo`), which can break when YouTube changes them, and the player answers "unknown" until it plays, so a request before that refuses with "The player has no quality levels yet". The hls.js driver reads `html5player.hlsobj`, the hls.js instance of the site's player: `levels`, and `loadLevel` to read the level and `nextLevel` only to switch (`-1` is auto), because `currentLevel` reads -1 until a fragment is buffered and a write to it flushes the buffer. A pure chooser (`choose_level`) turns `max`, `min`, a height (the highest level at or below it, else the lowest) and `up` or `down` (the count in steps, from the playing level) into a level, so the drivers hold no policy. `auto` hands the choice back to the site. With no value the notice lists the levels, best first, with the playing one marked. The driver reads the page again for each request, so a player that YouTube replaces on in-site navigation is found again. Where no driver probes, the notice says "No quality control on this page". `skip` takes `next` (the default) or `previous`, and refuses with "No next video" where the player offers none, as the hls.js driver does. `media captions` (`c` in the media mode) reads `video.textTracks` first in the `media` bundle: any showing subtitle or caption track goes to `disabled`, else the default track (or the first) goes to `showing`, and `hidden` counts as off, because a site that draws its own captions keeps its tracks hidden. With no such track the background asks the quality bundle, and the YouTube driver calls the player's unofficial `toggleSubtitles`, guarded so a player without it refuses. Else the notice says "No captions". The hls.js driver has no captions call, since its tracks reach `textTracks`, and the site may reset a mode that the key set. `media frame up|down` (`.` and `,`) pauses the video and moves it by the count of thirtieths of a second within 0 to the duration. No API gives the frame rate, so a 24 or 60 fps video steps by a guess. Binding `c`, `,` and `.` takes them from the page in the media mode. On the command line, `media quality ` completes `max min auto up down` and the levels the player offers when the line opens. The line asks the background the first time it reads the list, and keeps the answer until it closes, so the list is as old as the line. Each row is named by the height the schema takes, with the site label (such as 1080p60) in the description.
- A media key acts on every video or audio that plays with sound (not muted, volume above 0) in every frame, else on every one that plays, else on the largest visible video, else on the first media element. Size beats playing: a video that plays, or plays with sound, counts only when its visible area is at least a quarter of the largest visible video's area (`PLAYING_MIN_SHARE`). Otherwise the largest visible video acts, so a small ad that plays does not outrank the main video that waits to start. A frame with no video always counts, but a hidden or off-screen video does not. Inside one frame, an audible or playing target takes every playing element of that frame, and fullscreen and picture-in-picture take the largest. So a muted autoplay preview yields to the video the user hears. `ap` is the exception: with sound playing anywhere, it pauses every playing element on the tab, a muted preview too, so the next `ap` finds nothing playing and resumes the largest visible video. Picture-in-picture and fullscreen take one video: the open one (to close it), else the largest with sound, else the largest playing one (each only when big enough, as above), else the largest visible one. The code runs in the background (`src/background/media_actions.ts`), because the player often sits in a frame other than the one that took the key. It injects `media.js` by file into every frame with one `tabs.executeScript` call (`allFrames`, `runAt: document_start`, so a loading frame reports at once), and no list of frames is kept. Each frame pushes its scan to the background with a `media_report` message, and the background takes the frame id from the message sender, picks the frames and asks those to apply. It waits until every frame the injection reached has reported, or 1.5 s. A frame finds its media again at apply time, through closed shadow roots (`openOrClosedShadowRoot`), so it never acts on elements the page replaced after the scan. A frame that refuses the script, never reports within 1.5 s, or answers the apply with no result (it navigated or closed) counts as one with no media, and a report that comes after the wait is dropped. The content script's own listener answers nothing to the `media_apply` message, so the bundle's answer is the reply, and `content.js` grows by nothing. A second injection into a frame adds no second listener but reports again. One info notice in the frame that took the key says the result ("Speed 1.5x", "Volume 60%", "1:25 of 3:40", "Speed 1.25x, 2 players"). Failures are refusals: "No video or audio on this page", a blocked `play()` and the picture-in-picture errors in words. A `play()` still pending after 300 ms counts as started, because a buffering source resolves it only once playback runs, and the background stops waiting for a frame after 1.5 s. The key's activation reaches `play()` and picture-in-picture through the background round trip, except for picture-in-picture in a frame from another origin (see [firefox-behavior.md](firefox-behavior.md), "Media keys across frames").
- Known limits of the media keys: a muted preview counts as playing when nothing plays with sound. A frame scrolled out of its parent's view still reports its own visible area, which matters only when nothing plays. With several targets at different rates, each moves from its own rate and the notice shows the first. Two quick `ap` presses both see the same playing media, so the second does not toggle back. A report from an earlier media command in the same tab, still on its way, can fill the count of a later command, which then ranks on that earlier scan. A hidden `<audio>` sound effect can be the first media element on a page with no video.
- The media mode is a real mode with its own keymap section `[media]`, and the tab holds it, not one frame. `aa` (`media enter`), the hint `;M` and any element fullscreen start it, and `mode.set` cannot, so a page that is not fullscreen and a frame under an all-off rule stay out of it. Only normal mode enters it. A `fullscreenchange` listener on the document of each frame that runs the content script does the fullscreen part, whoever started the fullscreen: it enters media from normal when an element goes fullscreen and returns to normal when the fullscreen ends in media (`fullscreen_step` in `mode_state.ts`). Outside full screen the badge says MEDIA and the which-key panel of the mode opens by itself when the top frame enters or returns to it (`create_media_discovery` in `tab_media.ts` asks frame 0 once per move into the mode, never for a focus report, unless `which_key_delay_ms` is 0. The frame draws only while it is still in media mode and not in full screen, and a key that runs in a child frame in the mode closes the panel from the background, because child keys never reach the top frame). In full screen the badge hides and no panel opens, and a `fullscreenchange` refreshes the badge and closes the panel. `?` opens the panel by hand. Keys: `F` fullscreen, `h` `l` seek (`5l` repeats, `0` and `^` the start, `$` the end, `N%` goes to N percent), `H` `L` previous and next video, `j` `k` volume, `<` `>` `=` speed, `m` mute, Space play or pause, `p` picture-in-picture, `q` opens the line with `media quality `, `r` loop, `i` info, `c` captions, `,` and `.` the previous and next frame. `f`, `;` (with its modifiers) and `:` are the ones of normal mode. Every other key goes to the page, so a site player keeps its shortcuts, except `/` and `'`, which the mode cancels as normal mode does so Quick Find never starts. Normal mode's other keys (`j` scrolling) are out of reach. Digits are counts, as in normal mode. A key acts on the pinned video, else on the main video by the rule above. The pin is a weak reference that `;M` leaves on `window` in the frame of the video, and the background keeps the pinned frame; a video that leaves the page (a pre-roll ad swapped for the main video) hands the keys back to the main video rule. A hint (`f`, `;`) or the command line (`:`) opened from the mode returns to it, by Escape or after a pick or a command. The mode ends on Escape (which also calls `exitFullscreen`), when the fullscreen ends, when a field takes the focus (insert mode), and when a new page loads (`tabs.onUpdated` with `status: "loading"` and no `url`). An address change the page makes itself (`pushState` or `replaceState`, also one before the load event: YouTube's next video, autoplay) keeps the mode and drops the pin, so the keys act on the new main video. Entering the mode ends an active site mode. It is tab-wide: the background (`tab_media.ts`) keeps the frames that reported media in `storage.session`. The first frame to report media starts the mode in every frame of the tab that has started its content script: the background sends a media step to all of them, and each takes the step a fullscreen change takes, so a frame in ignore, insert or any mode but normal keeps its mode. `aa` sends that step to every frame itself, the frame that took the key among them, and the first report then sends none. A second step on could reach the key's frame after an Escape there and put it back in the mode. A frame that a step or a join reply put in the mode says so in its report (`step`). Such a report never starts a hold: with no live hold, the step came from a hold that ended before the frame took it (a site key that enters and leaves fullscreen at once, `aa` and a fast Escape), so the background sends that frame the step off. Without this, its report started a new hold, whose step on put every other frame back in the mode. With a live hold, the frame joins it. The frame that sees the end reports its new mode as every frame does, and the background sends the media step off to the other frames of the hold, never back to the reporter. A frame of the hold with a hint or the line open keeps it, and closing it lands in normal mode. A report of hint or command line mode keeps the hold. `aa` needs a video, not only audio. `;M` pins only a video (never audio) of its own frame and refuses one in a same-origin frame. `q`, `H` and `L` ask the player in the pinned frame first, while the pinned video is on the page. A fullscreen that ends in a frame while a hint or the line is open there, opened from the mode, closes it and keeps the frame in the mode, because Firefox spends the Escape on leaving fullscreen (see [firefox-behavior.md](firefox-behavior.md), "Escape in fullscreen"). The end reaches every frame of the fullscreen, so with the player in a child frame the frames without the line report normal, in any order with the line's close. The background keeps the hold while a frame of the hold has a hint or the line open that it opened from the mode, and sends the media step back to each frame that reported normal meanwhile once that frame closes it. A normal report within 500 ms after such a line closed back to the mode (`LINE_CLOSE_GRACE_MS`), from a frame without the focus, is the same end and goes back to the mode too. An Escape the user presses comes from the frame with the focus, so it still ends the mode. A line frame that no longer answers a ping keeps nothing. When the mode ends in another frame, closing the line lands in normal mode. A `%` key with no count refuses with "Type a number first". A frame that starts its content script on its first focus after the mode began joins it, when it starts in normal mode with no editable focus. Its first keymap read says so (`join`) and the reply carries `join: "media"` (`tab_media.join`: true when the hold has frames or `aa` stepped on, a pin alone does not count). The background writes the frame into the hold in the same turn, so an end after the read sends the frame the step off, and its report finds it in the hold. A step off that reaches the frame before it applies the reply is lost, and the rule that a stepped report (`step`) of media mode with no live hold gets the step off sends that frame back to normal. Insert wins over media. A frame under an all-off rule never joins, and a re-ask of the keymap (config reload, macro recording) never joins.
- `history` lists only history (`values: { from: "history" }`, `kind: "history"`), newest first, from the same fetch as `open` and with no dedup against bookmarks. A private line gets no rows, and Enter there refuses with "no history in a private window". The answer carries the `history_list_max` cap (default 20) for an empty word, and a typed word ranks every cached row, so history older than the 8000 newest addresses is not reachable by typing. The cache fills from one `history.search` when the background starts and stays current from `onVisited`, `onTitleChanged` and `onVisitRemoved` (`allHistory` clears it). Events that arrive during the fill apply after it, in order. A page the cache has not seen enters only after a one-row `history.search` lists it, since `onVisited` also fires for hidden pages such as redirect sources. Firefox sends no event when only some visits of a page are deleted, so such a page can keep a too-new last visit until the background restarts. Until the fill ends, a line gets the 1000 newest entries from `history.search` and never waits. The size comes from a measured limit: the page ranks every row on each keystroke, and at 20,000 rows that took 70 to 100 ms in Node, over the 16 ms a keystroke can spend. A typed word ranks by use as well as text. A pick puts the address in the line. Enter takes an exact address first, then the best match on title and address with the same use boost, so it opens the row the list shows first, and refuses an equal tie. It has no default key and no container flag.

- Ranking by use. `open`, `history`, `bookmark` and the finder raise a text match by how much a page is used, and never lower one: score times (1 + boost), with the boost from 0 to 0.6, added before the exact-name bonus, so an exact name still leads. The background computes the boost once per fetch and sends it on each row, so the page only multiplies. Half of it comes from the visit count (by its log, full at 50 visits) and half from the last visit (it halves every 14 days). Firefox gives only those two numbers per page, not the visit list its own frecency reads. A bookmark, quickmark or closed tab takes the boost of its address's history row, so a bookmark opened daily ranks as a page visited daily, though the history row drops out as a duplicate. An open tab gets 0.3 plus its page's boost, within the same cap. A private line reads no history, so in `open` and the finder only its tabs get a boost. The `bookmark` list and its Enter read the boost on every line, so they agree. Site rows: in `open` and the finder, a typed word of at least 2 characters with no space that starts a label of a visited web host (`git` finds `github.com`, not `digital.com`) offers that host's home page, at the scheme of its newest visit, as a row of its own. Up to 3 hosts show, the most used first, and each ranks with the summed visits of all its pages. A host whose home page is already a row (a bookmark, history row, quickmark or tab) gets no site row. A private line gets none. The page ranks site rows by the same scorer on the host name.
- Engines ride the same fetch (`kind: "engines"`) for the first word of `search`, `--engine=` and `engine.show`. A row shows the engine name and its label. The background marks each engine with a yes or no for whether the line's tab page can fill its slots, and sends no page data. A row the page cannot fill is dimmed and reads "unavailable" in the args column; `engine.show` marks none. A word that ends in a dot (`github.`) lists every engine under that prefix, deeper ones included. The parser still reads a hidden engine, so a picked or typed one runs and the router refuses it.

### Tab sessions

`ts` saves the tabs of the current window under a name and `tS` opens a saved session from a list. `ts` opens the line with `session.save ` typed, and `tS` with `session.open `. The command line also has `session.delete <name>` and `session.rename <name> --to=<new>`, with no keys. The flag comes before the name because the name is the `main` param and runs to the end of the line.

- The sessions live in `storage.local` under `desertfox_sessions` as `{ version: 1, sessions: { [name]: { saved_at, tabs } } }`. A tab keeps its address, title, pinned and active flags and, when it has one, its container id and name. The array order is the tab bar order. Only `src/background/session_store.ts` reads and writes the key, and its writes run one after another, so two saves at once both land. A stored version other than 1 is refused and never overwritten, and an entry this version cannot read is kept as it is when another session changes. A write that fails, for example on quota, refuses with the cause and leaves the stored sessions as they were. Measured: 100 sessions of 50 tabs are about 1.3 MB, and `storage.local` took 400 such sessions (5 MB) without `unlimitedStorage`.
- A name is trimmed with its inner spaces joined to one, must not be empty, may not start with `-` or `@` when saved or renamed to (the line would read it as a flag or a slot, and the param schema refuses it), and is unique ignoring case. Saving an existing name updates it, keeps its display case and says so in the toast with both tab counts. Rename refuses a name another session has.
- `session.open` takes `into`: `window` (default) opens a new window, `tab` adds the tabs to the end of the current window, all discarded, and the current tab stays active. There is no replace, because it would close the user's tabs. In a new window the tabs are created in order, and every tab but the active one is created discarded, so it shows its saved title and loads on first visit. Firefox refuses `tabs.create` with `discarded` and `pinned` together, so a pinned background tab is created discarded and pinned right after. A container is found by its saved id, then by its name, else the tab opens in the default container and the toast counts it. An address off the open allow-list (see "Routing") or one Firefox refuses is skipped and counted in the toast. When the saved active tab is one of those, the first tab that opened loads instead. The toast of a new window shows on a tab of that window. When the window closes while the tabs open, the restore stops and says so. A new window opens on `about:blank`, and that tab is removed when the session's tabs are in. The restore reads the session once at its start, so a save of the same name while it runs changes the store and not that restore.
- The settings page exports the sessions as `desertfox-sessions.json` (the stored shape, readable sessions only) and imports one. An import adds sessions and removes none. A name that is taken, ignoring case and counting entries this version cannot read, keeps both: the import arrives as `name (2)`, then `name (3)`, and a name that already ends in a suffix gets another. An imported name goes through the same rule as save (the shared `NEW_NAME_PATTERN`, with its spaces joined), so an entry named `-x` or `@x` is skipped and listed in the answer, as is an entry that is no session. A file that is not JSON or not version 1 is refused whole. A sessions file is data and not code, so no consent screen asks first. Only extension pages may send the two messages.
- Private windows refuse every session command and the list is empty there.
- The `sessions` completion source (`values: { from: "sessions" }`, `kind: "sessions"`) lists the names newest first with the tab count and age in the description column, which the background writes. It ships the whole list once per line, like the bookmarks.
- The `folders` completion source (`values: { from: "folders" }`, `kind: "folders"`) lists every bookmark folder as a path from the root, such as `Bookmarks Toolbar / Work`, with the count of bookmarks directly inside in the description column. The background builds it from `getTree` with a walk that keeps the parent chain. Folder titles are display text that Firefox localizes, so a folder is named by its path and a command re-reads the tree and looks the path up: an exact path wins, other text is a fuzzy match, and a path that two folders share is refused, as an equal tie is for `bookmark`. `bookmark.add --folder=` files a new bookmark there, and with no folder Firefox's default applies. A page that already has a bookmark refuses with a folder, because `bookmark.move` is the way to change its folder. `bookmark.move` takes the folder as its main param and `--bookmark=` for another bookmark (empty means the current page), and moves every unmanaged bookmark at that address. `bookmark.open_folder` opens the folder's own bookmarks, not those of its subfolders, in a tab (the first one active), in background tabs or in a new window, never `here`. It opens at most 25 and one toast says when the cap cut the list or an address was skipped. It skips the addresses off the open allow-list (see "Routing"), such as `place:` queries, `javascript:` bookmarklets and `about:` pages other than `about:blank`. An address that passes that filter and still fails is skipped and counted too, and the rest open. In a tab, the tabs open in the background in folder order and then the first one becomes active, so the strip keeps the folder order. When every address fails the command refuses.

### Tab groups

Firefox native tab groups (`tabs.group`, 138, and `tabGroups`, 139, under `strict_min_version` 153). The `tg` keys and `tabgroup.*` commands (`src/commands/tab_group.ts`) act on the line's own tab and its group: `tabgroup.add [group]` (`tga` prompts, `tgA` starts an untitled group), `tabgroup.remove` (`tgd`), `tabgroup.name <title>` (`tgn`), `tabgroup.collapse` (`tgc`), `tabgroup.expand` (`tge`), `tabgroup.toggle` (`tgt`), `tabgroup.color <color>` (`tgl`, the nine Firefox colors as an enum) and `tabgroup.next` / `tabgroup.prev` (`tgj`, `tgk`, a count moves over that many groups). Marked tabs reach no command today, so there is no many-tab form.

- `tab_actions.ts` holds `group_tabs`, `ungroup_tabs` and `set_group` over an injected `GroupDeps`. A pinned tab and a list that spans windows are refused with a `RuntimeRefusal`, as is a target group of another window, because a group stays in one window.
- `next` and `prev` focus the first tab of the neighbor group in the window, ordered by each group's first tab, and wrap at the ends. From a tab in no group, `next` lands on the first group after it and `prev` on the last group before it. A collapsed target group is expanded first, so focus never lands in a hidden group. Skipping it would make a collapsed group unreachable by key.
- `add` names a group of the tab's window. A name that no group has starts a group with that title. A group is named by its title, and a title that is empty or shared by several groups of the window gets the id as a suffix (`Play #12`, `#12`), which is also how the completion lists it (`src/shared/group_name.ts`). A bare title that several groups share is refused and the refusal names the id form.
- The `groups` completion source (`values: { from: "groups" }`) lists the groups of the line's window from the live tab model, so it needs no fetch. A group is not private or normal by itself: it takes the privacy of its window's tabs.
- The manifest needs the `tabGroups` permission. Measured in Firefox 160: without it `browser.tabGroups` is absent (see `docs/firefox-behavior.md`).
- The model keeps `group_id` per tab (-1 for none) and a groups table. A patch carries `groups` and `groups_removed` only when some changed. A group event patches the table. A removed group also clears the `group_id` of its tabs in the same patch. A group move reads the tabs again, because its tabs change index and Firefox may report it as tab moves or not.

### Live tab model

The background keeps one map of tab rows (`src/background/tab_model.ts`), built from one `tabs.query` and kept current from tab events. It stores nothing, because one query rebuilds it. Each row carries the tab's site key (`src/shared/site_key.ts`) and a favicon only when the list rule allows it. Changes batch on a 30 ms flush and go to clients on the port `desertfox_tab_model` as a snapshot, then patches (`TabRow` and the messages are in `src/shared/messages.ts`). A patch has `removed` ids, then `upserts`, and the upserts include every row whose index shifted. `rev` counts per port, because a port sees only tabs of its own privacy. A client that sees a gap in `rev` sends `resync` and gets a new snapshot. A `resync` and each new port first read tabs, windows and containers from Firefox again and send any difference from the model as a patch, so a stale or missed event does not last until restart. An event during those reads makes it read again, up to three times. After that the model keeps the rows the events built until the next `resync` or new port. A row also carries its window number (the place in `windows.getAll`, as `tab.attach` counts), whether it is the window's previous tab (the `#` tab, seeded from storage at load), and its container's name, color and icon. Only an extension page may connect. `cmdline.html` is web-accessible, so a web page can frame it, and such a port must also be the frame that redeemed its tab's command line ticket. Other extension pages cannot be framed and skip that check. A page with a sender tab gets that tab's privacy. A page with none (a sidebar) connects as `desertfox_tab_model:normal` or `:private` (the names are in `src/shared/tab_model_port.ts`), and a port that states nothing gets no rows. A tab moving between windows reads as removed until it attaches. The command line `tab` list reads the model: its page opens the port on the first tab read, after it redeemed its ticket, and closes it with the line. Row marks change only when a patch arrives.

### Hints

- Candidates come from one query per filter (all, every, clickable, buttons, inputs, links, prose, scrollable, media, images): a selector plus an optional test, such as `prose` keeping elements with a text node of their own. The search reaches open shadow roots and, through Firefox's `openOrClosedShadowRoot`, closed ones.
- An IntersectionObserver batch finds visible candidates. An `elementFromPoint` check removes covered ones.
- Labels render in a closed shadow root. All layout reads happen before any write.
- Typed text narrows hints. `/` switches hint mode from typing a label to typing text, for every filter and action. Tab does nothing in label mode. In text mode every one-character key is text and Space is part of it, so a query can hold several words. Hints keep their letter labels, but only for display. The matches rank by `rank.ts`: a whole first word scores 8, a whole later word 4, a first-word prefix 6, a later prefix 2 and a substring 1, summed over the query words (each must match) and divided by the log of the text length, so a short text wins a tie. Ties keep page order. The best match is active and shows with swapped colors, Tab and Shift-Tab move the active hint, Enter picks it, and a single remaining match picks at once. A key that matches nothing is dropped, as in label mode. In text mode `/` is text. Backspace trims the text, and on empty text it returns to label mode with every label back. The key that enters or leaves text mode never picks. The text of a hint is its visible text, else `aria-label`, `title`, the `alt` of a picture in it, or an input value, cut to 400 characters. The name list is shared with the link copy list and the next-page search (`name_candidates`), and a password value is never read. It is read once, on the first `/`. A rapid rebuild starts in label mode. The `text` param is only a launch filter and does not start text mode, so the labels stay typable. Tab, Shift-Tab, Enter and Space are bound in the hint keymap to the hidden command `hint.key`, so the content script holds them while the hints bundle loads. `/` has a row in the same keymap for its which-key label only, because the content script already holds every one-character key. The bundle sink takes them first once hint mode is open, so rebinding them changes nothing, and unbinding one only drops that hold. While hint mode is open a key line shows at the bottom right, where the mode badge sits (the badge is hidden in hint mode). It reads `/: type text · Space: turn labels` in label mode and `Enter: pick · Tab: next · Backspace: labels` in text mode. The words are fixed, not read from the keymap. The `hint_key_line` setting (default on) hides it. A match that typed text made unique picks after a 300 ms grace with hint mode still open. The keys that arrive in the grace are dropped, so the rest of a typed word never runs as normal keys or as labels of the next round. Enter picks at once, and Escape in the grace cancels the pick.
- Space in label mode turns the stacking order of overlapping labels. Each press reads the label boxes again, groups the boxes that cover each other, and sends the top label of each group to the bottom, so a covered label comes to the top.
- The actions are open, background tab, new window, start caret mode, start visual mode, copy link, copy text, copy CSS selector, copy outer HTML, select in the DevTools Inspector, delete element, focus, hover, double-click and, on a video or audio element, play or pause, mute or unmute and fullscreen. Hover sends the pointer events a mouse sends on entering (over, enter and move), from the middle of the element, so a menu or preview that a script opens appears. The next hover, Escape, a hidden tab or another pick ends it, and a pick inside the hovered element keeps it entered. A CSS `:hover` rule does not react, because synthetic events do not set it. Double-click (`;2`, `double_click`) sends the over events, then two presses (pointerdown, mousedown, pointerup, mouseup, click) with click count `detail` 1 and 2, then `dblclick`, all from the middle of the element. The clicks are dispatched events and not `click()`, because `click()` carries no count. The events are untrusted, so a page that checks `isTrusted` ignores them, and Firefox selects no word for them, so on a text node under the middle point the action selects that word with `caretPositionFromPoint` and a word range from `Intl.Segmenter`. A field and a box with no text get no selection change. Links, and elements inside a link, get no label in this mode, because the first click would navigate away. The `links` filter is refused by the `value_when` rule. Rapid mode keeps hints open for several picks. With `copy` or `copy_text` it collects the picks into one list instead: the first pick of an entry wins, a repeat adds nothing, and every pick rewrites the clipboard (and the `"a` register) with the whole list, one entry per line, so the list is right at Escape and survives a navigation. The toast counts the entries. `;Y` is `hint --copy --links --rapid` ("Copy several link URLs"). The `prompt` action (short `-L`, the `;:` modifier, so `;:l` and `;:a`) puts the address of the pick in the command line for editing. The `command` param (default `open`, valid only with `prompt`, a command name and flags by a pattern, so no pipe, no chain, no quote) is the text typed before the address, and the content script writes `<command> <address>` with the address single-quoted when the line would split or misread it. It is a prefix the user sees and edits, never a command string the extension runs: Enter submits the line through the one validator like any typed line. The line opens in the frame that ran the pick, and the `hint.run` answer stays pending until Enter or Escape, as for `;u`. An element with no address refuses with "This element has no web address", and `rapid` is ignored. The `media` filter labels visible `video` and `audio` elements, and skips the cover test because site controls lie over a player. `;m` runs `play_pause` on the pick, through the conditional `action` default for `filter=media`. Fullscreen shows the player box, the outermost ancestor with the size of the element, so site controls and subtitles stay, and a second pick leaves fullscreen. A hidden `<audio>` has no box and gets no hint, and a player in a cross-origin iframe is out of reach unless the hints run with `--all-frames`. The `images` filter labels an `img`, an image button and a box with a CSS background image, each rendered at least 24 px on both sides, and skips the cover test because a card lays a stretched link over its picture. Inline `svg` gets no label, because it has no address. `;I` opens the pick in a new tab, through the conditional `action` default for `filter=images`. Copy and open use the address of the element itself, never an ancestor's: for an image in a link, the `images` filter gives the picture and the `links` filter gives the `href`. An image address is `currentSrc`, then `src`, then a lazy `data-src` resolved against the page, and a web address wins over an inline placeholder. Under the `images` filter a CSS background image wins over the `href` of its own link. A `blob:` address, or a `data:` address over 8 KB, counts as no address. A short `data:` image can be copied but not opened, because Firefox refuses a `data:` URL in `tabs.create` ("Illegal URL", checked in Firefox 159), so open actions skip it and show no label for it. Under another filter, a copy of a picture or media element with no address refuses with "This element has no web address". `;u` opens the command line with `hint --custom `, so a typed CSS selector labels its matches. The selector is the verbatim main param of `hint`, so the line hands it over exactly as typed: a selector with spaces or double quotes (`.card a`, `a[href="/x"]`) needs no quoting, and a quote typed around it stays in the value. Flags go before it, and a selector that starts with `-` needs `--` first. The long flag `--filter custom` does not parse: an enum is set by its value as a flag. The `every` filter (short `e`, bound to `;a`) labels each visible element with a size, except a wrapper of one element child and no text of its own, and a link, button or label is exempt from that skip. The eight `;y` yank keys are plain `hint.run` bindings with a fixed action and filter, so they have no filter step and no modifier variants: `;yl` copies a link address, `;yi` the picture itself (`copy_image`, images only), `;yI` the image address, `;ym` the media address, `;yf` the frame address, `;yt` the text, `;yc` the CSS selector and `;yh` the outer HTML of any element, both with the `every` filter. `copy_selector` gives the shortest selector that is unique in the root of the element (the document, a shadow root or the frame's document, so it is relative to that root), preferring `#id`, then `tag`, `tag.class` or `tag:nth-of-type(n)` steps up to the nearest unique id. An id or class that looks generated (four or more digits in a row, eight or more hex digits, or a `css-`, `sc-` or `jsx-` prefix) or that needs CSS escaping is skipped. `copy_html` copies the whole `outerHTML` with no cap and leaves out shadow content. The toasts read `Copied selector` and `Copied HTML`. `;o` modifier (`inspect`) selects the pick in the Inspector of the tab's open DevTools, so `;oa` takes any visible element (the `every` filter, which also reaches a plain `div` or `span`), and `;ol` a link. The manifest has a required `devtools_page` (`devtools.html`), and each toolbox loads it. The content script sets `window.wrappedJSObject.__desertfox_pick` to the element and sends `inspect_pick`. The background relays it, by tab id, to the devtools page, which evals one constant string that deletes the property and passes the node to `inspect()`. A single eval keeps a second pick in rapid mode from being deleted between a separate select and delete. The node never travels as text, and no page data goes into an eval. With no toolbox open the page shows "press F12", and the pick waits 60 s in `storage.session` for the page to connect. A navigation or a closed tab drops it. The action skips the cover test, and an element in a cross-origin frame, or a pick made from a frame, is refused. After a pick, Firefox leaves focus in the Inspector, and the way back takes two keys (see firefox-behavior.md). The `;d` modifier (`download`, for images, links, media and all) saves the file at the address, so `;dI` saves a picture. Both send the address to the background. A copy fetches it with no Referer and with `credentials: "include"` for a tab in the default container, but with `credentials: "omit"` for a private or container tab, so it never borrows the default cookies. A picture behind a login then refuses in such a tab, and a site that blocks hotlinks refuses everywhere. The fetch times out after 20 seconds. A PNG or JPEG goes to `clipboard.setImageData` unchanged, read by its first bytes. Any other format, SVG included, is drawn and converted to PNG, and a GIF keeps its first frame. A copy over 20 MB is refused, and the read stops at the cap when the server sends no length. A download hands the http, https or `data:` address to `downloads.download` with the tab's private and container context and no forced file name, so the browser fetches it, streams it to disk and honors `Content-Disposition`. It needs the required `downloads` permission. A fetch, conversion, clipboard or download-start failure refuses with a message naming the step, and the clipboard stays as it was. The `frames` filter labels `iframe` and `frame` elements rendered at least 24 px on both sides, visible and uncovered, in the page and in same-origin frames, and never the command line frame. `;f` focuses the pick, through the conditional `action` default for `filter=frames`, with the short flag `-E`. A subframe gets its content script on its first focus, so keys act inside it. Hints reach into same-origin frames from the top page's own script, so those frames need no script of their own. A frame that already holds the focus when its script loads starts at once. `gF` runs `frame.exit` ("Focus top page"), which sends `focus_page` to frame 0 only, so the top page blurs its own iframe element whatever the frame's origin. It does nothing when the keys are already in the top frame. Open and copy of a frame use `contentDocument.URL` when readable and the `src` otherwise, and refuse with "This element has no web address" for `about:blank`, `srcdoc` and a frame with no `src`. Copying the text of a frame refuses. A frame inside a frame of another site gets no label from the top page: focus the outer frame, then press `;f` again, or use `--all-frames`.
- Hints across frames of other sites are opt-in: `hint --all-frames` (the `frames` param, `same_origin` by default). The frame that runs the command owns the keyboard and the typing rules. The background (`src/background/hint_frames.ts`) injects the hints bundle into every frame that takes scripts, waits up to 500 ms for each frame's count of candidates, and hands out one prefix-free label set, the top frame first. Each frame draws its own labels. A typed prefix and a pick go out through the background, and the owning frame runs the action. A frame that reports after 500 ms gets no labels and no later redraw. A frame outside the top viewport finds nothing visible and gets none. Escape, a hidden tab and a pick end hint mode in every frame. A same-origin or about:blank frame labels nothing itself, because its parent's walk already labels it, so each element gets one label. A focus pick or a field pick in another frame focuses that frame's window first. `inspect` keeps its frame refusal. `enter_media` keeps its frame refusal: no key test shows that the pin and the media keys follow focus into a frame of another site. For `caret` and `visual` the frame of the pick calls `window.focus()` and starts the mode itself, and the keys follow the focus into it (a key test shows this for a frame of another site). The keys typed before the labels showed go with the pick: the owner types them into the field it focuses and returns the rest, which the keyboard frame replays as normal keys. A mode that starts in the owner drops them, and one that fails to start leaves them to replay. After a hover in another frame, Escape in the keyboard frame releases the hover there, through a message to every frame of the tab. The message names the session of the pick that hovered, so a late release does not clear a newer hover. A copy or a `prompt` does not run in the frame of the pick: that frame answers with the text (the copy text, or the whole line for `prompt`, tracking parameters already stripped there), and the keyboard frame runs its usual copy or opens the line. So a rapid `copy` or `copy_text` keeps one list in the keyboard frame that joins the picks of every frame, the register applies, and the toast draws where the keyboard is. Text mode (`/`) ranks the hints of every frame: each frame sends the text of its candidates with its count, the background holds them in memory during the wait and returns them with the labels, and the typed relay carries the matching labels and the active one so the other frames hide the rest. With `--all-frames` the texts are a snapshot taken when the hints start, so a later page change does not show in text mode. A frame that ends the session before the start answer arrives is noticed by session id, so the run ends and does not enter hint mode. Known limits: keys typed during the round trip of a pick in another frame (a few milliseconds, and the same gap before a cross-frame `prompt` opens its line) run in the keyboard frame as normal keys. `copylinks` (`yL`) does not follow the flag.

### Which-key

Which-key is a first-class surface. After a prefix key, it lists each possible next key with the label of its command. Hovering a row shows the command's intent, or the `intent` of the binding when it has one. It reads both from the registry, so a new command appears without extra work.

The label of a key comes from one rule, applied to the args the binding sets (never the defaults the validator fills in):

- A binding `label` wins. It exists in the TOML table form and on the bindings of the default keymap. On a key that runs several commands, the label sits on the first command. The binding `intent` works the same way for the hover text, and modifier variants do not inherit it.
- A key that sets a container reads as the container name, and the container named `default` reads "Default container".
- Otherwise the label is the command label. A search engine with a label in `search_engines.toml` replaces it (a child engine's label is the chain of labels on its path), and a binding with no engine uses the default engine. Then each `enum` arg the binding sets to a non-default value adds its `value_labels` phrase, in param order ("Open URL in new tab"). A `bool` set to true adds the param name ("Reload hard"). Numbers, free strings and prompted params add nothing, so the keys that set them carry a hand `label` ("Scroll left", "Zoom in a lot"). A phrase that the name of any group above the key already says, as whole words and in any case, is left out: under a group named "Search in new tab", the key reads "Google", not "Google in new tab".
- A snippet key shows the `// label:` header of its snippet.

Two keys in one group may share a label only when they run the same binding (`zi` and `z+`). The unit tests check this for every group of the default keymap and of a copy of the user config, and print each group's labels.

- In the browser it draws in a closed shadow root, styled through the CSS variables in [Styles](#styles). It appears after a delay that is a setting.

### Caret and visual

Caret mode puts a text cursor in the page, so the user can move through text with vim motions. Visual mode extends a selection with the same motions. Line visual mode (`visual_line`, badge `V-LINE`) selects whole screen lines.

- Caret mode starts at the first visible text, or at a hinted element with `hint.run action=caret`, and visual mode at one with `action=visual`. In normal mode `v` starts caret mode and `V` visual mode. In caret mode `v` starts visual mode and `V` line visual mode. In visual mode `V` switches to line visual mode, and in line visual mode `v` switches to visual mode and `V` returns to caret mode. A switch between the two visual modes keeps both ends of the selection.
- Caret mode draws the caret as a one-character cell with the CSS Custom Highlight API, in the `mode_caret` color with `bg_core` text, and leaves the page selection empty. So `@selection` and Ctrl+C find no text in caret mode. The visual modes select the page text itself, in the `selection` color. A switch from caret mode to a visual mode replaces the cell with the selection, and the switch back does the reverse. A caret on an empty line has no cell. A click or a drag in the page during caret mode moves the caret there at the next key, and the next paint clears the page selection it made.
- The motions are `h`, `j`, `k`, `l`, `w`, `b`, `e`, `0`, `$`, `gg` and `G`, with count prefixes. The arrow keys move like `h`, `j`, `k` and `l`. The line motions (`j`, `k`, `0`, `^`, `$`) use Firefox's `Selection.modify`, so a wrapped paragraph moves per screen line, and `j` and `k` keep their column. The other motions run on a text model of the visible page, and word motions count letters and digits of any script.
- `f`, `t`, `F` and `T` read the next key as a target character and move to its next match anywhere on the page, exact case. `t` stops before the match and `T` after it. At a line break `t` stops on the last character of the line, because no motion moves off a line break. A count picks the Nth match, and with fewer matches the caret stays. The target is any printable key or a space, even a bound one, and the key layer reads it as the `char` param of `caret.find`, the way `m` reads a mark name. So a macro records the character with the step. Escape drops the waiting key and keeps the mode, in every mode and for every command that waits for a key (`m`, `'`, `q`, `@`, `"`), and a second Escape does what Escape does. A chord cancels the wait and then runs. In visual mode the selection end moves.
- After a target, every match on the screen and about a screen around it is lit (the CSS Custom Highlight API, under names of their own so a kept `/` search stays), the match the caret stands at or next to in the stronger color. While they show, the find is live: `;` and `,` repeat it, and so do `f` and `t` (as `;`) and `F` and `T` (as `,`), so `F` reverses an `f` find and, after an `F` find, `f` goes on backward. `t` after `fx` repeats the `f` find. A live find takes no new target: Escape or another motion ends it, and the next `f`, `t`, `F` or `T` then starts a new find. A count before the key repeats that many times. Scrolling or resizing lights the new screen. They end on Escape, on any other caret, visual or search command, and on a mode change, never on an unbound key. `;` and `,` still repeat the last find after the end, without highlights. `.` does not repeat a find or its repeat, but a macro replays both, because the repeat is a step of its own.
- A line is a screen line, the unit of `j`, `k`, `0` and `$`. Line visual mode keeps the anchor and caret of visual mode, and selects from the start of the screen line of the earlier end to the end of the screen line of the later end. The motions, `/`, `?`, `*`, `#`, `n`, `N`, `o`, `y` and `s` work as in visual mode on that wider selection. `y` adds no line break at the end, because a web page has no line-wise paste.
- In visual mode, `o` swaps the ends of the selection, `y` copies it, and `s` searches it with `open.search` and the `default_engine` setting. Any command whose param defaults to `{ from: "selection" }` uses it. Escape returns to caret mode, then to normal mode.
- Visual mode has the text objects `aw`, `iw`, `as` and `is` (`visual.object`, with `object` word or sentence and `scope` around or inner) and the open keys `p` (here) and `P` (new tab) (`visual.open`, with the `where` param). An object stays on the caret's line. With a one-character selection, `aw` takes the word and the blanks after it, or the blanks before it at the end of a line. With a longer selection it grows forward by one more object, so `3aw` and `awaw` work. In line visual mode an object switches to character visual mode first, as in vim. A sentence is what `Intl.Segmenter` finds, so an abbreviation such as `Dr.` may end one. Paragraph objects are not bound, because the edges of a paragraph are fuzzy on a page. `p` and `P` collapse line breaks to spaces and send the text to `open.url`, which opens a URL or searches with the `default_engine` setting. A blank selection shows a message and stays in visual mode, and a successful open returns to caret mode.
- The motions are registry commands in the `caret`, `visual` and `visual_line` modes, so keys, which-key and help cover them like any other command.
- Page text inside inputs and text areas belongs to insert mode, not caret mode.

### Page search

- `/` and `?` open the command line as a search line and search the page text as you type. `n` and `N` go to the next and previous match in the direction of the last search, and the last search is kept in register `/`. The code lives in `caret.js`, and `content.js` holds only `find.open`, `find.next` and `find.prev`.
- The search covers the page, open and closed shadow roots and same-origin frames. Text in fields is left out. The query is a regular expression with smartcase: a capital letter makes it exact. A typed space matches a line break. A pattern that is invalid, or that could backtrack without end, is searched as plain text instead, and the line says so.
- Enter keeps the highlights and the match, Escape clears the highlights. Both keep the search and the match as the place `n`, `N` and a new caret or visual session go on from.
- In caret mode `/` and `?` move the caret to the start of the match. Escape on the line leaves the caret where it was. Either way the mode returns to caret mode. `n` and `N` move the caret to the next and previous match.
- In visual mode `/` and `?` move the caret end to the match and keep the anchor. Escape on the line leaves the selection as it was. `n` and `N` do the same with the next and previous match: the caret end goes to the start of the match, so a match before the anchor flips the selection.
- `*` and `#` are `find.open --word` and `find.open --word --backward`. They search the word under the caret, whole and case-sensitive, with no line. In visual mode with a selection they search the selected text. In normal mode the start of the visible text stands in for the caret. They set register `/` like a typed search.
- A `MutationObserver` marks the text model stale when nodes or text change in the page, its shadow roots or its same-origin frames, ignoring the elements DesertFox adds itself. The observer also watches shadow roots and frame documents that held no text when the model was built, and a frame's `load` event counts as a change. A shadow root attached later to an element already on the page fires no event. The model lists the custom elements (a hyphen in the tag name) that had no root at build time, and `n` reads the model again once one has gained a root, open or closed. A plain element that gains a root is not seen until the next `/`. A class or style change that only shows or hides text is not seen, and a new `/` always reads the model again. The next keystroke or `n` reads the model again. The observer starts with the first search.
- A page with more than 4 million characters of text is searched only up to that point, and the line and toast say so.

### Registers

- The background owns the registers (`src/background/register_store.ts`). A value is text or a list of invocations (a macro). A normal window keeps them in `storage.local`, a private window keeps its own in `storage.session`, and the last private window to close drops them. The names are `a` to `z`, `A` to `Z` (append to the lowercase one), `"` (the last yank), `+` (the clipboard), `_` (the black hole) and `/` (the last search). `:registers` lists them.
- `"<reg>` is part of the next command, like a count, and not page state. The matcher (`src/shared/keys/matcher.ts`) keeps the typed register beside the count digits, in normal, caret, visual and visual line mode, and at the match it fills the `register` arg of each step whose command has a `register` param (the compiler flags the step). So `"ay`, `3"ayy` and `"a3yy` are the same command with a register, and `.` or a macro that replays the step keeps its register, because the register is an arg of the stored step. `:copy --register=a` does the same by hand. A user binding of `"` wins over the prefix. `"` then a key that names no register, or a key with no binding, ends the prefix and gives the key its usual meaning. Escape ends it too. Backspace drops the last key of the prefix. A change of mode drops it. In insert mode `"` is an ordinary key.
- While the name is awaited, which-key lists the stored registers instead of the tree. After the name it lists nothing until a key of a longer sequence follows.
- A yank is visual `y`, `yy` and the other `copy.url` keys, `yl` and `yL` (`copy.links`), and the hint copy actions. Each writes the system clipboard, the unnamed register, and the named one when `"<reg>` is given. `"+y` writes the clipboard and the unnamed register, and `"_y` copies nowhere and shows no toast. The registers fill even when the clipboard refuses the write, as on a plain http page. `"Ay` appends to `a`, and refuses when `a` holds a macro. No yank reads the live text of a field, so none needs `is_secret_field`. A copy of a web address drops tracking parameters first: the page address and its canonical and short links (`copy.url`), the link list (`copy.links`, before it merges equal addresses), the tab list (`copy.tabs`) and the hint `copy` of an address, but not `copy_text` or a text fallback. The `strip_tracking_params` setting lists the names, each a plain name or a `prefix*` glob, matched without case. It ships with `utm_*`, `fbclid`, `gclid` and the like, an empty list turns the stripping off everywhere. The per-site `strip_tracking` boolean (default true) chooses the sites that use the list, so a site row gives either recipe. All sites except some: leave `strip_tracking` on and add `strip_tracking = false` rows. No sites except some: set `strip_tracking = false` globally and add `strip_tracking = true` rows. A copy resolves the setting against the address of the page holding what it copies (a subframe against its own address), and `copy.tabs` against each tab's own address. The bundles ask the background (`read_strip_patterns`), which answers the list or an empty list, so content.js does not grow. `:help site_rules` shows the column like any per-site setting. The remaining query text, the fragment and the encoding stay as they were (`src/content/strip_tracking.ts`).
- `"app`, `"apt`, `"apw` and `"aP` are `open.clipboard` with a register: the text of register `a` opens as a URL, here, in a new tab or in a new window, and text that is no URL is searched. The empty register and a macro refuse.
- `<C-r><reg>` in insert mode is `register.paste`. It types the register through the shared field writer. The text joins the insert session, so `.` repeats it as typed text, and `register.paste` itself stays out of the `.` slot. It costs Firefox's Ctrl+R reload while a field has focus. Insert mode with no field leaves `<C-r>` to the browser. Pasting into a password field works. Only recording from one is blocked.

### Macros

- Recording, `@<reg>` replay, `@@` and counts are built. `q<reg>` is `macro.record`: `qa` replaces macro `a`, `qA` adds steps to it, and any other key refuses. Pressing `q` again is `macro.stop`, which stores the steps in the register as a list of invocations (the register store keeps the macro like any register value).
- The recorder (`src/background/macro_recorder.ts`) reads the same `record_step` call as `.`, so it sees every finished request and every leaf of content commands, including failed ones. A step that fails when recorded fails again on replay and stops the macro. It keeps the steps up to a failed or cancelled one, and drops `macro.record` and `macro.stop`. It skips a step that opened the command line for a value (the line sends the finished command as its own request) and the address a hint pick opens (the pick repeats it). A `hint.run` is kept from the message sent when the pick begins and not from the message of the leaf that ends later, which carries the same step.
- The recording state, `{ register, steps }`, lives in `storage.session`, and a private window has a key of its own. Every step is stored as it comes, so a background restart keeps the recording and no page buffers it. A held key sends its first press only, so a held `j` is one step.
- While a macro records, the background answers each page's `read_keymap` with the tree that has `macro.stop` where `macro.record` sat, and with the register name. Starting and stopping tell every tab to read its keymap again. The badge in every tab then adds `recording @a`, whatever the mode indicator setting says. No page code watches the key.
- Typed text is recorded as the `text.insert` step, led by the entry command, as for `.`. The same text lands in two places: in the `.` slot it stays in `storage.session`, and in a macro it is a register value in `storage.local`, so it survives a restart. A normal window and the private windows keep their own, as registers do. Text from a password field is never recorded, because the text recorder drops it before any step exists.
- Which-key under `q` and `@` lists the stored macros with their step counts when no recording runs. It reads the stored tree, so during a recording `q` is a leaf and shows no panel.
- `@<reg>` is `macro.play` (`src/background/macro_replay.ts`). Each step runs through the router as its own request, with no command line and with instant scrolls, so `.` after `@a` repeats the macro's last repeatable step. A failed step, a cancelled hint pick, the 10 s page-ready timeout or Escape stops the replay. `@a` inside a macro plays inside the same replay, up to 10 levels. A register with no macro refuses. Recording refuses while a macro plays, and the recorder keeps none of the replay's own steps, only the `@b` that started it.
- After a step that navigates or switches tabs, the replay waits for the page to be ready (`page_ready.ts`), then goes on in the active tab: in the frame `@a` came from while it stays in that tab, in the top frame of any other. A step counts as navigating when the tab reports `loading`, or when its status turned from complete to loading during the step. A same-tab hint click whose load starts after that status read does not wait: `run_in_order` does not pass the navigation on from the hints bundle, so the next step can run against the old page.
- `@@` plays the register the last play named, kept in `storage.session` (`src/background/macro_last_played.ts`, with a private key for private windows that clears with the last private window). Every play writes it before its first step, nested plays too, so `@@` after a failed `@a` plays `a` again, and after an `@a` that played `@b` it plays `b`, as in vim. `@@` with nothing played refuses. It reads the register when it runs, so it plays the content of that moment and refuses when the register is empty. `@@` inside a macro plays that macro again and ends at the depth limit. A failed pointer write does not stop the play.
- A count (`5@a`, `5@@`) is the `count` param of `macro.play`, so one replay runs the whole macro 5 times, one run after another, and stops at the first failed step or cancelled pick. The hold, Escape and the end of the replay span all the runs, and Escape stops the whole count. A count typed inside a macro stays on its own step, and `5@a` recorded in a macro is one step with its count. A nested `macro.play` step goes through the same validator as a typed one, so a recorded bad register or count fails the step. One play runs at most 10000 passes, nested plays and counts together, then stops like a failed step with a notice. Escape stops a replay only from a page that holds keys, so on a page DesertFox does not run on the pass limit is the only stop.
- Keys typed during a replay wait and run after it, in the mode the macro left, as vim's typeahead does. The background sends `replay_hold` to every tab the replay reaches, and each page holds its keys until its `replay_end` question is answered. A failure or a stop answers not ok, and the page drops the keys. A hint pick in the macro still takes its labels and Escape at once, because a new key in hint mode skips the captured-key holds. Escape anywhere in a held page sends `replay_stop`. A key typed in a tab the replay left runs there, and a background command from it waits for the end. Keys typed in a new page before its hold arrives (the time between its script start and the hold, after the page-ready wait) run at once.

### Help and palette

The help page is generated from `commands.json` and the live keymap: every command, its params, its keys and the keymap warnings. The palette is the command line with an empty prompt.

`:issue` (`help.issue`, no default key) opens the GitHub new-issue form prefilled with the extension and Firefox versions, the OS and the number of config warnings (`src/background/issue_report.ts`). The warning text stays out of the address, because a query string reaches GitHub when the form loads, before anyone reviews it. `--copy` puts the full report on the clipboard and opens the blank form. It holds the warnings word for word, at most 10 and 2 KB, with a count of the cut ones, and the user reads it before pasting. In every warning the config folder path becomes `<config dir>`, because the host reports it as an absolute path. A label that is no absolute path, such as `import`, is left alone. The command sends nothing itself.

The Site Rules page (`:help site_rules`, hash `#/site-rules?address=<address>`) lists the site rows that fit the invoking tab's address, from the stored keymap through `site_rules_view`. Each row shows its origin (yours or a shipped row's name), its pattern, the columns it sets as name and value pairs and the keys it changes with what each does instead. A column an earlier row already decides, or a key the page does not run (off, freed by pass, dropped by only, hidden by a shorter bind), is greyed with the reason; key changes are judged against the page tree from `normal_tree_for`. The list is for the tab's own address, and frames of other sites resolve against their own. Asked from the help page itself, or from the sidebar link, the page says where to run it.

The help page has a sidebar of page links on the left. In a window 40rem wide or less, the sidebar is a drawer and never a bar across the page. A bar that stays on top holds a menu button, which opens the drawer over the page. Escape, a picked link, a click outside the drawer or focus leaving it closes the drawer. Opening it focuses the current page's link, and Escape or a click outside returns focus to the menu button. The drawer starts closed on each render and is not stored.

### External editor

`text.edit_external` (insert mode `<C-o>`, content command, `bridge: false`) opens the focused field's text in the editor that the native host's own config names. The extension sends only text, an extension for the scratch file and an insert flag, so nothing executable crosses from the page or the extension. The `editor` bundle refuses a non-editable focus, a password field (`is_secret_field`) and text over 128 KiB (the host's cap), reads the field and asks the background. The background (`external_editor.ts`) calls `editor_start`, keeps `{ job, tab_id, token, frame_id, is_private, orphaned? }` per host job id in `storage.session`, and loops `editor_collect` (the host long-polls about 20 s and answers pending). The code is ready for a Manifest V3 event page, which restarts the background: a restart resumes every loop from storage. Under the persistent MV2 page only an add-on reload or update restarts it, and Firefox clears `storage.session` then, so a job does not survive one.

- One job per tab. A second press refuses with a toast, because closing a running editor needs a terminal-specific window class.
- A tab that closes or starts loading orphans its job. The editor stays open for the user and the loop keeps collecting, but the result goes to the unnamed register (with a toast when the tab still exists), because the page is gone. The same holds when the frame no longer takes the result: the page answers `true` only for the `token` it made, so a new page in the frame never takes a late result.
- Editors that show only part of their text (CodeMirror, Ace and Monaco, and the hidden textarea of CodeMirror 5, found by their container class) go through the clipboard. The page saves the clipboard text, sends the editor its own Ctrl+A and runs `execCommand("copy")`, and puts the saved text back before the editor opens. A marker left on the clipboard, or a copy that misses a drawn line, means the copy failed, and the page refuses as before. On return it copies again, and pastes the result only while the editor still holds the opened text. A read-back after the paste confirms the editor took it. Otherwise the result goes to the unnamed register. Only text is restored, and a toast says the clipboard was used.
- The result overwrites the field only while the field still holds the text it had at the press, checked again after the focus call. A plain input or textarea takes the value through the native setter and `input` and `change` events, and counts as refused when the field holds something else afterwards (it sanitized the text). A contenteditable takes one `insertText` over its whole content, so undo works. Otherwise the result goes to the unnamed register, and a toast says whether the field changed or refused the write, and says so only when the register took the text.
- A private tab's text goes to the private register, and is dropped with a toast when no private window is open any more, so private text never outlives its session.
- A failed collect is tried again, up to three in a row with a pause. After that, or on the host's unknown-job refusal, the job is dropped and the toast shows the error. After the retries the toast also names `~/.cache/desertfox/editor`, where the saved text stays.
- `<C-o>` in insert mode takes Firefox's Open File shortcut (Ctrl+O) in a field, as normal-mode `<C-o>` does outside one, on every site, whether or not a host is installed. Without the host or its editor config the key shows the host's refusal as a toast and does nothing else. A user who wants Open File back in a field unbinds the key or binds another one.
- The extension of the scratch file comes from the `ext` param, else the per-site `editor_ext` setting (up to 10 letters or digits, empty for none). A failure of the host (an old host, no editor config) shows its error as a toast. There is no enable setting. The command line cannot start an edit: it takes the focus off the field.

## Native host (optional)

### Config host (built)

A Python 3.9 stdlib-only host in `host/` (see `host/README.md`). The extension calls it with one-shot `runtime.sendNativeMessage`, and the host exits after its reply. It has six verbs:

- `read_config`: the raw text of every config file under `~/.config/desertfox/`, keyed by relative path. One reply carries all files, and the host returns a clear error above Firefox's 1 MB reply cap. Nothing is parsed host-side. The host reads only regular files of at most 1 MiB, following links, and opens them without blocking, so a FIFO in the folder cannot hang it. A file it will not read (not a regular file, or larger than 1 MiB) is refused with an error that names the file and the reason, so `config.reload` keeps the current config.
- `write_autoconfig`: writes the saved browser edits to `~/.config/desertfox/autoconfig.toml`, atomically. Nothing loads that file back. Browser storage stays the only source of saved edits.
- `self_update {version, sha256}`: replaces the installed host with GitHub release `v<version>`. The request carries the version and the SHA-256 of each script, which the extension takes from its signed build (`host_sha256.json`). It carries no URL, channel or path. The host accepts only `x.y.z` or `x.y.z.N`, builds every URL from this repo's releases, fetches over HTTPS only with size and time caps, and refuses a downgrade. Each file must match both the release `.sha256` and the extension's hash, so a replaced release asset fails. It then writes the five paths `install.sh` writes, each as `<path>.new` renamed over the old file: the bridge, the `desertfox` command line, both manifests, and the config host last. A development host (`release_version` `dev`) never updates itself.
- `editor_start {text, ext?, insert?}` and `editor_collect {job}`: run the user's editor on a scratch file and return the edited text. The command comes from `editor.toml` in the config folder, which only the host reads and `read_config` skips, so the request carries no argv. `editor_start` returns a job id and `editor_collect` long-polls for 20 s, so no call outlives a native-message timeout. See `host/README.md`.
- `open_firefox_page {page}`: opens one Firefox page (`about:preferences`, `about:config` and others) that no extension API can open. `page` is a key of a fixed table in the host, never a URL. The host runs its parent Firefox as a remote client with that profile and URL, argv only, and kills it after 10 s. `browser.open_firefox_page` (`:firefox`, the `,f` keys, `bridge: false`) calls it. Without the host, the command copies the address and the toast says to press Ctrl+L and paste. The first such toast also names `:native.install`. See `host/README.md`.

Every reply carries `release_version`, which `just release` stamps into the shipped hosts. The bridge sends it in its `ready` frame. Apart from `self_update` and the editor scratch files, the host writes no other file. `nativeMessaging` is an optional permission, requested from a button on the Help page that `:native.install` opens, the same panel `:permissions.grant nativeMessaging` opens (Firefox grants it only from a click). The page also shows a one-line command that runs `host/install.sh`, with a Copy button. For a release build it downloads `install.sh` of its own version from the GitHub release to a temp file, checks it against `install_sh` in the signed build's `host_sha256.json`, then runs it with the hash of each script from the same file, and `install.sh` refuses a script that does not match. A development install, and a build with no `host_sha256.json`, gets `curl ... | sh` from `main` with no checksum, and the page warns that it is for development only. `--channel main` forces main. `just release` uploads both hosts, the `desertfox` command line, their checksums and the script. `config.reload` reads the files through it, and each change to the saved edits writes `autoconfig.toml` (see [Delivery](#delivery)).

### Host updates (built)

Firefox updates the extension. DesertFox then updates its own native hosts and the `desertfox` command line to match, so a user installs the host once with `:native.install`.

- Channels. A stable extension (`x.y.z`) gets the stable release of its own version from AMO and the matching GitHub release. A beta extension (`x.y.z.N`, a self-hosted signed build; AMO refuses letters in a version, so the number counts up from the last stable release and 0.1.23.2 ranks above 0.1.23 and below 0.1.24) gets the GitHub prerelease of its own version. A development install (`installType` `development`) has no release and never updates its host, and a host with `release_version` `dev` refuses to update too. The channel is read from the fourth number, in `src/shared/host_version.ts`.
- When it checks. The extension reads `release_version` from the bridge's `ready` frame, from every reply of the config host, ok or error, and from one `read_config` request at start (only with the `nativeMessaging` permission), so a host is checked even with `bridge` off. A missing field, as in a host from before the updater, counts as older. The extension compares the numeric `x.y.z` parts, and a beta sorts after the release it counts from and before the next one. It sends nothing when the host is equal or newer, so with two Firefox profiles the newest host wins and none downgrades another.
- Consent. The `host_auto_update` setting is off by default. The "Install and keep the host updated" button on the `:native.install` page saves it as a browser edit and installs nothing itself, because Firefox cannot run the install command. With consent, an older host updates on connect and a toast says so. Without it, the extension shows one line per version that names `:native.update`, which runs the same update on demand and ignores consent and the limits below.
- Trust anchor. The first install checks `install.sh` and each script against the signed build only (see above). The update has two checks. The release carries a `.sha256` per script, and the signed extension build carries the hashes of the same stamped scripts in `host_sha256.json` (`just release_stamp` writes it and the build copies it into `dist/`). The host accepts a file only when it matches both, so a swapped release asset fails against the signed build, and a broken signed build fails against the release. The request holds the version and those hashes and no URL, so a page or a bridge client cannot point the host elsewhere. A build with no hashes sends no update. The update runs only in the config host, and there is no socket verb for it.
- Lock. The updater and `host/install.sh` take a non-blocking `flock` on `update.lock` in the data folder (`~/.local/share/desertfox/`), which both already write to, so both compute one path whatever the environment. They hold it from the first staged `.new` file to the last rename. The second caller fails with `update running`, so two writers never stage the same file.
- Reconnect. After an ok reply the extension closes the bridge port and connects again. The running bridge still holds the old code in memory, and it exits when its stdin closes. The new bridge waits up to 3 s for the old one to release `bridge.lock`. If it loses that race, it exits and the usual backoff connects again. The bridge never replaces its own file.
- Retry and toasts. The extension tries a version once per 24 hours (the time of the last attempt lives in `storage.local`, written before the call). A failure shows one toast per version, "Host update failed: <reason>. Run the command from :native.install", and is logged each time. A checksum mismatch blocks that version until a new extension build, which carries other hashes. Each success shows one toast. While the host is older, an error from it reads `host_outdated` and says whether it is updating or the update failed.
- Bootstrap. A host from before the updater has no `release_version` and no `self_update` verb. The extension treats it as any outdated host: the update fails with the host's "unknown cmd" refusal, and the failure toast names the manual `:native.install`. `INSTALL_HINT` stays for `host_missing` and `no_permission`, because a missing host cannot update itself.

### Bridge host (in progress)

One long-lived host, `desertfox_bridge` (`host/desertfox-bridge`), serves everything on the desktop that needs to talk to DesertFox. It is generic: it assumes no particular shell, bar or window manager. It sits beside the one-shot config host and does not change it.

The extension opens one `connectNative` port to it when the `bridge` setting is on and the optional `nativeMessaging` permission is granted. With either missing there is no port and no socket. A host that is missing or exits before its first message leaves nothing changed, and the extension reconnects with a growing pause (1 s up to 60 s). The host says `ready` once it holds its lock, and the extension trusts the port only after that. Firefox keeps the background awake while the port is open, which also helps a later move to MV3.

Two things come out of the host, both under `$XDG_RUNTIME_DIR/desertfox/` (a folder with mode 0700).

- `state.json`, written for a bar to read: the mode, the host's pid and start time, and `private`. The host writes it atomically (a temp file renamed over it). A reader treats a dead or reused pid as no state. A private window leaves only its mode and `private: true`: no window or tab id, no URL, no title.
- `bridge.sock`, a Unix socket with mode 0600, because a desktop program cannot open a channel into the extension. The first host to start owns the socket and the state file through a lock on `bridge.lock`. A second host waits 3 s for the lock, then exits with an error, so two Firefox profiles share one bridge and the second one gets none. The socket takes one JSON object per line and answers each with one line. A request over 64 KiB is refused, an idle connection closes after 5 s, and at most 16 connections are open at once. A connection from another user is closed.

The built verbs are `ping`, `state` (the latest snapshot, the same shape as the file), `list`, `run` and `theme`. More verbs follow, each with a fixed name, so there is never a shell or eval verb:

- `list`: the commands the bridge allows, as registry entries with their params, for completion.
- `run`: one command line from outside. The host forwards it to the extension, which refuses it unless the command's `bridge` field is true. A hard-coded never-list wins over the field: the `config`, `settings`, `session`, `copy`, `register`, `debug`, `native` and `permissions` groups, `page.reload` (it can clear cookies and site data), `page.save_pdf`, the hint picker, `visual.act`, `open.clipboard`, `command.repeat`, `macro.play`, every snippet, and an address that is not http or https. A handler refusal comes back as fixed text (`<id> failed`), because it can hold a tab title. An `open.url` address is resolved the way the handler resolves it (trim, scheme, bare host, search) and refused unless the result is http or https, so `localhost:3000` opens and `vscode://x` does not. A command that passes goes through the one validator (`check_args`) and then the router, with no command line to open, so a missing value is a refusal. The reply carries success or failure and a message, never data. The host cuts a run reply to those two fields.
- The tab verbs, all behind the separate `bridge_share_tabs` setting (off by default, and it needs `bridge`), because a tab list leaks browsing. With it off, each answers `tab sharing is off, set bridge_share_tabs to true`, and so does a `run` that names a tab. The extension sees every id and checks it itself.
  - `tabs {current?}`: the tabs of normal windows, each with `tab_id`, `window_id`, `title`, `url`, `active`, `audible`, `discarded`, `last_accessed`, `pinned`, `hidden`, `fav_icon_url` and, from the host's caches, `fav_icon_path`, `thumbnail` and `thumbnail_at`. A tab of a private window or a popup never appears. With `current: true` the list holds only the active tab of the last focused window, for a capture tool, and is empty when that window is private or a popup.
  - Icons: Firefox gives most tab icons as data URLs, and a list of them would outgrow one native message. So `fav_icon_url` is blank for a data URL icon, and the row carries the SHA-256 of the data URL instead. The host keeps that key to itself. For a key it has no file for, it asks the extension for that tab's icon (a `favicon` request the socket does not offer), within 3 s for the whole list, and saves the image in `$XDG_CACHE_HOME/desertfox/bridge-favicons/` (mode 0700) under the key with the suffix of its type. `fav_icon_path` names the file, or is empty. Tabs with the same icon share one file.
  - `activate {tab_id, preface?}`: selects the tab and focuses its window. The optional `preface` (letters and digits, 32 at most) goes in front of the window title, so a program that raises the window itself can find it by title. DesertFox does not raise windows through a window manager, because it assumes none. It clears itself after 10 s, and `clear_preface {window_id, preface?}` clears it early, but only when the preface is still the one DesertFox set. Activations run one after another, so two at once cannot swap each other's title. The reply is `window_id`, `focused` and `preface_set`.
  - `close {tab_id}`.
  - `capture {tab_ids?}`: renders each tab (all loaded ones without ids), one at a time, and the host saves a JPEG per address in `$XDG_CACHE_HOME/desertfox/bridge-thumbs/` (mode 0700), pruned after 7 days once no open tab has that address. The host asks only for ids in a fresh tab list from the extension, so it never saves the image of a tab the extension did not list as a normal one.
  - A tab id that is stale, private, in a popup or not a whole number gets the same refusal, `no such tab` (`no such window` for `clear_preface`), so an id cannot be used to probe for private tabs. Failures carry fixed text and never a title.
  - `run` takes an optional `tab_id` and runs the command in that tab, where a run otherwise uses the active tab of the focused window. Every rule of a plain run applies first, with the same refusal text, and the tab is looked up only after they pass.
- `theme {palette}`: the desktop tells DesertFox which palette it uses, and DesertFox maps the name onto its own roles. It changes the palette and nothing else: no other setting has a verb. The host checks the shape (a letter or digit first, then letters, digits, `_` and `-`, 1 to 64 characters), keeps the last name in `theme.json` beside the state file (it is the one file that outlives a host, and a host that dies mid-write leaves the old file) and forwards it. It forwards the kept name again right after each `ready`, in the same step that opens the link, so a push never overtakes the replay and a connection gets the name once. The extension accepts only a built-in theme name (`desktop` is not one), logs and ignores any other name, and keeps the current theme. The host deletes the kept name when the extension refuses it, in a push and in the replay, so a typo is refused once. While no host runs (the browser is closed), `desertfox theme` writes `theme.json` itself, atomically and under the `bridge.lock` flock, and exits 0, so the next host replays it. It needs `bridge` on to take effect, because no host starts otherwise. It stores the name in `storage.local` (key `desertfox_desktop_palette`: per machine, not Firefox Sync, so a browser restart keeps it) and publishes again only while `palette` is `desktop`. The name stays whether the bridge is later turned off or not. `light` or `dark` and `light_intensity` are not part of the push.
- `subscribe`: turns the connection into a one-way event stream. The host answers `{"ok": true}`, then the current mode if it has one, then one line per event, each with a `seq` that rises by one, so a reader can tell it missed one. A reader that also wants to send requests opens a second connection. The events:
  - `mode`: the same fields as the state file, so a private window gives only its mode and `private: true`. The host makes it from the mode it gets, and it needs no `bridge_share_tabs`.
  - `tab_activated {tab_id, window_id}`, `tab_updated {tab_id, window_id, title, url}`, `tab_audible {tab_id, window_id, audible, title, url}` and `tab_removed {tab_id}`: only while `bridge_share_tabs` is on, and only for a tab of a normal window. Title and address changes of a tab within 250 ms go out as one `tab_updated` with the values at the end, because some pages change their title every second. `tab_audible` and `tab_removed` go out at once. A closed tab can no longer be looked up, so the extension sends `tab_removed` only for a tab an earlier event named, and the host passes it only to a reader that an earlier event told about that tab. Each reader remembers its last 1024 tabs. The host cuts a title to 512 characters and an address to 2048.
  - `tabs_off`: `bridge_share_tabs` is off. The extension sends it when the setting goes off and again each time the port comes up with the setting off, so a host that missed it still hears it. A reader forgets its tabs, and no tab event follows until the setting is on again. A tab reply whose request came before the setting went off goes out as the sharing-off refusal.

  At most 4 readers stream at once, inside the 16 connections, so stuck readers cannot starve the command line. A fifth gets `too many subscribers`. Each reader has its own queue of 64 events and its own writer. A reader that falls 64 events behind, or does not take a write within 2 s, is dropped and can reconnect, so a slow reader never holds up the port, the requests or another reader. A stream is not closed for being idle. `subscribe` counts once against the rate limit and its events do not count. The extension sends tab events whether or not anyone reads, and the host drops them when nobody does.

A `run` targets the active tab of the last focused normal window, not the window Firefox thinks is current. It never toasts and never touches `.` or the macro recorder, so a script cannot change what the user repeats. A run that opens an address is refused when that window is private.

The host limits all connections together to 10 `run` and `list` requests per second (`theme` is not limited), because the CLI opens a connection per call (an excess request gets an error line and does not reach the extension), keeps the cap of 16 connections, and keeps at most 16 requests waiting on the extension. A request the extension does not answer in 10 s fails, and so do all waiting requests when the port closes, so a client never hangs on a reconnect. Each request carries an id and the reply that carries the id goes to the connection that asked.

The extension is the trust boundary. It drops everything from a private window before it reaches the host, so a host bug cannot leak it. The host writes only the socket, its lock, the state file and the kept palette (`theme.json`), all on tmpfs, and the thumbnail and icon caches in `$XDG_CACHE_HOME`. It prunes each cache at start (files over 7 days old, then the oldest beyond 500), prunes the icons again after each full tab list (an icon no open tab uses, once 7 days old), and deletes both caches when the extension says `bridge_share_tabs` is off: in a reply, or with the `tabs_off` event. A write and a delete never overlap, and an image the extension sent before a delete is dropped, so a deleted cache does not come back.

`host/desertfox` is the command line for the socket, a stdlib Python script: `desertfox run [--tab <id>] <command> [args]`, `desertfox list`, `desertfox state`, `desertfox theme <palette>`, `desertfox events` (prints the stream, one JSON line per event), `desertfox tabs [--current]`, `desertfox activate <id> [--preface <nonce>]`, `desertfox clear-preface <window id>`, `desertfox close <id>` and `desertfox capture [id...]`. It prints plain text and exits 0 when done, 1 when refused or failed, 2 for bad usage and 3 when the bridge is not running (`theme` keeps the name and exits 0 instead). `-h` or `--help` after a verb prints the usage and sends nothing. The installer puts it beside the hosts and links it into `~/.local/bin`.

## Release channels

Two channels exist, stable and beta. The `update_url` in the installed build's manifest decides which one a copy follows. A stable build has none and updates from AMO. A beta build points at `updates.json`.

- Versions. Betas are `x.y.z.N`, where N counts builds after the stable `x.y.z` (see [Host updates](#host-updates-built)). `.github/workflows/beta.yml` builds one nightly from `main`.
- Update feed. `updates.json` sits on the fixed `beta-channel` release tag and lists only the latest beta. Its `update_link` and `update_hash` point at the signed xpi on that beta's own release.
- Trust. The owner's AMO key sits in the `beta-signing` environment, and only the sign job sees it. The other jobs build and publish from the signed output.
- Moving from a beta to a lower stable build. The host keeps the newer one, because it never downgrades. Use the stable build from AMO only after it passes the beta.
- Policy pin. `tools/install_policy.sh beta` pins the https URL of the latest beta in the policy file. The pin only seeds the first install: the `update_url` carries every update after that. The stable pin is a `file://` URL to the local xpi, and it replaces a beta whenever the local xpi ranks higher, so it is not for a beta machine.
- Manual beta. `just beta` starts the beta workflow on `main` and watches the run. `just release` starts no beta, because it pushes the bump to a release branch and main still has the old version. After the release PR merges, the nightly builds the matching `x.y.z.N` beta because main changed. Run `just beta` to get it at once. On a machine whose policy follows the beta (an https `install_url`), `just release` skips the local install and keeps the beta pin. Go back to stable with `bash tools/install_policy.sh stable`.
- Local installs. On a beta machine, never run `just install`. It overwrites the beta with a local build.

## Trade-offs

| Choice | Picked | Cost |
| --- | --- | --- |
| MV2 persistent vs MV3 event page | MV2 | Mozilla can remove MV2 some day. The migration is small because state lives in storage. |
| Keymap as data vs as code | Data | None for rebinding. New behavior comes from snippets or a new DesertFox build. |
| Snippets vs plugin extensions | Snippets | Page code only, no extension APIs. A move to MV3 means a rewrite to the `userScripts` API, which shows the user an extra permission warning. |
| Config as JSONC vs Lua | JSONC | No loops or helpers. The `search_keys` and `container_keys` sections remove most repetition, and tools can still edit the files. |
| Config through managed storage vs the native host | The native host. Managed storage is removed | A helper program to install and an optional permission. An edit applies with one key and no restart, so temp edits and modes stay. |
| Command line in an iframe vs a shadow root | iframe | Focus handling is harder. Isolation and direct API access are better. |
| Content script in all frames vs the top frame | All frames. A subframe starts its script on its first focus | Hints and keys work inside an embed after `;f` or a click. Ad frames the user never enters stay inert, with one idle focus listener each. `hint --all-frames` is the exception: the hints bundle starts each such frame through its loaded flag, so the frame can report and draw labels. |
| Plain `J/K` only vs plus chords | Plus `Alt+J/K` | Two keys for one command. The chord is the only way to switch tabs from about: pages, the PDF viewer or the address bar. |

## Risks

- Keys are lost on a page with no committed document, for example a new tab before its first byte. No extension can fix that. The chords cover it.
- A page that cancels a chord before Firefox sees it blocks the Firefox shortcut. The content script catches the chord first on pages where it runs, so only pages without a content script are exposed.
- Release Firefox needs a signed build for each change in code. `just release` signs on AMO and installs through the policy file.
- Snippets run code from a config string through `tabs.executeScript`. AMO review of DesertFox can question that. The code comes only from the user's own file, which other extensions with this feature also do.
- Scope creep. The binding map is the scope: a feature not in it needs a reason.

## Roadmap

1. Phase 0, measurements. Done. See [firefox-behavior.md](firefox-behavior.md).
2. Phase 1, core. It covers the registry, `commands.json`, the config build, `tools/build-config`, `config.reload`, keymap validation, the prefix tree, modes, scroll and page commands, tab commands, the shortcut slots and the help page. Exit: every v1 row of the binding map that needs no hints or command line works, and the content script stays under its size target.
3. Phase 2, interfaces. Command line, completion, explicit prompts, hints, which-key, snippets, and caret and visual modes. Exit: the whole v1 column of the binding map works, and DesertFox replaces the current extension in daily use.
4. Command line status area. Done. See [Command line and completion](#command-line-and-completion). `history` is a later widget. `keypress`, `progress`, `scroll_raw`, `text` and `clock` are not planned. `search_match` waits for a page search built on Firefox's find API, because Firefox's find bar hides its count.
5. Phase 3, browser data. Local and global marks are done (`m<a-zA-Z>`, `'<key>` and the backtick). Quickmarks, the remaining later rows, and the help page import for users without a shell.
6. The site table: per-site key pass-through, off and per-site settings. Done. `site_rules` is one site table: a list of tables, each with `site` (a match pattern) and optional columns. `off` is true or false. `pass` or `only` holds key sequences in keymap notation split by spaces, and `check` refuses a row that sets both. Each column resolves on its own: the first matching row that sets a column decides it, and `pass` and `only` form one column, the key rule. So a broad row can turn a whole domain off while a narrower row above it sets `off = false` for one path, and a key row and an off row for the same page combine. So a narrow key row above a broad bare row now leaves that site off, unless the narrow row also sets `off = false`. A row that sets nothing but `site` loads as `off = true`, the shape older configs and the popup wrote. A page is all off when `off` resolves true or when its key rule frees every normal binding: it enters ignore mode, so the badge and `<S-Escape>` work as before. This is how to start a site in ignore mode: there is no start-mode setting. The top frame matches its own address. A subframe matches its own address or the tab address. `pass` removes the listed sequences from the normal tree, and a passed prefix removes its whole subtree, so `pass = "g"` frees every `g` key and `pass = "gg"` frees only that key. `only` keeps just the listed sequences, and a listed prefix keeps its subtree. It also keeps `<C-v>` and `<S-Escape>`, so the one-shot pass and the way into ignore mode work on every ruled page. Normal-mode `<Escape>` goes to the page under `only`, and insert mode still leaves on `<Escape>`. The key rule covers normal mode only. Insert, hint, command line, caret and visual behave as before, `browser` chords stay on, and `<C-v>` stays the one-shot escape. The `bind` column is a table from a key sequence to a binding in any format a keymap entry takes (a command string, a list of command strings that run in order, or `{ run, label, intent }`) that binds normal-mode keys on the row's sites, for example `h` to `page send_key ArrowLeft`. The config build parses the text with the keymap's own parser and stores invocations, the form the shipped rows write directly. A list is a chain: the steps run in order, a failed step stops it, the count goes to every step, and the first step's `label` (or the bind's `label`) is what which-key shows. A bind holds at most 20 steps, checked by the settings check and again by the compiler. A macro is a chain too: `macro play a` with a fixed register binds like any command. It merges key by key: for each key the first matching row that binds it decides, so a user row that binds only `j` keeps the other keys of a later row. The background grafts the merged binds onto the normal tree, then `pass` and `only` prune it, so `pass = "j"` frees a bound `j` and `off` wins over all of it. The compiler checks each bind with the one validator and skips a bad one with a warning. A bind that waits for a key press is refused. When rows bind a key and a longer key under it (`g` and `gx`), the compiler warns and the shorter bind wins, as a complete binding hides the keys under it in a keymap. This holds for rows of one pattern and for rows of different patterns, unless their hosts are provably different (a page can fit both patterns otherwise), and it holds in either row order. Named site modes are not compared across rows, as a mode comes whole from the first matching row. A cross-site iframe can still drop a bind silently, as a frame resolves rules by its own address and the tab's. `page.send_key` takes optional `ctrl`, `shift`, `alt` and `meta` flags (all off by default) that set the modifier flags of its events, and a `keypress` flag that adds a keypress between the keydown and the keyup (skipped when the page cancelled the keydown, and carrying the character code of a one-character key). It takes the count as its `times` param and sends the pairs through a per-page queue with 10 ms between pairs, one entry per call, because Sheets applies only the first of several pairs sent in the same millisecond. DesertFox ships site rows after the user's rows (`src/background/default_site_rows.ts`). The first is `sheets`, two rows for the two address forms of Google Sheets, which bind `h`, `j`, `k` and `l` to the arrow keys through `page.send_key` (a `keydown` and a `keyup` with `keyCode`, which Sheets reads, sent to `#waffle-rich-text-editor`), `gg` to Ctrl+Home, `G` to a chain of Ctrl+End then Home (the bottom of column A, labeled so) and `<C-h>`, `<C-j>`, `<C-k>` and `<C-l>` to Ctrl+Left, Down, Up and Right (so they hide Firefox's Ctrl+H, J, K and L on Sheets tabs, and Sheets' own Ctrl+H (find and replace) and Ctrl+K (insert link)), bind `x`, `y` and `p` to `page.clipboard` (cut, copy and paste, which a synthetic Ctrl+X, Ctrl+C or Ctrl+V does not do, so `xx`, `xp`, `pp`, `pt`, `pw` and the whole `y` group are gone on Sheets only), and give the row a `visual` site mode (label VISUAL) that `v` and `V` start: in it `h`, `j`, `k`, `l`, `gg`, the `G` chain and `<C-h/j/k/l>` send the same keys with Shift held, and `x`, `y` and `p` end the mode first and then cut, copy or paste the range, so a refused clipboard step cannot leave the mode on. Escape ends the mode through the site-mode exit policy and sends no key that collapses the range. `page.clipboard` runs through the same per-page queue as `page.send_key`, so `l l x` typed fast cuts after both arrows, and pass `<C-a>`, `<C-x>` and `<C-v>` to the page so Select all, Cut and Paste work. A user Sheets row that sets `pass` replaces that pass column, so it must list all three to keep them. A row that sets `only` replaces it too, and keys left out of `only` go to the page, so it must leave `<C-a>` and `<C-x>` out. `only` always keeps `<C-v>` for the one-shot pass, so an `only` row cannot free the real Ctrl+V. The top-level setting `default_site_rows_off` lists the names of shipped rows to turn off. The popup and the settings page list the user's rows only, and which-key shows the shipped binds. The compiled keymap stores per row `{ site, origin, name, regex, off, keys, bind, modes, values }`, each column present only when the row sets it, with `keys` holding parsed sequences. `site` is the pattern as written, `origin` is `user` or `default`, and `name` is the shipped row's name. The site rules view (`site_rules_view.ts`) reads them: it lists the rows that fit one address in table order, the columns each sets and the keys each changes, marking what an earlier row already decides. The background resolves the columns for the sender's address (the top frame uses its own address only, because `sender.tab.url` can lag during navigation, and a subframe adds the tab address), prunes the normal tree with the shared `prune_tree`, marks the page all off when nothing is left, and sends the page that tree with `all_off` and the freed keys (`frees`, a list of keys and a flag that inverts it). The content script never sees `site_rules` and swaps the tree in before the matcher, so held keys replay against the right tree. An all-off page gets the whole normal tree, so `,i` still works. Which-key lists the same pruned tree through the same resolution. A key the rule frees (a passed `/`, `'` or digit, or any such key under `only`) matches nothing and is not cancelled or counted. Every `tree_updated` resolves the columns again, so a rule edit reaches open tabs at once. An install enters ignore mode only on the change into all-off, so a manual `,i` or `<S-Escape>` survives an unrelated edit. On the change out of all-off (removing the row, or setting `off = false` above it) a page in ignore mode returns to normal. A history change (pushState) is not checked again.

   Per-site settings: a row of `settings_table.ts` with `per_site: true` opts its setting in, and a `site_rules` row may then set it as a column. That setting's own check (`SETTING_SPECS`) checks the value, the editor schema lists it, and an unknown column is a typo. On the sites a row names, its value beats every global layer, `:set` and `:set --temp` included: the row names the site and `:set` does not. The compiled row keeps such values in `values`, and the background resolves them with the other columns (`site_columns_for` and `site_value` in `page_keymap.ts`). A value about the whole tab resolves against the top frame's address: a frame's message passes through `top_frame_address_of`, and the zoom reads the tab's own address from `tabs.onUpdated`. A value about one frame's own content resolves against that frame's address. `zoom`, `blur_on_load`, `editable_add`, `editable_remove`, `editable_remove_unsized`, `escape_to_page`, `hint_add`, `hint_remove` and `strip_tracking` opt in (below). The settings that act inside one frame (`FRAME_SITE_SETTINGS` in `prefix_tree.ts`) resolve against the frame's own address only, never the tab address that key rules add for a subframe: a row for the top page says nothing about a frame of another site. `blur_on_load`, `escape_to_page` and the three `editable_` settings reach each frame as `site_values` in its page keymap reply. The hint selectors do not ride in that reply, so content.js does not grow: the hints bundle asks for them (below). A value at its default stays out of both answers. Their global values travel in the compiled keymap (`frame_site_globals`), which the background strips before it replies.

   Zoom: `zoom` is a level from 0.3 to 5 (Firefox's range), set per site in a `site_rules` row or for every site at the top level. It has no default, so with neither a page keeps the zoom Firefox remembers. Firefox remembers zoom per host and `tabs.setZoom` writes that memory (see [Per-site zoom memory](firefox-behavior.md#per-site-zoom-memory-and-tabssetzoom-per-site-settings)), so the background (`site_zoom.ts`) sets the level from `tabs.onUpdated` only the first time a tab reaches the host in a browser session. Firefox's memory then carries it to the host's later tabs. `storage.session` holds the level set on each host, with a separate record for the private windows that clears with the last private window. So a manual zoom sticks across reloads, pages of the site, new tabs and a round trip to another site. A level that changed since (a config edit, `:set`) is set on the next load. An add-on reload or update clears `storage.session`, so each host gets the level once more then. A zoom column acts per host: a row for one path also zooms the rest of the host, and two paths of one host with different levels set the zoom at each crossing, so give a host one level. The tab's address is its top frame's. The switch off sets nothing.

   Escape to the page: `escape_to_page` (default off, per-site) lets a page keep Escape while a field is focused. In insert mode with a field focused, the content script passes the Escape keydown to the page, does not blur and stays in insert mode. The focus follower returns to normal mode once the page drops the field, as when Sheets parks its cell editor after a cancelled edit. A manual insert (`i`, no field) still ends on Escape. Set it only for sites whose editor handles Escape itself: on a plain input the field keeps the focus and so does insert mode. The shipped `sheets` rows turn it on. `<A-Escape>` in the insert keymap sends Escape to the focused element with `page.send_key` on any site, so a site with no row has a way to give the page its Escape.

   Blur on load: `blur_on_load` (default off, per-site) takes the focus away from a field that the page focuses as it loads, so keys work at once. The content script blurs a field already focused at its first install, and while the window is open it blurs any field that takes the focus, before the frame enters insert mode. A field focused before the reply came has already put the frame in insert mode, and the blur's focusout takes it back to normal. The window opens at the first install and ends about 1 s later. While the page has user activation (`navigator.userActivation.isActive`, set by a key or a click), nothing is blurred, so a field the user clicks keeps the focus. That also covers input from before the content script started, as in a subframe that starts on its first focus. A command that runs in the frame (`run_in_content`) closes the window, so `gi` in a macro replay right after a load keeps its field. A page that focuses a field after the window still gets insert mode. A page shown from the back-forward cache runs no install, so its focus stays as the user left it. A later `tree_updated` opens no new window.

   Media quality: `media_quality` (default `max`, per-site) is a rule that takes a site player to a quality level, so every site has it unless a site value says otherwise. The values are `off` (leave the site alone), `auto` (hand the choice back to the site), `max`, `min`, or a height (144, 240, 360, 480, 720, 1080, 1440, 2160 or 4320, written as a bare number in TOML, the highest level at or below it). It is an enum setting, so any other height is refused with the value list. A `site_rules` row sets it for its sites, and a site value beats the global one. The background (`media_quality.ts`) listens to `tabs.onUpdated`, filtered to `url` and `status` changes: a changed `url` (a hard load, or a `pushState` such as a click on a related video) and a finished load each inject `quality.js` into every frame, and so does a second pass 1 s later that adds `about:blank` frames. Nothing is injected when the extension is off, or when the global value is `off` and no site row sets a level. That check reads the keymap once per trigger for the tab. A settings change that turns the rule from off to on injects the open web tabs at once. Each frame reports to the background (`quality_report`, with `has_video`). The answer to a report from a frame with a video is the rule for that frame's address, so a frame never asks for it and a page with no video costs no keymap read. A frame with no video ends at once, with no poll. It wakes on the first `loadstart`, `loadedmetadata` or `play` event that reaches its document (a capture listener sees them), and a local check every 2 s for 10 s also looks for a video or a known player, inside open shadow roots too, because their events do not cross the root. Either one reports again and starts the poll with the answer. A frame with a video polls its driver every 100 ms, for 10 s at most, until the player lists its levels (YouTube answers "unknown" until it plays) and sits at the rule's level. A video that reaches the level and holds 3 s ends the poll. After a navigation inside a site the old video may already hold, so the poll ends early only for another video (YouTube's `video_id`, the address of the hls.js source) and otherwise runs to the 10 s deadline, and a new video restarts the watch. A player with no video identity keeps the plain 3 s watch. A new address in a frame is a navigation for it, and a second run at the same address (the load finishing, the about:blank pass, a media command that injects the bundle) is not: in a frame that already has a rule it only reports and changes no level. A settings change reaches a frame that has a video through `tree_updated`, which the background sends to every tab after each config or `:set` change: the frame reports again and a changed rule takes effect at once, and a switch-off stops the poll. A navigation to a non-web page cancels the work still pending for the tab. A newer start replaces the poll of an earlier one, so repeated navigations leave one poll. A `media quality` choice that took ends the poll and stands over a finished load, until the next navigation applies the rule again. A choice made in the site's own menu while the poll runs is not seen, so the poll can undo it for up to 3 s. A frame that loads after the tab's last event misses the rule, and so does an `about:blank` frame until the second pass, because the first injection leaves out `matchAboutBlank` (with it, a frame under an all-off site rule left ignore mode when the tab's insert hold ended). Pages that are not http or https, and the extension switched off, start nothing.

   Editable rules: `editable_add` and `editable_remove` (per-site lists of CSS selectors) decide what counts as a text field, so insert mode follows focus. A match of `editable_remove` is not a field, one of `editable_add` is, and remove wins. With `editable_remove_unsized` on, a remove match counts only while it has no width, which is how the shipped `sheets` rows drop the parked cell editor. A selector that does not parse matches nothing. The hints bundle reads the answer through `window.desertfox_host.is_editable_`.

   Scroll target: `scroll_selector` (default empty, per-site) is one CSS selector for the element that the scroll commands scroll, for an app with an inner scroll area. `scroll_target()` tries the first match before the focus chain, so every scroll uses it, bundle scrolls through `scroll_box_` too. A match that cannot scroll on the axis, a selector that does not parse and no match leave the usual order (focused element, page, largest scroller). The pick of that last scan is kept per axis, weakly, and reused while the box is connected and still scrolls on the axis. A `focusin`, a `pointerdown`, a failed re-check and a pause of 1 s between scroll keys drop it. The page keymap reply carries it, like `escape_to_page`.

   Hint selectors: `hint_add` and `hint_remove` (per-site, default empty lists) are lists of CSS selectors. Each `hint.run` sends `read_hint_selectors` from the hints bundle, and the background answers with the frame's values (`frame_site_values_for` against `sender.url`). Keys typed during that ask are held, so they reach hint mode. A rapid session keeps what its run read. A settings edit or another address applies from the next run, and a new page loads a new bundle anyway. `hint_add` runs as a second query for the `all`, `clickable` and `every` filters, skips the filter's test, and its matches count as clickable, so a pointer wrapper around one gives way to it. The filters that promise an address or a kind (`links`, `images`, `inputs` and the rest) take nothing added. `hint_remove` drops every candidate that sits in a match (`closest`, so within its own document or shadow root, never across one) for every filter but `custom`. The run resolves the selectors for the frame that starts it, and elements in its same-origin frames use those too, not their own frame's rows. The check accepts any non-empty text, because only a page can parse a selector: the bundle skips one that does not parse, shows one notice for the run and applies the rest.
7. Registers, before macros. `"` holds the last yank, `a` to `z` are named, `+` is the clipboard, `_` is the black hole and `/` is the last search. `"ay` yanks into a register, `"app` opens it as a URL and `:registers` lists them. `<C-r>a` pastes it into a field in insert mode.
8. Macros, with `.` repeat first. `.` repeats the last command or inserted text. Recording and replay follow: `q<reg>` records into a register, `@<reg>` replays it, a count (`5@q`) or `@@` repeats it. A macro records commands and the text typed in insert mode. Replay inserts text like a paste, not as key events, and stops at the first failed step.
9. Base16 theme importer, after macros.
10. Toolbar popup and icon. Done. The toolbar button opens a popup (`src/popup/`) with the on/off switch, Settings, Help, Disable on this site, Reload config, the warnings count and the version. Off is one global switch kept in `storage.local` (`desertfox_disabled`, absent means on). While off, the background stores an empty keymap, so the content script matches no key and hides its badge, and sends every open tab to normal mode, which ends hints, the command line and insert mode. The router and the Firefox shortcut slots refuse every command. The manifest shortcut `toggle_enabled` (default `Ctrl+Alt+D`, rebindable in `about:addons`) and the popup stay live while off. The icon turns grey and the title reads "DesertFox (off)". Off differs from an all-off site rule: that rule is a start mode per matching page that a binding can leave, while off stops every key and command on every site until it is turned on. Off wins over a disabled site. "Disable on this site" appends the row `{ site = "*://*.host/*", off = true }` (host without `www.`) to the saved `site_rules` through the same edits as `:set`, and open tabs follow at once. It is live while no matching row sets the off column, so a page under a key rule can still be turned off, because the appended row then decides the column. "Enable on this site" removes the popup's rows for the pattern (an older bare row too) and is live only while such a saved row decides the column and no other row would. The popup shows what the matching rows set ("pass 3 keys", "only 2 keys", "all off", or "on, pass 1 key" under `off = false`) with a link to the settings page. The saved list starts as the config file's list and then replaces it, so later edits to the file's `site_rules` do not apply until `:unset site_rules` clears the saved list. The grey icon is a generated copy of the placeholder, so a real logo with an off state is still owner work.
11. Phase 4, Oasis. The native bridge host, the mode chip, `desertfox list` and `run`, and the Oasis theme file written on theme change.
12. Phase 4, saved edits on disk. Done: the native host writes the saved edits to a generated `autoconfig.toml` beside the user's files. It never edits the user's own files.
13. Release path. The maintainer installs through `just release` (signed, unlisted) now. A listed addons.mozilla.org release is a later piece: the listing, a source upload, Mozilla review, permission justifications and a privacy note.
