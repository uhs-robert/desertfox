# DesertFox design

DesertFox is a keyboard-first Firefox extension. It has a small scope and one command registry. Every command is defined once. Keys, the command line, completion, help, the palette and which-key all read that definition.

The extension works on its own. Oasis Dots adds an optional native host. Through it, a desktop shell can show the mode, list the commands and run them.

The measurements this design rests on are in [firefox-behavior.md](firefox-behavior.md). [keymap.md](keymap.md) maps every binding in the current browser config to a command here.

## Constraints from Firefox

These were measured on Firefox 159 with real key presses. They shape every choice below.

- A content script catches plain keys such as `Shift+J` on web pages only. It catches nothing on about: pages, addons.mozilla.org, view-source, reader view, the PDF viewer, or while the address bar has focus. The address bar keyword `df` runs commands on these pages (see "Command line and completion").
- `moz-extension://` pages do not match `<all_urls>`, so no content script runs on them by itself. The help page loads `content.js` with a script tag, and `tabs.sendMessage` reaches it like any other tab.
- The `commands` API (Firefox shortcuts) catches a modifier chord such as `Alt+J` everywhere except on a page that cancels the key first. Firefox rejects bare keys and Shift plus a letter there.
- A `document_start` listener is ready 11-58 ms (median 27) after the first byte of a page. Keys before that moment are lost. Navigating from a live page keeps the old listener until the new page commits.
- A message from a content script to the background and back takes under 1 ms. So does a round trip to a native host over an open port.
- Firefox still supports Manifest V2 with a persistent background page. MV3 in Firefox uses event pages that sleep after 30 s.

## Decisions

- Manifest V2 with a persistent background page. No state lives only in memory, so a later move to MV3 changes the manifest and little else. A copy of stored state may sit in memory when it refills from storage and drops on `storage.onChanged` (the compiled keymap, `keymap_source.ts`).
- TypeScript, bundled with esbuild. No framework. No runtime dependency in the content script.
- No Rust and no WASM. The slow parts are DOM work and messages between processes, not computation. WASM also adds load cost to every page.
- No ex-command language. The command line parses text into the same typed invocation that a key produces. Snippets are the only user code. They come from the user's own config folder, or from an import the user accepts snippet by snippet.
- No shell access. The native host has a fixed set of verbs.
- Native tab groups and the parked sidebar stay separate layers. A native group is the user's own, named and collapsed by keys. The sidebar groups tabs by site on its own, and a sidebar, not yet built, shows `group_id` only as a badge.

## Registry

The registry lives in the background page. A command is plain data plus a handler:

```ts
define("tab.close", {
  label: "Close tab",
  intent: "Close the current tab and focus the next one, or close the tabs around it.",
  params: [
    { name: "side", type: "enum", values: ["none", "all_before", "all_after", "focus_previous"],
      default: "none", short: { all_before: "B", all_after: "A", focus_previous: "P" },
      value_labels: { focus_previous: "and focus previous" } },
  ],
  runs_in: "background",
  count: "repeat",
  run: async (ctx, { focus }) => { /* ... */ },
});

define("open.search", {
  label: "Search",
  intent: "Search with a keyword engine from the search engine list.",
  name: "search",
  params: [
    { name: "engine", type: "enum", values: from_engines },
    { name: "query", type: "string", main: true, default: { from: "selection" } },
    { name: "where", type: "enum", values: WHERE, default: "here",
      short: { tab: "t", background: "b", window: "w" } },
    { name: "container", type: "string", values: from_containers, short: "c",
      when: { where: ["tab", "background", "window"] } },
  ],
  runs_in: "background",
  run: async (ctx, { engine, query, where, container }) => { /* ... */ },
});
```

The fields follow the Oasis action library (`home/hypr/.config/hypr/lib/act/init.lua`) so the two lists have one shape:

- `id`: `group.name`, lowercase with underscores. Same pattern as Oasis actions.
- `name`: the command line name, set by hand. It is optional, and it holds no `.`. The full id always works on the command line, and it is the name of most commands: you type `tab.close`, `window.new`, `tab.pin`. Only two kinds of command get a name. The one-word commands are `open`, `search`, `paste`, `copy`, `hint`, `heading`, `find` and `github`. The family words are `tab` (switch), `bookmark` (open), `history` (open), `zoom` (set), `scroll` (lines), `mode` (set) and `help` (open), one per group, for the main action. Names are never derived from the id, because derived names collide (`tab.close` and `window.close`).
- `aliases`: more command line names. The defaults ship none.
- `label`: a short title in sentence case ("Close tab"). Which-key, the palette and completion show it. A key shows this label plus a phrase for each arg its binding sets, see [Which-key](#which-key).
- `intent`: plain text on one line. Its first sentence is the summary that the completion list shows: it starts with a verb, takes at most 60 characters and names no other command. Later sentences are detail. Help, the status page and which-key hover show all of it. The registry rejects an empty or multi-line one, and a test holds every built-in command to the summary rule.
- `params`: typed and named. The types are `int`, `float`, `string`, `bool` and `enum`. `key` is one key press (one character, so `a`, `Z`, `'`). It takes `pattern` for the set a command accepts and no `optional`, `values` or `strict`. A command has at most one `key` param. On the command line a required `key` param is a bare word (`markadd a`), and one with a default is a flag (`--slot=a`). A param with no `default` that applies, no `optional` and no `when` is required. The order is for display only.
- Value rules, plain data that travels in `commands.json`: `min` (the smallest value of an `int`), `pattern` (the source of a regular expression that a `string` must match), `format` (`"url"`: a `string` must be an absolute address, as `URL.canParse` reads it), `strict` (a `string` with a static `values` list accepts only those values, where `values` alone is completion only) and `optional` (a `string` or `enum` may be left out or empty and then reads as `""`, in place of `default: ""`) and `value_of` (a `string` holds the value of the setting named by a sibling `strict` param, and `check_args` checks it with that setting's entry in `SETTING_SPECS`, an empty value passing). `strict` compares exactly, like an enum value. `check_args` applies them. The registry checks at define time that each sits on a param type that can carry it.
- `value_labels`: on an `enum` param with a fixed value list, a short phrase for each value ("and focus previous"). Which-key adds the phrase to the label when a binding sets that value, and completion shows it beside the value. Every key must be one of `values`, and a value that is the default in every context has no phrase. A value with no phrase reads as the raw value with spaces for underscores. The registry checks this at define time.
- `description`: one sentence for a flag, under the same rule as the first sentence of an `intent`. A string on a bool or valued param. A map from value to sentence on an enum with a fixed value list, with no entry for a value that is the default in every context. Completion shows it beside the flag. Every flag of a built-in command has one, and a test checks it. The registry checks the sentence at define time when one is present.
- `main`: the one `string` param that config and the command line take as the subject, for example the URL of `open` or the query of `search`. At most one per command.
- `short`: the one-letter flag of a param. A string for a bool or a valued param (`short: "r"` gives `-r`, `short: "c"` on a string gives `-c=Work`). A map from value to letter for an enum with a fixed value list (`{ tab: "t" }` gives `-t`). Never on `main`, `rest` or an enum with a runtime list. `-t -b -w` mean where (tab, background, window) and `-c` means container on every command that has those params. A default value gets no letter, because the printer leaves it out.
- `rest`: marks a `string` param as text with spaces. The grammar already lets the `main` value run to the end of the line.
- `when`: the param is valid only if one other param has one of the listed values. For example, `container` needs `where` to open a new tab or window, because Firefox cannot change the container of an open tab. This is the only kind of condition, apart from the default list, `value_when` and `pattern_arms` below. A command that needs more is split into two commands. A new window with no `container` keeps the container and private state of the tab that opened it, and a private tab refuses a named container.
- Default list: `default: [{ value, when }, ..., plain]`, an ordered list of arms with an optional plain value last. Each arm uses the `when` syntax, and unlike a param's own `when` it may name several params, which must all have a listed value (AND). The first arm that holds wins, else the plain value applies, else the param has no default and is required. This holds for a param with `when` too: when its `when` holds and no arm does, the param is required, so `media seek percent` needs its count while `media seek up` defaults to one. `open.url` sets `default: [{ value: "", when: { where: ["tab", "window", "background"] } }]` on `url`, so `open` with no URL is an error for `here` and opens the new tab page elsewhere. A hint `action` can default to `play_pause` for the `media` filter and to `here` otherwise. An arm may name a param that has a default list itself, the define check refuses a cycle and names its path (`action -> filter -> action`), and an arm that names several params makes the param depend on each of them. The list travels in `commands.json`. Help prints the plain value first, then each arm: `here; play_pause when filter is media`, and `background when filter is links and rapid is true` for an arm with two params. A value that is the default under only some arms keeps its flag, short, phrase and description, because it is a choice elsewhere. Flag completion hides the value that is the default for the flags already typed. The printer drops an arg equal to the default that the other args give, so `.` replays the same value. The key compiler stores the resolved default in the leaf.
- `value_when`: on an `enum` param, `{ value: { sibling: [values], ... } }`. The value is allowed only while every named sibling has a listed value (AND, as in a default arm). A value with no entry is allowed everywhere, so a new sibling value gets no restricted enum value until someone lists it. `check_args` checks the final value, explicit or default, so a combination that makes no sense is an error on the command line and never compiles into a key. A hint `action` of `background` needs a `filter` that has an address, and `mute` needs `media`. The define check refuses a key that is not one of `values`, a bad sibling, and a default arm whose value its own condition does not allow (the arm must name every sibling the rule names). The rules travel in `commands.json`.
- `pattern_arms`: on a `string` param, `[{ pattern, when }, ...]`. The final text must match the pattern of the first arm whose `when` holds (several siblings allowed, AND). Each value of a sibling, such as the `action` of `media`, so takes its own value set, which one `pattern` cannot give. With no arm holding, the plain `pattern`, if any, applies instead. A `when` param may also carry a default list: when its `when` holds and no arm of the list does, the param is required, so `media seek percent` needs its count while `media seek up` defaults to one. The arms travel in `commands.json`.
- Every static argument rule lives in the param schema, and one `check_args` applies it for the command line, key map compile, `tools/build-config` and the router. A context source (`@selection`) passes the check as a marker, so the router runs `check_args` again on the expanded text. `help` takes a page name (`quick_start`) or a command id, matched exactly. A command handler never judges argument values. It reports only runtime failures, such as a tab that is gone, a refusal from Firefox or an empty selection, and throws them as `RuntimeRefusal`. `test/registry/handler_static_rules.test.ts` fails when a background handler throws anything else on args the schema accepts.
- `default`: a value, or a context source (`{ from: "current_url" }`, `"selection"`, `"clipboard"`, `"bookmark_title"`, the title of the current page's bookmark, `"search_query"`, the query of the search results page, read back through the engines' URL templates). A context source can carry `then`, a second source read when the first has nothing: `{ from: "selection", then: "search_query" }` is the default of the `query` of `search`. The router fills a context source where it is available, so a background command can ask for the page selection.
- `runs_in`: `background` or `content`. The router sends the invocation to that side. A command never runs in both.
- `needs`: what must be true to run it. `content` means a content script in the tab. A permission name means an optional permission. The router refuses with a message instead of failing silently. A command that needs a permission only for some args (`page.reload` with `clear`) checks it in the handler and throws `RuntimeRefusal`. Either way the message names `:permissions.grant <permission>`, which opens the grant panel.
- `count`: what a numeric prefix does. `repeat` runs the command that many times. A param name fills that param, for example `tab.goto` takes the count as its `index`. `ignore` drops it.
- `repeat_limit`: the largest count prefix the router accepts, for a command whose repeats are hard to undo. It needs a `count` rule other than `ignore`. A bigger prefix is refused with a toast (`A count of 100 is over the limit of 20 for tab.close`) before any step of the request runs, so `.`, `3.`, macro replay and snippets refuse the same way and a sequence never runs half. A typed param count (`tab.unload --count=100`) is not a prefix and is not limited. `tab.close` and `tab.unload` carry 20. A yes/no confirmation line, so a big count can still run, is a possible follow-up.
- `bridge`: whether a program outside the browser may run the command through the bridge socket (see [Bridge host](#bridge-host)). Every built-in command states it with `bridge: true` or `bridge: false`, and a test fails when one does not. The tab commands that move between tabs (not `tab.switch`, which matches a title or address and so tells a caller which tabs exist, and not `tab.close`, which closes whole sides of the tab bar: the id-addressed `activate` and `close` verbs behind `bridge_share_tabs` do both), `tab.mute`, `open.url`, `media.act`, the `scroll.*` commands and the mode commands (`mode.set`, `mode.insert`, `mode.escape`) say true. The rest say false. A hard-coded never-list wins over a true.
- `repeatable`: whether `.` can replay the command. The default is true. These commands opt out: `command.repeat`, `browser.close_all`, `browser.focus_page`, `config.reload`, `debug.perf`, `debug.restart`, `page.print`, `page.save_pdf`, `frame.exit`, `help.open`, `help.key`, `native.install`, `native.update`, `permissions.grant`, `engine.show`, `settings.set`, `settings.toggle` and `settings.unset`, and the page commands that only change a mode or open a prompt: `mode.set`, `mode.escape`, `mode.pass_next`, `hint.key`, `find.open`, `help.whichkey`, every `cmdline.*` and `list.*` command, `caret.move` and `visual.act` (a motion replays in normal mode, where it does not apply). One command opts out by its args: `page.reload` is not repeatable with `clear` set to `all`, so `.` and a macro never run a clear of every site. The `repeatable` field takes a function of the checked args for this.
- `jumps`: whether a successful run moves the view in the tab it ran in, so the router records the place it left in the jump list. Absent means false, and a command without it pays nothing. The field takes a function of the checked args: `open.url`, `open.search`, `open.anything`, `open.clipboard` and `page.follow` jump only with `where` set to `here`. `scroll.to`, `find.next`, `find.prev`, `heading.go`, `page.heading`, `mark.step` and `mark.jump` always jump. Reading and recording are in the jump list paragraph under Marks.
- `modes`: the modes where a key can run the command. The default is normal.
- `completion`: where the command line list offers the command. Absent means always. `hidden` means never, and a list of modes means only when the line was opened from one of them. Typing the name still runs the command.
- `advanced`: `true` for a rarely used command (`config.reload`, `debug.restart`, `native.install`, `native.update`). Only the help Commands page reads it: the cards stay hidden until `#/commands?advanced` (the "Show advanced commands" button sets it), and a `#command=<id>` link still shows its card. Completion, keys and which-key ignore it.
- `run`: the handler. It gets the context (tab, frame, mode) and the checked args.

Validation is strict and happens in one place, the same as `Act.resolve` in Oasis. The command line, keys, the native host and the palette all pass through it.

Define-time checks cover names and params too:

- `name` and `aliases` are unique across all commands, snippets included.
- At most one param is `main`, and it is a `string`.
- A long flag names at most one param of a command: no two enum params share a value, and no bool name repeats a value. `_` reads as `-` in a flag, and no value or bool is called `help`. Names and values are lowercase with underscores.
- A short letter is one ASCII letter, never `h`, and unique within the command.
- A `when`, and every param named in the `when` of a default arm, is a param that exists, with valid values, and never the param itself.

A set of options where at most one can apply, for example open, background tab or copy link for a hint, is one `enum` param with a value per option. Two flags from the set both set that param, so the command line rejects them together. No list of exclusions exists. This turns the hint command into five params: `action`, `filter`, `selector` (with `when: { filter: "custom" }`), `text` and the `rapid` switch.

A build step writes `commands.json` from the registry: id, name, aliases, label, intent, params, count, repeat_limit, modes, completion and advanced. Help, the palette, which-key and the native `list` verb read it. The content script does not load it.

## Invocations and prompts

Every caller produces one shape:

```ts
type Invocation = { id: string; args?: Record<string, unknown>; count?: number };
```

- A key binding is one invocation, or an array of invocations that run in order. Pipes have no replacement, because context sources cover the cases the config uses. If a binding ever needs one command's result, a command declares `returns` with a type, and a later step in the array takes it with `{ from: "previous" }`. The keymap loader checks the types. This is not built.
- A binding asks for input only through an explicit `prompt`. If a binding leaves a required param out and sets no `prompt`, the loader warns and skips the key. The prompt opens the command line with completion for that param's type. A binding can prefill the prompt from a context source, for example the current URL for editing.
- A binding that leaves a required `key` param out captures it: the next key press fills the param. The compiler checks the other args at load, stores the step on the background side, and moves the leaf under a branch of its own, in the child `ANY_KEY` (the empty token). The matcher takes one printable key there and fills the param in a copy of the leaf. So the captured key is a value even when it is a prefix elsewhere (`g` after `m`), and a count typed before the binding reaches the command (`5@q`); a command decides whether to use it. Escape, a chord or a named key ends the wait, and the key gets one more try as a first key, as after a stray prefix. Backspace drops the wait like any prefix key. A binding in `browser` mode cannot capture. A character find (`caret.find`) also gets a second child, `LIVE_KEY`, holding `caret.move` with `unit=find_repeat`, in the direction of the binding (`forward` for `f` and `t`, `back` for `F` and `T`). While the caret sink reports a live find, the key flow feeds `LIVE_KEY` in the same key press, so the find key repeats at once and a typed count reaches the repeat. Which-key shows the wait as a group with one `<key>` row and skips `LIVE_KEY`. The `only` form of a site rule matches the capture by its first key and not by the captured one.
- A binding that starts with `:` carries `prompt: { param, prefill? }` in the stored file. The key types its command into the command line and waits, and the user edits it and presses Enter.
- The command line and the config parse the same grammar into an invocation, as described below. Keymaps and the native host also accept the `args` object.

### Command line syntax

One grammar covers the command line and every binding in the config. The text is what the user types and what a `:` key shows. `search arch -b "rust lifetimes"` becomes:

```json
{ "id": "open.search", "args": { "engine": "arch", "where": "background", "query": "rust lifetimes" } }
```

- The first word is a `name`, an alias or a full id. The config uses the same words, and the build tool maps them to the id.
- Flags come first, then the subject. `--value` sets an enum (`hint --background --links`), `--name` turns a switch on (`hint --rapid`), and `--name=value` sets any param, split at the first `=`: `scroll.pixels --dx=-50`. This is the way to turn a switch off (`--rapid=false`). A declared short letter does the same as the long flag: `-b`, `-r`, and `-c=Work` for a valued param. A hyphen in a flag reads as `_` in the name (`--word-end`).
- There are no `--no-` flags, no space-separated values (`-c Work`) and no clusters (`-tb`). An unknown dash word before the subject is an error, so a typo never becomes a query. `-h` and `--help` show a usage line.
- The subject is the `main` param. The first word that is not a flag starts it, and the rest of the line joins into it: `search arch pacman mirrors` gives the query `pacman mirrors`. After the subject starts, everything is text, so `open https://a.example -b` opens that whole string. Write `--` to end the flags early when the subject starts with a dash: `open -- -b`, `search -- -std c++`.
- Quoted words are never flags, engines, values or `@source`s: `open '-b'` opens the text `-b`. Quote a value that has spaces or `=` with shell rules: `open -t "https://a.example/?q=a b"`.
- A `main` param marked `verbatim` (the `selector` of `hint`) takes the raw typed text from its first word to the end of the line, end-trimmed. Quotes, backslashes and inner spacing stay, and a leading `@name` is text, not a source: `hint --custom a[href="x"] > b` gives `a[href="x"] > b`. The usual rules for flags and `--` still apply before it. A verbatim param must be a `string`, `main`, and not `value_of`. The printer writes its value raw, and completion reads quotes inside it as plain text.
- A required `strict` string param that is not the subject is positional. The first bare words fill the positional params in schema order, then the subject takes the rest: `set hint_letters asdf` gives `name` then `value`. A positional param takes its word whatever it says, so a typo reads "name expects one of ...". It shows as `<name>` in the usage line.
- When a command has exactly one number param, and no `main` param, a bare number is its subject: `tab.goto 1`, `zoom.set 1.5`. A negative number is a value, never a flag. A command with two number params needs `--name=value` for them. When the command has a `main` param, a leading number is part of the main text, even when the command also has a number param: `tab.unload 3 GitHub` picks the tab `3 GitHub`, and the count is `--count=2`. A negative number word there is text too: `tab.move -1`.
- A command whose only argument is a required value takes it as the bare subject: `mode ignore`, `cmdline.history prev`, `visual.act yank`. `mode --ignore` works too.
- An enum whose values come from a runtime list, the search engine, is the first bare word, and only when it names an engine: `search arch pacman`. An engine name can hold dots (`search github.repo.issues foo`). `--engine=arch` also works, and the printer writes it only when the bare word would not read back. `--` stops the engine check, so `search -- arch maps` searches the default engine for "arch maps". Build time knows the resolved engine names from `search_engines.toml` plus the built-in `duck`, and the command line from the loaded engines. `tools/build-config` warns about an engine name that starts with `-`, because only `--engine=` can name it.
- An unquoted `@current_url`, `@selection`, `@clipboard`, `@bookmark_title` or `@search_query` is a context source. The router fills it in when the key is pressed. It works as the subject or after `=`.
- A leading `:` (config only) makes the binding type its command into the command line and wait. `gO = ":open -t @current_url"` shows `open -t https://this.page/...`. The stored file names one param to fill: the one that holds a `@source` (which becomes the prefill), else the `main` param, else the first param. A command with no params cannot take a `:`.
- Unknown flags, a param set twice and an unknown source are errors with a message.
- A param whose `when` condition does not hold is an error with a message, for example "container needs where tab, background or window".
- The printer writes the shortest text that reads back as the same args, with short flags: the engine, then flags in param order, then the subject. It leaves out args equal to the default and adds `--` when the subject would read as a flag. `gO` prefills `open -t `. Docs and the help page use the long form.
- Wording says before, after, previous and next, never left or right, because vertical tab layouts exist.
- The `desertfox run` script uses the same parser.

Completion reads the same definition:

- A command word completes by fuzzy match on the dotted id.
- A `-` lists that command's flags with their descriptions, from `short` and the long names. Flags already set drop out.
- A `--name=` prefix completes that param's value from its source, for example the containers.
- Any other word completes the subject by its type, for example engine names, tabs or bookmarks, then the query.

## Keys and modes

The keymap is data, not code. It maps a mode and a key sequence to an invocation:

```json
{
  "normal": {
    "J": { "id": "tab.next" },
    "D": { "id": "tab.close", "args": { "side": "focus_previous" } },
    "sa": { "id": "open.search", "args": { "engine": "arch" } },
    "ca": { "id": "tab.reopen_in_container", "args": { "container": "Family" } }
  },
  "browser": {
    "<A-j>": { "id": "tab.next" },
    "<A-k>": { "id": "tab.prev" }
  }
}
```

- The extension ships a default keymap. The user config overrides it, as described in [Config](#config).
- The background checks each entry against the registry when it loads. A bad entry logs a warning and is skipped, so one typo does not break the rest. The help page lists the warnings.
- Key notation is vim style: `<C-x>`, `<A-j>`, `<S-Escape>`. Sequences match through a prefix tree. A complete match runs at once, with no timeout.
### Modes and insert mode

- The modes are normal, insert, ignore, hint, cmdline, caret, visual, line visual, media and grab. See [Caret and visual](#caret-and-visual) and [Grab](#grab). Insert mode follows `focusin` and `focusout` on editable elements. Each keydown and keyup also re-reads the focused element and follows a change in whether it takes typing, because a page can change that with no focus event. A key that finds no change leaves the mode alone, so Escape holds in a frame whose body is the editor and keeps the focus.
- The case that needs the re-read: the Google Sheets cell editor holds the focus all the time and counts as a field only while a cell is being edited (see [Firefox behavior](firefox-behavior.md#the-google-sheets-cell-editor-sheets-cell-editor)). `i` enters insert mode with no field, in every frame of the tab, and a frame that loads later joins it.
- The background sends one message to the tab with no frame id and keeps only a flag for the hold, never a list of frames. A frame under an all-off site rule drops the message and stays in ignore mode, in both directions. Focus leaving a field does not end it. Escape in any frame returns all frames to normal, and so does a navigation. With no field focused, insert mode handles only Escape, so `<C-r>` and the other insert keys go to the browser.
- `gi` focuses the first field. A hidden input frame is a child frame of the page's own origin that the user cannot see: under 4 px on one side. Where the frame sits does not count, so an editor in a full-size frame that is scrolled out of view is not one. A page such as Google Docs types into one. While such a frame is in normal mode it blurs its own frame element, so the document that holds it gets the keys and every command, sink and panel works there.
- It hands off on each change into normal mode and when it gains the focus in normal mode, and no rule names a site. Escape hands off in the key's own turn. Every other hand-off waits one tick, so a focus move that leaves the frame for a field of the page is not cancelled. A mouse press that focuses the frame's field returns to insert mode, and so does `gi`, which picks a field in one of the page's hidden input frames ahead of the page's own visible fields.
- A frame that gains the focus again within 500 ms of a hand-off, with no insert mode between, keeps it, so a page that fights for the focus does not loop. While the page holds the focus, keys the page's editor handles in the frame (arrows and PageDown in Docs) do nothing.

### Layout fallback

- On a layout whose letters are not Latin (Cyrillic, Greek, Hebrew, Arabic and others), a plain letter whose typed character binds nothing acts as the Latin letter on its physical key (`event.code`). Shift gives upper case. A Latin letter outside ASCII, such as the Turkish `ı`, never swaps.
- A typed character that binds something never changes, so Latin layouts see no difference. A Ctrl, Alt or Meta chord has no fallback here: `token.ts` already maps it.
- A mode with a sink (hint mode) gets the typed letter and the physical one beside it. Label mode takes the typed letter when it continues a label, else the physical one, so Latin labels work on a Cyrillic layout. Text mode (after `/`) takes the typed letter only, so its filter keeps the typed text. With the setting off the sink gets no physical letter.
- The `layout_fallback` setting (default on) controls it. The compiled keymap carries `layout_fallback: false` only when off, and `key_flow` reads it on each install, so a config reload applies it.
- Only the content script applies it. A key typed before the keymap reply is held with its physical letter and replays under the rule. The command line page does not apply it: its default keymap binds no plain letter, and a letter typed in the line stays text.
- Letters only. No punctuation key was measured as needed.

### Leader and cancelled keys

- `,` is the built-in leader for DesertFox's own commands (`,r` reload, `h` help, `s` settings page, `t` toggle a setting, `i` ignore mode, `b` blur, `?` all keys, `"` registers). `<A-?>` lists the first keys in every mode except ignore and the command line (which keeps its own `<C-h>` help). In insert mode with no field focused the chord goes to the page. Space stays with the page, so pause on video sites and Space-to-scroll keep working. `,` alone runs nothing, because a key cannot be both a binding and a prefix.
- The which-key panel shows the group after the pause, and a key outside the group starts a new sequence, so `,G` scrolls to the bottom. A lone `,` in normal mode no longer reaches the page. `pass = ","` in a site rule gives it back on one site, and `<C-v>,` passes one comma. DesertFox reserves no user leader: `\` and `<Space>` are unbound by default, and a user who binds Space as a leader loses Space on the page.
- In every mode except insert, ignore, hint and cmdline, DesertFox cancels a `/` or `'` keydown that no binding takes, when focus is not in a field. Shift does not matter, but Ctrl, Alt or Meta do. Firefox starts Quick Find on these keys in page content (see [Firefox behavior](firefox-behavior.md#firefox-defaults-not-measured)), and Quick Find competes with DesertFox's own [page search](#page-search). Insert and ignore mode give keys to the page, and hint and cmdline mode own theirs. Every other mode is covered, so a new mode is covered without a change.
- In caret, visual and line visual mode, DesertFox also cancels every other unbound key without Ctrl, Alt or Meta, outside fields. These are reading modes, and a site shortcut (a letter in a mail app, a digit in a video player) moves the user away from the caret. Tab and Shift+Tab, the function keys, Escape, Page Up, Page Down, Home and End still reach the page. So focus moves, Firefox's own keys work, a page dialog closes and the page scrolls. Space and Backspace stay blocked. Every chord passes too, so Ctrl+C copies a selection. Normal mode passes unbound keys, apart from `/` and `'`.
### Key editor capture

- The Keys section of the settings page edits one binding in a row editor: a capture box, a command field and a live check. The capture box is a focusable `div`, not a text field, so insert mode and the IME stay out. One window `keydown` listener in the capture phase takes the keys. `main.ts` registers it before `content.js` and the drawer's Escape handler load, so it runs first and stops the event. It acts only while the box holds focus: the box binds on focus and unbinds on blur, on a route change and on removal from the page. No other listener is added.
- Opening an editor moves the focus into the capture box. On an existing row the box shows the row's keys, and the first press replaces them. Escape cancels the capture and puts the row's keys back. Backspace drops the last key. A Clear button empties the sequence. Tab and Shift+Tab move the focus as usual, so the box never traps the keyboard. Enter saves. A modifier on its own is ignored. Saving an existing row on other keys moves it: one `change_keymap` set with `move_from` frees the old key (an empty text for a file or default binding, a dropped edit for a key only an edit binds) and binds the new one, in one change with one rollback. A row with several steps keeps its keys. Firefox keeps some chords for itself (Ctrl+T, Ctrl+W, Ctrl+N, F5) and the page never sees them. Escape, Backspace, Tab and Enter cannot be bound from the box, so the page tells the user to use the config files.
- A row with several steps shows its steps joined by ` ; ` and is read-only, because the check refuses that text. Its Remove and Reset still work. The command field offers the command line names, the aliases and the installed snippets in a native `datalist`. The check, 250 ms after the last change, is the real validator.

### Badge, toast and which-key panel

- A mode badge sits in the bottom right corner, 8 px above the bottom edge. The `mode_indicator` setting controls it: `always` (the default), `not_normal` or `off`. The `theme` setting names a theme (default `oasis_moonlight`), see [Themes](#themes). Light or dark follows Firefox, and Firefox's Settings > General > Website appearance (Automatic, Light or Dark) switches it.
- A toast is one short message in the bottom right corner, framed in the color of its kind (error, warning, info or success). It disappears after `toast_error_ms` (default 6000) for an error and `toast_ms` (default 3000) for every other kind, whole milliseconds from 500 to 30000. The compiled keymap carries both values, as it does `which_key_delay_ms`, and the content script hands the one that fits the kind to the `ui` bundle with each toast.
- The which-key panel is a floating frame with a 1 px tinted border and its title set into the top border. The `which_key_border` setting picks the corners: `square` (the default), `round` or `chamfer`. The `which_key_skip` setting lists key prefixes, in keymap notation, whose panel does not open after the delay (exact match, global, checked with the key parser). An instant redraw still shows it: Backspace back to the prefix, or a key typed while a panel is already up. `?` lists only the first keys of the mode. A footer names the exit keys. Below them a `.` line shows the step `.` would repeat, as the command line that does the same (a command with no name shows its label), while the panel is open. A saved count shows too: a count that maps to an argument shows as that argument, and a repeat count, which the command line cannot spell, shows as a prefix such as `5× :scroll`. A label has no argument, so a command with no name shows either kind of count as that prefix. The `which_key_repeat` setting (default on) turns it off. The panel bundle asks the background with `read_repeat_preview` and the background reads the normal slot of the repeat memory only, so a private tab gets no line.
### Bridge and browser mode

- The `bridge` setting (default off) opens the native bridge, and `bridge_share_tabs` (default off, needs `bridge`) lets it list, activate, close and capture tabs, see [Bridge host](#bridge-host). Neither changes the badge or the which-key panel: both stay in the page.
- `browser` mode holds the chords for the Firefox shortcuts. The manifest reserves a fixed number of shortcut slots, and the background assigns the chords to them with `commands.update`. A chord keeps its slot: `desertfox_slot_map` (chord to slot) is stored, a new chord takes the first free slot, a removed chord frees its slot and no later chord shifts. The first run seeds the map from the keymap order the slots had before, so no chord moves. A chord past the last free slot is refused at save and skipped with a warning at publish. The map is read and written inside the publish, in the change queue, and a failed change puts it back with the edit layers. The content script also catches these chords. If it cancels a chord, Firefox does not fire the shortcut as well, which the key test showed (see [firefox-behavior.md](firefox-behavior.md), "Phase 1 measurements").

## Config

The user config is a directory of files, one file per kind of setting. `config.reload` reads them through the native host, and the extension merges and checks them with the same code `tools/build-config` runs. Each start rereads the files through the host once and applies them when they differ from the stored build, so an edit made while the browser was closed needs no `config.reload`. When the browser copy holds changes made in the browser (an import, an editor save, a snippet change), the start asks on the settings page first. Without the host or its permission the extension runs on the stored build, and on the built-in defaults before the first load. `just build-config` only lints the directory and writes nothing Firefox reads. The native host is optional: browser edits cover casual use, and only the config files (TOML, snippets and CSS) need it. A stale `~/.mozilla/managed-storage/desertfox@uhs-robert.json` from older versions is ignored and safe to delete.

### Source files

The tool reads `~/.config/desertfox/` by default. Every data file is TOML. The build reports any file or directory it does not know as unknown, a leftover `.jsonc` file included. Only `.toml` files belong in the `.d` directories and in `themes/`, only `.css` files in `style.d/` and only `.js` files in `snippets/`.

| File | Holds |
| --- | --- |
| `keymap.toml` | Every key: bindings per mode, plus the `search_keys`, `container_keys`, `site_keys` and `modifiers` shortcuts. `""` removes a default binding. |
| `search_engines.toml` | Search engines: a tree of named URL templates with slots (`{query}`, `{repo}`, and others). `%s` still reads as `{query}`. Data only, no keys: the letters of the `s/` group live in `[site_keys]` in `keymap.toml`. The built-in `duck` and `site` need no entry, and an entry with their name replaces them. See [Starting engines](#starting-engines). |
| `command_aliases.toml` | Extra command line names, for example `g = "open.search"`. |
| `quickmarks.toml` | Quickmarks: one letter or digit mapped to an address, for example `g = "https://github.com"`. `M<key>` adds entries in browser storage on top of these, and the stored entry wins for the same key. |
| `settings.toml` | Settings such as the which-key delay and the new tab page. |
| `snippets/*.js` | One custom command per file. See [Snippets](#snippets). |
| `themes/<name>.toml` | A local theme that `theme = "<name>"` picks. Every file counts, and the theme importer saves each scheme here. See [Themes](#themes). |
| `style.css` | Custom CSS for the DesertFox surfaces. See [Styles](#styles). |

Each data file can also have a matching directory, for example `keymap.d/`. The tool merges the main file first, then the files in the directory in name order. A later entry wins for the same key. This is how private config joins without editing public files: a private repo links `keymap.d/50-private.toml` and `snippets/` files into place.

Every key lives in `keymap.toml`. The other files hold only data. A binding is one line of command text, in the grammar of [Command line syntax](#command-line-syntax), or a list of them that run in order, or a table `{ run = "...", label = "...", intent = "..." }` that names the key for which-key and can replace its hover text (`run` is a string or a list). TOML quotes any key that has symbols, so `"<C-[>"` and `"$"` are quoted and `gx` is not. Two shortcut sections remove most repetition:

```toml
# keymap.toml
[search_keys]                   # sa/Sa, sb/Sb
a = "arch"
b = "brave"

[site_keys]                     # s/i, S/i: the engine of the page's site
i = ["github.issues", "gitlab.issues"]
I = ["github.repo.issues"]

[container_keys]                # ca/Ca, cc/Cc, cp/Cp
a = "Family"
c = "Client"
p = "Personal"

[normal]
J = "tab.next"
b = "bookmark.open"
gO = ":open -t @current_url"    # types the command into the command line and waits
y = ""                          # removes a default binding
ww = { run = ":open -w @current_url", label = "New window, edit current URL" }
```

- `sa` searches with the `arch` engine in this tab, and `Sa` in a new tab.
- `ca` reopens the current page in the Family container, and `Ca` opens a prompt, set by an explicit `prompt` on the generated key, prefilled with the current URL in a new Family tab.
- `s/` is the group for the page you are on. Each `[site_keys]` letter lists engines of different sites. On a page the first listed engine whose `hosts` include the page host and whose page slots the page fills runs. Which-key shows a letter only when such an engine exists, so on a GitHub repo page `s/` offers GitHub-wide search and search in this repo, on a user page the GitHub-wide ones, and on an unrelated site nothing. `S/` does the same in a new tab. A member key behaves like `sa`: it searches the selection at once, or opens the command line with the engine typed in. A letter is one key, not `/`, and lists only engines whose `hosts` do not overlap (an engine with no `hosts` overlaps all). `tools/build-config` refuses the rest, and a `search_keys` letter `/` unless the user unbinds both `s//` and `S//`. A row reads the label of the engine the page selects, and which-key hides a letter it cannot resolve. A typed key on a site that fits none refuses with a toast, "No <letter> search for this site".
- `s//` and `S//` search the current site with the built-in `site` engine: the default engine's URL with `site:{host}` added to the query. They show on every page that has a host. The shipped keymap sets the letter `/`, which the build refuses in a user file. If the default engine needs a page slot, `site` uses DuckDuckGo and the load warns. `site` is built when the config loads, so a live `:set default_engine` does not change it.
- `[modifiers]` maps a key inside a group to the args it adds, for example `";r" = { rapid = true, label = "Rapid" }`. The key becomes a group that holds a variant of every other key of the group, with those args added. The `label` names the group. A variant exists only when the command's param schema accepts the args, so an invalid combination is never bound or shown. A key that sets its own `action` gets no variants, and modifiers do not stack. An explicit key at the modifier key wins and the load warns. An explicit key under it wins silently. Normal mode only.
- Containers themselves need no file. Firefox lists their names, colors and icons through `contextualIdentities.query()`, and completion and the `container` param use that list. A name in `container_keys` that does not exist gets a warning at load and is skipped.
- The prefixes for generated bindings (`s` and `S`, `c` and `C`) are settings. An explicit binding in the keymap wins over a generated one.
- A key cannot be both a binding and the start of a longer one, so a user key that extends a default binding (default `sg`, user `sgg`) takes its place: the build drops the default binding and warns once per mode, naming the user keys. A default that a user key replaces includes a binding made by a modifier. The default stays when no extending user key passes the registry check. The build does not check the mode of the extending key, so a user key whose command does not run in its mode still drops the default. This holds for keys from `search_keys` and `container_keys` too. The reverse needs no rule. A user binding shorter than a default group (user `g`, default `gg`) keeps the user key and skips the longer default keys. Two user keys that clash, or two default keys, still skip the longer one with a warning. A vim-style wait on the shorter key is not built, because it adds a pause to every such key.

#### Starting engines

DesertFox has one built-in engine, `duck` (DuckDuckGo), and the `default_engine` setting defaults to it. So clipboard search works with no config. It is added when the config loads and when `tools/build-config` checks names, so the merged file stays as written. An entry named `duck` in `search_engines.toml` replaces the built-in whole. Nothing hides or removes it.

[`examples/engines.toml`](../examples/engines.toml) resolves to 69 engines, `duck` among them, and teaches the tree rules in two worked trees (GitHub and YouTube). Copy it to `~/.config/desertfox/search_engines.toml` and edit it. A TOML file cannot include another file. A `search_engines.d/` file also works, and a later file replaces the table at the same dotted path (a later `[github.repo]` replaces only that node and leaves `github` alone).

#### Engines

An engine is a named URL template. It replaces the former site commands. No provider is built in except `duck`.

- Slots. `{query}` is the typed or selected text, and `%s` means the same. Page slots read the current tab: `{url}`, `{host}`, `{title}`, `{repo}` (GitHub), `{subreddit}` and `{channel}` (YouTube). Each page slot is a small pure function in `src/shared/engines/slots.ts` with its own message for a page that cannot fill it. `{a|b}` takes the first slot that has a value, so `{query|url}` is the typed address, else this page. `{name:raw}` skips escaping, for a path such as `/web/{url:raw}`. Every other value takes `encodeURIComponent`.
- Tree. A table inside an engine is a child, named with a dot (`github.repo.issues`). A child inherits every field and overrides by name. `label`, `keyword` and `reverse` do not inherit: the label is the chain of labels on the path ("GitHub: this repo: issues"), and a `label` field sets one link. A `keyword` names one engine, so a child sets its own. A child cannot be named `url`, `label`, `params`, `fallback`, `hosts`, `keyword` or `reverse`, or like a field or param of its parent. `reverse` is an optional regex that reads the query back from a results page address (see `docs/search_engines.md`, "Reading the query back"); without it the reader comes from `url`. A later file replaces the table at one dotted path.
- Params. `[github.params.type]` declares `default`, `values` (name to URL text) and `children = true`, which generates one child per value. A field set to a value name picks it, and `type = { only = [...] }` narrows the values below that level. A hand-written child beats a generated one. A query pair whose whole value is one empty param (`&type=`) is left out.
- Hosts. `hosts = ["github.com"]` lists the host names of the sites an engine belongs to, and children inherit it. A host matches only itself, so `gist.github.com` needs its own entry. It gates only the generated `s/` and `S/` keys: explicit keys and completion ignore it. The build refuses a `hosts` that is not a list of lower-case host names, and one on a node with no url on it or above it.
- Availability. An engine is available on a page only when every page slot in its URL can be filled. Which-key hides the keys of an unavailable engine, and a group left empty. A key still works when typed, and shows the slot message. An engine with `fallback = "<engine>"` never hides and runs the fallback when its slots cannot fill. Snippets can require slots with a `// requires: repo` header. The background filters the key list, so the content script is unchanged.
- Resolution. `tools/build-config` resolves the tree into a flat map keyed by the dotted name and the extension stores the result, so it only fills page slots and the query. `tools/build-config` runs the same resolution as a lint and writes no engine file. It rejects an unknown slot, a param no URL uses, a field that is neither a known field nor a var some URL reads, a value outside the declared list, a fallback to a missing engine, a fallback loop and a default engine that needs a page slot.
- Help. `help` lists the resolved tree with each engine's URL, slots and the file and level that set each field. `engine.show <name>` opens it at that engine.
- Which tool. A result that is a URL is an engine. Page DOM or several steps is a snippet. Browser APIs (tabs, windows, bookmarks, containers) is a built-in command. A fuller real example: [https://github.com/uhs-robert/oasis-dots/blob/main/home/desertfox/.config/desertfox/search_engines.toml](https://github.com/uhs-robert/oasis-dots/blob/main/home/desertfox/.config/desertfox/search_engines.toml).

### Merge and checks

The merged file has one section per kind: `keymap`, `search_engines`, `command_aliases`, `quickmarks`, `settings`, `snippets` and `css`, plus a format version. The stored keymap holds invocations, so the extension never parses command text. The tool:

- rejects unknown files and unknown sections with a message, so a misspelled file name does not vanish silently. A TOML syntax error names the file, line and column.
- parses every binding string with the registry grammar, then checks it, every alias and every snippet against `commands.json` and reports errors before the extension loads.
- reads snippet code and CSS as text and escapes it, so nobody edits code inside JSON.
- generates a JSON Schema for each data file from `commands.json`, so an editor with TOML schema support (Taplo) completes command names and setting names.

The TOML parser (`smol-toml`) is a dev dependency of the tool only. None of it reaches the extension bundles.

### The settings table

- Each setting is one row of data in `src/shared/settings_table.ts`: its kind (true or false, a word from a list, a number, text, a list, a table), the values the kind takes and its default. The check, the expectation text in a problem message, the values the command line offers, the editor JSON Schema, the `Settings` type and the defaults all follow from the row, so a new setting takes one row and one description.
- A row of kind `custom` (`hint_letters`, `theme`, `new_tab_page`) has its check and expectation written in `settings_schema.ts`. `settable: false` marks a setting that `:set` refuses. `per_site: true` lets a `site_rules` row set the setting for its sites (see [Site table](#site-table)). The one row of kind `site_table` (`site_rules`) takes each such setting as an extra column, checked by that setting's own check.
- A table field of kind `site_modes` (the `modes` column) holds named site modes, each `{ label, bind }`, where `bind` follows the rules of the `bindings` kind. A table field of kind `mode_bindings` (the `keymap` column) holds one `bindings` table per keymap mode in `SITE_KEYMAP_MODES`. A table field of kind `bindings` (the `bind` column) holds a table from a key sequence to a binding in the formats of a keymap entry (a command string, a list of steps, `{ run, label, intent }`, plus `when_focus` and `when_present`, or a list of such tables as choices; the stored form is an invocation table `{ id, args }`, and a list of step lists for choices).
- Every setting has a default except `home_page`, because `page.home` refuses without one, and `zoom`, because without one Firefox keeps the zoom it remembers for each site. The editor descriptions live in `settings_docs.ts`, which only the tool imports: the prose is large and no page needs it. The content script reads `src/shared/default_settings.ts`, which `just settings-defaults` writes from the table with one constant per setting, so the content script carries only the defaults it reads.
- The command line page reads `src/shared/setting_completion.ts` the same way, one row per setting with its name, flags, expectation text and listed values (theme names as of generation), so it bundles neither the table nor the setting rules. The page checks the shape of a line only (`check_args_shape`), and a bad `:set` value shows its error at Enter, from the background. `just test` fails when either generated file is stale, and `just themes` changes the theme names in the second.

### Delivery

`config.reload` (key `,r`) asks the native host for the raw text of the files (`read_config`), builds the config in the background with `build_config` and swaps it in place. Nothing restarts, so the temp edits, the modes and open hints stay.

- The swap runs in the same queue as `set`, `toggle` and `unset`, so a reload and an edit never publish over each other. It replaces the snippet commands (the old ones leave the registry first), compiles and publishes the keymap, tells open tabs (`tree_updated`) and replaces the config the background runs on. Commands that arrive during the swap wait for it to commit. The toast counts every warning Help shows.
- The built config goes to `storage.local` (`desertfox_files_config`), with its build warnings, so Help still lists them after a restart. The raw file text goes beside it (`desertfox_files_source`) in the same write, so an import can rebuild it. A restart, the help page and the new tab page all read what the last reload or import built.
- An import (a zip or a picked folder) goes through the same swap (`apply_files`) and the same slot. It passes the zip guards, drops one top folder that every path shares, and refuses an empty result. Its config files replace the ones in the slot, the installed snippets stay, and the browser edits stay on top: the temp edits, the consent settings, the key edits and any value an older version saved in the browser that the start has not moved into `settings.toml`. Each imported snippet is stored only when the user accepts its exact code. The settings keys `bridge`, `bridge_share_tabs`, `host_auto_update` and `newtab_ip_info` are each a consent given on this machine, so an import drops them from its settings files. The review lists what the built import reaches (`src/background/import_reach.ts`): the search engine, new tab page, home page, new tab link, quickmark and fixed-address key addresses it adds, and the keys that read the clipboard, press keys or click on a page, change settings or use the native host, with at most 12 rows a list. It only informs. Import is the one consent, and a key that names a consent setting is shown and kept, not stripped. The settings page also exports the config as `desertfox-config.zip` (the config files, with the saved browser edits as `settings.toml`, or as the last file of `settings.d` when the config has settings files of its own, and the key edits in force as the last file of `keymap.d`, so an import elsewhere gives the same keymap) and the snippets as `desertfox-snippets.zip`. It lists the installed snippets, and Remove rebuilds the config without one through the same swap. A key that binds the snippet refuses the removal, in the files or as a key edit. The snippet returns on the next `config.reload` while its file stays in the config folder. A later `config.reload` replaces the whole import.
#### Start read

- The start read (`reload_config_at_start`) reuses the host call every start makes for the version check. It waits for the cached config and runs in the same queue as the swap, then compares the folder's files with the stored source (`desertfox_files_source`). The compare leaves out `autoconfig.toml`, which the host writes from the key edits and the build never reads, and the folder label, which an import or an editor save changes. An unchanged start builds and publishes nothing.
- Each swap to the folder's files (a start, Use the folder, `config.reload`) stores a digest of them (`desertfox_host_start_applied`), and a start that finds the copy equal to the folder stores it too. When the browser copy is empty, or still matches that digest, the start applies the folder with `apply_files`. Otherwise the copy holds browser changes, and the start replaces nothing (`host_start.ts`). A profile with no stored digest counts as changed, so it asks once rather than risk a loss.
- It stores the question (`desertfox_host_start_pending`: the folder, a digest of each side and the files the folder would replace, add or drop) and toasts once. The settings page shows it as a banner with Export config, Use the folder and Keep the browser copy. A choice reads the folder again in the change queue and runs only when the browser copy still matches what the page showed. Keep also needs the folder the page showed. Otherwise it refuses and stores the fresh question.
- Use the folder takes a folder changed since, because it drops only the browser copy: the user who unpacks the export into the folder clicks once. The export carries the saved edits in its settings file, so the folder then holds them too. Use the folder swaps through `apply_files`, so the edit layers stay on top, and a folder that does not build keeps the browser copy and the question. Keep the browser copy stores the folder digest (`desertfox_host_start_kept`), so the start asks again only when the folder changes.
- Any swap (an import, an editor save, a reload) drops the question, because its list no longer fits. The first answer wins, and a second page is told it is settled. A host start that cannot read the host drops it too, because no choice can run. Writing the whole browser copy into the folder stays manual: export the zip and unpack it. One setting at a time does reach the folder: a scalar or list setting changed by `set`, `toggle`, `unset`, the popup or the settings page is written into `settings.toml` (see Settings in the file). The host read and a waiting `settings.toml` write happen outside the queue, so a slow host never blocks a `:set`.
- A start reply is dropped when a config swap (reload or import) commits during the read, because the swap is newer. No permission, no host, a host error and a missing or empty config folder keep the stored config and only warn on the console. Empty means no file but `autoconfig.toml`, because the host creates the folder when it writes that file. The installer never creates the folder.
- A file that fails the build of a start that adopts keeps the stored config too, and a toast names the problem on every start until the file is fixed. `,r` stays the explicit replace: it applies the folder over any browser copy and refuses a missing or empty folder.
#### Failed reloads and managed storage

- A reload that cannot finish keeps the current config whole: config, snippets, keymap and stored files. Its toast names the cause and the fix: no permission or no host (run `:native.install`), a host error, a missing config folder, or the problems in the files (the first three, and a count).
- The load checks every setting in the files against `SETTING_SPECS`. It drops a setting with an unknown name or a value the check refuses, warns, and lets the layer below apply. `build-config` refuses both, but a stored slot from an older version can still hold one.
- Managed storage is removed. Firefox read its file once per extension load (see [firefox-behavior.md](firefox-behavior.md), "Managed storage"), which is why `config.reload` uses the host. A fresh install starts on the defaults until the first start or `,r` that reaches the host.
#### Debug commands and the warnings list

- `debug.perf` (`:perf`, no key) copies the recent timings to the clipboard for a slowness report and toasts the slowest p95. It covers bundle loads (`load_log.ts`), command round trips (background commands only, timed in `router.ts` from the start of a step to its answer; content commands are left out because hint mode, find and caret wait on the user and the registry cannot tell which ones do) and hint build time (recorded by the `hints` bundle).
- There is no per-key timing, because `content.js` has little headroom and every frame pays for it. The timings are a ring of 300 in `storage.session`, summarized as count, median, p95 and max per name.
- `debug.restart` (no key) restarts the whole extension, for debugging. Firefox loads the content script into open tabs by itself after `runtime.reload`, so the reinjection step stays only as a fallback (see [firefox-behavior.md](firefox-behavior.md), "Phase 1 measurements").
- The help page's Home shows the warnings. The settings page at `home.html#/settings` shows the config source and the steps to apply an edit, and has an input for each setting that `:set` takes. An Export and import section exports the two zips and `desertfox-sessions.json`, imports a zip, a folder or a sessions file, and lists the installed snippets. The sessions file holds the stored shape of the tab sessions (see Tab sessions). The add-on Preferences button opens the settings page, so no separate options page exists.

A host from before that verb gets the text through its older `write_settings`. The host call runs outside the change queue, so a slow or hung host blocks no other change. After three such rounds in one write loop, or otherwise, the copies-differ question takes over. When the folder cannot be read again, the record stays and the next start tries again. A pick never drops a pending question: after a write it reads the folder again and asks again or settles the question. The host is asked only when the browser copy came from the folder: a folder read is on record, and the copy is no import. A setting a `settings.d` file sets, which wins over `settings.toml`, is refused and the reply names that file. `site_rules` is the exception: its files add up (see Site table), so a write to `settings.toml` is never hidden. The record maps each path the folder lags (`settings.toml`, and `themes/<name>.toml` and `search_engines.d/zz-desertfox.toml`, which the host writes too) to its base, and each path has its own write loop state: a refusal, a drop or a write out on one file never decides another file's outcome. A host that knows only `write_settings` still gets every `settings.toml` replacement. A theme write and a delete wait for an update there. A record stored as `{ base }` reads as `settings.toml`'s base until the next store writes the map. A start writes the waiting paths one after another. A file the copy no longer has is deleted through the same base check. A refused write of a whole file such as a theme is not put onto the folder's text, so the question takes over. A refusal whose folder read began before another file's write settled is sent again, so the merge never takes that file's old text. A refused `settings.toml` is put onto the folder's text only while each other waiting file in the folder still holds its base or the copy's text. An editor save or a snippet change (a removal, or an import of snippets alone) that leaves `settings.toml` as it was keeps the record. A reload, an import of config files or a save of `settings.toml` drops it, and the reply of a pick it drops names that swap and says whether the file got the pick before it. A refused write leaves a record that a later pick started after such a swap, even one with the same base, and that pick's write runs from its own base. An old file the host cannot read back after its rename goes back in place, and the reply says the file was not written and is tried again at the next start, not that it changed on disk. ### Styles

Every surface (which-key, the command line, hints and the mode indicator) draws from CSS custom properties, for example `--desertfox-bg-core`, `--desertfox-fg-core`, `--desertfox-primary` (titles and groups), `--desertfox-secondary` (keys), `--desertfox-font` and `--desertfox-radius`. The variables are the stable way to restyle DesertFox. Documented class names use the same `desertfox-` prefix.

- The defaults are declared on an inner element of each surface, not on the shadow host. The host sits in the page, so page CSS can match the host, but a variable set on the host or on `:root` does not reach the inner element, which sets every role token itself. The long prefix and the inner element together keep page CSS out.
- Exception: the help and new tab pages read their fallback tokens from `:where(:root)` in `page_base.css`, so a variable set on `:root` reaches them. The shadow-root surfaces keep the rule above.
- User CSS must name the inner class of a surface to change a variable there, for example `.desertfox-whichkey { --desertfox-primary: #ff6ec7; }`. Variables on `:root` or `:host` alone do not reach inside a surface. The help page lists the classes.
- `style.css` and `style.d/*.css` load after the built-in styles in the shadow roots (hints, which-key, toast, badge) and in the command line, help and new tab pages, after the theme sheet, and follow a reload. Those pages stay hidden until the theme and the user CSS have both been read. Variables set outside DesertFox, on `:root` or in a browser user stylesheet, stay unsupported.
- The help and new tab pages share one base sheet, `src/shared/page_base.css`, which they link before any other style. Its fallback palette and tokens sit in `:where(:root)`, so the theme and user CSS always override it. Its classes (`desertfox-keycap`, `desertfox-card`, `desertfox-pill`) are listed on the Styling page.
- The background resolves the theme at startup and at every `set`, and stores it as `desertfox_theme` (`{ dark, light }`, the light set already picked by `light_intensity`) in `storage.local`. Each surface turns it into one style block on its inner element, after the built-in styles and before user CSS, and follows `storage.onChanged`, so a `set theme` reaches open pages at once. A surface stays hidden until the first read of the theme and of user CSS returns, and a page stays hidden until the theme read returns, so the default colors never show. A failed read counts as returned. The first hint or which-key panel on a page appears a few ms later, once per page. Light or dark is a `prefers-color-scheme` block.
- The `font_family`, `font_family_mono` and `font_scale` settings ride in the same stored record, in an optional `font` field that holds `--desertfox-font-family`, `--desertfox-font-family-mono` and `--desertfox-font-scale` (the percent divided by 100), written once in the base block and only for the settings that are set. Each surface writes its font as `var(--desertfox-font, calc(<own size> * var(--desertfox-font-scale, 1)) / <line height> var(--desertfox-font-family, <own family>))`, so the order is the surface's own font, then the setting, then a `--desertfox-font` or family variable in `style.css`. `parse_font_family` checks the family text and stores it canonical. The help and new tab pages scale only their text, in the font variable and the small text token, and keep the root size, so the layout and the breakpoints stay as they are. Firefox zoom is the whole-page tool. The command line, the key caps and the hint labels read the mono variable.
- The font list that the Settings page and `set font_family` (and `font_family_mono`) offer comes from one of two sources: the names `list_fonts` returns where the native host is installed (they stand alone, because Firefox resolves fontconfig aliases and the probe would add names that are not installed), else a canvas probe of a built-in candidate list (`src/shared/font_candidates.ts`) in the background page. A name counts as installed when its width differs from the width of the generic family it falls back to, measured against both `monospace` and `serif`. The background stores the list in `storage.local` as `desertfox_font_names` and refreshes it at startup, when the Settings page opens, after a host update and when a permission is granted. A host that is missing (not installed, no permission, or too old to know the verb) gives the probe list. A host call that fails keeps the cached host list, and only a refresh with no cached host list falls back to the probe. It is a cache, so a missing or malformed value rebuilds. The command line page gets the stored names when it opens and does no probing. Typing any name always works: the list only suggests. Measured on Firefox 160 for Linux, neither `privacy.resistFingerprinting` nor Strict tracking protection changed what the probe finds: the background page is exempt from the first, and a web page probing the same names found the same set under both. Other systems are not measured.
- Setting variables covers colors, fonts and sizes. Full selectors can change layout. The documented class names on each surface are part of the public format, and the help page lists them.
- In Oasis Dots, the theme switcher writes `style.d/00-oasis-theme.css` with the variables for the current Oasis theme, then runs the reload. Without Oasis, the built-in defaults apply.
- CSS cannot run code. User CSS may not load remote addresses: `style.css` or `style.d/*.css` that holds `@import`, `@font-face`, `image-set(`, `src(` or a `url()` that is not `data:` is refused, with the file and line. The check runs on an import, a reload of the config folder and a save in the files editor, so the current config stays when it fails (`build_files_config`). The engines and aliases layer rebuild skips it, because it reuses CSS that already passed. CSS that an older version stored stays until the next reload, because there is no recheck at startup. `@namespace` with a quoted string passes, because it names an XML namespace and fetches nothing. Its `url()` form is refused like any other non-`data:` `url()`, so write the string form. A theme color value cannot carry CSS, because `parse_color` accepts only a hex, `rgb()`, `rgba()` or `hsl()` color and stores it as hex. The import review and the permission grant panel show no user CSS.
- The manifest CSP covers the extension pages (new tab, help, popup, command line frame, workers) and not the surfaces DesertFox draws inside web pages, which the check above covers. It sets `script-src 'self'`, `object-src 'none'`, `style-src 'self' 'unsafe-inline'`, `font-src 'self'`, `worker-src 'self'`, `img-src` limited to `'self'`, `data:`, `blob:`, `resource:` and `moz-icon:`, and `connect-src` (with `'self'`) open to `https:` and `http:`. Remote scripts, `@import`, remote fonts and remote images are blocked in those pages, so a remote `url()` image in user CSS does not load on an extension page. Tab favicons arrive as `data:` URLs and container icons as `resource:`. Only the image copy fetch and the weather fetch need the remote `connect-src`.

### Themes

A theme file maps colors onto a fixed public list of roles. The theme's own color names never reach DesertFox. A file is TOML with a `[dark]` table, a `[light]` table or both, and a file with one table serves both system settings. Each table maps a role to a color: `#rgb`, `#rrggbb`, `rgb()`, `rgba()` with alpha 1 or `hsl()`, stored as `#rrggbb`. Named colors are not accepted.

The 27 roles: `bg_core`, `bg_mantle`, `bg_crust`, `selection`, `fg_core`, `fg_comment`, `fg_dim`, `fg_muted`, `primary`, `secondary`, `accent`, `border`, `error`, `warn`, `ok`, `info`, `mode_normal`, `mode_insert`, `mode_ignore`, `mode_caret`, `mode_visual`, `mode_item`, `mode_media`, `search_bg`, `search_fg`, `search_current_bg` and `search_current_fg`. `fg_core` is the text, `fg_comment` is secondary text, `fg_dim` is hints such as the command line usage line, and `fg_muted` is disabled text, which has no contrast floor. `error`, `warn`, `ok` and `info` color the toast kinds. A mode badge is its `mode_*` role with `bg_core` as the text. `selection` also paints the selection in visual mode, and caret mode paints one cell in `mode_caret` with `bg_core` text. `mode_caret` is the Neovim cursor color, so the badge and the cell match, with exceptions in the Oasis build (`tools/build_themes.ts`), made because two badges sat too close in color. Every Oasis dark theme sets it to `#f7d46c`, because the shared yellow cursor `#f0e68c` sits too close to the yellow normal or insert badge in five of them. Oasis Desert light sets it per level (1, 2 and 4) for the same reason. The build also sets Oasis Scorpion light level 4 `mode_insert` by hand and gives Oasis Canyon light `mode_visual` the theme's own `secondary` at every level, because its brown visual badge sat on its brown normal badge. `mode_item` colors the ITEM badge and derives from `info` when a theme leaves it out. The Oasis build sets it from the terminal magenta. No base16 slot feeds it. `mode_media` colors the MEDIA badge and derives from `error`. The Oasis build sets it from the green `ok` diagnostic color. No base16 slot feeds it either. The `search_*` pair colors every match of a `/` search and the `f`, `t`, `F` and `T` targets, and the `search_current_*` pair colors the current match. They come from the Neovim `Search` and `CurSearch` groups without the bold, because a CSS `::highlight()` rule cannot set it. The page document has no tokens, so the caret bundle reads these colors from the stored theme. `bg_core`, `fg_core`, `primary` and `accent` are required. Every other role derives from them when missing, by the one table in `src/shared/theme/derive.ts`. A role's CSS variable is `--desertfox-` plus the role with hyphens, for example `--desertfox-bg-mantle`. The list is a contract: a later rename breaks contributed themes, an addition does not. An old name such as `bg`, `fg` or `muted` in a theme file is an unknown role, and the error lists the valid ones.

`theme = "<name>"` looks in `<config dir>/themes/<name>.toml` first, then in the built-in themes. The default is `oasis_moonlight`, and a bare name such as `moonlight` is a config error that lists the known names. A local file wins over a built-in theme of the same name. Every file of `themes/` is kept, not only the one `theme` names, so `:set theme <name>` takes any of them.

`theme = "desktop"` follows the theme the desktop pushed over the bridge (the `theme` verb, see [Bridge host](#bridge-host)). The background resolves it at every publish to the last stored push, or to `oasis_moonlight` while none was stored, with the bridge off too. `:set theme <name>` stops the following until `:set theme desktop`. A push stores its name either way and changes the theme only while `theme` is `desktop`. The default stays `oasis_moonlight`, so following is off until chosen. A built-in theme name is what a push can carry, so a local theme is not reached through it. Light or dark and `light_intensity` stay as they are.

A base16 or base24 scheme can be imported on the settings page, under the Appearance settings. Schemes are in the tinted-theming collections at `github.com/tinted-theming/schemes`, browsable in the tinted gallery at `tinted-theming.github.io/tinted-gallery`. The box takes pasted text or a picked file and shows a live preview (hint labels, mode badges, toasts, which-key and search highlights) before Save. `src/shared/theme/base16.ts` reads the classic YAML, the tinted-theming YAML and base24 with no YAML library: one `baseNN: "hex"` line per color, `name` or `scheme`, `variant`, and a refusal of flow style, a second document and a duplicate slot. The slot-to-role table sits in that file: `base00` to `bg_core`, `base01` (base24 `base10`) to `bg_mantle`, base24 `base11` to `bg_crust`, `base02` to `selection`, `base05` to `fg_core`, `base03` to `fg_comment` and `border`, `base04` to `fg_dim`, `base0D` to `primary` and `mode_normal`, `base0E` to `secondary`, `accent` and `mode_visual`, `base08` to `error`, `base09` to `warn` and the current search match, `base0B` to `ok` and `mode_insert`, `base0C` to `info`, `base0A` to `mode_caret` and the search match. The rest derive, `mode_item` from `info` and `mode_media` from `error`. `fg_dim` is raised to 3:1 by the clamp in `src/shared/theme/contrast.ts`, which the Oasis build uses too. A scheme has one variant, so it fills both the dark and the light table. A built-in name, `desktop` and a name outside lowercase letters, digits, `_` and `-` are refused. A save writes the scheme as `themes/<name>.toml` (`set_theme_file`), in the browser copy and through the host's `write_config_file` (kind `theme`), the same way a `:set` writes `settings.toml` (see Settings in the file): one queue turn, the same record of a lagging folder, the same base check. The page lists every theme file with a Remove button. A file whose name the host does not write (for example `themes/Nord.toml`) is listed with no Remove, and a remove of it is refused. Saving over a name asks first. A file added to the folder by hand since the last read is never overwritten: the write is refused and the copies-differ question takes over. `:set theme` accepts the names and the picker lists them. Remove deletes the file through the host, only while it still holds the text of the last read. A file that shadows a built-in theme of the same name leaves every `theme` selection alone, as the built-in takes over. Otherwise, when `settings.toml` sets `theme` to that name, Remove takes the key out in the same change, and it drops a saved or temp `theme` edit that names it, so the theme falls back to the default. A `settings.d` file that sets `theme` to it refuses the remove and names that file. An editor save of a theme file starts no write, as for `settings.toml`. A `settings.toml` that names a theme file waits until that file reaches the folder, and a `settings.toml` that no longer names a theme goes before the theme's delete, so the folder always builds. A host that knows only `write_settings` then holds both until it is updated. When that `settings.toml` write goes to the copies-differ question, the delete goes with it. Versions before theme files kept imports in `storage.local` (`desertfox_imported_themes`). The first start after the update moves each into `themes/<name>.toml`, or `<name>-browser.toml` when a file of that name holds other text, and moves a saved `theme` edit that names one into `settings.toml`, under the new name (a `settings.d` file that sets `theme` keeps it a saved edit). The stored list goes in the same queue turn, after the files and the record are stored, so a stop before that moves nothing twice: a file that holds an import's text already counts as moved. Without the host the record waits and a later start writes the files. The importer changes no Firefox chrome and needs no permission.

The 16 Oasis themes are not TOML. `themes/oasis/` holds byte copies of the oasis.nvim CSS files, one dark file and five light files per theme (`just oasis-themes <oasis.nvim dir>` copies them). `tools/build_themes.ts` reads each role from one named `--oasis-*` variable, with no mixing, and the table of which variable fills which role is at the top of that file. The `light_intensity` setting (1 to 5, default 3) picks the light set of an Oasis theme. Other themes have one light set. `tools/build-config` checks every local theme file and rejects an unknown role (the error lists the valid ones), a missing required role and a bad color, each with the file, table and key. `just themes` compiles `themes/oasis/*.css` and the contributed `themes/*.toml` into `src/shared/themes.ts`, and `just test` fails when that module is stale. The stored theme sets every role token on every surface.

`primary` is the brand color: links, titles, groups, the hint labels (a filled label with `bg_core` text and a 1px primary border). `secondary` colors the keys in which-key and the new tab clock second hand. `accent` marks highlights. A `style.css` that sets or reads `--desertfox-accent` for the brand color moves to `--desertfox-primary`.

### Site table

- `site_rules` adds up across files, unlike every other setting, which a later file replaces. The combined list is `settings.toml`'s rows, then each `settings.d` file's rows in name order, then the shipped rows. An earlier row wins (first match per column), so this order is the reverse of a scalar, where the later file wins. Each row keeps its file (`origins`, section `settings.site_rules`, by index in the combined list), so a problem names the file of the row. A list saved in the browser by an older version is folded into `settings.toml` once at start (rows no file has yet) and dropped, so nothing replaces the combined list. The popup and the keys form write `settings.toml` only.
- `site_rules` is one site table: a list of tables, each with `site` (a match pattern) and optional columns. `off` is true or false. `pass` or `only` holds key sequences in keymap notation split by spaces, and `check` refuses a row that sets both. Each column resolves on its own: the first matching row that sets a column decides it, and `pass` and `only` form one column, the key rule.
- So a broad row can turn a whole domain off while a narrower row above it sets `off = false` for one path, and a key row and an off row for the same page combine. So a narrow key row above a broad bare row now leaves that site off, unless the narrow row also sets `off = false`. A row that sets nothing but `site` loads as `off = true`, the shape older configs and the popup wrote.
- A page is all off when `off` resolves true or when its key rule frees every normal binding: it enters ignore mode, so the badge and `<S-Escape>` work as before. This is how to start a site in ignore mode: there is no start-mode setting. The top frame matches its own address. A subframe matches its own address or the tab address. `pass` removes the listed sequences from the normal tree, and a passed prefix removes its whole subtree, so `pass = "g"` frees every `g` key and `pass = "gg"` frees only that key.
- `only` keeps just the listed sequences, and a listed prefix keeps its subtree. It also keeps `<C-v>` and `<S-Escape>`, so the one-shot pass and the way into ignore mode work on every ruled page. Normal-mode `<Escape>` goes to the page under `only`, and insert mode still leaves on `<Escape>`. The key rule covers normal mode only. Insert, hint, command line, caret and visual behave as before, `browser` chords stay on, and `<C-v>` stays the one-shot escape.
- The `bind` column is a table from a key sequence to a binding in any format a keymap entry takes (a command string, a list of command strings that run in order, or `{ run, label, intent }`, which also takes `when_focus`) that binds normal-mode keys on the row's sites, for example `h` to `page send_key ArrowLeft`. The config build parses the text with the keymap's own parser and stores invocations, the form the shipped rows write directly.
- `when_focus` on a bind (`{ run, when_focus }`, or on the first step's invocation table) is a CSS selector, a focus guard. The bind runs while nothing has focus (body counts as none) or the focused element or one of its ancestors matches it, so a control inside a map counts as the map. Otherwise the key runs the binding the bind replaced, with its count, as if the row did not bind the key. A bind that replaced no leaf (a new key, or a key that was a prefix) passes the key to the page then, as if the key were unbound. A selector that does not parse matches nothing. The background keeps the replaced leaf on the bind's leaf (`otherwise`) when it grafts, and the content script picks one of the two before it runs the leaf (`leaf_for_page`). A keymap entry with `when_focus` is skipped with a warning, as it replaces nothing.
- `when_present` on a bind is a CSS selector, a page guard. The bind runs while the frame's document shows a match: a match counts only when `is_shown` accepts it (a box, and not hidden by `visibility` or opacity), the rule `page.item` uses for its items, so a guard never runs a move that finds nothing. A bind with both guards runs only while both hold. A selector that does not parse matches nothing. The guard is read when the key runs, so it follows a page that changes its view without a load. A keymap entry with `when_present` is skipped with a warning, as for `when_focus`. A bind with `otherwise = "page"` (a field on the bind table or its first step, with the guards) keeps the leaf it replaced off the chain, so a failed guard leaves no leaf and `run_leaf_` in the content script hands the real key to the page, as a key with no binding gets it. A keymap entry with `otherwise` is skipped too. The setting accepts only the value `page`.
- A bind can be a choice list, an ordered list of up to 8 `{ run, label, intent, when_present, when_focus }` tables, so one key does different things by what the page shows, for example `h = [{ run = "page.item --direction=left li.tile", when_present = "ul.grid" }, { run = "page.back", when_present = "table.list" }]`. The first choice whose guards hold runs. With none, the key runs the binding the bind replaced, as for a single guarded bind. Every choice but the last needs a guard, or the choices after it could never run, and the settings check refuses such a list. A list that mixes `run` tables and steps is refused too. The build stores each choice as its own list of invocations. The compiler turns the choices into a chain of leaves through `otherwise`, the graft adds the replaced leaf at the end of the chain, and `leaf_for_page` walks it. The merge across rows does not change: the first row that binds a key decides it, choices and all. Which-key shows the first choice's label, and the site rules view lists each choice with its guards. A keymap entry cannot be a choice list.
- A list is a chain: the steps run in order, a failed step stops it, the count goes to every step, and the first step's `label` (or the bind's `label`) is what which-key shows. A bind holds at most 20 steps, checked by the settings check and again by the compiler. A macro is a chain too: `macro play a` with a fixed register binds like any command. It merges key by key: for each key the first matching row that binds it decides, so a user row that binds only `j` keeps the other keys of a later row.
- The `keymap` column binds keys in other keymap modes: `[site_rules.keymap.<mode>]` is a table of binds in the same formats as `bind`, and `<mode>` is `normal`, `visual`, `visual_line`, `caret` or `item` (the validator refuses any other mode and names the allowed ones). `bind` is the short form of `keymap.normal`: a row may set both, the two merge key by key into one normal table, and the same key in both is a config error that names the key. Each mode merges across rows as `bind` does (the first matching row decides each key), the compiler checks each bind against the commands that run in its mode, and prefix clash warnings are per mode. The background grafts a mode's merged binds onto that mode's tree for the page, so the content script and the matcher do not change, and which-key reads the same grafted trees. A mode bind is skipped on a page that is all off, and `pass` and `only` leave it alone, because they prune the normal tree only. The Site Rules view tags each such change with its keymap mode. This is not a site mode: `modes.visual` (the shipped Sheets row) is an overlay on normal mode that `mode.site visual` starts, and `keymap.visual` binds keys in visual mode.
- The background grafts the merged binds onto the normal tree, then `pass` and `only` prune it, so `pass = "j"` frees a bound `j` and `off` wins over all of it. The compiler checks each bind with the one validator and skips a bad one with a warning. A bind that waits for a key press is refused. When rows bind a key and a longer key under it (`g` and `gx`), the compiler warns and the shorter bind wins, as a complete binding hides the keys under it in a keymap.
- This holds for rows of one pattern and for rows of different patterns, unless their hosts are provably different (a page can fit both patterns otherwise), and it holds in either row order. Named site modes are not compared across rows, as a mode comes whole from the first matching row. A cross-site iframe can still drop a bind silently, as a frame resolves rules by its own address and the tab's.
- `page.send_key` takes optional `ctrl`, `shift`, `alt` and `meta` flags (all off by default) that set the modifier flags of its events, a `keypress` flag that adds a keypress between the keydown and the keyup (skipped when the page cancelled the keydown, and carrying the character code of a one-character key), and a `focus` flag that focuses the target before the key, for a page that reads keys only while its element has focus.
- It takes the count as its `times` param and sends the pairs through a per-page queue with 10 ms between pairs, one entry per call, because Sheets applies only the first of several pairs sent in the same millisecond. DesertFox ships site rows after the user's rows (`src/background/default_site_rows.ts`).
- `page.click <selector>` clicks the first element that the selector finds and that shows (`is_shown`, the rule of `when_present`), with the pointer and mouse events of a hint click (`click_like_a_hint` in `hints/actions.ts`). It is for a control that a site script opens only on a click and ignores Enter on. It refuses when nothing shown matches. The handler lives in the hints bundle, which holds that click, because the `site_actions` bundle has no room for it.
- The first is `sheets`, two rows for the two address forms of Google Sheets, which bind `h`, `j`, `k` and `l` to the arrow keys through `page.send_key` (a `keydown` and a `keyup` with `keyCode`, which Sheets reads, sent to `#waffle-rich-text-editor`), `gg` to Ctrl+Home, `G` to a chain of Ctrl+End then Home (the bottom of column A, labeled so) and `<C-h>`, `<C-j>`, `<C-k>` and `<C-l>` to Ctrl+Left, Down, Up and Right (so they hide Firefox's Ctrl+H, J, K and L on Sheets tabs, and Sheets' own Ctrl+H (find and replace) and Ctrl+K (insert link)), bind `x`, `y` and `p` to `page.clipboard` (cut, copy and paste, which a synthetic Ctrl+X, Ctrl+C or Ctrl+V does not do, so `xx`, `xp`, `pp`, `pt`, `pw` and the whole `y` group are gone on Sheets only), and give the row a `visual` site mode (label VISUAL) that `v` and `V` start: in it `h`, `j`, `k`, `l`, `gg`, the `G` chain and `<C-h/j/k/l>` send the same keys with Shift held, and `x`, `y` and `p` end the mode first and then cut, copy or paste the range, so a refused clipboard step cannot leave the mode on.
- Escape ends the mode through the site-mode exit policy and sends no key that collapses the range. `page.clipboard` runs through the same per-page queue as `page.send_key`, so `l l x` typed fast cuts after both arrows, and pass `<C-a>`, `<C-x>` and `<C-v>` to the page so Select all, Cut and Paste work. A user Sheets row that sets `pass` replaces that pass column, so it must list all three to keep them.
- A row that sets `only` replaces it too, and keys left out of `only` go to the page, so it must leave `<C-a>` and `<C-x>` out. `only` always keeps `<C-v>` for the one-shot pass, so an `only` row cannot free the real Ctrl+V. The top-level setting `default_site_rows_off` lists the names of shipped rows to turn off. The popup and the settings page list the user's rows only, and which-key shows the shipped binds.
- The second is `maps`, two rows for `www.google.com/maps*` and `google.com/maps*`. Maps pans on arrow keys only while its map element (`div[role="application"][tabindex="0"]`, its localized aria-label left out) has focus, real or synthetic arrows alike, and Escape blurs it. So the row binds `h`, `j`, `k` and `l` to `page.send_key` arrows aimed at the map, guarded by `when_focus` on the same selector: with focus on the place panel or another element, the keys scroll as usual. A field puts the page in insert mode, so the binds do not apply there. Maps focuses its search box as it loads, so the row sets `focus_on_load` to the map, which takes the focus in place of the search box, and hjkl pan from the page as loaded. The binds also set `page.send_key`'s `focus` flag, so each key focuses the map before its arrow, and hjkl pan again after Escape blurs the map. The match patterns cannot name every `google.<country>` host, so the country domains keep the plain keys.
- The compiled keymap stores per row `{ site, origin, name, regex, off, keys, bind, modes, values }`, each column present only when the row sets it, with `keys` holding parsed sequences. `site` is the pattern as written, `origin` is `user` or `default`, and `name` is the shipped row's name. The site rules view (`site_rules_view.ts`) reads them: it lists the rows that fit one address in table order, the columns each sets and the keys each changes, marking what an earlier row already decides.
- The background resolves the columns for the sender's address (the top frame uses its own address only, because `sender.tab.url` can lag during navigation, and a subframe adds the tab address), prunes the normal tree with the shared `prune_tree`, marks the page all off when nothing is left, and sends the page that tree with `all_off` and the freed keys (`frees`, a list of keys and a flag that inverts it).
- The content script never sees `site_rules` and swaps the tree in before the matcher, so held keys replay against the right tree. An all-off page gets the whole normal tree, so `,i` still works. Which-key lists the same pruned tree through the same resolution. A key the rule frees (a passed `/`, `'` or digit, or any such key under `only`) matches nothing and is not cancelled or counted. Every `tree_updated` resolves the columns again, so a rule edit reaches open tabs at once.
- An install enters ignore mode only on the change into all-off, so a manual `,i` or `<S-Escape>` survives an unrelated edit. On the change out of all-off (removing the row, or setting `off = false` above it) a page in ignore mode returns to normal. A page that changes its address in place (pushState, replaceState, history traversal, a hash change) asks again on the Navigation API's `currententrychange`. `sender.url` stays the address the document loaded at, so each request that matches rows carries the page's own `location.href` (`url`): the keymap ask, `read_hint_selectors`, `editor_open`, `list_keys` and `quality_report`. The background matches on it (`sender_at`) and falls back to `sender.url` when it is missing, has another origin or has an opaque origin (an about:blank frame that wrote its document reports its parent's address, which must not give it the parent's rows). An answer identical to the last one installs nothing, so a running site mode survives a step within its row, while a `tree_updated` still installs. A step into or out of an `off` row enters or leaves ignore mode through the same rule as a rule edit.

#### Per-site settings

- Per-site settings: a row of `settings_table.ts` with `per_site: true` opts its setting in, and a `site_rules` row may then set it as a column. That setting's own check (`SETTING_SPECS`) checks the value, the editor schema lists it, and an unknown column is a typo. On the sites a row names, its value beats every global layer, `:set` and `:set --temp` included: the row names the site and `:set` does not. The compiled row keeps such values in `values`, and the background resolves them with the other columns (`site_columns_for` and `site_value` in `page_keymap.ts`). A value about the whole tab resolves against the top frame's address: a frame's message passes through `top_frame_address_of`, and the zoom reads the tab's own address from `tabs.onUpdated`. A value about one frame's own content resolves against that frame's address. `zoom`, `blur_on_load`, `editable_add`, `editable_remove`, `editable_remove_unsized`, `escape_to_page`, `hint_add`, `hint_remove` and `strip_tracking` opt in (below). The settings that act inside one frame (`FRAME_SITE_SETTINGS` in `prefix_tree.ts`) resolve against the frame's own address only, never the tab address that key rules add for a subframe: a row for the top page says nothing about a frame of another site. `blur_on_load`, `escape_to_page` and the three `editable_` settings reach each frame as `site_values` in its page keymap reply. The hint selectors do not ride in that reply, so content.js does not grow: the hints bundle asks for them (below). A value at its default stays out of both answers. Their global values travel in the compiled keymap (`frame_site_globals`), which the background strips before it replies.

#### Zoom

- Zoom: `zoom` is a level from 0.3 to 5 (Firefox's range), set per site in a `site_rules` row or for every site at the top level. It has no default, so with neither a page keeps the zoom Firefox remembers. Firefox remembers zoom per host and `tabs.setZoom` writes that memory (see [Per-site zoom memory](firefox-behavior.md#per-site-zoom-memory-and-tabssetzoom-per-site-settings)), so the background (`site_zoom.ts`) sets the level from `tabs.onUpdated` only the first time a tab reaches the host in a browser session. Firefox's memory then carries it to the host's later tabs. `storage.session` holds the level set on each host, with a separate record for the private windows that clears with the last private window. So a manual zoom sticks across reloads, pages of the site, new tabs and a round trip to another site. A level that changed since (a config edit, `:set`) is set on the next load. An add-on reload or update clears `storage.session`, so each host gets the level once more then. A zoom column acts per host: a row for one path also zooms the rest of the host, and two paths of one host with different levels set the zoom at each crossing, so give a host one level. The tab's address is its top frame's. The switch off sets nothing.

#### Escape to the page

- Escape to the page: `escape_to_page` (default off, per-site) lets a page keep Escape while a field is focused. In insert mode with a field focused, the content script passes the Escape keydown to the page, does not blur and stays in insert mode. The focus follower returns to normal mode once the page drops the field, as when Sheets parks its cell editor after a cancelled edit. A manual insert (`i`, no field) still ends on Escape. Set it only for sites whose editor handles Escape itself: on a plain input the field keeps the focus and so does insert mode. The shipped `sheets` rows turn it on. `<A-Escape>` in the insert keymap sends Escape to the focused element with `page.send_key` on any site, so a site with no row has a way to give the page its Escape.

#### Blur on load

- Blur on load: `blur_on_load` (default off, per-site) takes the focus away from a field that the page focuses as it loads, so keys work at once. The content script blurs a field already focused at its first install, and while the window is open it blurs any field that takes the focus, before the frame enters insert mode. A field focused before the reply came has already put the frame in insert mode, and the blur's focusout takes it back to normal. The window opens at the first install and ends about 1 s later. While the page has user activation (`navigator.userActivation.isActive`, set by a key or a click), nothing is blurred, so a field the user clicks keeps the focus. That also covers input from before the content script started, as in a subframe that starts on its first focus. A command that runs in the frame (`run_in_content`) closes the window, so `gi` in a macro replay right after a load keeps its field. A page that focuses a field after the window still gets insert mode. A page shown from the back-forward cache runs no install, so its focus stays as the user left it. A later `tree_updated` opens no new window.
- Focus on load: `focus_on_load` (a CSS selector, default empty, per-site) uses the same window. Where the blur takes a field's focus, or the first install finds nothing focused, the first match takes the focus instead. A row that sets it opens the window without `blur_on_load`. A selector that does not parse and no match leave the plain blur. The shipped `maps` rows set it to the map element.

#### Media quality

- Media quality: `media_quality` (default `auto`, per-site) is a rule that takes a site player to a quality level. The default leaves players alone, so a site gets the rule only from a global value other than `auto` and `off`, or from a site value. The values are `off` (leave the site alone), `auto` (the default: leave the choice to the site and touch nothing), `max`, `min`, or a height (144, 240, 360, 480, 720, 1080, 1440, 2160 or 4320, written as a bare number in TOML, the highest level at or below it). It is an enum setting, so any other height is refused with the value list.
- A `site_rules` row sets it for its sites, and a site value beats the global one. The background (`media_quality.ts`) listens to `tabs.onUpdated`, filtered to `url` and `status` changes: a changed `url` (a hard load, or a `pushState` such as a click on a related video) and a finished load each inject a small probe (`quality_probe.js`) into every frame, and so does a second pass 1 s later that adds `about:blank` frames. A frame whose probe finds a video (a `video` element, also inside the open shadow root of a custom element) or a known site player handle (the YouTube or hls.js one) reports once per address, and again when the background refused it (the rule was off), and the background then injects `quality.js` into that frame alone. A page or frame with no video never loads `quality.js`. A probe looks again for 10 s and wakes on a media event, as the bundle's rule does. Nothing is injected when the extension is off, or when the global value is `off` or `auto` and no site row sets a level. The `media quality auto` command still resets a player to adaptive, because the user asks for it there.
- That check reads the keymap once per trigger for the tab. A settings change that turns the rule from off to on injects the open web tabs at once. Each frame reports to the background (`quality_report`, with `has_video`). The answer to a report from a frame with a video is the rule for that frame's address, so a frame never asks for it and a page with no video costs no keymap read. A frame with no video ends at once, with no poll.
- The probe wakes on the first `loadstart`, `loadedmetadata` or `play` event of a `video` element that reaches its document (a capture listener sees them), and a local check every 2 s for 10 s also looks for a video or a known player, inside the open shadow roots of custom elements too, because their events do not cross the root. Either one reports, the background loads `quality.js` into the frame, and the bundle starts the poll with the answer. A report the background refuses (the rule is off) is sent again later. A frame with a video polls its driver every 100 ms, for 10 s at most, until the player lists its levels (YouTube answers "unknown" until it plays) and sits at the rule's level.
- A video that reaches the level and holds 3 s ends the poll. After a navigation inside a site the old video may already hold, so the poll ends early only for another video (YouTube's `video_id`, the address of the hls.js source) and otherwise runs to the 10 s deadline, and a new video restarts the watch. A player with no video identity keeps the plain 3 s watch.
- A new address in a frame is a navigation for it, and a second run at the same address (the load finishing, the about:blank pass, a media command that injects the bundle) is not: in a frame that already has a rule it only reports and changes no level. A settings change reaches a frame that has a video through `tree_updated`, which the background sends to every tab after each config or `:set` change: the frame reports again and a changed rule takes effect at once, and a switch-off stops the poll.
- A navigation to a non-web page cancels the work still pending for the tab. A newer start replaces the poll of an earlier one, so repeated navigations leave one poll. A `media quality` choice that took ends the poll and stands over a finished load, until the next navigation applies the rule again. A choice made in the site's own menu while the poll runs is not seen, so the poll can undo it for up to 3 s.
- A frame that loads after the tab's last event misses the rule, and so does an `about:blank` frame until the second pass, because the first injection leaves out `matchAboutBlank` (with it, a frame under an all-off site rule left ignore mode when the tab's insert hold ended). Pages that are not http or https, and the extension switched off, start nothing.

#### Editable rules

- Editable rules: `editable_add` and `editable_remove` (per-site lists of CSS selectors) decide what counts as a text field, so insert mode follows focus. A match of `editable_remove` is not a field, one of `editable_add` is, and remove wins. With `editable_remove_unsized` on, a remove match counts only while it has no width, which is how the shipped `sheets` rows drop the parked cell editor. A selector that does not parse matches nothing. The hints bundle reads the answer through `window.desertfox_host.is_editable_`.

#### Scroll target

- Scroll target: `scroll_selector` (default empty, per-site) is one CSS selector for the element that the scroll commands scroll, for an app with an inner scroll area. `scroll_target()` tries the first match before the focus chain, so every scroll uses it, bundle scrolls through `scroll_box_` too. A match that cannot scroll on the axis, a selector that does not parse and no match leave the usual order (focused element, page, largest scroller). The pick of that last scan is kept per axis, weakly, and reused while the box is connected and still scrolls on the axis. A `focusin`, a `pointerdown`, a failed re-check and a pause of 1 s between scroll keys drop it. The page keymap reply carries it, like `escape_to_page`.

#### Hint selectors

- Hint selectors: `hint_add` and `hint_remove` (per-site, default empty lists) are lists of CSS selectors. Each `hint.run` sends `read_hint_selectors` from the hints bundle, and the background answers with the frame's values (`frame_site_values_for` against `sender.url`). Keys typed during that ask are held, so they reach hint mode. A rapid session keeps what its run read. A settings edit or another address applies from the next run, and a new page loads a new bundle anyway. `hint_add` runs as a second query for the `all`, `clickable`, `every`, `draggable` and the internal `drop` filters, skips the filter's test, and its matches count as clickable, so a pointer wrapper around one gives way to it. The filters that promise an address or a kind (`links`, `images`, `inputs` and the rest) take nothing added. `hint_remove` drops every candidate that sits in a match (`closest`, so within its own document or shadow root, never across one) for every filter but `custom`. The run resolves the selectors for the frame that starts it, and elements in its same-origin frames use those too, not their own frame's rows. The check accepts any non-empty text, because only a page can parse a selector: the bundle skips one that does not parse, shows one notice for the run and applies the rest.

## Snippets

A snippet is a user command written as page code. It is how users add behavior that DesertFox does not ship, for example helpers for one private web app. DesertFox has no plugin system: snippets are the only extension point.

A snippet file has a header with the command fields, then the code:

```js
// id: myapp.toggle_ids
// label: Toggle IDs
// intent: Show or hide record IDs in My App.
// matches: https://app.example.com/*
// name: ids
// modes: normal, visual
// param: query string main default=selection
// param: all bool short=a
window.wrappedJSObject.my_app.toggle_ids(args.query);
```

- `default=selection` reads a context source. `default=selection,search_query` is a chain: the selection, else the query of the results page. `short=` gives a bool or a valued param its flag letter (`short=a`). An enum maps values to letters: `short=tab:t,window:w`. The letter rules are the define-time checks above.
- `modes` is optional. It lists the modes where a key can run the snippet, from `normal`, `caret`, `visual` and `visual_line`. The default is `normal`. Any other name is a build-config error.
- `tools/build-config` turns the header into a normal registry entry. Snippet commands get keys, which-key rows, help, completion and prompts (through an explicit `prompt`) the same as built-in commands.
- The router checks args, then runs the code in the tab's content script with `tabs.executeScript`, with `args` defined. `window.wrappedJSObject` reaches the page's own functions.
- `matches` limits where the command runs. On other pages the router refuses with a message.
- Errors from the code are caught and shown as a message, with the snippet id.
- Snippets have no storage of their own. The code runs in the content script world, so the body's scope hides `browser` and `chrome`. That guards against accidents and is not a sandbox: `globalThis.browser` still reaches the extension APIs, and the code is the user's own.
- A snippet runs other commands with `desertfox.run(command_text)`, which takes the same text as the command line, for example `await desertfox.run("open -t https://example.com")`. It rejects when the command fails. Snippets can call snippets up to 5 levels deep.
- A relative URL in `fetch` resolves against the extension, not the page. Build the address from `location.origin`, for example `fetch(location.origin + "/api/items")`.
- Snippet ids cannot use a group name that DesertFox uses.

The config file is code, so whoever can write it can run code on pages. The file lives in the user's home directory and only the user's own tools write it, so this adds no new access. An import through the settings page shows each snippet's code, `matches` and `requires`, and stores only the snippets the user accepts. Its consent screen says a snippet can use every DesertFox permission. CSS that loads a remote address is refused on an import, a reload and a save, and the consent views show no user CSS. The import asks on every import and remembers no trust.

## Routing

1. The content script catches a trusted `keydown` in the capture phase on `window`, at `document_start`.
2. It walks the prefix tree for the current mode. On a match it cancels the key and its keypress and keyup. It also cancels a trusted keyup whose keydown this frame never saw, so a page never acts on half a press that began in another frame or in the browser's own UI. This rule runs in normal, insert and the other modes. In ignore mode, on a site that is off and with DesertFox switched off, a lone keyup passes, but a key whose keydown was cancelled still swallows its keyup.
3. It runs a `content` command itself. It sends a `background` command to the background page.
4. The background resolves context sources, checks args and runs the handler. Tab commands act on the tab that is active when they run, never on the tab that was active when the key arrived.

A Firefox shortcut enters at step 4 through `commands.onCommand`.

Every command that opens an address checks it against one allow-list, `openable_url` in `src/commands/url_build.ts`: http, https, ftp, mailto, tel, magnet, `about:blank`, `view-source:` of an http or https address, and DesertFox's own `moz-extension:` pages. Typed text, hints, the clipboard, bookmarks, quickmarks, history and session restore all pass it. Text that names an address off the list is refused, not searched. A request from a page's content script carries `from_page` in its command context, and typed text in it may not open DesertFox's own pages, nor may clipboard or register text from any sender, so a link a page offers cannot reach the grant panel of the help page. Config and stored addresses, such as `home_page` and quickmarks, may open them.

`.` (`command.repeat`) replays the last request that ran to the end. Every finished request or leaf passes `record_step` (`src/background/record_step.ts`), which stores the repeatable steps in `storage.session` when every step succeeded, with the count it had. The router calls it for background commands and for replays, before it answers. The content script calls it, through a `record_step` message, when a leaf of content commands ends, so `j` then `.` scrolls again. A held key sends its first press only. The background checks the message like any page message: content commands only, args through the one validator, at most 16 steps. A failed, cancelled, prompted or `skip_repeat` request never overwrites the slot. A private window has a slot of its own, which Firefox's own rule for private data clears: the background clears it when the last private window closes. A `.` that follows a page record waits for the write. A request that opens the command line stores nothing until the typed command runs. A hint start records itself from the `hints` bundle at the pick start, because a pick that opens the link in this tab can end the page before the leaf ends. So `.` after a hint pick shows hints again with the same action and filter. `3.` replaces the stored count and `.` keeps it. With nothing stored, `.` shows "Nothing to repeat". A pick that opens a link runs as `open.url` marked `from_hints`, which the router does not store, so `.` shows hints and does not reopen the address. A replay re-reads context sources such as the selection and the clipboard, so it uses their values at that time.

Typed text repeats too. A lazy recorder (the `text` bundle) builds one insert session from `input` events: the text typed in one field, never in a secret field (`is_secret_field`: a password input, an autocomplete of `current-password`, `new-password`, `one-time-code` or any `cc-*` token, and a field that was once one). The session ends on Escape, on focusout, on page hide and before any command is sent from the field, so the text is stored before that command. It is stored as a `text.insert` step through the same `record_step` message, led by the command that focused the field (`gi`, `]i`, `[i`, a hint pick on a field) when there was one. `.` runs the entry, then types the text through one field writer; a field focused by a click has no entry, and the replay types into the field the last Escape left, or refuses with "No text field to type into". `3.` types the text three times. The text stays in `storage.session`, in the slot of the window it was typed in.

The content script must have the keymap before the first key. At start it sends `read_keymap` to the background, which reads the compiled prefix tree from `storage.local`, trims it for the page's site rule and replies with the tree as a JSON string. The page keeps every key until the reply arrives, then replays them against the trimmed tree. A held key that the tree leaves unbound goes back to the page as a synthetic keydown on the element it was pressed on, so page scripts see it, and a keyup follows when the real one was already swallowed. Its default action (scroll, Tab focus) is lost, and so is the key when its element has left the page. A rejected ask (the background has not registered its listener yet) is retried every 100 ms, up to 30 asks in all, and then the page installs an empty tree. The next `tree_updated` asks again and heals it. An ask answered after a newer one started is dropped. The old direct storage read took 6-10 ms (median 8). The ask through the background keeps the median under 12 ms (see [firefox-behavior.md](firefox-behavior.md), "Phase 1 measurements").

## Bundles and loading

- A site mode is a named set of binds in a site row (`modes.<name> = { label, bind }`) that `mode.site <name>` lays over normal mode, and `mode.site off` ends. ### Content script size

`content.js` loads in every frame of every page, so its size has two numbers and one admission rule. The measurements behind them are in [firefox-behavior.md](firefox-behavior.md), "content.js size".

#### Admission rule

Code goes in `content.js` only if one of these holds:

- A. It runs before the first key or decides what happens to a key: the capture listeners, the matcher, modes, focus tracking, the blur-on-load window, held-key replay.
- B. It serves a key that is pressed on most pages in most frames, so a lazy load saves nothing and adds a round trip to nearly every page: scrolling.
- C. The bundles cannot load without it: the bundle host and the proxies that queue calls.
- D. It must work while the page navigates, when Firefox can leave a bundle injection unanswered until the loader times out: `xp` (`page.stop`) and `<A-,>` (`focus_page`). Both matter most on a page that is still loading, so a bundle would fail them where they are needed. A command that only needs a loaded page does not qualify.

Everything else goes in an on-demand bundle. The price of a bundle is a first use that is 11 to 16 ms slower, once per frame. A second test for code admitted under A or B: keep only the part that must be instant. A rare branch of an instant feature goes behind the bundle host.

#### Two numbers

- Guard: 22 KB (22528 bytes). A step past it fails the build and someone has to decide.
- Ceiling: 32 KB (32768 bytes). The guard never passes it, and the build fails when the guard is set above it. Passing it needs the maintainer's decision and a fresh run of the measurements in `tools/measure/` on the Firefox of that day.

The reason for 32 KB: size does not delay the first key below about 64 KB. Probe runs at 0, 4, 16, 32 and 64 KB mostly put the key listener 5 to 7 ms after the response starts. A few runs were slower (54.5, 17.3 and 11.8 ms) and did not repeat in the second pass. What size costs below 64 KB is memory, about 2.4 KB of heap per KB of script in every frame, including frames that never start DesertFox. At 32 KB that is about 8 MB for a typical session (about 100 frames) and 31 MB for a heavy one (about 400 frames). The frame counts are estimates, not measurements. The ceiling sits at half the point where timing starts to count, and it keeps the memory cost bounded.

#### When the guard may rise

1. The new code passes the admission rule, and the commit says which clause.
2. Code that fails the rule has been moved out first. A raise is the last step, not the first.
3. The raise is the smallest step of 512 bytes that fits the feature.
4. The commit that raises it names the feature that needs the room.
5. The guard never passes the ceiling.

## Interfaces

### Command line and completion

The address bar keyword `df` (the `omnibox` manifest key, `src/background/omnibox.ts`) runs a command on a page where no key reaches DesertFox. You type `df`, a space and the command text, for example `df tab.next`, and press Enter. The text takes the command line's path: the same parser, then the router, whose check is the one validator. Every router command runs. A command that needs the page, such as a scroll, refuses on a page with no content script, as it does anywhere else. Nobody can type a missing value into a prompt there, so a command with a missing value refuses with its usage, and so does text that is no command (`df rust`). Refusals reach the user as a notification when the page has no content script to draw a toast. Enter in a new tab or a background tab sets `where` on a command that has that param. A parsed line is added to the command line history, except from a private window. A line typed while DesertFox is off is refused and not added to that history. Command aliases from the config work after `df`, as on the command line. The keyword is fixed in the manifest, so it cannot change at run time. The address bar shows the hint "Type a DesertFox command" as its first row. Below it come up to nine suggestions from the command line's own completer (`onInputChanged`), built from the loaded commands, configured aliases and the setting and engine lists. A row's content is the full command text, and its description is the command name, the summary and the keys. The completer has no live source here, so no tab, bookmark or history row appears, in any window. An answer that finishes after a newer keystroke is dropped. The description is plain text (see `docs/firefox-behavior.md`).

The command line is an extension page in an iframe, so page scripts and CSS cannot reach it. It reads the stored keymap itself and asks the background for everything else. Keys typed while it opens are buffered and replayed.

The list opens with the line and shows every command, so the line is never an empty list. Each row has a name, the first sentence of the intent, the args (flag names and the subject) and the keys. In a narrow window the description shrinks first, then the args collapse to "…". The name never drops. The list shows up to 10 rows of 26px, with no scroll bar, and the host grows the frame upward to fit.

The cursor word decides what the list offers. A first word completes command names, fuzzy over the whole dotted name: `tab.` lists the tab family and `tc` finds `tab.close`. A word that starts with `-` lists the flags of that command with their descriptions, and the value after `=` lists the values of that param. Any other word lists the subject candidates. A quoted word never completes, and after `--` only the subject candidates show. One fuzzy scorer ranks every source: a name hit beats a description hit, a dot is a word break, an exact name ranks first and a tie goes to the shorter name.

Tab previews the selected row in the line and cycles. The list keeps ranking the text the user typed, and typing starts over. A single match goes in at once. Up and Down move and preview like Tab while the list is open, and stop at its ends. On a fresh line, before any typing or Tab, and with the list closed, they walk the history, so `:` Up Enter reruns the last command. Escape closes the list first and the line second. Enter runs the line as shown. The note row shows the usage of the selected row, or "no match".

Completion sources load only when the param being completed needs them: commands, open tabs, bookmarks, search engines, containers, headings, sessions and enum values.

`heading` lists the headings of the page, and `sh` opens the line with `heading ` typed. Jumping to a heading is a reading task, not a hint task, so it uses the list and the line's own typing, with no labels. The rows come in page order, each indented by its level counted from the shallowest level on the page (a page without an h1 loses no width) and tagged `h2`, `h3` in the description column. The indent is padding, so the highlight of a fuzzy match still counts the letters of the heading. Typing ranks by the one fuzzy scorer, best match first, and Enter with text and no selected row jumps to the best match. A pick puts `3 Heading text` in the line, and the leading number wins over the text. The heading goes to the top of the view, instantly, and focus, caret and address stay. A page with no heading shows the usual "no match" row. Which headings count is the rule of the hints bundle (`src/content/hints/headings.ts`): h1 to h6 and `role=heading`, by the aria level. A hidden, empty, tiny or clipped heading, and one in a closed `<details>`, gets no row. A heading in a same-origin frame is listed unless the frame is hidden or clipped, and the jump scrolls the frame too. Row text is the rendered text. The headings sit in the page, so the host script answers: the page sends `list_headings` over the port, the host runs `heading.list` in the hints bundle and sends the rows back, with no trip through the background. The bundle keeps the list as a snapshot of elements. The line drops it when it closes, except after Enter, when it drops it once the submitted command has run. A reply that arrives after the line closed is ignored. If the chosen element has left the page at Enter, `heading` refuses with "That heading is gone".

`copytabs` (`yT`) copies the open web tabs of this window as a list in the same formats, one line per tab, and `scope=all` adds the other windows, a blank line apart. It runs in the background and drops tracking parameters like `copylinks`. `copylinks` copies the web links of the page as a list, one line per link. `yL` takes the whole page and `yl` only what is in view, both as Markdown. The `scope` param (`page`, `viewport`) and the `format` param (`markdown`, `plain`, `org`) reach the rest from the command line. Only http, https, ftp and file addresses count: mailto, tel, javascript, data and links to a fragment of the same page are dropped. A link counts once, by its absolute address, in page order, and a hidden link is skipped. Its text is the visible text, else the aria-label, the title, the image alt, then the address. The list stops at 500 links. A same-origin frame and a shadow root count, a cross-origin frame does not (`copylinks` has no `--all-frames`). The toast says "Copied N links", and an empty list refuses with "No links on this page". The code sits in the hints bundle (`src/content/hints/yank_links.ts`), because the content script has no room for it.

`]i` and `[i` (`page.focus_field`) focus the next or previous form control: text fields, `contenteditable`, selects, checkboxes, radios and every kind of button, in page order. Disabled controls, hidden inputs and controls with no box are skipped, and off-screen ones count. The start is the focused control, else the last one Escape left, else the top of the view (the first control not above it). A count moves that many controls and stops on the last. Past the last or before the first the key shows a notice and leaves focus alone, and it does not wrap. The control takes focus without a scroll and is then centered if it is not fully in view, in each frame that holds it. Insert mode follows the existing `focusin` rule, so a checkbox or a button gets focus and the mode stays normal. The code is in the hints bundle (`src/content/hints/focus_fields.ts`), which reaches shadow roots and same-origin frames. The content script passes the last blurred field along, because the bundle cannot see it. `gi` keeps its own text-field rule in the content script.

`]l` and `[l` (`page.focus_link`) walk the links with an address the same way and only focus them. Enter then follows the focused link. Known limit for `]i` and `]l`: when a key focuses an element inside a same-origin frame, the next step walks only that frame, until Escape or a click leaves it.

`]h` and `[h` (`page.heading`) scroll the next or previous heading to the top of the view, instantly, as the heading search does, and leave focus, caret and address alone. Which headings count is the rule of `heading` above. The start is the heading the last `]h` or `[h` jumped to while it is still on screen, so a heading near the page end, which cannot scroll to the top, is passed and not picked again. The bundle keeps that heading as one weak reference. `zt`, `zz` and `zb` (`scroll.align`) align that heading, and its frames innermost first, when it is the newest of the heading jump, a focus change and a selection change: a focus or selection change after the jump empties the slot, so the field or selection wins. A heading that left the page, or whose frame navigated away, is skipped for the next candidate. `sh` picks fill the same slot. Otherwise the start is the view and not the caret: next is the first heading whose top is below the view top, previous the last one above it, and `.` keeps going. A count moves that many headings and stops on the last. Past the last or before the first the key shows a notice ("No next heading", "No previous heading") and does not wrap. Every jump of `]h`, `[h`, `}`, `{` and the `sh` pick leaves the target just below a fixed or sticky bar that covers the top of the view. The bundle finds the bar with one `elementFromPoint` at the top edge and walks up to the element whose `position` is fixed or sticky. A bar over a third of the view is no header and counts as no bar. The bar bottom is also the top line of the next pick, so the next press passes the block just placed. The code is in the hints bundle (`src/content/hints/headings.ts`). `]H` and `[H` go to the last and first heading of the page, take no count, set the same align slot (so `zt` works after them) and show "No headings" on a page with none. `}` and `{` (`page.heading` with `next_block` and `prev_block`) step the same way over a wider set: headings plus `p`, `pre` and `blockquote` of at least 40 characters (a blockquote counts once, not its paragraphs), minus page chrome (navigation, footer, aside, form and dialog, by tag or role, and every header that no article, aside, main, nav or section holds). They show "No next section" or "No previous section" at the ends and "No sections" on a page with none. `li`, `dt`, `figure` and tables are no stops.

Tabs and bookmarks come from the background, because it knows the window and privacy of the line's tab. A string param asks for them with `values: { from: "tabs" }` or `{ from: "bookmarks" }`. The page asks once per kind, keeps the answer for the line and ranks it with the shared scorer on every key. The row list shows "loading" in the note row until the answer lands. Each kind has its own fetch in flight, so kinds do not drop each other. A reply is dropped when the line has closed. The background answers only the frame whose line redeemed a ticket, until the tab closes or navigates or the next line redeems. The frame matters, because any frame of the page can embed its own copy of `cmdline.html`. A normal line lists only normal tabs and a private line only private tabs. Bookmarks list in both.

- A tab row reads `3: GitHub`: the number is the tab's place in its window's tab bar, counted from 1, so it stays while the user types. Picking it puts the number and title in the line. `tab` reads a leading number as that place, and the number wins over the title. Other text is a fuzzy match on title and address, and an equal tie is refused with both tabs named. The `completion_all_windows` setting (default false) lists the tabs of every window. The same number then exists once per window, so the title picks one, else the line's own window.
- The `cmdline_prompt` setting sets the text before the input. `caret` (the default) shows `> `, bold, in the `secondary` theme role. `colon` shows `:` in the `primary` role, normal weight, with a small gap. Any other value is custom text in the caret style and holds its own trailing space. Every value is 1 to 8 characters on one line.
- The `statusbar_widgets` setting (default `url, scroll, tabs`) lists the widgets on the right of the open command line, in list order. An empty list hides the area. `url` shows the host and path without the scheme, query or fragment, in the `ok` token for https and the `warn` token for http. The label is cut to 30 characters with an ellipsis, so a long path can be partly or fully hidden. The full address is the title. Other schemes get no color, and the widgets do not use the `error` token. `scroll` shows `Top`, `N%` (kept between 1 and 99, so the edges read `Top` and `Bot`, never 0% or 100%), `Bot` or `All` for the page's `scrollingElement`. `tabs` shows `[n/m]`, the tab's place in its window. Each value is a snapshot taken when the line opens and does not change while the user types. The widgets are hidden on `/` and `?` search lines, whose note row shows the match count, and on a line narrower than 30rem.
- A bookmark row shows the title and the address. With no word typed, the list shows the 20 newest. Picking one puts the address in the line. A typed word ranks by use as well as text. `bookmark` takes an exact address first, then the best fuzzy match with the same use boost, and refuses an equal tie. The answer is `{ rows, folders }`: the folder paths go once and each row holds indexes into them, newest copy first. A dim cell shows the last part of the row's newest folder, and `+N` when more folders hold the address. `bookmark` and `bookmark.remove` take `--folder=` (the `folders` list), which keeps the rows filed in that folder or any subfolder. The folder matches as filing does: an exact path, else a fuzzy match, and an equal tie or a shared path is refused. The list shows no row for text that picks no folder, and Enter refuses it. `bookmark.remove --folder=X` removes only the copies at that address inside X. `open` rows and the new tab page keep the flat list with no folder cell.
- A tab row leads with fixed-width cells, in this order: a status cell (`%` the current tab, `#` the alternate tab, which is the tab the user was on before, then small icons for pinned, audible, muted and discarded), a container mark, a favicon, then the name, the address and the keys. The icons are CSS masks, so they take the text color. The container mark is Firefox's own container icon in the container color, and a colored dot when the icon cannot load. The default container and private tabs have no mark. The favicon is sent only as a data: URL of at most 32768 characters (Firefox gives loaded, restored and discarded tab icons as data: URLs, measured on six sites in Firefox 160 with lengths from 1306 to 23682, and gives `chrome:` icons to `about:` pages, which are dropped), and a failed load shows a plain glyph. The favicons load from the data: URL, so the list opens with no network request. The tab model port sends each row's favicon in every snapshot and patch, so 100 tabs with a Reddit-size icon send about 2.4 MB per command line open. `#` is the tab the window was on before its current one, which the background tracks from `tabs.onActivated` in `storage.session`. The `contextualIdentities` lookup fails quietly when containers are off, and then no row has a mark.
- `open` and its tab variants complete from bookmarks and history (`values: { from: "open" }`, `kind: "open"`). The background answers every row, tagged `bm` or `hist`, in the group order of the `open_completion` setting (default `["bookmarks", "history"]`, a source left out is not read), and drops a history row whose address is a bookmark. History comes from a cache of the 20000 newest visited addresses that the rank Worker holds (`history_cache.ts`), minus `about:`, `moz-extension:` and `data:` addresses. A private line lists no history. With no word typed the page shows the 20 newest bookmarks and `history_completion_max` history rows (default 10), a cap that rides in the answer. A typed word ranks every row as one list, raised by use, and an equal score keeps the group order of `open_completion`. Site rows (tag `site`) follow the rules in "Ranking by use" and come last on an equal score. A dim `bm`, `hist` or `site` cell tells the rows apart. Enter on text that matches no row still opens the address or searches with the default engine. The `history` permission adds an install prompt on update.
- The `p` group is Page. `pp`, `pt` and `pw` open the clipboard here, in a new tab and in a new window, and `P` stays the one-key paste in a new tab. `pr` (`page.print`) calls `tabs.print`, which opens Firefox's print window on the active tab and returns no result. `ps` (`page.save_pdf`) calls `tabs.saveAsPDF`, which asks for a file name: a cancelled picker is silent, and a failed write shows a notice. Both run in the background, so the content script grows by nothing, and neither is repeatable: `.` skips them, but a macro records and replays them. Neither takes a tab id, so `:page.print` from another tab still acts on the active one.
- `history` lists only history (`values: { from: "history" }`, `kind: "history"`), newest first, from the same fetch as `open` and with no dedup against bookmarks. A private line gets no rows, and Enter there refuses with "no history in a private window". The answer carries the `history_list_max` cap (default 20) for an empty word, and a typed word ranks every cached row, so history older than the 20000 newest addresses is not reachable by typing. The cache fills from one `history.search` when the background starts and stays current from `onVisited`, `onTitleChanged` and `onVisitRemoved` (`allHistory` clears it). Events that arrive during the fill apply after it, in order. A page the cache has not seen enters only after a one-row `history.search` lists it, since `onVisited` also fires for hidden pages such as redirect sources. Past 50 such pages waiting, one full search refills the cache instead of the one-row checks. Firefox sends no event when only some visits of a page are deleted, so such a page can keep a too-new last visit until the background restarts. Until the fill ends, a line gets the 1000 newest entries from `history.search` and never waits, and it ranks again over the whole cache once the fill ends. The rows of `open`, `history` and the finder rank in a Worker the background starts, which holds the only copy of the cache, and the page gets the top 100 rows of each word over a port (`background/rank_service.ts`). Keys typed during a rank collapse into one rank of the newest word. Tab, Up, Down, the row keys and the finder's Enter wait up to 1 s for rows on their way, then run in order. Typed keys and keys bound to those row commands wait behind them in order. Any other key acts at once: a bound key such as Ctrl+U runs, and a browser key such as a paste or Shift with an arrow keeps its action. With no word typed, a list shows at most 100 rows, whatever its cap. The cap is 20000 because the Worker ranks off the page: a first key over that many rows takes tens of milliseconds there and blocks no key. The page no longer ranks, which at 20,000 rows took 70 to 100 ms in Node. A typed word ranks by use as well as text. A pick puts the address in the line. Enter takes an exact address first, then the best match on title and address with the same use boost, so it opens the row the list shows first, and refuses an equal tie. It has no default key and no container flag.

- Ranking by use. `open`, `history`, `bookmark` and the finder raise a text match by how much a page is used, and never lower one: score times (1 + boost), with the boost from 0 to 0.6, added before the exact-name bonus, so an exact name still leads. The background computes the boost once per line and list. Half of it comes from the visit count (by its log, full at 50 visits) and half from the last visit (it halves every 14 days). Firefox gives only those two numbers per page, not the visit list its own frecency reads. A bookmark, quickmark or closed tab takes the boost of its address's history row, so a bookmark opened daily ranks as a page visited daily, though the history row drops out as a duplicate. An open tab gets 0.3 plus its page's boost, within the same cap. A private line reads no history, so in `open` and the finder only its tabs get a boost. The `bookmark` list and its Enter read the boost on every line, so they agree. Site rows: in `open` and the finder, a typed word of at least 2 characters with no space that starts a label of a visited web host (`git` finds `github.com`, not `digital.com`) offers that host's home page, at the scheme of its newest visit, as a row of its own. Up to 3 hosts show, the most used first, and each ranks with the summed visits of all its pages. A host whose home page is already a row (a bookmark, history row, quickmark or tab) gets no site row. A private line gets none. Site rows rank by the same scorer on the host name.
- Engines ride the same fetch (`kind: "engines"`) for the first word of `search`, `--engine=` and `engine.show`. A row shows the engine name and its label. The background marks each engine with a yes or no for whether the line's tab page can fill its slots, and sends no page data. A row the page cannot fill is dimmed and reads "unavailable" in the args column; `engine.show` marks none. A word that ends in a dot (`github.`) lists every engine under that prefix, deeper ones included. The parser still reads a hidden engine, so a picked or typed one runs and the router refuses it.

### Tab sessions

`ts` saves the tabs of the current window under a name and `tS` opens a saved session from a list. `ts` opens the line with `session.save ` typed, and `tS` with `session.open `. The command line also has `session.delete <name>` and `session.rename <name> --to=<new>`, with no keys. The flag comes before the name because the name is the `main` param and runs to the end of the line.

- The sessions live in `storage.local` under `desertfox_sessions` as `{ version: 1, sessions: { [name]: { saved_at, tabs } } }`. A tab keeps its address, title, pinned and active flags and, when it has one, its container id and name. The array order is the tab bar order. Only `src/background/session_store.ts` reads and writes the key, and its writes run one after another, so two saves at once both land. A stored version other than 1 is refused and never overwritten, and an entry this version cannot read is kept as it is when another session changes. A write that fails, for example on quota, refuses with the cause and leaves the stored sessions as they were. Measured: 100 sessions of 50 tabs are about 1.3 MB, and `storage.local` took 400 such sessions (5 MB) without `unlimitedStorage`.
- A name is trimmed with its inner spaces joined to one, must not be empty, may not start with `-` or `@` when saved or renamed to (the line would read it as a flag or a slot, and the param schema refuses it), and is unique ignoring case. Saving an existing name updates it, keeps its display case and says so in the toast with both tab counts. Rename refuses a name another session has.
- `session.open` takes `into`: `window` (default) opens a new window, `tab` adds the tabs to the end of the current window, all discarded, and the current tab stays active. There is no replace, because it would close the user's tabs. In a new window the tabs are created in order, and every tab but the active one is created discarded, so it shows its saved title and loads on first visit. Firefox refuses `tabs.create` with `discarded` and `pinned` together, so a pinned background tab is created discarded and pinned right after. A container is found by its saved id, then by its name, else the tab opens in the default container and the toast counts it. An address off the open allow-list (see "Routing") or one Firefox refuses is skipped and counted in the toast. When the saved active tab is one of those, the first tab that opened loads instead. The toast of a new window shows on a tab of that window. When the window closes while the tabs open, the restore stops and says so. A new window opens on `about:blank`, and that tab is removed when the session's tabs are in. The restore reads the session once at its start, so a save of the same name while it runs changes the store and not that restore.
- The settings page exports the sessions as `desertfox-sessions.json` (the stored shape, readable sessions only) and imports one. An import adds sessions and removes none. A name that is taken, ignoring case and counting entries this version cannot read, keeps both: the import arrives as `name (2)`, then `name (3)`, and a name that already ends in a suffix gets another. An imported name goes through the same rule as save (the shared `NEW_NAME_PATTERN`, with its spaces joined), so an entry named `-x` or `@x` is skipped and listed in the answer, as is an entry that is no session. A file that is not JSON or not version 1 is refused whole. A sessions file is data and not code, so no consent screen asks first. Only extension pages may send the two messages.
- Private windows refuse every session command and the list is empty there.
- The `sessions` completion source (`values: { from: "sessions" }`, `kind: "sessions"`) lists the names newest first with the tab count and age in the description column, which the background writes. It ships the whole list once per line, like the bookmarks.
- The `folders` completion source (`values: { from: "folders" }`, `kind: "folders"`) lists every bookmark folder as a path from the root, such as `Bookmarks Toolbar / Work`, with the count of bookmarks directly inside in the description column. The background builds it from `getTree` with a walk that keeps the parent chain. Folder titles are display text that Firefox localizes, so a folder is named by its path and a command re-reads the tree and looks the path up: an exact path wins, other text is a fuzzy match, and a path that two folders share is refused, as an equal tie is for `bookmark`. `bookmark.add --folder=` files a new bookmark there, and with no folder Firefox's default applies. A page that already has a bookmark refuses with a folder, because `bookmark.move` is the way to change its folder. `bookmark.move` takes the folder as its main param and `--bookmark=` for another bookmark (empty means the current page), and moves every unmanaged bookmark at that address. `bookmark.open_folder` opens the folder's own bookmarks, not those of its subfolders, in a tab (the first one active), in background tabs or in a new window, never `here`. It opens at most 25 and one toast says when the cap cut the list or an address was skipped. It skips the addresses off the open allow-list (see "Routing"), such as `place:` queries, `javascript:` bookmarklets and `about:` pages other than `about:blank`. An address that passes that filter and still fails is skipped and counted too, and the rest open. In a tab, the tabs open in the background in folder order and then the first one becomes active, so the strip keeps the folder order. When every address fails the command refuses.

### Tab groups

Firefox native tab groups (`tabs.group`, 138, and `tabGroups`, 139, under `strict_min_version` 153). The `tg` keys and `tabgroup.*` commands (`src/commands/tab_group.ts`) act on the line's own tab and its group: `tabgroup.add [group]` (`tga` prompts, `tgA` starts an untitled group), `tabgroup.remove` (`tgd`), `tabgroup.close` (`tgD`, closes the group and all its tabs after moving focus to the nearest tab outside it, and refuses when the group holds every tab in the window), `tabgroup.name <title>` (`tgn`), `tabgroup.collapse` (`tgc`), `tabgroup.expand` (`tge`), `tabgroup.toggle` (`tgt`), `tabgroup.color <color>` (`tgl`, the nine Firefox colors as an enum) and `tabgroup.next` / `tabgroup.prev` (`tgj`, `tgk`, a count moves over that many groups). Marked tabs reach no command today, so there is no many-tab form.

- `tab_actions.ts` holds `group_tabs`, `ungroup_tabs` and `set_group` over an injected `GroupDeps`. A pinned tab and a list that spans windows are refused with a `RuntimeRefusal`, as is a target group of another window, because a group stays in one window.
- `next` and `prev` focus the first tab of the neighbor group in the window, ordered by each group's first tab, and wrap at the ends. From a tab in no group, `next` lands on the first group after it and `prev` on the last group before it. A collapsed target group is expanded first, so focus never lands in a hidden group. Skipping it would make a collapsed group unreachable by key.
- `add` names a group of the tab's window. A name that no group has starts a group with that title. A group is named by its title, and a title that is empty or shared by several groups of the window gets the id as a suffix (`Play #12`, `#12`), which is also how the completion lists it (`src/shared/group_name.ts`). A bare title that several groups share is refused and the refusal names the id form.
- The `groups` completion source (`values: { from: "groups" }`) lists the groups of the line's window from the live tab model, so it needs no fetch. A group is not private or normal by itself: it takes the privacy of its window's tabs.
- The manifest needs the `tabGroups` permission. Measured in Firefox 160: without it `browser.tabGroups` is absent (see `docs/firefox-behavior.md`).
- The model keeps `group_id` per tab (-1 for none) and a groups table. A patch carries `groups` and `groups_removed` only when some changed. A group event patches the table. A removed group also clears the `group_id` of its tabs in the same patch. A group move reads the tabs again, because its tabs change index and Firefox may report it as tab moves or not.

### Split view

Firefox split view shows two tabs side by side in one window. The extension API (`tabs.Tab.splitViewId`, Firefox 149) reads a split and moves within it, and creating or ending one is Firefox's alone (see `docs/firefox-behavior.md`, "Split view").

- `gp` (`tab.split_other`) moves focus to the other tab of the split the tab is in, and `gP` (`tab.split_swap`) swaps the two. Both refuse with "This tab is not in a split view" otherwise. The handlers sit in `src/background/tab_split.ts` over an injected `TabSplitDeps`. A swap is a `tabs.move` of the partner onto the tab's place, because there is no swap call.
- The tab model keeps `split_id` per tab (-1 for none). A tab list row of a split tab shows a split flag next to the pinned and unloaded flags.
- `tab.next`, `tab.prev` and `tab.goto` count the two tabs of a pair as two stops, so `gp` is the jump to the other pane.
- `tab.close` closes one tab, and the other tab stays and takes the focus. `tab.move` moves the pair as one unit: the move acts on the pair's first tab, the place is where the pair starts, and one step right moves the tab after the pair over it, because a move onto the partner's place would swap. Pinning one tab of a pair ends the split. A tab group command on one tab acts on both.
- A session restore loses the split. The saved tabs carry no split id, and the extension cannot create a split.

### Live tab model

- The background keeps one map of tab rows (`src/background/tab_model.ts`), built from one `tabs.query` and kept current from tab events. It stores nothing, because one query rebuilds it. Each row carries the tab's site key (`src/shared/site_key.ts`) and a favicon only when the list rule allows it. Changes batch on a 30 ms flush and go to clients on the port `desertfox_tab_model` as a snapshot, then patches (`TabRow` and the messages are in `src/shared/messages.ts`).
- A patch has `removed` ids, then `upserts`, and the upserts include every row whose index shifted. `rev` counts per port, because a port sees only tabs of its own privacy. A client that sees a gap in `rev` sends `resync` and gets a new snapshot. A `resync` and each new port first read tabs, windows and containers from Firefox again and send any difference from the model as a patch, so a stale or missed event does not last until restart. An event during those reads makes it read again, up to three times.
- After that the model keeps the rows the events built until the next `resync` or new port. A row also carries its window number (the place in `windows.getAll`, as `tab.attach` counts), whether it is the window's previous tab (the `#` tab, seeded from storage at load), and its container's name, color and icon. Only an extension page may connect. `cmdline.html` is web-accessible, so a web page can frame it, and such a port must also be the frame that redeemed its tab's command line ticket.
- Other extension pages cannot be framed and skip that check. A page with a sender tab gets that tab's privacy. A page with none (a sidebar) connects as `desertfox_tab_model:normal` or `:private` (the names are in `src/shared/tab_model_port.ts`), and a port that states nothing gets no rows. A tab moving between windows reads as removed until it attaches. The command line `tab` list reads the model: its page opens the port on the first tab read, after it redeemed its ticket, and closes it with the line.
- Row marks change only when a patch arrives.

### Hints

- Candidates come from one query per filter (all, every, clickable, buttons, inputs, links, prose, scrollable, media, images): a selector plus an optional test, such as `prose` keeping elements with a text node of their own. The search reaches open shadow roots and, through Firefox's `openOrClosedShadowRoot`, closed ones.
- An IntersectionObserver batch finds visible candidates. An `elementFromPoint` check removes covered ones.
- Labels render in a closed shadow root. All layout reads happen before any write.
#### Typed text narrows hints

- Typed text narrows hints. `/` switches hint mode from typing a label to typing text, for every filter and action. Tab does nothing in label mode. In text mode every one-character key is text and Space is part of it, so a query can hold several words. Hints keep their letter labels, but only for display.
- The matches rank by `rank.ts`: a whole first word scores 8, a whole later word 4, a first-word prefix 6, a later prefix 2 and a substring 1, summed over the query words (each must match) and divided by the log of the text length, so a short text wins a tie. Ties keep page order. The best match is active and shows with swapped colors, Tab and Shift-Tab move the active hint, Enter picks it, and a single remaining match picks at once. A key that matches nothing is dropped, as in label mode. In text mode `/` is text.
- Backspace trims the text, and on empty text it returns to label mode with every label back. The key that enters or leaves text mode never picks. The text of a hint is its visible text, else `aria-label`, `title`, the `alt` of a picture in it, or an input value, cut to 400 characters. The name list is shared with the link copy list and the next-page search (`name_candidates`), and a password value is never read. It is read once, on the first `/`. A rapid rebuild starts in label mode.
- The `text` param is only a launch filter and does not start text mode, so the labels stay typable. Tab, Shift-Tab, Enter and Space are bound in the hint keymap to the hidden command `hint.key`, so the content script holds them while the hints bundle loads. `/` has a row in the same keymap for its which-key label only, because the content script already holds every one-character key. The bundle sink takes them first once hint mode is open, so rebinding them changes nothing, and unbinding one only drops that hold.
- While hint mode is open a key line shows at the bottom right, where the mode badge sits (the badge is hidden in hint mode). It reads `/: type text · Space: turn labels` in label mode (with ` · Tab: every element` added in the narrowed target pass of a grab) and `Enter: pick · Tab: next · Backspace: labels` in text mode. The words are fixed, not read from the keymap. The `hint_key_line` setting (default on) hides it. A match that typed text made unique picks after a 300 ms grace with hint mode still open.
- The keys that arrive in the grace are dropped, so the rest of a typed word never runs as normal keys or as labels of the next round. Enter picks at once, and Escape in the grace cancels the pick.
#### Grab

- `;g` and `;G` are modifiers (like `;2`) that set the `grab` and `grab_move` actions of `hint`, so `;gb` grabs a button and `;ga` any element. The default group is `;gg` and `;Gg`, the `draggable` filter: `draggable="true"` elements, range inputs, ARIA sliders, scrollbars and separators, `aria-grabbed` and sortable handles, library handles, and any element that sets a grab, move or resize cursor where it starts or `touch-action: none` (which pointer-driven cards set). A widget with none of these signs and no role, such as a plain div thumb with the default cursor or a SortableJS item (native before its first press, or in fallback mode), is not in the group: reach it with `;ga` (the `every` filter). A link, image or plain button is in the group only when it sets `draggable`. The `links` filter is refused for both grabs by the `value_when` rule. `hint_add` and `hint_remove` apply to `draggable` per site. The hints bundle hands the pick to `grab.js` the way it hands a caret pick to `caret.js`: the element goes in a window slot and the bundle's `<bundle>.mode` handler reads it.
- `;g` picks an element, then runs `hint` again for the target (the internal `drop` filter) and drives a drag from one to the other in eight steps. A macro records it as one `hint.run`, because the target hint passes a bundle-internal `nested_` arg that skips the record.
  - The `drop` filter (`src/content/hints/drop_targets.ts`) labels where the source can likely go, because a page does not declare its drop targets: the elements that share the source's tag and a class, test id, role or `draggable` (the other cards), their parents (the columns), the siblings of each ancestor of the source (an empty column, a trash box beside the board) and the marked drop places (`ondrop`, `ondragover`, `dropzone`, `aria-dropeffect`, the react-beautiful-dnd droppable ids, `.ui-droppable`, `.ui-sortable`). A pointer widget (slider, scrollbar, separator) or a source with no kin gets every element, and so does any pass that shows fewer than two places. Tab in label mode switches the labels to every element, the one guard against a place the guess missed. A page-world hook for drop listeners is not built: React and Pragmatic drag and drop listen at the root, so a hook would say little.
- `;s` swipes: it picks from the `swipeable` filter (the `draggable` signs, scroll-snap boxes, boxes that set `touch-action: pan-x` or `pan-y` but not both (Embla with its own class names) and `.swiper`, `.splide`, `.embla`, `.glide`, `.slick-list`, `.flickity-viewport` containers) and enters grab mode with `h j k l` as flings, where `l` shows the next slide. A scroll-snap box scrolls by one view with `scrollBy` and gets no pointer events. Any other target gets a pointer fling forced onto the pointer route (a short fast drag, 60% of the box in 6 steps, with a pause of at least 30 ms that grows with the box to hold about 2 px per ms, which Splide reads as one slide, never a native drag of a link or picture). Each fling releases itself. Fast keys queue, up to two waiting, and each fling finishes and settles for 350 ms before the next starts (Splide and Swiper ignore a press during the slide change, and 350 ms fits their default speed, so a slider with a slower transition can drop a fast second press). A key past the cap is dropped. The mode stays open until Escape, whose exit drops the queue and releases anything held. The New window modifier is `;n`.
- `;G` picks an element, presses it and enters grab mode. The press lands on the slider's thumb (a child with `role=slider`, else the place `aria-valuenow` gives along the box, else the middle), so a slider that reads the pointer position does not jump on grab. `h j k l` move it one step, which starts at `grab_step_px` (3 px by default, from 3, 6, 12, 24, 48, 96 or 192) on each new grab. `[` halves the step and `]` doubles it (3 to 192 px, shown in a toast), and a range input keeps its native step. Enter drops it. Escape on a range input or a draggable element puts it back to where it began first. On the pointer route Escape releases where the element is, because a move back would set a position-reading slider to the press point. The sink of grab mode passes every key to the keymap and exists for its exit, which every way out of the mode reaches: Escape, a second command, a page that goes hidden. The exit is the one place a held drag is released.
- The source picks the route, after a press with pointerdown and mousedown, because a library such as SortableJS makes its items draggable in its own pointerdown handler. A draggable source gets DragEvents with a new `DataTransfer`. A range input gets a value plus `input` and `change`, and `change` only when the value changed. Any other source gets pointer and mouse events, with no mouse events after a cancelled pointerdown. A drag always ends with its closing events, also on a cancel. The toast says that the drag ran and nothing about what the page did, because the page's reaction cannot be read.
- The events are untrusted, so a page that checks `isTrusted` ignores the drag. A drag stays inside one frame and cannot reach another tab or app, which needs real input through the native host, not yet built.
#### Label stacking

- Space in label mode turns the stacking order of overlapping labels. Each press reads the label boxes again, groups the boxes that cover each other, and sends the top label of each group to the bottom, so a covered label comes to the top.
#### Actions

- The actions are open, background tab, new window, start caret mode, start visual mode, copy link, copy text, copy CSS selector, copy outer HTML, select in the DevTools Inspector, delete element, focus, hover, double-click and, on a video or audio element, play or pause, mute or unmute and fullscreen. Hover sends the pointer events a mouse sends on entering (over, enter and move), from the middle of the element, so a menu or preview that a script opens appears.
- `;f` is the Focus modifier: `;fl`, `;fi`, `;fb`, `;fa`, `;ft`, `;fm` and `;fI` pick as `;l`, `;i`, `;b`, `;a`, `;t`, `;m` and `;I` do and focus the element without clicking it. `;ff` focuses a frame, `;fs` a scroll box and `;fh` a heading (the `headings` filter, short flag `-T`, labels the headings `]h` counts). `;fF` is `frame.exit` and `;fe` is `page.focus_input`, as `gF` and `gi`. A heading takes focus through `tabindex=-1`, which it sets and leaves in place, so `j` starts there. `zt`, `zz` and `zb` align the focused heading, as they align a focused field.
- The next hover, Escape, a hidden tab or another pick ends it, and a pick inside the hovered element keeps it entered. A CSS `:hover` rule does not react, because synthetic events do not set it. Double-click (`;2`, `double_click`) sends the over events, then two presses (pointerdown, mousedown, pointerup, mouseup, click) with click count `detail` 1 and 2, then `dblclick`, all from the middle of the element. The clicks are dispatched events and not `click()`, because `click()` carries no count.
- The events are untrusted, so a page that checks `isTrusted` ignores them, and Firefox selects no word for them, so on a text node under the middle point the action selects that word with `caretPositionFromPoint` and a word range from `Intl.Segmenter`. A field and a box with no text get no selection change. Links, and elements inside a link, get no label in this mode, because the first click would navigate away. The `links` filter is refused by the `value_when` rule. Rapid mode keeps hints open for several picks.
- With `copy` or `copy_text` it collects the picks into one list instead: the first pick of an entry wins, a repeat adds nothing, and every pick rewrites the clipboard (and the `"a` register) with the whole list, one entry per line, so the list is right at Escape and survives a navigation. The toast counts the entries. `;Y` is `hint --copy --links --rapid` ("Copy several link URLs"). The `prompt` action (short `-L`, the `;:` modifier, so `;:l` and `;:a`) puts the address of the pick in the command line for editing.
- The `command` param (default `open`, valid only with `prompt`, a command name and flags by a pattern, so no pipe, no chain, no quote) is the text typed before the address, and the content script writes `<command> <address>` with the address single-quoted when the line would split or misread it. It is a prefix the user sees and edits, never a command string the extension runs: Enter submits the line through the one validator like any typed line.
- The line opens in the frame that ran the pick, and the `hint.run` answer stays pending until Enter or Escape, as for `;u`. An element with no address refuses with "This element has no web address", and `rapid` is ignored. The `media` filter labels visible `video` and `audio` elements, and skips the cover test because site controls lie over a player. `;m` runs `play_pause` on the pick, through the conditional `action` default for `filter=media`.
- Fullscreen shows the player box, the outermost ancestor with the size of the element, so site controls and subtitles stay, and a second pick leaves fullscreen. A hidden `<audio>` has no box and gets no hint, and a player in a cross-origin iframe is out of reach unless the hints run with `--all-frames`. The `images` filter labels an `img`, an image button and a box with a CSS background image, each rendered at least 24 px on both sides, and skips the cover test because a card lays a stretched link over its picture.
- Inline `svg` gets no label, because it has no address. `;I` opens the pick in a new tab, through the conditional `action` default for `filter=images`. Copy and open use the address of the element itself, never an ancestor's: for an image in a link, the `images` filter gives the picture and the `links` filter gives the `href`. An image address is `currentSrc`, then `src`, then a lazy `data-src` resolved against the page, and a web address wins over an inline placeholder.
- Under the `images` filter a CSS background image wins over the `href` of its own link. A `blob:` address, or a `data:` address over 8 KB, counts as no address. A short `data:` image can be copied but not opened, because Firefox refuses a `data:` URL in `tabs.create` ("Illegal URL", checked in Firefox 159), so open actions skip it and show no label for it. Under another filter, a copy of a picture or media element with no address refuses with "This element has no web address".
- `;u` opens the command line with `hint --custom `, so a typed CSS selector labels its matches. The selector is the verbatim main param of `hint`, so the line hands it over exactly as typed: a selector with spaces or double quotes (`.card a`, `a[href="/x"]`) needs no quoting, and a quote typed around it stays in the value. Flags go before it, and a selector that starts with `-` needs `--` first. The long flag `--filter custom` does not parse: an enum is set by its value as a flag.
- The `every` filter (short `e`, bound to `;a`) labels each visible element with a size, except a wrapper of one element child and no text of its own, and a link, button or label is exempt from that skip.
- The eight `;y` yank keys are plain `hint.run` bindings with a fixed action and filter, so they have no filter step and no modifier variants: `;yl` copies a link address, `;yi` the picture itself (`copy_image`, images only), `;yI` the image address, `;ym` the media address, `;yf` the frame address, `;yt` the text, `;yc` the CSS selector and `;yh` the outer HTML of any element, both with the `every` filter.
- `copy_selector` gives the shortest selector that is unique in the root of the element (the document, a shadow root or the frame's document, so it is relative to that root), preferring `#id`, then `tag`, `tag.class` or `tag:nth-of-type(n)` steps up to the nearest unique id. An id or class that looks generated (four or more digits in a row, eight or more hex digits, or a `css-`, `sc-` or `jsx-` prefix) or that needs CSS escaping is skipped.
- `copy_html` copies the whole `outerHTML` with no cap and leaves out shadow content. The toasts read `Copied selector` and `Copied HTML`. `;o` modifier (`inspect`) selects the pick in the Inspector of the tab's open DevTools, so `;oa` takes any visible element (the `every` filter, which also reaches a plain `div` or `span`), and `;ol` a link. The manifest has a required `devtools_page` (`devtools.html`), and each toolbox loads it.
- The content script sets `window.wrappedJSObject.__desertfox_pick` to the element and sends `inspect_pick`. The background relays it, by tab id, to the devtools page, which evals one constant string that deletes the property and passes the node to `inspect()`. A single eval keeps a second pick in rapid mode from being deleted between a separate select and delete. The node never travels as text, and no page data goes into an eval.
- With no toolbox open the page shows "press F12", and the pick waits 60 s in `storage.session` for the page to connect. A navigation or a closed tab drops it. The action skips the cover test, and an element in a cross-origin frame, or a pick made from a frame, is refused. After a pick, Firefox leaves focus in the Inspector, and the way back takes two keys (see firefox-behavior.md). The `;d` modifier (`download`, for images, links, media and all) saves the file at the address, so `;dI` saves a picture.
- Both send the address to the background. A copy fetches it with no Referer and with `credentials: "include"` for a tab in the default container, but with `credentials: "omit"` for a private or container tab, so it never borrows the default cookies. A picture behind a login then refuses in such a tab, and a site that blocks hotlinks refuses everywhere. The fetch times out after 20 seconds. A PNG or JPEG goes to `clipboard.setImageData` unchanged, read by its first bytes.
- Any other format, SVG included, is drawn and converted to PNG, and a GIF keeps its first frame. A copy over 20 MB is refused, and the read stops at the cap when the server sends no length. A download hands the http, https or `data:` address to `downloads.download` with the tab's private and container context and no forced file name, so the browser fetches it, streams it to disk and honors `Content-Disposition`. It needs the required `downloads` permission.
- A fetch, conversion, clipboard or download-start failure refuses with a message naming the step, and the clipboard stays as it was. The `frames` filter labels `iframe` and `frame` elements rendered at least 24 px on both sides, visible and uncovered, in the page and in same-origin frames, and never the command line frame. `;ff` focuses the pick, through the conditional `action` default for `filter=frames`, with the short flag `-E`. A subframe gets its content script on its first focus, so keys act inside it.
- A focused subframe keeps the keys and every action, and the top frame draws what does not touch the frame's own content: the command line and its list, the `/` and `?` search input, the which-key panel (the marks and registers lists too) and the toasts. The mode badge and the media panel already drew there. Hint labels, find highlights, the caret and visual marks and grab stay in the frame, because they sit on its elements. Site rules still follow the frame's own address, and which-key lists the frame's keys.
  - A bundle in the subframe asks the background to run one of its handlers in the top frame (`relay`, with the allow list in `src/shared/relay.ts`). The line drawn for a subframe gets a ticket that names it, so a command run from that line, its headings and marks lists and its page search act in the subframe. The status line shows the subframe's scroll place. When the line closes, the focus goes back to the subframe. A top frame under 120 px tall leaves the line to the subframe, and so does a top frame that does not answer.
  - The badge shows FRAME while a subframe in normal mode holds the focus. After `;ff` picks a frame, one toast in the top frame says "Keys act in this frame. gF returns to the page.", with the key bound to `frame.exit`, and only the first sentence when none is bound. Escape stays with the page and does not leave a frame.
  - A frame of another origin that takes the focus on its own is parked: the background hands the focus back to the top page through the `gF` path (`focus_page` to frame 0), so `j` scrolls the page at once and a sign-in popup frame no longer holds the keys. A frame is parked at its first focus only, when it is cross-origin to the tab's address (http and https origins), has had no click or key (`navigator.userActivation.hasBeenActive`) and does not hold a text field. The frame reports `activated` and `in_field` with `mode_changed`, a task after its focus event, because its window focus comes before its element's focus. A Tab into a frame looks the same to the frame as a focus on load, so a Tab user is parked once and the next Tab enters the frame. A frame on a field, a same-origin frame and a frame the user clicked keep the keys as before.
  - The park is a record in the tab's mode record (`parked`, and `focused_once` for every child frame that has had its first focus). The record goes with the tab and with a top page navigation, so a new page parks its frame again. A frame that navigates or reloads on its own keeps its id and stays in `focused_once`: the once-only rule lasts for the frame's lifetime, and is not keyed by the frame's address. A focus of the parked frame ends the park when it has a click or key in it, or comes after the frame was blurred: a hint that moves the focus in, or Firefox giving the focus back (which ends in frame mode, as before, and never parks a second time). A mode-change report of the same focus, which can reach the background before the blur, ends nothing. Every focus the extension moves into a frame (`;ff`, a `here` pick on a frame, a hint pick inside a frame) first marks the entry through one helper. A frame that marks names itself. The top page cannot name a frame of another site, so its mark covers the next first focus of any frame. A mark lasts 3 s and only a first focus spends it. The background asks the frame first whether it is still free (no click or key reached it), and the top page then blurs only its iframe element, so a click that lands in the hand-back or a field the page focused meanwhile is not undone. The park blurs the frame, so a popup that closes on blur closes. The field read is one task late, so a frame that focuses its field after an async step is parked as a non-field.
  - The top page hears the park in `frame_mode` (`parked`), and its `f` then labels the page and the parked frame only, through the hints collection of `hint --all-frames` limited to that frame (injection and ask by frame id). A parked frame that is gone refuses the injection, which ends the wait at once and drops the record. With no parked frame the default `frames` setting asks no frame.
  - When the focused frame hides, the focus returns to the top frame. Firefox does this itself for `display: none` and `visibility: hidden`. The top frame checks the focused frame element every 300 ms for opacity 0 and a side under 4 px, because a frame of another site cannot see its own frame element. A frame that was hidden when it got the focus and then shows, as a panel that animates open, keeps it. A frame nested in the focused frame is out of the top frame's reach.
- Hints reach into same-origin frames from the top page's own script, so those frames need no script of their own. A frame that already holds the focus when its script loads starts at once. `gF` runs `frame.exit` ("Focus top page"), which sends `focus_page` to frame 0 only, so the top page blurs its own iframe element whatever the frame's origin. It does nothing when the keys are already in the top frame.
- Open and copy of a frame use `contentDocument.URL` when readable and the `src` otherwise, and refuse with "This element has no web address" for `about:blank`, `srcdoc` and a frame with no `src`. Copying the text of a frame refuses. A frame inside a frame of another site gets no label from the top page: focus the outer frame, then press `;ff` again, or use `--all-frames`.
#### Hints across frames

- Hints across frames of other sites are opt-in: `hint --all-frames` (the `frames` param, `same_origin` by default), except for the one parked frame of a tab (see the frame mode bullets above). The frame that runs the command owns the keyboard and the typing rules. The background (`src/background/hint_frames.ts`) injects the hints bundle into every frame that takes scripts, waits up to 500 ms for each frame's count of candidates, and hands out one prefix-free label set, the top frame first. Each frame draws its own labels.
- A typed prefix and a pick go out through the background, and the owning frame runs the action. A frame that reports after 500 ms gets no labels and no later redraw. A frame outside the top viewport finds nothing visible and gets none. Escape, a hidden tab and a pick end hint mode in every frame. A same-origin or about:blank frame labels nothing itself, because its parent's walk already labels it, so each element gets one label. A focus pick or a field pick in another frame focuses that frame's window first.
- `inspect` keeps its frame refusal. `enter_media` keeps its frame refusal: no key test shows that the pin and the media keys follow focus into a frame of another site. For `caret` and `visual` the frame of the pick calls `window.focus()` and starts the mode itself, and the keys follow the focus into it (a key test shows this for a frame of another site).
- The keys typed before the labels showed go with the pick: the owner types them into the field it focuses and returns the rest, which the keyboard frame replays as normal keys. A mode that starts in the owner drops them, and one that fails to start leaves them to replay. After a hover in another frame, Escape in the keyboard frame releases the hover there, through a message to every frame of the tab. The message names the session of the pick that hovered, so a late release does not clear a newer hover.
- A copy or a `prompt` does not run in the frame of the pick: that frame answers with the text (the copy text, or the whole line for `prompt`, tracking parameters already stripped there), and the keyboard frame runs its usual copy or opens the line. So a rapid `copy` or `copy_text` keeps one list in the keyboard frame that joins the picks of every frame, the register applies, and the toast draws in the top frame.
- Text mode (`/`) ranks the hints of every frame: each frame sends the text of its candidates with its count, the background holds them in memory during the wait and returns them with the labels, and the typed relay carries the matching labels and the active one so the other frames hide the rest. With `--all-frames` the texts are a snapshot taken when the hints start, so a later page change does not show in text mode.
- A frame that ends the session before the start answer arrives is noticed by session id, so the run ends and does not enter hint mode. Known limits: keys typed during the round trip of a pick in another frame (a few milliseconds, and the same gap before a cross-frame `prompt` opens its line) run in the keyboard frame as normal keys. `copylinks` (`yL`) does not follow the flag.

### Which-key

Which-key is a first-class surface. After a prefix key, it lists each possible next key with the label of its command. Hovering a row shows the command's intent, or the `intent` of the binding when it has one. It reads both from the registry, so a new command appears without extra work.

The label of a key comes from one rule, applied to the args the binding sets (never the defaults the validator fills in):

- A binding `label` wins. It exists in the TOML table form and on the bindings of the default keymap. On a key that runs several commands, the label sits on the first command. The binding `intent` works the same way for the hover text, and modifier variants do not inherit it.
- A key that sets a container reads as the container name, and the container named `default` reads "Default container".
- Otherwise the label is the command label. A search engine with a label in `search_engines.toml` replaces it (a child engine's label is the chain of labels on its path), and a binding with no engine uses the default engine. Then each `enum` arg the binding sets to a non-default value adds its `value_labels` phrase, in param order ("Open URL in new tab"). A `bool` set to true adds the param name ("Reload hard"). Numbers, free strings and prompted params add nothing, so the keys that set them carry a hand `label` ("Scroll left", "Zoom in a lot"). A phrase that the name of any group above the key already says, as whole words and in any case, is left out: under a group named "Search in new tab", the key reads "Google", not "Google in new tab".
- A snippet key shows the `// label:` header of its snippet.

Two keys in one group may share a label only when they run the same binding (`zi` and `z+`). The unit tests check this for every group of the default keymap and of a copy of the user config, and print each group's labels.

- In the browser it draws in a closed shadow root, styled through the CSS variables in [Styles](#styles). It appears after a delay that is a setting.

### Caret and visual

Caret mode puts a text cursor in the page, so the user can move through text with vim motions. Visual mode extends a selection with the same motions. Line visual mode (`visual_line`, badge `V-LINE`) selects whole screen lines.

- Caret mode starts at the first visible text, or at a hinted element with `hint.run action=caret`, and visual mode at one with `action=visual`. In normal mode `v` starts caret mode and `V` visual mode. In caret mode `v` starts visual mode and `V` line visual mode. In visual mode `V` switches to line visual mode, and in line visual mode `v` switches to visual mode and `V` returns to caret mode. A switch between the two visual modes keeps both ends of the selection.
- Caret mode draws the caret as a one-character cell with the CSS Custom Highlight API, in the `mode_caret` color with `bg_core` text, and leaves the page selection empty. So `@selection` and Ctrl+C find no text in caret mode. The visual modes select the page text itself, in the `selection` color. A switch from caret mode to a visual mode replaces the cell with the selection, and the switch back does the reverse. A caret on an empty line has no cell. A click or a drag in the page during caret mode moves the caret there at the next key, and the next paint clears the page selection it made.
- A drag during a visual mode becomes the selection at the next key.
- A click during a visual mode ends it, as in vim. The next key runs in caret mode, with the caret at the click. DesertFox has no mouse listener, so the click shows only at that key.
- The motions are `h`, `j`, `k`, `l`, `w`, `b`, `e`, `0`, `$`, `gg` and `G`, with count prefixes. The arrow keys move like `h`, `j`, `k` and `l`. The line motions (`j`, `k`, `0`, `^`, `$`) use Firefox's `Selection.modify`, so a wrapped paragraph moves per screen line, and `j` and `k` keep their column. The other motions run on a text model of the visible page, and word motions count letters and digits of any script.
- `f`, `t`, `F` and `T` read the next key as a target character and move to its next match anywhere on the page, exact case. `t` stops before the match and `T` after it. At a line break `t` stops on the last character of the line, because no motion moves off a line break. A count picks the Nth match, and with fewer matches the caret stays. The target is any printable key or a space, even a bound one, and the key layer reads it as the `char` param of `caret.find`, the way `m` reads a mark name. So a macro records the character with the step. Escape drops the waiting key and keeps the mode, in every mode and for every command that waits for a key (`m`, `'`, `q`, `@`, `"`), and a second Escape does what Escape does. A chord cancels the wait and then runs. In visual mode the selection end moves.
- After a target, every match on the screen and about a screen around it is lit (the CSS Custom Highlight API, under names of their own so a kept `/` search stays), the match the caret stands at or next to in the stronger color. While they show, the find is live: `;` and `,` repeat it, and so do `f` and `t` (as `;`) and `F` and `T` (as `,`), so `F` reverses an `f` find and, after an `F` find, `f` goes on backward. `t` after `fx` repeats the `f` find. A live find takes no new target: Escape or another motion ends it, and the next `f`, `t`, `F` or `T` then starts a new find. A count before the key repeats that many times. Scrolling or resizing lights the new screen. They end on Escape, on any other caret, visual or search command, and on a mode change, never on an unbound key. `;` and `,` still repeat the last find after the end, without highlights. `.` does not repeat a find or its repeat, but a macro replays both, because the repeat is a step of its own.
- A line is a screen line, the unit of `j`, `k`, `0` and `$`. Line visual mode keeps the anchor and caret of visual mode, and selects from the start of the screen line of the earlier end to the end of the screen line of the later end. The motions, `/`, `?`, `*`, `#`, `n`, `N`, `o`, `y` and `s` work as in visual mode on that wider selection. `y` adds no line break at the end, because a web page has no line-wise paste.
- In visual mode, `o` swaps the ends of the selection, `y` copies it, and `s` searches it with `open.search` and the `default_engine` setting. Any command whose param defaults to `{ from: "selection" }` uses it. Escape returns to caret mode, then to normal mode.
- Visual mode has the text objects `aw`, `iw`, `as` and `is` (`visual.object`, with `object` word or sentence and `scope` around or inner) and the open keys `p` (here) and `P` (new tab) (`visual.open`, with the `where` param). An object stays on the caret's line. With a one-character selection, `aw` takes the word and the blanks after it, or the blanks before it at the end of a line. With a longer selection it grows forward by one more object, so `3aw` and `awaw` work. In line visual mode an object switches to character visual mode first, as in vim. A sentence is what `Intl.Segmenter` finds, so an abbreviation such as `Dr.` may end one. Paragraph objects are not bound, because the edges of a paragraph are fuzzy on a page. `p` and `P` collapse line breaks to spaces and send the text to `open.url`, which opens a URL or searches with the `default_engine` setting. A blank selection shows a message and stays in visual mode, and a successful open returns to caret mode.
- The motions are registry commands in the `caret`, `visual` and `visual_line` modes, so keys, which-key and help cover them like any other command.
- A caret or visual command run outside these modes, from the command line or a macro, enters a mode first or refuses:
  - `caret.move` enters caret mode, then moves.
  - `visual.object` enters visual mode, then selects the object.
  - `visual.act` and `visual.open` need a selection, which only the visual modes hold. In normal and caret mode they refuse with "No selection".
  - `caret.find` from normal mode does nothing, because the line gives it no session to move.
- Page text inside inputs and text areas belongs to insert mode, not caret mode.

### Page search

- `/` and `?` open the command line as a search line and search the page text as you type. `n` and `N` go to the next and previous match in the direction of the last search, and the last search is kept in register `/`. The code lives in `caret.js`, and `content.js` holds only `find.open`, `find.next` and `find.prev`.
- The search covers the page, open and closed shadow roots and same-origin frames. Text in fields is left out. The query is a regular expression with smartcase: a capital letter makes it exact. A typed space matches a line break. A pattern that is invalid, or that could backtrack without end, is searched as plain text instead, and the line says so.
- Enter keeps the highlights and the match, Escape clears the highlights. Both keep the search and the match as the place `n`, `N` and a new caret or visual session go on from.
- In caret mode `/` and `?` move the caret to the start of the match. Escape on the line leaves the caret where it was. Either way the mode returns to caret mode. `n` and `N` move the caret to the next and previous match.
- In visual mode `/` and `?` move the caret end to the match and keep the anchor. Escape on the line leaves the selection as it was. `n` and `N` do the same with the next and previous match: the caret end goes to the start of the match, so a match before the anchor flips the selection.
- `*` and `#` are `find.open --word` and `find.open --word --backward`. They search the word under the caret, whole and case-sensitive, with no line. In visual mode with a selection they search the selected text. In normal mode the start of the visible text stands in for the caret. They set register `/` like a typed search.
- A `MutationObserver` marks the text model stale when nodes or text change in the page, its shadow roots or its same-origin frames, ignoring the elements DesertFox adds itself. The observer also watches shadow roots and frame documents that held no text when the model was built, and a frame's `load` event counts as a change. A shadow root attached later to an element already on the page fires no event. The model lists the custom elements (a hyphen in the tag name) that had no root at build time, and `n` reads the model again once one has gained a root, open or closed. A plain element that gains a root is not seen until the next `/`. A class or style change that only shows or hides text is not seen, and a new `/` always reads the model again. The next keystroke or `n` reads the model again. The observer starts with the first search.
- A page with more than 4 million characters of text is searched only up to that point, and the line and toast say so.

### Registers

- The background owns the registers (`src/background/register_store.ts`). A value is text or a list of invocations (a macro). A normal window keeps them in `storage.local`, a private window keeps its own in `storage.session`, and the last private window to close drops them. The names are `a` to `z`, `A` to `Z` (append to the lowercase one), `"` (the last yank), `+` (the clipboard), `_` (the black hole) and `/` (the last search). `:registers` lists them.
- `"<reg>` is part of the next command, like a count, and not page state. The matcher (`src/shared/keys/matcher.ts`) keeps the typed register beside the count digits, in normal, caret, visual and visual line mode, and at the match it fills the `register` arg of each step whose command has a `register` param (the compiler flags the step). So `"ay`, `3"ayy` and `"a3yy` are the same command with a register, and `.` or a macro that replays the step keeps its register, because the register is an arg of the stored step. `:copy --register=a` does the same by hand. A user binding of `"` wins over the prefix. `"` then a key that names no register, or a key with no binding, ends the prefix and gives the key its usual meaning. Escape ends it too. Backspace drops the last key of the prefix. A change of mode drops it. In insert mode `"` is an ordinary key.
- While the name is awaited, which-key lists the stored registers instead of the tree. After the name it lists nothing until a key of a longer sequence follows.
- A yank is visual `y`, `yy` and the other `copy.url` keys, `yl` and `yL` (`copy.links`), and the hint copy actions. Each writes the system clipboard, the unnamed register, and the named one when `"<reg>` is given. `"+y` writes the clipboard and the unnamed register, and `"_y` copies nowhere and shows no toast. The registers fill even when the clipboard refuses the write, as on a plain http page. `"Ay` appends to `a`, and refuses when `a` holds a macro. No yank reads the live text of a field, so none needs `is_secret_field`. A copy of a web address drops tracking parameters first: the page address and its canonical and short links (`copy.url`), the link list (`copy.links`, before it merges equal addresses), the tab list (`copy.tabs`) and the hint `copy` of an address, but not `copy_text` or a text fallback. The `strip_tracking_params` setting lists the names, each a plain name or a `prefix*` glob, matched without case. It ships with `utm_*`, `fbclid`, `gclid` and the like, an empty list turns the stripping off everywhere. The per-site `strip_tracking` boolean (default true) chooses the sites that use the list, so a site row gives either recipe. All sites except some: leave `strip_tracking` on and add `strip_tracking = false` rows. No sites except some: set `strip_tracking = false` globally and add `strip_tracking = true` rows. A copy resolves the setting against the address of the page holding what it copies (a subframe against its own address), and `copy.tabs` against each tab's own address. The bundles ask the background (`read_strip_patterns`), which answers the list or an empty list, so content.js does not grow. `:help site_rules` shows the column like any per-site setting. The remaining query text, the fragment and the encoding stay as they were (`src/content/strip_tracking.ts`).
- `"app`, `"apt`, `"apw` and `"aP` are `open.clipboard` with a register: the text of register `a` opens as a URL, here, in a new tab or in a new window, and text that is no URL is searched. The empty register and a macro refuse.
- `<C-r><reg>` in insert mode is `register.paste`. It types the register through the shared field writer. The text joins the insert session, so `.` repeats it as typed text, and `register.paste` itself stays out of the `.` slot. It costs Firefox's Ctrl+R reload while a field has focus. Insert mode with no field leaves `<C-r>` to the browser. Pasting into a password field works. Only recording from one is blocked.

### Macros

- Recording, `@<reg>` replay, `@@` and counts are built. `q<reg>` is `macro.record`: `qa` replaces macro `a`, `qA` adds steps to it, and any other key refuses. Pressing `q` again is `macro.stop`, which stores the steps in the register as a list of invocations (the register store keeps the macro like any register value).
- The recorder (`src/background/macro_recorder.ts`) reads the same `record_step` call as `.`, so it sees every finished request and every leaf of content commands, including failed ones. A step that fails when recorded fails again on replay and stops the macro. It keeps the steps up to a failed or cancelled one, and drops `macro.record` and `macro.stop`. It skips a step that opened the command line for a value (the line sends the finished command as its own request) and the address a hint pick opens (the pick repeats it). A `hint.run` is kept from the message sent when the pick begins and not from the message of the leaf that ends later, which carries the same step.
- The recording state, `{ register, steps }`, lives in `storage.session`, and a private window has a key of its own. Every step is stored as it comes, so a background restart keeps the recording and no page buffers it. A held key sends its first press only, so a held `j` is one step.
- While a macro records, the background answers each page's `read_keymap` with the tree that has `macro.stop` where `macro.record` sat, and with the register name. Starting and stopping tell every tab to read its keymap again. The badge in every tab then adds `recording @a`, whatever the mode indicator setting says. No page code watches the key.
- Typed text is recorded as the `text.insert` step, led by the entry command, as for `.`. The same text lands in two places: in the `.` slot it stays in `storage.session`, and in a macro it is a register value in `storage.local`, so it survives a restart. A normal window and the private windows keep their own, as registers do. Text from a password field is never recorded, because the text recorder drops it before any step exists.
- Which-key under `q` and `@` lists the stored macros with their step counts when no recording runs. It reads the stored tree, so during a recording `q` is a leaf and shows no panel.
- `@<reg>` is `macro.play` (`src/background/macro_replay.ts`). Each step runs through the router as its own request, with no command line and with instant scrolls, so `.` after `@a` repeats the macro's last repeatable step. A failed step, a cancelled hint pick, the 10 s page-ready timeout or Escape stops the replay. `@a` inside a macro plays inside the same replay, up to 10 levels. A register with no macro refuses. Recording refuses while a macro plays, and the recorder keeps none of the replay's own steps, only the `@b` that started it.
- After a step that navigates or switches tabs, the replay waits for the page to be ready (`page_ready.ts`), then goes on in the active tab: in the frame `@a` came from while it stays in that tab, in the top frame of any other. A step counts as navigating when the tab reports `loading`, or when its status turned from complete to loading during the step. A same-tab hint click whose load starts after that status read does not wait: `run_in_order` does not pass the navigation on from the hints bundle, so the next step can run against the old page.
- `@@` plays the register the last play named, kept in `storage.session` (`src/background/macro_last_played.ts`, with a private key for private windows that clears with the last private window). Every play writes it before its first step, nested plays too, so `@@` after a failed `@a` plays `a` again, and after an `@a` that played `@b` it plays `b`, as in vim. `@@` with nothing played refuses. It reads the register when it runs, so it plays the content of that moment and refuses when the register is empty. `@@` inside a macro plays that macro again and ends at the depth limit. A failed pointer write does not stop the play.
- A count (`5@a`, `5@@`) is the `count` param of `macro.play`, so one replay runs the whole macro 5 times, one run after another, and stops at the first failed step or cancelled pick. The hold, Escape and the end of the replay span all the runs, and Escape stops the whole count. A count typed inside a macro stays on its own step, and `5@a` recorded in a macro is one step with its count. A nested `macro.play` step goes through the same validator as a typed one, so a recorded bad register or count fails the step. One play runs at most 10000 passes, nested plays and counts together, then stops like a failed step with a notice. Escape stops a replay only from a page that holds keys, so on a page DesertFox does not run on the pass limit is the only stop.
- Keys typed during a replay wait and run after it, in the mode the macro left, as vim's typeahead does. The background sends `replay_hold` to every tab the replay reaches, and each page holds its keys until its `replay_end` question is answered. A failure or a stop answers not ok, and the page drops the keys. A hint pick in the macro still takes its labels and Escape at once, because a new key in hint mode skips the captured-key holds. Escape anywhere in a held page sends `replay_stop`. A key typed in a tab the replay left runs there, and a background command from it waits for the end. Keys typed in a new page before its hold arrives (the time between its script start and the hold, after the page-ready wait) run at once.

### Marks and the jump list

- Local marks keep a scroll position per page. `m<a-z>` stores the offset of the box the vertical scroll keys move (the page, or an inner box that has the focus or most room), and `'<key>` or the backtick jumps there with an instant scroll, which ends a smooth scroll in flight. The page is its address without the hash. Only whole pixels are kept, and a page that fits the window stores 0. A jump stores the position it left under `'`, so `''` and the backtick twice toggle between two spots. Only mark jumps set it: `gg`, `G` and search do not, because the jump list owns that history. Marks sit in the background, in `storage.local` (`desertfox_marks`) for a normal window and in `storage.session` (`desertfox_private_marks`) for a private one, which the background clears when the last private window closes. Writes run one at a time. The store keeps at most 500 pages, drops the page written longest ago, and refuses an address over 2048 characters. A mark works in the frame that has the focus. The code sits in the `page` bundle, and the which-key rows under `m`, `'` and the backtick list the page's marks with their offsets in px. A mark remembers an offset, not the box: set with the focus in an inner box, it later scrolls whichever box the keys move. "Clear all history" in Firefox (`history.onVisitRemoved` with `allHistory`) drops every mark of the normal windows, global ones too, and the command line history, because both hold page addresses. Registers, macros, quickmarks and sessions stay, and so do the private marks. A clear of a time range sends no `allHistory`, so it drops nothing.

- `]'` and `['` (`mark.step`) scroll to the nearest mark of the page below or above the current scroll offset, by position and not by key, instantly. A global mark counts when it names this page's address, a mark of another page is skipped, and the `'` slot never counts. With no mark that way the key shows "No next mark" or "No previous mark". A count moves that many marks and stops on the last one. It does not wrap and leaves `'` alone. The lookup is the background's `mark_step` message, which stores nothing.
- Global marks (`m<A-Z>`, jumped to by `'<A-Z>` or the backtick) keep an address and an offset, in the same value as the local marks (`globals`, which a value stored before them lacks and reads as none). Only a top frame on an http or https page sets one, with the address of its tab, and a jump from a frame works: on the tab itself the top frame does the jump, so a frame never scrolls its own box. A normal and a private window keep separate sets, and a jump never uses a tab of the other kind. A jump goes to the tab on that address (the hash ignored, the container ignored): the current tab, then the newest accessed tab of the current window, then the newest of the other windows, and with none it opens the address in the current tab. The background answers the key press once the switch or the navigation has started, so the old tab does not hold keys while the user looks elsewhere. It then waits up to 10 s for the page (`src/background/page_ready.ts`) and runs `mark.jump` in the top frame of the target tab, which scrolls there. The scroll is not retried when a page builds its height late, and a refused wait (timeout, a page with no content script) shows a toast on the target tab. A page that redirected still scrolls, because the arrival jump uses the stored mark whatever address the tab ended on. `''` stays per page: the arrival scroll stores the offset the target page had under that page's `'`, and nothing is stored for the page left, so a return across tabs belongs to the jump list. Which-key lists the page's marks, then the global marks with their address (no scheme, 36 characters) and offset.

#### Jump list

- The jump list (`<C-o>` back, `<C-i>` forward, `page.jump` with a `direction` and a count that moves that many places) keeps the places that big jumps left, one list per window with a cursor, in `storage.session` (`desertfox_jumps`, and `desertfox_private_jumps` for private windows, which the background clears when the last private window closes). A closed window drops its list. An entry is an address without the hash and an offset in whole pixels.
- The list holds 100 entries, and a place within 4 px of the last one on the same page, on both axes, is the same place. Stepping back from the present first adds the place you are on, so `<C-i>` comes back to it. A new place after a step back drops the entries after the cursor. A step past either end refuses with "No older jump" or "No newer jump", moves nothing and does not wrap, and a count past the end refuses whole. A step to a place on the page you are on scrolls instantly.
- A step to another address goes to the tab on it, found as for a global mark (the same privacy, the hash and the container ignored) but only in the current window, because another window has its own list. It opens the address in the current tab when no tab of this window has it, even if another window does, and scrolls after the page is ready (`src/background/address_arrival.ts`, shared with global marks). The cursor moves before the switch, so a target that never loads leaves the cursor on it.
- A step from a child frame runs in the top frame. The keys work in normal mode only. `g;` is dropped, because a page keeps no history of edits. Two things record into it. The router records for a command that has the `jumps` flag. The key compiler marks such a step (`jump`), so a first press of a key like `gg` goes through the router, one round trip more than a plain scroll, and the keys typed right after it wait until it has run, as they do after `m`.
- A held key's repeats run in the page and record nothing, and `$` and `^` (`scroll.to` on the x axis) are no jumps. Before the command runs the router asks the top frame's `page` bundle for the scroll offset (the box the scroll keys move, through `scroll_target`), which loads `page.js` on the first use in that page, then runs the command and, only when it succeeded and was not cancelled, puts the place it left in the window's list.
- So a refused command, a bad argument and `5j` (not flagged) record nothing, and `50%G` does. The read ends before the command starts, so the command cannot move the view first, and a page that gives no answer within 1 s runs the command and records nothing. A command typed in a child frame records nothing, because an entry holds no frame.
- A global mark jump records apart from the router, in `global_mark_jump.ts`, because only the background knows where it lands: the top frame's place goes into the list of the window the jump lands in, so after a jump to a tab in another window `<C-o>` there comes back. That holds for a jump a child frame asks for too.
- The second source is the page changing in a tab, from any cause that loads a new document (a click, a typed address, a script): the `page` bundle reports its offset as the page hides, and the background records that place once the tab shows another page.
- Each event (the report, the address change, the end of the load) judges against the tab as it is then, so their order does not matter: another page records, the same page loaded to the end is a reload and records nothing, and a hash change neither records nor ends the wait. An address change inside the same document (a single-page app's `pushState`, and back or forward between its entries) hides no page, so the leave watch (`src/content/page/leave_watch.ts`) records it.
- It reads the address left and the offset on `navigate`, before the app scrolls, and records when the change commits (`currententrychange`). So a change the page cancels records nothing, a link the app intercepts records, and one that loads another document is left to the page hiding.
- It records only in the top frame of a visible tab and not within 1 s of its last record or of a jump or step that scrolled the page (the router's offset read counts as one), so a burst records once and a page that changes its address as it scrolls does not record the list's own moves. A hint pick ends that window, so a follow right after a jump records.
- The same commit ends hint mode in the frame that holds the session (not a `replaceState`, and not a change the session's own pick makes, such as a table-of-contents anchor in rapid mode), as a page hiding does. These changes record through the Navigation API, which every supported Firefox has. `replaceState` and a hash change record nothing. The background drops such a push while a step is arriving in the tab and refuses one for another site.
- A step back to an earlier address of the same app loads it again in the tab, because the step opens addresses with `tabs.update`. A redirect after the first change records nothing more. A step of the jump list that opens its address in the current tab marks the page it leaves before the navigation starts, so that page's report records nothing, however late it comes.
- The Navigation API cannot classify the leave in the page, because Firefox fires `navigate` only for navigations the page starts (see [firefox-behavior.md](firefox-behavior.md), "The Navigation API in a content script"). The `page` and `hints` bundles both arm the leave watch, which also sends the report as the page hides. A page where neither bundle loaded (only scrolled with `j`, left by a plain mouse click) has no offset to report, so a navigation from it records nothing.
- Hint picks record through that navigation, not at the start of the pick.

#### Clearing marks

- `mark.clear` takes a `scope`. `page` clears the page's marks with its `'` slot and every global mark, and `all` clears every page and every global mark. A private window clears only its own set, and quickmarks stay. It has no default key and no confirmation, so typing the command is the confirmation, and `.` never replays it. With no marks to clear it refuses, as `mark.delete` does.

### Quickmarks

- Quickmarks bind a key to an address. `M<key>` saves the address of the current tab, `go<key>` opens a quickmark in this tab and `gn<key>` in a new tab (`quickmark.add` and `quickmark.open`, with the shared `where` flag, so a user can bind a window variant). The table is `quickmarks.toml` as the base, with the entries `M` saved in `storage.local` on top: the saved entry wins for the same key, as saved settings win over the settings file. A private window saves into `storage.session` and loses those entries with its last private window, and it reads the normal entries too. A key is one letter or digit. The URL edit prompt that `go` and `gO` held moved to `ge` and `gE`. Which-key under `go` and `gn` lists the keys with their addresses. Counts do nothing.

### Mark and quickmark lists

- `:marks` and `:quickmarks` (`mark.list`, `quickmark.list`) take one picked row from the command line list and show no summary: the key, with the same text as the which-key rows (the address, no scheme and 36 characters, and for a mark the scroll offset). `:marks` lists the page's marks first, then the global ones, and leaves `'` out. Enter on a row jumps to the mark (the top frame of the line's tab runs `mark.jump`, so a global mark switches tabs as `'<A-Z>` does) or opens the quickmark in this tab. `mark.delete` and `quickmark.delete` pick a row the same way and have no default key. `quickmark.delete` lists only quickmarks saved with `M` in its own layer (`saved_quickmarks`): a private window lists and deletes only private ones, never changes `storage.local`, and refuses a normal one with where to delete it. An entry of `quickmarks.toml` is not listed and stays. When a deleted key still has an address from `quickmarks.toml`, the toast says what it opens now. The lists are the completion sources `marks`, `quickmarks` and `saved_quickmarks` (`values: { from: "marks" }`, `kind: "marks"`), which the background fills from the line tab's page and privacy.

### Finder

- `,,` opens the finder, `open.anything` (`anything`): one fuzzy list over open tabs, quickmarks, bookmarks, history, recently closed tabs, visited sites and search rows. A query ranks all of them but the search rows as one list with the one scorer, raised by use (see "Ranking by use" above), so a strong history hit leads a weak tab hit. An equal score keeps the group order tabs, quickmarks, bookmarks, history, closed tabs, sites.
- An address shows once, in the first group that holds it, so a page open in a tab shows as the tab. A closed tab wins over the history row of its address, so Enter restores the tab. The list covers every window of the line's privacy, whatever `completion_all_windows` says, and a private line lists private tabs, quickmarks and bookmarks only: no history, closed tabs or sessions.
- With no query it shows every quickmark, then the 8 most recently used tabs (the line's own tab left out, ordered by `lastAccessed` read once when the line opens), `history_completion_max` history rows and 5 closed tabs, and no bookmarks or search rows.
- Search rows come last and show only with a query: when the first word equals an engine's `keyword` (case-sensitive) and a space and more text follow, that engine's search row goes first in the whole list and is the highlighted one, and the last row always searches the default engine with the whole query by the rule of `o`. With a query typed the first row is highlighted and Enter opens it.
- The line submits a reference to the highlighted row (kind plus tab id, session id, engine name and query, `shared/anything_ref.ts`) in the `query` argument, so a repeated address or title cannot pick the wrong row. Enter switches to a tab row (and focuses its window), restores a closed-tab row, and opens any other row here.
- `<S-Enter>` is `cmdline.submit` with `where = "tab"`: the optional `where` argument of `cmdline.submit` replaces the `where` of the submitted command when that command has one (`open`, `bookmark`, `history`, `search` and the finder) and is ignored otherwise. On a tab or closed-tab row it acts as Enter. Tab rows keep their marks, so the row keys (`<C-Space>`, `<A-x>`, `<A-m>`, `<A-p>`, `<A-u>`, `<A-c>`) work on them. The page reads the rows from the tab model and one `complete_items` fetch of kind `anything`.

### Tab unload

- `tab.unload` and `tab.load` free and restore a tab's memory (default keys `tuu`, `tuh` and `tul` in the `tu` group, `tUh` and `tUl` in the `tU` group). They take a subject like `tab`, a `side` and a `count`. Unloading the current tab switches to the alternate tab first, else the next loaded tab, else the previous one. Audible tabs and the active tab of another window are refused, and a side or a count skips pinned tabs.
- The site of a tab is its site key (`src/shared/site_key.ts`): the host in lower case, with one trailing dot and one leading `www.` dropped and the port ignored, so `www.github.com` is `github.com` and `docs.github.com` is another site, because no public suffix list is used. An IP address and `localhost` are their own keys.
- All `file:` pages are one site, all `about:` pages are one site (`about:reader` and `view-source:` take the key of the page they wrap), each extension is one site, and `blob:`, `data:`, `javascript:` and unparsable addresses are one `other:` site. `--side=site` (short `S`, on `tab.close`, `tab.unload` and `tab.load`, with no default key) acts on the tab and every unpinned tab of the same site in the line's window. `tab.close` first moves focus to the nearest tab outside the site.
- A count is invalid with `site` on `tab.unload` and `tab.load`. A count prefix with `tab.close --side=site` is a known gap (it repeats the close), tracked in #187. `tab.load` reloads in place and keeps focus. Both report one line, such as "unloaded 3 tabs, skipped 1 (audible)". In the list, `<C-Space>` (`list.select --action=toggle`) marks or unmarks the highlighted tab row and moves down. The marks are tab ids kept in the line, so filtering keeps them and the actions include hidden marked tabs.
- A tab that closes drops out, `<Esc>` clears the marks before it does anything else, and they end with the line. `list.act` runs on the marked tabs, or on the highlighted row when none is marked: `<A-x>` closes (the highlight then goes to the first row below the closed rows, else above), `<A-m>` mutes and `<A-p>` pins (any off turns all on, else all off), and `<A-u>` unloads the loaded tabs, or loads all when none is loaded.
- The ids are fixed at the key press and go to the background in a `tab_rows_action` message that needs the line's ticket, skips ids that no longer name a tab and refuses ids of the other privacy. The list stays open and the rows show the change, with a name dimmed while unloaded. The line's own tab cannot unload this way, because the line lives in it. `<A-c>` (`list.act --action=reopen`) swaps the line to a `container:` prompt over the same line, ranking the containers by name with `default` as one entry.
- Enter reopens the marked tabs, or the tab that was highlighted when none is marked, in the previewed container, or in the one whose name was typed in full. `<Esc>` returns to the tab list with the marks, filter and highlight kept, and the `<Esc>` order above holds after that. The ids are read when Enter is pressed, so a tab that closed meanwhile drops out. The message carries the container's store id, because names can repeat.
- The background refuses a private line, an id of the other privacy and a store id it does not know. It leaves out the line's own tab and the tabs already in that container, skips a tab that fails to reopen while the rest go on, and opens no new tab as the active one, because hiding the line's tab ends the line. The note names what moved and what stayed, such as "reopened 2, 1 already there, line tab left out". A private line has no containers, so the prompt refuses there.

### Reload and clear

- `rc` (`page.reload --site`) clears one site and reloads. `rC` opens the line with `page.reload --all`, and Enter runs it, so no key press clears every site. `site` clears the cookies of the page's exact host in the tab's container, plus the parent-domain cookies the page sends (`cookies.getAll` for the page URL), then the whole HTTP cache, then asks the page to clear its own localStorage, sessionStorage, IndexedDB, Cache Storage and service workers through a fixed `tabs.executeScript` string (not a content-script message, because the content script is near its size limit). Firefox ignores `browsingData` `hostnames` for the cache and localStorage (see [firefox-behavior.md](firefox-behavior.md), "browsingData hostnames"), which is why the cache goes whole and the page clears itself. A database the page holds open blocks its own delete and `browsingData` `indexedDB` ignores `hostnames` too, so that delete stays pending until the reload closes the connection, and the notice names IndexedDB. `all` clears every type for every site and container with one `browsingData` call. The cache call never carries a `cookieStoreId`, which Firefox rejects for it. The clear finishes before the reload (`bypassCache`), and a failed cookie or cache clear stops the reload. A page the extension cannot script (addons.mozilla.org, an error page) or a step that stalls past 3 s still reloads, and a notice names what stayed. A `file:` or `about:` page refuses a site clear before anything is cleared. `browsingData` is an optional permission, and `cookies` stays required because the container option of `tabs.create`, `windows.create` and `downloads.download` needs it. Without `browsingData`, `rc` and `rC` refuse before they clear anything and name `:permissions.grant browsingData`. That opens a Help panel, and its Allow button asks for the permission (see [Permissions](firefox-behavior.md#permissions)). The keys work at once after the grant, and a plain reload never needs them.

### Media keys and media mode

#### Keys and actions

- The `a` group is Media. `am` mutes the tab (`tab.mute`, also `<A-m>`).
- The rest run `media` (`media.act`) with an action: `ap` play or pause, `as` and `aS` speed up and down by 0.05x (0.25x to 4x), `ar` speed back to 1x, `av` and `aV` volume up and down by 5 points, `al` and `ah` seek 5 s forward and back, `aP` picture-in-picture on or off, `af` fullscreen (`src/content/media/fullscreen.ts`): it clicks the site player's own fullscreen button when one inside the player box carries a label, title or class that names fullscreen, relying on the key press's activation.
- Otherwise it requests fullscreen on the player box (the same box as the `;F` hint, `src/content/player_box.ts`, so the site's controls stay). A fixed pixel height inside the box can then leave the video short of full screen, because Firefox allows one fullscreen request per key press (see [firefox-behavior.md](firefox-behavior.md), "Fullscreen requests per key press"). The key again leaves every nested level, since `exitFullscreen` leaves one.
- `media mute`, `media loop`, `media info`, `media quality` and `media skip` have no key. `mute` and `loop` toggle the element (the tab stays unmuted), and `info` shows the time, speed, quality and volume. `A` opens the line with `media ` typed.
- On the line the value of `speed`, `volume` and `seek` is `up`, `down`, `reset` (1x, 100% or the start), `end` (the top of the range, the media end for `seek`), `percent` (the count as a percent of the range, so `50` goes to the middle of the media and `volume` to 50%), a signed number that moves by it (`media seek -10`) or a bare number that sets it (`media speed 1.5`, `media volume 60`).
- Each action takes its own values, as `pattern_arms` keyed on `action`, so the schema refuses `media speed end`, `media volume percent` and any value on an action that takes none. `percent` is for `seek` only, and it needs its count: `media seek percent` with no count is refused as `missing <times>`. A value outside the range is set to the nearest end, not refused: speed stays within 0.25x to 4x, volume within 0 to 100 and seek within the media.
- Without a value the notice shows the current one and nothing is written. A count fills `times`, which the schema allows only with `up`, `down` or `percent`, so `3as` moves three steps in one press and `2ap` is refused. Speed is not kept: a new video starts at its own rate.

#### Quality, skip, captions and frame step

- `media quality` and `media skip` reach the site's own player, not the media element, because a video element has no quality control. `quality.js` (`src/content/quality/`) holds one driver per site player and no host list: each driver probes the page for its handle.
- The background injects the bundle into every frame, each frame reports whether it has a player and whether the player lists its levels, and the background sends the one `quality_apply` request to a single frame: one that lists levels first, then the top frame, then the lowest frame id. So a page with several embeds changes or skips one player. A frame that refuses the script does not stop the others, and the whole request ends after 1.2 s without sending anything late.
- The bundle reaches the handle through `window.wrappedJSObject`, the way `hints/inspect.ts` does, so a site CSP does not matter and no script is injected into the page. The drivers use player calls only and write no cookie or storage.
- The YouTube driver reads the `#movie_player` element's unofficial calls (`getAvailableQualityData`, `setPlaybackQualityRange`, `nextVideo`, `previousVideo`), which can break when YouTube changes them, and the player answers "unknown" until it plays, so a request before that refuses with "The player has no quality levels yet".
- The hls.js driver reads `html5player.hlsobj`, the hls.js instance of the site's player: `levels`, and `loadLevel` to read the level and `nextLevel` only to switch (`-1` is auto), because `currentLevel` reads -1 until a fragment is buffered and a write to it flushes the buffer. A pure chooser (`choose_level`) turns `max`, `min`, a height (the highest level at or below it, else the lowest) and `up` or `down` (the count in steps, from the playing level) into a level, so the drivers hold no policy.
- `auto` hands the choice back to the site. With no value the notice lists the levels, best first, with the playing one marked. The driver reads the page again for each request, so a player that YouTube replaces on in-site navigation is found again. Where no driver probes, the notice says "No quality control on this page". `skip` takes `next` (the default) or `previous`, and refuses with "No next video" where the player offers none, as the hls.js driver does.
- `media captions` (`c` in the media mode) reads `video.textTracks` first in the `media` bundle: any showing subtitle or caption track goes to `disabled`, else the default track (or the first) goes to `showing`, and `hidden` counts as off, because a site that draws its own captions keeps its tracks hidden. With no such track the background asks the quality bundle, and the YouTube driver calls the player's unofficial `toggleSubtitles`, guarded so a player without it refuses. Else the notice says "No captions".
- The hls.js driver has no captions call, since its tracks reach `textTracks`, and the site may reset a mode that the key set. `media frame up|down` (`.` and `,`) pauses the video and moves it by the count of thirtieths of a second within 0 to the duration. No API gives the frame rate, so a 24 or 60 fps video steps by a guess. Binding `c`, `,` and `.` takes them from the page in the media mode. On the command line, `media quality ` completes `max min auto up down` and the levels the player offers when the line opens.
- The line asks the background the first time it reads the list, and keeps the answer until it closes, so the list is as old as the line. Each row is named by the height the schema takes, with the site label (such as 1080p60) in the description.

#### Which media a key acts on

- A media key acts on every video or audio that plays with sound (not muted, volume above 0) in every frame, else on every one that plays, else on the largest visible video, else on the first media element. Size beats playing: a video that plays, or plays with sound, counts only when its visible area is at least a quarter of the largest visible video's area (`PLAYING_MIN_SHARE`). Otherwise the largest visible video acts, so a small ad that plays does not outrank the main video that waits to start.
- A frame with no video always counts, but a hidden or off-screen video does not. Inside one frame, an audible or playing target takes every playing element of that frame, and fullscreen and picture-in-picture take the largest. So a muted autoplay preview yields to the video the user hears. `ap` is the exception: with sound playing anywhere, it pauses every playing element on the tab, a muted preview too, so the next `ap` finds nothing playing and resumes the largest visible video.
- Picture-in-picture and fullscreen take one video: the open one (to close it), else the largest with sound, else the largest playing one (each only when big enough, as above), else the largest visible one. The code runs in the background (`src/background/media_actions.ts`), because the player often sits in a frame other than the one that took the key.
- The background lists the tab's frames with `webNavigation.getAllFrames` and asks each one for its scan by frame id (`media_scan`), each ask cut off after 300 ms, so a frame that hangs holds the key for 300 ms and no longer. The list holds every frame the tab has. It then picks the frames and asks those to apply. A frame that ran `media.js` for an earlier key still has its listener, so a later key injects nothing.
- A frame that rejects the ask or answers something else has no listener: its document is new (the first key on a page, a frame created or navigated since) or only `content.js` runs there. The background injects `media.js` into those frames by `frameId` (`runAt: document_start`, each call cut off after 300 ms) and asks only them again. A frame that times out is left alone: injecting a hung frame would add a second wait. So a slow frame that misses the 300 ms is not injected on that key and counts as one with no media. A sandbox without `allow-scripts` refuses the script (measured, see [firefox-behavior.md](firefox-behavior.md), "Media keys across frames"), and so does a privileged page. `about:blank` and `srcdoc` frames are reached. A `data:` frame is not: its player is out of reach by any call, and a page whose only video sits there refuses with "No video or audio on this page" (measured in the same section). A frame that refuses costs two quick failed calls per key, and one whose injection hangs adds up to 300 ms. If the frame list call fails or takes over 300 ms, the top frame is the one frame asked. The scans are sorted by frame id, so ties go to the lowest id whatever order `getAllFrames` lists. The `webNavigation` permission is the cost: it very likely adds an install prompt line and makes Firefox ask users again on update (not measured). It reads the frame list and nothing else, and the extension already holds `tabs` and `<all_urls>`.
- A frame finds its media again at apply time, through closed shadow roots (`openOrClosedShadowRoot`), so it never acts on elements the page replaced after the scan. A frame that refuses the script, never answers a scan within 300 ms, or answers the apply with no result (it navigated or closed) counts as one with no media, and an answer that comes after its wait is dropped, so a late frame never acts twice. Each answer returns to the request that asked, so two keys pressed fast never read each other's scans. The content script's own listener answers nothing to the `media_apply` message, so the bundle's answer is the reply, and `content.js` grows by nothing.
- A second injection into a frame adds no second listener. One info notice in the frame that took the key says the result ("Speed 1.05x", "Volume 60%", "1:25 of 3:40", "Speed 1.1x, 2 players"). Failures are refusals: "No video or audio on this page", a blocked `play()` and the picture-in-picture errors in words. A `play()` still pending after 300 ms counts as started, because a buffering source resolves it only once playback runs, and the background stops waiting for a frame's apply after 1.5 s.
- The key's activation reaches `play()` and picture-in-picture through the background round trip, except for picture-in-picture in a frame from another origin (see [firefox-behavior.md](firefox-behavior.md), "Media keys across frames").

- Known limits of the media keys: a muted preview counts as playing when nothing plays with sound. A frame scrolled out of its parent's view still reports its own visible area, which matters only when nothing plays. With several targets at different rates, each moves from its own rate and the notice shows the first. Two quick `ap` presses both see the same playing media, so the second does not toggle back. A hidden `<audio>` sound effect can be the first media element on a page with no video.

#### Media mode

- The media mode is a real mode with its own keymap section `[media]`, and the tab holds it, not one frame. `aa` (`media enter`), the hint `;M` and any element fullscreen start it, and `mode.set` cannot, so a page that is not fullscreen and a frame under an all-off rule stay out of it. Only normal mode enters it.
- A `fullscreenchange` listener on the document of each frame that runs the content script does the fullscreen part, whoever started the fullscreen: it enters media from normal when an element goes fullscreen and returns to normal when the fullscreen ends in media (`fullscreen_step` in `mode_state.ts`).
- Outside full screen the badge says MEDIA and the which-key panel of the mode opens by itself when the top frame enters or returns to it (`create_media_discovery` in `tab_media.ts` asks frame 0 once per move into the mode, never for a focus report, unless `which_key_delay_ms` is 0. The frame draws only while it is still in media mode and not in full screen, and a key that runs in a child frame in the mode closes the panel from the background, because child keys never reach the top frame).
- In full screen the badge hides and no panel opens, and a `fullscreenchange` refreshes the badge and closes the panel. `?` opens the panel by hand. Keys: `F` fullscreen, `h` `l` seek (`5l` repeats, `0` the start, `$` the end, `N%` goes to N percent), `H` `L` previous and next video, `j` `k` volume, `<` `>` `=` speed, `m` mute, Space play or pause, `p` picture-in-picture, `q` opens the line with `media quality `, `r` loop, `i` info, `c` captions, `,` and `.` the previous and next frame.
- `f`, `;` (with its modifiers) and `:` are the ones of normal mode. Every other key goes to the page, so a site player keeps its shortcuts, except `/` and `'`, which the mode cancels as normal mode does so Quick Find never starts. Normal mode's other keys (`j` scrolling) are out of reach. Digits are counts, as in normal mode. A key acts on the pinned video, else on the main video by the rule above.
- The pin is a weak reference that `;M` leaves on `window` in the frame of the video, and the background keeps the pinned frame; a video that leaves the page (a pre-roll ad swapped for the main video) hands the keys back to the main video rule. A hint (`f`, `;`) or the command line (`:`) opened from the mode returns to it, by Escape or after a pick or a command.
- The mode ends on Escape (which also calls `exitFullscreen`, and returns to item mode when the mode began there with `aa` or `;M` from item mode), when the fullscreen ends, when a field takes the focus (insert mode), and when a new page loads (`tabs.onUpdated` with `status: "loading"` and no `url`). An address change the page makes itself (`pushState` or `replaceState`, also one before the load event: YouTube's next video, autoplay) keeps the mode and drops the pin, so the keys act on the new main video. Entering the mode ends an active site mode.
- It is tab-wide: the background (`tab_media.ts`) keeps the frames that reported media in `storage.session`. The first frame to report media starts the mode in every frame of the tab that has started its content script: the background sends a media step to all of them, and each takes the step a fullscreen change takes, so a frame in ignore, insert or any mode but normal keeps its mode. `aa` sends that step to every frame itself, the frame that took the key among them, and the first report then sends none.
- A second step on could reach the key's frame after an Escape there and put it back in the mode. A frame that a step or a join reply put in the mode says so in its report (`step`). Such a report never starts a hold: with no live hold, the step came from a hold that ended before the frame took it (a site key that enters and leaves fullscreen at once, `aa` and a fast Escape), so the background sends that frame the step off.
- Without this, its report started a new hold, whose step on put every other frame back in the mode. With a live hold, the frame joins it. The frame that sees the end reports its new mode as every frame does, and the background sends the media step off to the other frames of the hold, never back to the reporter. A frame of the hold with a hint or the line open keeps it, and closing it lands in normal mode. A report of hint or command line mode keeps the hold. `aa` needs a video, not only audio.
- `;M` pins only a video (never audio) of its own frame and refuses one in a same-origin frame. `q`, `H` and `L` ask the player in the pinned frame first, while the pinned video is on the page. A fullscreen that ends in a frame while a hint or the line is open there, opened from the mode, closes it and keeps the frame in the mode, because Firefox spends the Escape on leaving fullscreen (see [firefox-behavior.md](firefox-behavior.md), "Escape in fullscreen").
- The end reaches every frame of the fullscreen, so with the player in a child frame the frames without the line report normal, in any order with the line's close. The background keeps the hold while a frame of the hold has a hint or the line open that it opened from the mode, and sends the media step back to each frame that reported normal meanwhile once that frame closes it.
- A normal report within 500 ms after such a line closed back to the mode (`LINE_CLOSE_GRACE_MS`), from a frame without the focus, is the same end and goes back to the mode too. An Escape the user presses comes from the frame with the focus, so it still ends the mode. A line frame that no longer answers a ping keeps nothing. When the mode ends in another frame, closing the line lands in normal mode. A `%` key with no count refuses with "Type a number first".
- A frame that starts its content script on its first focus after the mode began joins it, when it starts in normal mode with no editable focus. Its first keymap read says so (`join`) and the reply carries `join: "media"` (`tab_media.join`: true when the hold has frames or `aa` stepped on, a pin alone does not count). The background writes the frame into the hold in the same turn, so an end after the read sends the frame the step off, and its report finds it in the hold.
- A step off that reaches the frame before it applies the reply is lost, and the rule that a stepped report (`step`) of media mode with no live hold gets the step off sends that frame back to normal. Insert wins over media. A frame under an all-off rule never joins, and a re-ask of the keymap (config reload, macro recording) never joins.

### Help and palette

The help page is generated from `commands.json` and the live keymap: every command, its params, its keys and the keymap warnings. The palette is the command line with an empty prompt.

`:issue` (`help.issue`, no default key) opens the GitHub new-issue form prefilled with the extension and Firefox versions, the OS and the number of config warnings (`src/background/issue_report.ts`). The warning text stays out of the address, because a query string reaches GitHub when the form loads, before anyone reviews it. `--copy` puts the full report on the clipboard and opens the blank form. It holds the warnings word for word, at most 10 and 2 KB, with a count of the cut ones, and the user reads it before pasting. In every warning the config folder path becomes `<config dir>`, because the host reports it as an absolute path. A label that is no absolute path, such as `import`, is left alone. The command sends nothing itself.

The Site Rules page (`:help site_rules`, hash `#/site-rules?address=<address>`) lists the site rows that fit the invoking tab's address, from the stored keymap through `site_rules_view`. Each row shows its origin (yours or a shipped row's name), its pattern, the columns it sets as name and value pairs and the keys it changes with what each does instead. A column an earlier row already decides, or a key the page does not run (off, freed by pass, dropped by only, hidden by a shorter bind), is greyed with the reason; key changes are judged against the page tree from `normal_tree_for`. The list is for the tab's own address, and frames of other sites resolve against their own. Asked from the help page itself, or from the sidebar link, the page says where to run it.

The help page has a sidebar of page links on the left. In a window 40rem wide or less, the sidebar is a drawer and never a bar across the page. A bar that stays on top holds a menu button, which opens the drawer over the page. Escape, a picked link, a click outside the drawer or focus leaving it closes the drawer. Opening it focuses the current page's link, and Escape or a click outside returns focus to the menu button. The drawer starts closed on each render and is not stored.

### New tab page

- Answered: DesertFox owns the new tab page through `chrome_url_overrides`. `new_tab_page` is a web URL, which the page redirects to, or `desertfox` for the built-in page, and unset means the built-in page. `home_page = "desertfox"` opens the built-in page, even when `new_tab_page` redirects. After Firefox's one-time "Your new tab has changed" notice, its hidden Keep Changes button keeps access key K for that browser session, so Alt+K (previous tab) does nothing on about: pages until a restart. Accepting the notice once avoids it. Firefox still gives the address bar focus on Ctrl+T, so the user presses Esc or clicks the page before keys work. The page loads `content.js` by script tag and every other bundle on first use, as a website does: `executeScript` cannot reach extension pages, so the background asks the page to add the tag (`src/shared/page_bundle_tag.ts`). See [`src/newtab/README.md`](../src/newtab/README.md).

- Answered: the built-in new tab page shows a clock and the date. `newtab_clock` is `false` (off), `true` or `"analog"` (a 12 hour analog face with no tick marks, the default) or `"digital"` (seven-segment `HH:mm` in the DSEG7 Classic font, shipped with its OFL text and declared only on this page). `newtab_clock_format` is 12 (default, with an AM or PM suffix) or 24 and applies to the digital clock only. `newtab_date` switches the date off. The page makes no network request unless the owner turns on the weather card or the IP info line (see the next answer). The page colors are var() fallbacks over the theme roles (`bg_core`, `fg_core`, `primary`, `accent`, `bg_mantle`, `border`), so a bare install shows a dark blue page and a theme restyles it once the role variables reach the page.

- Answered: the built-in new tab page can list links, recent tabs and bookmarks. `[[newtab_links]]` in `settings.toml` takes tables of `label`, `url` (http or https only) and an optional `group`, and links with the same group share a list. The settings page writes the list into `settings.toml` through a row control in the New tab group (see Settings in the file), and Reset removes every link row there; a typed `:set` refuses it, as for `site_rules`. `newtab_recent_tabs` (open tabs, last used first) and `newtab_bookmarks` (newest added first) are off by default, with `newtab_recent_tabs_max` and `newtab_bookmarks_max` rows, 8 each. The page calls the tab and bookmark APIs itself and reuses the completion's pure readers by import, so it adds no background message. It skips private tabs and lists no tabs on a private page. Every row is a card that is one anchor (icon, title and site), so hints reach it once. Card icons come from the favicon cache only, then a letter tile: the page never loads a remote icon, and it ignores a tab's own `favIconUrl`. The cache is `favicon_cache` in `storage.local` (host to a 32x32 PNG data: URL, at most 200 hosts and 6144 characters each, about 1.3 MB at most). Firefox hands the background every tab icon as a data: image in any size or format. When a load completes or the icon changes, the background redraws it through a canvas to 32x32 (`background/favicon_saver.ts`). It makes no request, saves nothing for a private tab, and stores nothing when `favIconUrl` is not a data: image. An icon that did not change is not redrawn: the saver keeps a short key of each source icon in memory (loaded once from the stored entries) and in the entry. A host is saved at most once every 3 minutes, so a page that changes its icon all the time (an unread count) costs little. A redraw that fails is not tried again until the icon changes. "Clear all history" clears the cache and the memory, including a redraw that finishes after it. There is no icon service and no layout setting. ### External editor

`text.edit_external` (insert mode `<C-o>`, content command, `bridge: false`) opens the focused field's text in the editor that the native host's own config names. The extension sends only text, an extension for the scratch file, an insert flag and, from a private window, a private flag, so nothing executable crosses from the page or the extension. The `editor` bundle refuses a non-editable focus, a password field (`is_secret_field`) and text over 128 KiB (the host's cap), reads the field and asks the background. The background (`external_editor.ts`) calls `editor_start`, keeps `{ job, tab_id, token, frame_id, is_private, orphaned? }` per host job id in `storage.session`, and loops `editor_collect` (the host long-polls about 20 s and answers pending). The code is ready for a Manifest V3 event page, which restarts the background: a restart resumes every loop from storage. Under the persistent MV2 page only an add-on reload or update restarts it, and Firefox clears `storage.session` then, so a job does not survive one.

- One job per tab. A second press refuses with a toast, because closing a running editor needs a terminal-specific window class.
- A tab that closes or starts loading orphans its job. The editor stays open for the user and the loop keeps collecting, but the result goes to the unnamed register (with a toast when the tab still exists), because the page is gone. The same holds when the frame no longer takes the result: the page answers `true` only for the `token` it made, so a new page in the frame never takes a late result.
- Editors that show only part of their text (CodeMirror, Ace and Monaco, and the hidden textarea of CodeMirror 5, found by their container class) go through the clipboard. The page saves the clipboard text, sends the editor its own Ctrl+A and runs `execCommand("copy")`, and puts the saved text back before the editor opens. A marker left on the clipboard, or a copy that misses a drawn line, means the copy failed, and the page refuses as before. On return it copies again, and pastes the result only while the editor still holds the opened text. A read-back after the paste confirms the editor took it. Otherwise the result goes to the unnamed register. Only text is restored, and a toast says the clipboard was used.
- The result overwrites the field only while the field still holds the text it had at the press, checked again after the focus call. A plain input or textarea takes the value through the native setter and `input` and `change` events, and counts as refused when the field holds something else afterwards (it sanitized the text). A contenteditable takes one `insertText` over its whole content, so undo works. Otherwise the result goes to the unnamed register, and a toast says whether the field changed or refused the write, and says so only when the register took the text.
- A private tab's text goes to the private register, and is dropped with a toast when no private window is open any more, so private text never outlives its session. The host keeps the scratch file in `$XDG_RUNTIME_DIR/desertfox/editor` (memory-backed when it is tmpfs or ramfs) and sweeps files older than a day. With no usable runtime folder it falls back to `~/.cache/desertfox/editor`. It refuses a private edit there, and also when the runtime folder is not on tmpfs or ramfs, which the extension marks with `private: true`. A host that predates the field refuses too, and the toast tells the user to run `:native.update`. Private text then stays in memory but, like Firefox's own private-window memory, can reach swap. See `host/README.md`.
- A failed collect is tried again, up to three in a row with a pause. After that, or on the host's unknown-job refusal, the job is dropped and the toast shows the error. After the retries the toast also names the host's editor folder, `$XDG_RUNTIME_DIR/desertfox/editor` or `~/.cache/desertfox/editor` without that variable.
- `<C-o>` in insert mode takes Firefox's Open File shortcut (Ctrl+O) in a field, as normal-mode `<C-o>` does outside one, on every site, whether or not a host is installed. Without the host or its editor config the key shows the host's refusal as a toast and does nothing else. A user who wants Open File back in a field unbinds the key or binds another one.
- The extension of the scratch file comes from the `ext` param, else the per-site `editor_ext` setting (up to 10 letters or digits, empty for none). A failure of the host (an old host, no editor config) shows its error as a toast. There is no enable setting. The command line cannot start an edit: it takes the focus off the field.

## Native host (optional)

### Config host (built)

A Python 3.9 stdlib-only host in `host/` (see `host/README.md`). The extension calls it with one-shot `runtime.sendNativeMessage`, and the host exits after its reply. It has nine verbs:

- `read_config`: the raw text of every config file under `~/.config/desertfox/`, keyed by relative path. One reply carries all files, and the host returns a clear error above Firefox's 1 MB reply cap. Nothing is parsed host-side. The host reads only regular files of at most 1 MiB, following links, and opens them without blocking, so a FIFO in the folder cannot hang it. A file it will not read (not a regular file, or larger than 1 MiB) is refused with an error that names the file and the reason, so `config.reload` keeps the current config.
- `write_autoconfig`: writes the key edits to `~/.config/desertfox/autoconfig.toml`, atomically. Nothing loads that file back. Browser storage stays the only source of key edits.
- `write_config_file {kind, name?, text, base_sha256}`: writes one file of a fixed kind table, `settings` (`settings.toml`, no name), `engines` (`search_engines.d/zz-desertfox.toml`, no name), `search_keys` (`keymap.d/zz-desertfox.toml`, no name) or `theme` (`themes/<name>.toml`). The host builds the path and checks the theme name again, so a request never carries a path and no name leaves the `themes` folder. A `null` text deletes the file, only while it still has `base_sha256`. A linked file loses only its link. `write_settings {text, base_sha256}` is kind `settings` under its older name. Either replaces the file with the text the extension edited, atomically (a temporary file renamed over it), only while the file's SHA-256 is still `base_sha256` (`null`: no file). Otherwise it refuses with `changed on disk` and writes nothing. Host writers take a lock file in the folder, so two writes never pass the check against one base. Just before the rename it checks the digest again and that the link still points at the same file, and it hard-links the old file aside. After the rename it compares that old file's bytes with the base again, and an edit an editor saved into it in the meantime goes back and refuses with `changed on disk`. An old file it cannot read goes back too and refuses with `could not be read back`. An old file whose size differs from the base is an edit found without reading it. A filesystem without hard links refuses every write, because a copy could not see an edit saved after it. It follows a symlink so the link stays, keeps the target's mode, refuses a file that is not UTF-8, and never creates the config folder. The request names no path. See Settings in the file.
- `self_update {version, sha256}`: replaces the installed host with GitHub release `v<version>`. The request carries the version and the SHA-256 of each script, which the extension takes from its signed build (`host_sha256.json`). It carries no URL, channel or path. The host accepts only `x.y.z` or `x.y.z.N`, builds every URL from this repo's releases, fetches over HTTPS only with size and time caps, and refuses a downgrade. Each file must match both the release `.sha256` and the extension's hash, so a replaced release asset fails. It then writes the five paths `install.sh` writes, each as `<path>.new` renamed over the old file: the bridge, the `desertfox` command line, both manifests, and the config host last. A development host (`release_version` `dev`) never updates itself.
- `editor_start {text, ext?, insert?, private?}` and `editor_collect {job}`: run the user's editor on a scratch file and return the edited text. The command comes from `editor.toml` in the config folder, which only the host reads and `read_config` skips, so the request carries no argv. `editor_start` returns a job id and `editor_collect` long-polls for 20 s, so no call outlives a native-message timeout. See `host/README.md`.
- `open_firefox_page {page}`: opens one Firefox page (`about:preferences`, `about:config` and others) that no extension API can open. `page` is a key of a fixed table in the host, never a URL. The host runs its parent Firefox as a remote client with that profile and URL, argv only, and kills it after 10 s. `browser.open_firefox_page` (`:firefox`, the `,f` keys, `bridge: false`) calls it. Without the host, the command copies the address and the toast says to press Ctrl+L and paste. The first such toast also names `:native.install`. See `host/README.md`.
- `list_fonts`: the installed font family names, from one `fc-list` run (argv only, 5 s timeout), deduplicated, sorted, cut to 2000, with every name that `parse_font_family` refuses dropped. The extension uses them alone when the host answers, and falls back to a canvas probe otherwise (see Styles). See `host/README.md`.

Every reply carries `release_version`, which `just release` stamps into the shipped hosts. The bridge sends it in its `ready` frame. Apart from `self_update` and the editor scratch files, the host writes only these files in the config folder: `autoconfig.toml` (a copy of the key edits), `settings.toml`, `themes/<name>.toml`, `search_engines.d/zz-desertfox.toml`, `keymap.d/zz-desertfox.toml` and the empty lock file `.settings.lock`. `nativeMessaging` is an optional permission, requested from a button on the Help page that `:native.install` opens, the same panel `:permissions.grant nativeMessaging` opens (Firefox grants it only from a click). The page also shows a one-line command that runs `host/install.sh`, with a Copy button. For a release build it downloads `install.sh` of its own version from the GitHub release to a temp file, checks it against `install_sh` in the signed build's `host_sha256.json`, then runs it with the hash of each script from the same file, and `install.sh` refuses a script that does not match. A development install, and a build with no `host_sha256.json`, gets `curl ... | sh` from `main` with no checksum, and the page warns that it is for development only. `--channel main` forces main. `just release` uploads both hosts, the `desertfox` command line, their checksums and the script. `config.reload` reads the files through it, and each change to the key edits writes `autoconfig.toml` (see [Delivery](#delivery)).

### Host updates (built)

Firefox updates the extension. DesertFox then updates its own native hosts and the `desertfox` command line to match, so a user installs the host once with `:native.install`.

- Channels. A stable extension (`x.y.z`) gets the stable release of its own version from AMO and the matching GitHub release. A beta extension (`x.y.z.N`, a self-hosted signed build; AMO refuses letters in a version, so the number counts up from the last stable release and 0.1.23.2 ranks above 0.1.23 and below 0.1.24) gets the GitHub prerelease of its own version. A development install (`installType` `development`) has no release and never updates its host, and a host with `release_version` `dev` refuses to update too. The channel is read from the fourth number, in `src/shared/host_version.ts`.
- When it checks. The extension reads `release_version` from the bridge's `ready` frame, from every reply of the config host, ok or error, and from one `read_config` request at start (only with the `nativeMessaging` permission), so a host is checked even with `bridge` off. A missing field, as in a host from before the updater, counts as older. The extension compares the numeric `x.y.z` parts, and a beta sorts after the release it counts from and before the next one. It sends nothing when the host is equal or newer, so with two Firefox profiles the newest host wins and none downgrades another.
- Consent. The `host_auto_update` setting is off by default. The "Install and keep the host updated" button on the `:native.install` page saves it as a browser edit and installs nothing itself, because Firefox cannot run the install command. With consent, an older host updates on connect and a toast says so. Without it, the extension shows one line per version that names `:native.update`, which runs the same update on demand and ignores consent and the limits below.
- Trust anchor. The first install checks `install.sh` and each script against the signed build only (see above). The update has two checks. The release carries a `.sha256` per script, and the signed extension build carries the hashes of the same stamped scripts in `host_sha256.json` (`just release_stamp` writes it and the build copies it into `dist/`). The host accepts a file only when it matches both, so a swapped release asset fails against the signed build, and a broken signed build fails against the release. The request holds the version and those hashes and no URL, so a page or a bridge client cannot point the host elsewhere. A build with no hashes sends no update. The update runs only in the config host, and there is no socket verb for it.
- Lock. The updater and `host/install.sh` take a non-blocking `flock` on `update.lock` in the data folder (`~/.local/share/desertfox/`), which both already write to, so both compute one path whatever the environment. They hold it from the first staged `.new` file to the last rename. The second caller fails with `update running`, so two writers never stage the same file.
- Reconnect. After an ok reply the extension closes the bridge port and connects again. The running bridge still holds the old code in memory, and it exits when its stdin closes. The new bridge waits up to 3 s for the old one to release `bridge.lock`. If it loses that race, it exits and the usual backoff connects again. The bridge never replaces its own file.
- Retry and toasts. The extension tries a version once per 24 hours (the time of the last attempt lives in `storage.local`, written before the call). A failure shows one toast per version, "Host update failed: <reason>. Run the command from :native.install", and is logged each time. A checksum mismatch blocks that version until a new extension build, which carries other hashes. Each success shows one toast. While the host is older, an error from it reads `host_outdated` and says whether it is updating or the update failed.
- Bootstrap. A host from before the updater has no `release_version` and no `self_update` verb. The extension treats it as any outdated host: the update fails with the host's "unknown cmd" refusal, and the failure toast names the manual `:native.install`. `INSTALL_HINT` stays for `host_missing` and `no_permission`, because a missing host cannot update itself.

### Bridge host

One long-lived host, `desertfox_bridge` (`host/desertfox-bridge`), serves everything on the desktop that needs to talk to DesertFox. It is generic: it assumes no particular shell, bar or window manager. It sits beside the one-shot config host and does not change it.

The same script serves DesertBird, the Thunderbird extension, through a second manifest, `desertbird_bridge`, which allows only `desertbird@uhs-robert`. A fourth manifest, `desertbird_host`, starts the config host for the same extension id, so DesertBird reaches `editor_start` and `editor_collect`. The installer and the updater write both beside the other two in `~/.mozilla/native-messaging-hosts`. The app passes the host the manifest path and the extension id, and the host takes its app from them. A manifest name or id it does not know, or a pair that names two different apps, stops the host before it takes a lock, so a guess can never put one app's host on the other's socket. A host run with no arguments is Firefox's, as before. Each app has its own runtime folder, `$XDG_RUNTIME_DIR/desertfox/` for Firefox and `$XDG_RUNTIME_DIR/desertbird/` for Thunderbird, each with its own lock, socket, state file and kept theme. So both hosts run at once and never contest one lock, and the second-host rule below holds per folder. The rest of this section names the Firefox folder. The tab verbs, the tab events and the tab caches belong to Firefox alone: the Thunderbird socket refuses the tab verbs with `tab verbs need --app firefox`, and a Thunderbird host drops tab events and never prunes or deletes the caches. A Thunderbird host also refuses a `run` with a `tab_id` the same way, and refuses `theme` with `theme needs --app firefox` and replays no kept theme, because DesertBird takes no theme. The mail reads belong to Thunderbird alone, and the Firefox socket refuses them with `mail reads need --app thunderbird`:

- `folders {}`, `messages {folder, limit?, unread_only?}`, `message {id}` and `attachments {id}`. The host checks the fields (`folder` is the opaque folder id from `folders`, 1 to 1024 characters; `limit` is 1 to 200; `id` is a whole number), counts each read against the rate limit, sends only the checked fields, and passes the add-on's reply on as it came. The add-on checks its share settings, which are off by default, and builds each reply, so the host checks no setting. A reply frame over 1 MiB is skipped unread, so that read fails as unanswered. A body arrives marked `untrusted: true`. The command line that prints it wraps it in a nonce envelope (see below).
- The mail writes, `draft {to, cc?, subject, body, from?, reply_to_id?}` and `act {action, ids, folder?}`, belong to Thunderbird alone too. The Firefox socket refuses them with `mail writes need --app thunderbird`. The host checks the shapes: `to` holds 1 to 10 addresses (0 to 10 with `reply_to_id`), `cc` at most 10, an address at most 320 characters, the subject at most 998, neither with a control character, and the body at most 64 KiB of UTF-8 with no control character but tab, newline and carriage return, so its JSON stays under the request cap. `action` is `archive`, `trash` or `move`, `ids` holds 1 to 50 different whole numbers, and only `move` takes a `folder`, which it needs. The host sends only the checked fields, counts each write against the rate limit, and cuts the reply to `ok`, `message` and an act's `count`, so no draft id or mail data leaves through it. The add-on checks its settings (`bridge_allow_drafts`, `bridge_allow_actions`, and `bridge_share_folders` for a move), the address shapes and the identity, never sends, and shows a person a y or n prompt for each act. The add-on gives up saving a draft after 30 s with `timed out`, so a draft waits 40 s. A person answers an act, so an act waits 70 s, past the add-on's 30 s prompt timeout, and the host holds one act at a time: a second one gets `busy` and never reaches the add-on. The slot frees on the reply, the timeout, the port closing and the client closing its connection, which the host checks every 0.5 s while it waits. A client that closes only its write side still gets its answer. The add-on has no cancel, so a y on the prompt still moves the messages after the client has left, and nobody hears the result. The other verbs keep working while an act waits.

The extension opens one `connectNative` port to it when the `bridge` setting is on and the optional `nativeMessaging` permission is granted. With either missing there is no port and no socket. A host that is missing or exits before its first message leaves nothing changed, and the extension reconnects with a growing pause (1 s up to 60 s). The host says `ready` once it holds its lock, and the extension trusts the port only after that. Firefox keeps the background awake while the port is open, which also helps a later move to MV3.

Two things come out of the host, both under `$XDG_RUNTIME_DIR/desertfox/` (a folder with mode 0700).

- `state.json`, written for a bar to read: the mode, the host's pid and start time, and `private`. The host writes it atomically (a temp file renamed over it). A reader treats a dead or reused pid as no state. A private window leaves only its mode and `private: true`: no window or tab id, no URL, no title.
- `bridge.sock`, a Unix socket with mode 0600, because a desktop program cannot open a channel into the extension. The first host to start owns the socket and the state file through a lock on `bridge.lock`. A second host waits 3 s for the lock, then exits with an error, so two Firefox profiles share one bridge and the second one gets none. The socket takes one JSON object per line and answers each with one line. A request over 192 KiB is refused (the size lets a 64 KiB draft body through as JSON), an idle connection closes after 5 s, and at most 16 connections are open at once. A connection from another user is closed.

The built verbs are `ping`, `state` (the latest snapshot, the same shape as the file), `list`, `run` and `theme`. Each verb has a fixed name, so there is never a shell or eval verb:

- `list`: the commands the bridge allows, as registry entries with their params, for completion.
- `run`: one command line from outside. The host forwards it to the extension, which refuses it unless the command's `bridge` field is true. A hard-coded never-list wins over the field: the `config`, `settings`, `session`, `copy`, `register`, `debug`, `native` and `permissions` groups, `page.reload` (it can clear cookies and site data), `page.save_pdf`, the hint picker, `visual.act`, `open.clipboard`, `command.repeat`, `macro.play`, every snippet, and an address that is not http or https. A handler refusal comes back as fixed text (`<id> failed`), because it can hold a tab title. An `open.url` address is resolved the way the handler resolves it (trim, scheme, bare host, search) and refused unless the result is http or https, so `localhost:3000` opens and `vscode://x` does not. A command that passes goes through the one validator (`check_args`) and then the router, with no command line to open, so a missing value is a refusal. The reply carries success or failure and a message, never data. The host cuts a run reply to those two fields.
- The tab verbs, all behind the separate `bridge_share_tabs` setting (off by default, and it needs `bridge`), because a tab list leaks browsing. With it off, each answers `tab sharing is off, set bridge_share_tabs to true`, and so does a `run` that names a tab. The extension sees every id and checks it itself.
  - `tabs {current?}`: the tabs of normal windows, each with `tab_id`, `window_id`, `title`, `url`, `active`, `audible`, `discarded`, `last_accessed`, `pinned`, `hidden`, `fav_icon_url` and, from the host's caches, `fav_icon_path`, `thumbnail` and `thumbnail_at`. A tab of a private window or a popup never appears. With `current: true` the list holds only the active tab of the last focused window, for a capture tool, and is empty when that window is private or a popup.
  - Icons: Firefox gives tab icons of web pages as data URLs (measured on loaded, restored and discarded tabs) and `chrome:` icons to `about:` pages. A list of the data URLs would outgrow one native message. So `fav_icon_url` is blank for a data URL icon, and the row carries the SHA-256 of the data URL instead. The host keeps that key to itself. For a key it has no file for, it asks the extension for that tab's icon (a `favicon` request the socket does not offer), within 3 s for the whole list, and saves the image in `$XDG_CACHE_HOME/desertfox/bridge-favicons/` (mode 0700) under the key with the suffix of its type. `fav_icon_path` names the file, or is empty. Tabs with the same icon share one file.
  - `activate {tab_id, preface?}`: selects the tab and focuses its window. The optional `preface` (letters and digits, 32 at most) goes in front of the window title, so a program that raises the window itself can find it by title. DesertFox does not raise windows through a window manager, because it assumes none. It clears itself after 10 s, and `clear_preface {window_id, preface?}` clears it early, but only when the preface is still the one DesertFox set. Activations run one after another, so two at once cannot swap each other's title. The reply is `window_id`, `focused` and `preface_set`.
  - `close {tab_id}`.
  - `capture {tab_ids?}`: renders each tab (all loaded ones without ids), one at a time, and the host saves a JPEG per address in `$XDG_CACHE_HOME/desertfox/bridge-thumbs/` (mode 0700), pruned after 7 days once no open tab has that address. The host asks only for ids in a fresh tab list from the extension, so it never saves the image of a tab the extension did not list as a normal one.
  - A tab id that is stale, private, in a popup or not a whole number gets the same refusal, `no such tab` (`no such window` for `clear_preface`), so an id cannot be used to probe for private tabs. Failures carry fixed text and never a title.
  - `run` takes an optional `tab_id` and runs the command in that tab, where a run otherwise uses the active tab of the focused window. Every rule of a plain run applies first, with the same refusal text, and the tab is looked up only after they pass.
- `theme {theme}`: the desktop tells DesertFox which theme it uses, and DesertFox maps the name onto its own roles. It changes the theme and nothing else: no other setting has a verb. The host checks the shape (a letter or digit first, then letters, digits, `_` and `-`, 1 to 64 characters), keeps the last name in `theme.json` beside the state file (it is the one file that outlives a host, and a host that dies mid-write leaves the old file) and forwards it. It forwards the kept name again right after each `ready`, in the same step that opens the link, so a push never overtakes the replay and a connection gets the name once. The extension accepts only a built-in theme name (`desktop` is not one), logs and ignores any other name, and keeps the current theme. The host deletes the kept name when the extension refuses it, in a push and in the replay, so a typo is refused once. While no host runs (the browser is closed), `desertfox theme` writes `theme.json` itself, atomically and under the `bridge.lock` flock, and exits 0, so the next host replays it. It needs `bridge` on to take effect, because no host starts otherwise. It stores the name in `storage.local` (key `desertfox_desktop_theme`: per machine, not Firefox Sync, so a browser restart keeps it) and publishes again only while `theme` is `desktop`. The name stays whether the bridge is later turned off or not. `light` or `dark` and `light_intensity` are not part of the push.
- `subscribe`: turns the connection into a one-way event stream. The host answers `{"ok": true}`, then the current mode if it has one, then one line per event, each with a `seq` that rises by one, so a reader can tell it missed one. A reader that also wants to send requests opens a second connection. The events:
  - `mode`: the same fields as the state file, so a private window gives only its mode and `private: true`. The host makes it from the mode it gets, and it needs no `bridge_share_tabs`.
  - `tab_activated {tab_id, window_id}`, `tab_updated {tab_id, window_id, title, url}`, `tab_audible {tab_id, window_id, audible, title, url}` and `tab_removed {tab_id}`: only while `bridge_share_tabs` is on, and only for a tab of a normal window. Title and address changes of a tab within 250 ms go out as one `tab_updated` with the values at the end, because some pages change their title every second. `tab_audible` and `tab_removed` go out at once. A closed tab can no longer be looked up, so the extension sends `tab_removed` only for a tab an earlier event named, and the host passes it only to a reader that an earlier event told about that tab. Each reader remembers its last 1024 tabs. The host cuts a title to 512 characters and an address to 2048.
  - `tabs_off`: `bridge_share_tabs` is off. The extension sends it when the setting goes off and again each time the port comes up with the setting off, so a host that missed it still hears it. A reader forgets its tabs, and no tab event follows until the setting is on again. A tab reply whose request came before the setting went off goes out as the sharing-off refusal.

  At most 4 readers stream at once, inside the 16 connections, so stuck readers cannot starve the command line. A fifth gets `too many subscribers`. Each reader has its own queue of 64 events and its own writer. A reader that falls 64 events behind, or does not take a write within 2 s, is dropped and can reconnect, so a slow reader never holds up the port, the requests or another reader. A stream is not closed for being idle. `subscribe` counts once against the rate limit and its events do not count. The extension sends tab events whether or not anyone reads, and the host drops them when nobody does.

A `run` targets the active tab of the last focused normal window, not the window Firefox thinks is current. It never toasts and never touches `.` or the macro recorder, so a script cannot change what the user repeats. A run that opens an address is refused when that window is private.

The host limits all connections together to 10 `run`, `list`, tab and mail requests per second (`theme` is not limited), because the CLI opens a connection per call (an excess request gets an error line and does not reach the extension), keeps the cap of 16 connections, and keeps at most 16 requests waiting on the extension. A request the extension does not answer in 10 s fails, and so do all waiting requests when the port closes, so a client never hangs on a reconnect. Each request carries an id and the reply that carries the id goes to the connection that asked.

The extension is the trust boundary. It drops everything from a private window before it reaches the host, so a host bug cannot leak it. The host writes only the socket, its lock, the state file and the kept theme (`theme.json`), all on tmpfs, and the thumbnail and icon caches in `$XDG_CACHE_HOME`. It prunes each cache at start (files over 7 days old, then the oldest beyond 500), prunes the icons again after each full tab list (an icon no open tab uses, once 7 days old), and deletes both caches when the extension says `bridge_share_tabs` is off: in a reply, or with the `tabs_off` event. A write and a delete never overlap, and an image the extension sent before a delete is dropped, so a deleted cache does not come back.

`host/desertfox` is the command line for the socket, a stdlib Python script: `desertfox run [--tab <id>] <command> [args]`, `desertfox list`, `desertfox state`, `desertfox theme <theme>`, `desertfox events` (prints the stream, one JSON line per event), `desertfox tabs [--current]`, `desertfox activate <id> [--preface <nonce>]`, `desertfox clear-preface <window id>`, `desertfox close <id>` and `desertfox capture [id...]`, and for Thunderbird `desertfox --app thunderbird mail folders|list <folder id>|read <id>|attachments <id>`, `mail draft --to A [--cc B] --subject S [--from EMAIL] [--reply-to ID] --body-file PATH|-` and `mail archive|trash <id>...` and `mail move <folder id> <id>...`. The draft body comes from a file or stdin, never from an argument, so neither the shell history nor `ps` holds mail text. A write prints one short line with no mail text, and a refusal prints the add-on's text on stderr and exits 1. `--app firefox` or `--app thunderbird` in front of the verb picks the socket. Without it the command line always talks to Firefox, so a desktop call written before Thunderbird never lands in Thunderbird. `theme` is Firefox's alone, and `mail` without `--app thunderbird` is a usage error. Mail is text from strangers, and a reader of the output can be a language model that follows instructions. So every sender field (from, to, subject, the message's content type, the body, attachment names and types) prints only between `<<<UNTRUSTED mail <what> nonce=<n>>>>` and `<<<END <n>>>>`, in plain and in `--json` output alike. The command line draws the nonce with `secrets.token_hex(16)` for each print, after the reply came, and draws again while the text holds it, so a guessed or an old END line in a body cannot close the envelope. The folder list prints inside an envelope as well, because feed titles, newsgroups and shared IMAP folders let third parties name folders. It prints plain text and exits 0 when done, 1 when refused or failed, 2 for bad usage and 3 when the bridge is not running (`theme` keeps the name and exits 0 instead). `-h` or `--help` after a verb prints the usage and sends nothing. The installer puts it beside the hosts and links it into `~/.local/bin`.

## Release channels

Two channels exist, stable and beta. The `update_url` in the installed build's manifest decides which one a copy follows. A stable build has none and updates from AMO. A beta build points at `updates.json`.

- Versions. Betas are `x.y.z.N`, where N counts builds after the stable `x.y.z` (see [Host updates](#host-updates-built)). `.github/workflows/beta.yml` builds one nightly from `main`.
- Update feed. `updates.json` sits on the fixed `beta-channel` release tag and lists only the latest beta. Its `update_link` and `update_hash` point at the signed xpi on that beta's own release.
- Trust. The maintainer's AMO key sits in the `beta-signing` environment, and only the sign job sees it. The other jobs build and publish from the signed output.
- Moving from a beta to a lower stable build. The host keeps the newer one, because it never downgrades. Use the stable build from AMO only after it passes the beta.
- Policy pin. `tools/install_policy.sh beta` pins the https URL of the latest beta in the policy file. The pin only seeds the first install: the `update_url` carries every update after that. The stable pin is a `file://` URL to the local xpi, and it replaces a beta whenever the local xpi ranks higher, so it is not for a beta machine.
- Manual beta. `just beta` starts the beta workflow on `main` and watches the run. `just release` starts no beta, because it pushes the bump to a release branch and main still has the old version. After the release PR merges, the nightly builds the matching `x.y.z.N` beta because main changed. Run `just beta` to get it at once. On a machine whose policy follows the beta (an https `install_url`), `just release` skips the local install and keeps the beta pin. Go back to stable with `bash tools/install_policy.sh stable`.
- Local installs. On a beta machine, never run `just install`. It overwrites the beta with a local build.

## Trade-offs

| Choice | Picked | Cost |
| --- | --- | --- |
| MV2 persistent vs MV3 event page | MV2 | Mozilla can remove MV2 some day. The migration is small because state lives in storage. |
| Keymap as data vs as code | Data | None for rebinding. New behavior comes from snippets or a new DesertFox build. |
| Snippets vs plugin extensions | Snippets | Page code only, no extension APIs. A move to MV3 means a rewrite to the `userScripts` API, which shows the user an extra permission warning. |
| Config as TOML vs Lua | TOML | No loops or helpers. The `search_keys` and `container_keys` sections remove most repetition, and tools can still edit the files. |
| Config through managed storage vs the native host | The native host. Managed storage is removed | A helper program to install and an optional permission. An edit applies with one key and no restart, so temp edits and modes stay. |
| Command line in an iframe vs a shadow root | iframe | Focus handling is harder. Isolation and direct API access are better. |
| Content script in all frames vs the top frame | All frames. A subframe starts its script on its first focus | Hints and keys work inside an embed after `;ff` or a click. The line, which-key and toasts still draw in the top frame, where the user looks. Ad frames the user never enters stay inert, with one idle focus listener each. `hint --all-frames` is the exception: the hints bundle starts each such frame through its loaded flag, so the frame can report and draw labels. |
| Plain `J/K` only vs plus chords | Plus `Alt+J/K` | Two keys for one command. The chord is the only way to switch tabs from about: pages, the PDF viewer or the address bar. |

## Risks

- Keys are lost on a page with no committed document, for example a new tab before its first byte. No extension can fix that. The chords cover it.
- A page that cancels a chord before Firefox sees it blocks the Firefox shortcut. The content script catches the chord first on pages where it runs, so only pages without a content script are exposed.
- Release Firefox needs a signed build for each change in code. `just release` signs on AMO and installs through the policy file.
- Snippets run code from a config string through `tabs.executeScript`. AMO review of DesertFox can question that. The code comes only from the user's own file, which other extensions with this feature also do.
- Scope creep. The binding map is the scope: a feature not in it needs a reason.
